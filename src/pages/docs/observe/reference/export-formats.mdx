## About

There are two directions for trace data: **out of** Observe (exporting what you're viewing) and **into** Observe (the OTLP endpoints traceAI sends to). This page covers both.

## Export from the trace explorer

The download icon in the [trace explorer](/docs/observe/guides/explore-dashboard) header exports the **current view** — the traces that match your active filters and time range.

**CSV is the only export format.** There is no JSON or Parquet download from the trace explorer.

| Format | Use for |
|---|---|
| CSV | Spreadsheet analysis, sharing, importing elsewhere. |

The CSV holds one row per span in the current view, with the columns the explorer shows: trace ID, span name, status, model, provider, latency, token counts, cost, timestamp, and any eval scores present on the span.

<Note>
  The export reflects the current view, so a very large view may be truncated. Narrow the filters or time range to export a complete slice.
</Note>

## Ingestion endpoints

traceAI exports spans over OTLP to FutureAGI. The transport and target are environment-driven:

| Variable | Transport | Default |
|---|---|---|
| `FI_BASE_URL` | HTTP collector | FutureAGI cloud collector |
| `FI_GRPC_URL` | gRPC collector | FutureAGI cloud collector |

When unset, both variables default to the FutureAGI cloud collector, so a cloud project needs no endpoint configuration — only `FI_API_KEY` and `FI_SECRET_KEY`.

- **Cloud:** leave the defaults; set `FI_API_KEY` and `FI_SECRET_KEY`.
- **Self-hosted:** point `FI_BASE_URL` / `FI_GRPC_URL` at your own collector host so spans stay in your network.

Choose the transport with `transport=Transport.HTTP` (default) or `Transport.GRPC` in `register()`. See [Set up tracing](/docs/sdk/tracing/set-up-tracing).

### Endpoint contract

The ingestion endpoint is an **OTLP/traces** receiver — you don't call it directly; the traceAI SDK's exporter does. The contract:

| Aspect | Detail |
|---|---|
| Protocol | OTLP over HTTP (protobuf or JSON) or gRPC: the [OpenTelemetry](https://opentelemetry.io/docs/) standard, not a proprietary API. |
| Compression | gzip or none over OTLP/HTTP; none over gRPC. See [Compression](#compression). |
| Project | The `project_name` resource attribute, or the `X-Project-Name` header when the exporter cannot set resource attributes. See [Naming the project](#naming-the-project). |
| Operation | Export spans (write-only). There is no read/query endpoint; reading happens in the trace explorer. |
| Auth | `FI_API_KEY` + `FI_SECRET_KEY` from the [keys page](https://app.futureagi.com/dashboard/keys), sent by the SDK on every export. Keys are workspace-scoped. |
| Success | The exporter batches spans and sends them in the background; a successful export returns no payload. Spans appear in Observe within seconds. |
| Errors | A `401` means the keys are wrong for this workspace; a `4xx` means a malformed/oversized batch (`400` also covers a missing project name and a corrupt gzip body, `413` a body or batch over a [limit](#ingestion-request-limits), `415` an unsupported content type or encoding); transient `5xx`/network errors, including a `503` with `Retry-After` when the collector is busy with other requests, are retried by the batch exporter. |
| Limits | Spans are sent by the **batch** span processor on an interval, so a short-lived process must call `trace_provider.force_flush()` before exit or the last batch is lost. Very large payloads (huge prompts/outputs) can be dropped: [cap attribute size](/docs/sdk/tracing/trace-config#cap-attribute-size) or [mask](/docs/sdk/tracing/mask-span-attributes) them at the SDK. Future AGI Cloud accepts OTLP requests up to 16 MiB over HTTP or gRPC. See [Ingestion request limits](#ingestion-request-limits). |
| Versioning | Pin `fi-instrumentation-otel` and each instrumentor to a tested version so a release can't change span shape under you; the wire format follows the OTLP version the SDK ships. |

### Compression

OTLP/HTTP accepts gzip-compressed requests, as the [OTLP specification](https://opentelemetry.io/docs/specs/otlp/) requires. OTLP/gRPC accepts uncompressed requests only. Uncompressed requests keep working on both.

| Transport | gzip | Other encodings |
|---|---|---|
| OTLP/HTTP | Send `Content-Encoding: gzip`, with a protobuf or JSON body | `415 Unsupported Media Type`, with `Accept-Encoding: gzip, identity` |
| OTLP/gRPC | Not supported: a call with `grpc-encoding: gzip` fails with `UNIMPLEMENTED` | `UNIMPLEMENTED` |

- **Turning gzip on.** In an OpenTelemetry SDK, use the HTTP exporter (`OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`) with `OTEL_EXPORTER_OTLP_COMPRESSION=gzip`. In the OpenTelemetry Collector, the `otlphttp` exporter sends gzip by default and needs no `compression` setting. The `otlp` (gRPC) exporter also defaults to gzip, so keep `compression: none` on it.
- **Encoding must match the body.** A body labelled `Content-Encoding: gzip` must be gzip: a plain body with that label, or a gzip body that is truncated or fails its checksum, is rejected with `400`. `x-gzip` is treated as `gzip`, and only one gzip layer is accepted (`gzip, gzip` is rejected with `415`). Any encoding other than `gzip` or `identity`, such as `deflate`, `br` or `zstd`, is rejected with `415`, even when the body is actually uncompressed. Earlier collector versions ignored `Content-Encoding`, so an uncompressed body sent with one of these labels used to be accepted; make sure the exporter's compression setting matches what it sends.
- **Request size.** An OTLP/HTTP request gets `413` if its body exceeds 16 MiB as sent. A gzip request also gets `413` if its body exceeds 16 MiB after decompression. As in the OpenTelemetry Collector's `max_request_body_size`, one limit applies to both sizes.
- **Busy collector.** A gzip request shares the collector's memory limit with every other request. See [Busy collector](#busy-collector).

### Naming the project

When collector auth is enabled, every batch must name its Observe project. The collector looks for the name in this order, separately for each resource in the batch:

| Order | Source | Set by |
|---|---|---|
| 1 | Resource attribute `project_name` | traceAI's `register()`, or `OTEL_RESOURCE_ATTRIBUTES=project_name=<name>` |
| 2 | Request header `X-Project-Name` (gRPC metadata key `x-project-name`) | Any exporter that can set headers, for example `OTEL_EXPORTER_OTLP_HEADERS` or a vendor's "custom headers" field |
| 3 | Neither | The batch is rejected with `400` (gRPC `INVALID_ARGUMENT`), `no project_name` |

The header is for senders that can set headers but not resource attributes, such as hosted gateways and telemetry drains. A non-empty string `project_name` resource attribute wins, even when the header names a different project; the header fills only missing, empty or non-string attributes. A name from the header is trimmed and then handled like the attribute: when auth is enabled, it is looked up in the workspace of your API key, and an Observe project is created with that name if none exists. The collector stores the name it used in the span's resource attributes.

The production collector requires PostgreSQL auth configuration. In auth-disabled test harnesses only, the header still fills `project_name` in the stored resource attributes, but there is no key/workspace lookup or project auto-creation.

These settings send traces over OTLP/HTTP. Set the protocol explicitly: some SDKs, the Python one included, default to gRPC.

```bash
OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://api.futureagi.com/tracer/v1/traces
OTEL_EXPORTER_OTLP_TRACES_HEADERS="X-Api-Key=<FI_API_KEY>,X-Secret-Key=<FI_SECRET_KEY>,X-Project-Name=checkout-agent"
OTEL_EXPORTER_OTLP_TRACES_COMPRESSION=gzip
```

Over gRPC, send the same name as the `x-project-name` metadata key, without compression.

The collector reads the header only when a resource in the batch has no `project_name`. The checks below never reject a batch whose resources all name their project.

| Header detail | Behaviour |
|---|---|
| Whitespace | Trimmed. A blank value counts as no header. |
| `FI-Project-Name` | Read as the same header. traceAI's Java and C# exporters send it. |
| Values that disagree between `X-Project-Name` and `FI-Project-Name` | `400`, gRPC `INVALID_ARGUMENT`. The two spellings may both be sent if they agree. |
| Header sent more than once (including repeated lines with the same value) | `400`, gRPC `INVALID_ARGUMENT`. Send one field line. |
| Comma in the header value | `400`, gRPC `INVALID_ARGUMENT`. A proxy may join repeated lines into a comma-separated value, so lists are rejected. |
| Value that is not valid UTF-8 | `400`, gRPC `INVALID_ARGUMENT`. |
| Value longer than 255 characters | `400`, gRPC `INVALID_ARGUMENT`. Project names hold at most 255 characters. |
| Control characters, such as a tab or newline, inside the value | `400`, gRPC `INVALID_ARGUMENT`. |
| Line or paragraph separators (U+2028, U+2029) inside the value | `400`, gRPC `INVALID_ARGUMENT`. |
| Invisible Unicode characters: format characters (category `Cf`), such as U+200B or U+202E, and other default-ignorable characters, such as the Hangul filler U+3164 or the variation selector U+FE0F | `400`, gRPC `INVALID_ARGUMENT`. |
| Value with no visible character: only combining marks, or symbols that display as blank space, such as U+2800 | `400`, gRPC `INVALID_ARGUMENT`. Inside a name that has visible characters, these are kept. |
| Spaces in `OTEL_EXPORTER_OTLP_HEADERS` | Percent-encode spaces, for example `X-Project-Name=checkout%20agent`. The SDK decodes percent-encoding before sending. |
| Project type | There is no header for it. A project the header names that does not exist yet is created as an Observe project. |

### Ingestion request limits

Future AGI Cloud enforces the same supported request limit for both OTLP transports. For gzip OTLP/HTTP, the limit applies to the body as sent and again after decompression:

| Transport | Maximum request size | Error when exceeded |
|---|---:|---|
| OTLP/HTTP | 16 MiB | `413 Request Entity Too Large` |
| OTLP/gRPC | 16 MiB | `INVALID_ARGUMENT` |

An oversized request is rejected as a whole and its spans are not stored. If you see `413` or `INVALID_ARGUMENT` (`RESOURCE_EXHAUSTED` from earlier collector versions) in your exporter logs, reduce the number of spans sent in each batch. OpenTelemetry's default maximum export batch size is 512 spans. Start with:

```bash
OTEL_BSP_MAX_EXPORT_BATCH_SIZE=256
```

#### What one request may contain

The collector also checks what a request contains before it decodes it. A request over one of these limits is rejected as a whole, its spans are not stored, and exporters do not retry it:

| Limit | Per request | OTLP/HTTP | OTLP/gRPC |
|---|---:|---|---|
| Spans | 65,536 | `413` | `INVALID_ARGUMENT` |
| Resources (`ResourceSpans`) | 10,000 | `413` | `INVALID_ARGUMENT` |
| Attributes, counting each entry of an array value | 1,048,576 | `413` | `INVALID_ARGUMENT` |
| Resource attributes, keys and values, of one resource | 64 KiB | `413` | `INVALID_ARGUMENT` |
| Stored size of the batch's spans | 8 times the maximum request size (128 MiB) | `413` | `INVALID_ARGUMENT` |
| Memory the collector needs to process the batch | what the collector can give one request | `413` | `INVALID_ARGUMENT` |
| Nesting of an attribute value (arrays and key-value lists inside each other) | 64 levels | `400` | `INVALID_ARGUMENT` |
| Nesting of an OTLP/JSON body | 512 levels | `400` | not applicable |

Resource attributes are stored with every span of their resource, so keep large values (prompts, outputs, documents) in span attributes rather than resource attributes. Batches from OpenTelemetry SDKs (512 spans by default) stay within the count limits. The OpenTelemetry Collector's batch processor sends at 8,192 spans by default but sets no upper bound unless `send_batch_max_size` is set, so set it (for example to `8192`) in Collector pipelines. A batch that needs more memory than the collector can give one request gets a `413` whose message says so: send smaller batches.

#### Busy collector

Each collector process limits the memory that all OTLP requests, plain, gzip and gRPC alike, hold at once, from receiving a body until its spans are stored. A request waits for its share, in arrival order, while the collector frees memory, for up to 10 seconds. If the collector is still busy, it gets `503 Service Unavailable` with `Retry-After: 1` over OTLP/HTTP and `UNAVAILABLE` over OTLP/gRPC, and OpenTelemetry exporters retry it. Exporters also retry these refusals:

| Refusal | OTLP/HTTP | OTLP/gRPC |
|---|---|---|
| The collector is busy with other requests | `503`, `Retry-After: 1` | `UNAVAILABLE` |
| Too many OTLP/gRPC calls in flight on one collector | | `UNAVAILABLE` |
| The batch names more than 16 projects new to its API key. Up to 16 are added per request, so each retry adds more. | `503`, `Retry-After: 1` | `UNAVAILABLE` |
| The body arrived too slowly | `503`, `Retry-After: 1` | `DEADLINE_EXCEEDED` |

OTLP/gRPC calls are authenticated before the collector reads their message; a call without `X-Api-Key` and `X-Secret-Key` metadata is refused with `UNAUTHENTICATED` before it is accepted.

<Note>
  These limits apply to Future AGI Cloud. For a self-hosted deployment, the configured collector and proxy limits apply. The collector's settings are:

  | Variable | Default | Effect |
  |---|---|---|
  | `FI_INGEST_BUDGET_MIB` | About half of the collector's Go memory limit, less a fixed allowance | Memory, in MiB, that all OTLP requests may hold at once. Without `GOMEMLIMIT`, the collector sets its Go memory limit to 90% of its container's memory limit; with neither, the budget is 256 MiB. A third of the budget is for receiving bodies. |
  | `FI_OTLP_MAX_BODY_MIB` | `16` | Largest OTLP/HTTP body, as sent and after gzip decompression. Lowered at start to a sixth of the budget when that is smaller. |
  | `FI_GRPC_MAX_RECV_MIB` | The OTLP/HTTP body limit | Largest OTLP/gRPC message (`INVALID_ARGUMENT` above it), lowered like the body limit. |
  | `FI_OTLP_MAX_CONNECTIONS` | `0` (no cap) | Open connections each OTLP listener accepts. |
  | `FI_GZIP_INFLIGHT_MIB` | | Earlier versions' budget for gzip requests only. No longer read: set `FI_INGEST_BUDGET_MIB`. |

  The Helm chart sets them from `fiCollector.ingestBudgetMiB`, `fiCollector.maxBodyMiB`, `fiCollector.grpcMaxRecvMiB` and `fiCollector.maxConnections`, and derives the budget from `fiCollector.goMemLimit`. The collector logs the limits it uses at startup (`ingest limits`), and its `/healthz` endpoint on the admin port reports the budget in use and the requests refused, by transport, reason and status, under `ingest`. A batch that is refused with `413` for the memory it needs names `FI_INGEST_BUDGET_MIB`: send smaller batches, or raise the collector's memory limit and the budget with it.
</Note>

<Warning>
  Span input and output can carry customer data before they leave your process. Redact at the SDK with `TraceConfig` or the `FI_HIDE_*` variables — see [Mask span attributes](/docs/sdk/tracing/mask-span-attributes).
</Warning>
