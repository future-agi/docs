## About

If a customer contacts support twice about the same return, sampling individual spans can leave you with only half the exchange. In Observe, you can pick the **contact** once and evaluate every **eligible span** for that contact, even across traces. The contact counts once toward your quota; each span gets its own evaluation.

## Choose what to score and what to pick

<Steps>
  <Step title="Score individual spans">
    From your project's trace explorer, choose **Evaluate > Add evaluators**. Name the task `Ridgeline return review`. Under **Run evaluations on**, choose **Spans**. Use **Add Evaluation** to [configure an evaluator and map its inputs](/docs/observe/guides/setup-evals).
  </Step>
  <Step title="Pick whole contacts">
    Under **When to run**, choose **Historical data**. Under **Data to evaluate**, choose **Pick whole groups of spans**. Under **Pick:**, choose **Custom ID**.
  </Step>
  <Step title="Identify each contact">
    Ridgeline's support agent records `support.contact_id` and `support.region` on each span it wants to review. Set **Location** to **Span attribute** and enter `support.contact_id` in **Custom ID attribute**. Use your own key, or leave it blank to use the project's configured contact attribute.
  </Step>
</Steps>

<img src="/images/docs/observe/sample-eval-tasks/pick-contacts.gif" alt="Ridgeline return review scores spans in historical data and picks whole groups using the support.contact_id span attribute." style={{ borderRadius: '5px' }} />

Choose the smallest unit whose evidence must stay together. With span evaluations, these are your choices:

| Pick | API `sampling_unit` | What one selection includes |
| --- | --- | --- |
| Individual spans | `span` | One eligible span |
| Traces | `trace` | Eligible spans from one request |
| Conversations | `session` | Eligible spans across the traces in one session |
| Users | `user` | Eligible spans across a user's conversations |
| Custom ID | `attribute` | Eligible spans sharing your chosen attribute value |

The pick level cannot be finer than the evaluation row. For example, you can pick users and score sessions, but not pick individual spans and score sessions. The task filters and time window still apply: selecting a contact does not bring filtered-out spans back in.

## Set a quota for each region

Choose **Set a count per group**. Set **Group field** to the span attribute `support.region`. In **Group values**, add `west` and `east` separately. Set `west` to **1**, `east` to **2**, and the count for all other custom IDs to **0**. Expand **Change time window** and set the UTC start and end to cover the support traffic you want to review.

![The support.region quotas pick one western contact, two eastern contacts, and no others between 16:00 and 18:00 UTC on November 19.](/images/docs/observe/sample-eval-tasks/regional-counts-window.png)

| If you need… | Schedule and rule |
| --- | --- |
| A fixed number of contacts from last week's traffic | **Historical data** uses counts, bounded by the contacts available in each group. The window includes its start, excludes its end, must end in the past, and can span at most 31 days. |
| An ongoing sample of new contacts | Choose **New incoming data** and **Set a share per group**. For example, a 10% share in `west` gives each new western contact a 10% chance, not a promise of one in every ten. Its first decision also applies to later eligible spans. |

Switching from historical counts to live shares resets every group to 10%, including the one for all other contacts. Switching back resets every count to 100. After confirming a switch, set the amounts and window you want before saving. Set the all-other amount back to 0 if you only want `west` and `east`.

## Preview, then check the run

Click **Preview sample**. For example, suppose the window contains just these four contacts:

| Region | Eligible contacts | Eligible spans per contact | Contacts picked | Spans to score |
| --- | ---: | ---: | ---: | ---: |
| `west` | 2 | 3 each | 1 | 3 |
| `east` | 2 | 2 each | 2 | 4 |

The preview reads **3 custom IDs · 7 spans evaluated**. That is the planned work, not completed evaluations. Expand **Evaluation work**: one evaluator means seven evaluation runs. Add a second evaluator and the same sample needs 14 runs. Previewing does not run evaluations or reserve contacts. A historical sample freezes when the task first runs. A live preview covers only the last 24 hours, or the time since the policy started if shorter.

![The preview selects three of four custom IDs. Evaluation work shows seven spans times one evaluator, for seven expected runs.](/images/docs/observe/sample-eval-tasks/sample-preview-work.png)

Click **Create task** to start. Once the task runs, open **Sampling audit**. Compare **Target** with **Achieved** per group. The editor names the rules in the order you added them. With `west` added first, look for **Group 1**: its population is 2, its target is 1, and 1 contact was picked. If you ask for 3 contacts where only 2 exist, **Shortage** is 1 even when the task picked both.

![The sampling audit shows two contacts in each group. Group 1 achieved its target of one and Group 2 its target of two; both show zero shortage and an Exact check.](/images/docs/observe/sample-eval-tasks/sampling-audit-by-region.png)

The audit counts contacts, not completed evaluations. To check which spans got scores, open **Usage**, choose a date range covering the evaluation runs, and select a run. Choose **Open trace** to inspect the span's `support.contact_id`. Compare the **Span ID** values for one evaluator with the eligible span IDs for that contact in the explorer. If all runs succeeded, you should find all three spans for the selected western contact and none for the other. **Usage** lists successful runs only. In the example below, **Status: success** means the evaluator ran; **Result: Failed** means the span's output didn't pass the return-link check. If a span is missing, check **Logs** for errors before concluding it was not sampled.

## Preview and create the same policy by API

Set `FI_API_KEY`, `FI_SECRET_KEY`, and `PROJECT_ID` in your environment. To find the project UUID, call `GET /tracer/project/list_project_ids/` and take your project's `id` from `result.projects`, then run `export PROJECT_ID=your-project-id`. Save this as `sample_contacts.py` and run `python3 sample_contacts.py`. The preview needs no evaluator. To **start a task** instead of just previewing, set `EVAL_CONFIG_ID` to a [configured evaluator](/docs/api/custom-eval-configs/create-custom-eval-config) UUID from the same project (`export EVAL_CONFIG_ID=your-config-id`) and run `python3 sample_contacts.py --create`.

```python
import argparse
import json
import os
from datetime import datetime, timedelta, timezone
from urllib.request import Request, urlopen

parser = argparse.ArgumentParser()
parser.add_argument("--create", action="store_true")
args = parser.parse_args()
eval_id = os.getenv("EVAL_CONFIG_ID")
if args.create and not eval_id:
    parser.error("Set EVAL_CONFIG_ID to start a task.")

base = os.getenv("FI_BASE_URL", "https://api.futureagi.com").rstrip("/")
headers = {
    "Content-Type": "application/json",
    "X-Api-Key": os.environ["FI_API_KEY"],
    "X-Secret-Key": os.environ["FI_SECRET_KEY"],
}


def post(path, body):
    request = Request(base + path, data=json.dumps(body).encode(), headers=headers)
    with urlopen(request, timeout=60) as response:
        return json.load(response)["result"]


end = datetime.now(timezone.utc) - timedelta(minutes=1)
policy = {
    "version": 1,
    "mode": "closed",
    "window": {"start": (end - timedelta(days=7)).isoformat(), "end": end.isoformat()},
    "sampling_unit": "attribute",
    "unit_attribute": {"source": "span", "key": "support.contact_id"},
    "missing_id": "exclude",
    "strata": [
        {
            "name": region,
            "filters": [{"source": "span", "key": "support.region", "op": "in", "values": [region]}],
            "target_n": count,
        }
        for region, count in [("west", 1), ("east", 2)]
    ],
    "default": {"target_n": 0},
}
body = {
    "project": os.environ["PROJECT_ID"],
    "row_type": "spans",
    "sampling_policy": policy,
    "evals": [eval_id] if eval_id else [],
}
preview = post("/tracer/eval-task/sampling_preview/", body)
for group in preview["strata"]:
    print(group["stratum"], f"{group['selected_units']} of {group['eligible_units']} contacts,",
          f"{group['selected_rows']} spans")
historical = policy["mode"] == "closed"
if not any(group["selected_units"] for group in preview["strata"]):
    print("No contacts selected. Check the window, attributes and region values.")
    if args.create and historical:
        raise SystemExit("Historical task not created.")

if args.create:
    task = post("/tracer/eval-task/", {
        **body,
        "name": "Ridgeline return review",
        "run_type": "historical" if historical else "continuous",
        "sampling_rate": 100,
    })
    print(task["id"])
```

`strata` is an ordered list of group rules. If one contact has eligible spans in both regions, it counts only toward `west`, the first matching rule here. If picked, it contributes its eligible spans from **both** regions. `default` covers contacts that match no rule. The create endpoint requires `sampling_rate`, but with `sampling_policy` set, the policy selects the units; no extra row limit cuts a selected contact short.

### Adapt the policy

| Goal | Change to the example |
| --- | --- |
| Pick a share of new contacts in each region | In the Python policy, set `mode` to `"live"`, `window.start` to the UTC time you want to start admitting contacts, and `window.end` to `None`. Replace each `target_n` with a `rate` from 0 to 100 (up to six decimal places), including `default`. The script creates a `continuous` task. An empty live preview does not prevent future contacts from qualifying. Live rules do not accept floors, caps, or exact quotas. |
| Set a count per support queue **within** each region | Add `"group_by": [{"source": "span", "key": "support.queue"}]` to the policy. Each region's quota now applies separately to each queue. Two populated western queues can yield two contacts instead of one. Leave `group_by` empty if the quota is for the whole region. |
| Override just one historical group | Preview first. Use its exact `stratum` string from `result.strata` as a key in the policy's `cell_quotas` object, with the new count as the value. Other groups keep their rules. Preview again before creating the task. |

### Read the audit

Set `TASK_ID` to the returned task UUID and get the audit. The first run creates the cohort asynchronously, so the example waits up to a minute if the audit is not ready. Read `result.strata` for each group's `population_size`, `target`, and `achieved`. For a live policy, compare `achieved` with `expected_size`, not an exact target. To inspect an earlier cohort of the same task, also pass `cohort_id`.

```bash
for attempt in {1..13}; do
  status=$(curl --silent --show-error --get --output audit.json --write-out '%{http_code}' \
  "${FI_BASE_URL:-https://api.futureagi.com}/tracer/eval-task/sampling_audit/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  --data-urlencode "eval_task_id=${TASK_ID:?Set TASK_ID}") || exit 1
  case "$status" in
    200) cat audit.json; break ;;
    404|409) if [ "$attempt" -lt 13 ]; then sleep 5; continue; fi ;;
  esac
  printf 'Audit unavailable (HTTP %s). Check the task ID and status.\n' "$status" >&2
  exit 1
done
```

## Limits and troubleshooting

| What you see | What to do |
| --- | --- |
| Fewer contacts than expected | Check the UTC window, task filters, attribute location and key. `missing_id: "exclude"` skips rows without the ID. Via the API, `missing_id: "row"` samples those rows independently; it does not combine them into one unknown contact. |
| The audit is unavailable just after creation | There is no cohort until the task first runs. If the audit returns HTTP 409, the historical sample is still freezing. Retry after it finishes. |
| A live Custom ID task stops admitting new contacts | Each new contact must be checked against project spans since the policy start. The read ceiling defaults to 20 million spans and cannot be set higher. The task can also reach its configured history limit before hitting that ceiling. In either case, start a new live policy with a later start; lowering the percentage does not shorten the history to check. |
| A saved policy previews but its controls are read-only | API policies can do more than the simple editor, such as subdividing each rule by up to four `group_by` attributes or setting historical floors and caps. Other edits preserve those settings. Choose **Replace with simple group picking** and confirm **Replace settings** only if you intend to discard them. If results already exist, duplicate the task to preserve them rather than starting fresh on the same task. |
