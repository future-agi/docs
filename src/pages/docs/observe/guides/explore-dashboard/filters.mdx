Filters cut a busy trace table down to the traces you actually care about, whether that is failed requests, one model, a time window, or a single conversation. This guide filters the `support-agent` project from the [Observing a LangGraph agent](/docs/cookbook/observe-langgraph-agent-and-obtain-insights) cookbook.

## Open the filter panel

Click **Filter** at the top right of the trace table.

<img src="/images/docs/observe/filters-open-panel.png" alt="Observe trace table with the Filter button highlighted at the top right" style={{ borderRadius: '5px' }} />
*Open the filter panel from the top right of the trace table*

## Three ways to filter

The panel gives you three ways to build the same filter:

- **AI search**: describe what you want in plain English, such as *"errors on gpt-4o today"*, and Observe builds the filter for you
- **Basic**: pick a property, a condition, and a value; add more conditions and they apply together (AND)
- **Query**: type the filter expression directly, for conditions the Basic builder can't express

<img src="/images/docs/observe/filters-three-modes.png" alt="Filter panel showing the Ask AI search box above the Basic property, condition, and value builder and the Query tab" style={{ borderRadius: '5px' }} />
*The filter panel: AI search on top, the Basic builder below, and a Query tab*

## Build a filter in Basic

Building a filter takes two picks: a property, then its value.

Search for the property you want. Properties are grouped into **System**, **Evals**, **Annotations**, and **Attributes**, so you can filter on anything the SDK recorded, not just the visible columns.

<img src="/images/docs/observe/filters-pick-property.png" alt="Basic filter builder with the property search open, showing Model and related model attributes grouped by System and Attributes" style={{ borderRadius: '5px' }} />
*Search for a property; here `Model`, one of the System properties*

Then choose one or more values. For `Model`, those are the models your traces actually ran on.

<img src="/images/docs/observe/filters-pick-value.png" alt="Basic filter builder with Model equals and the value dropdown showing gpt-4o-mini as a multi-select option" style={{ borderRadius: '5px' }} />
*Pick the value or values; every support-agent turn ran on `gpt-4o-mini`*

Click **Add filter** to stack another condition. Conditions apply together, so `Model is gpt-4o-mini` plus `Status is ERROR` returns only the failed gpt-4o-mini turns.

## Follow a skill load to its traces

The **Skills** group requires the [skill-trace preview integration](/docs/skills/trace-skills) and the `skillTraces` feature. The screenshots above show the earlier general filter builder, not evidence that this preview is deployed.

1. Open **Filter → Skills**. Choose the skill and one or more versions. A picker label such as **v3 (production now)** describes today's label assignment, not what a past request asked for.
2. Under **More**, add **Asked for**, **Agent**, **Context**, **Evidence**, **Contents**, or **Service**. Sub-fields in this chip match the same load. To require another skill in the trace, choose **and also loaded…**; the groups are ANDed.
3. To investigate failures, choose **Load result → Failed**. Version, Evidence, and Contents disappear because a failed read has no verified version or digest. Its row is matched by the name reported by the app, not verified identity.
4. Read the **Traces / Failed requests / p95 / Cost per trace** cohort strip. It covers the whole filter, not just the first chip. Use **Split by skill version** in the graph to compare overlapping cohorts with label-move markers; do not add the cohort totals together.
5. Open a trace, expand **Skills loaded**, and select a load row to find its span. Inspect failures and **Linked … and not loaded in this trace** separately. The **Ran after loading** filter belongs to the Span tab; earlier spans may lack those attributes even when the trace contains a load.

Alternatively, start at a skill/context **Runtime** metric. A number opens Observe with its exact project and window; a multi-project version row first offers a small project menu. Failed requests selects failed roots; p95 opens the measured latency cohort and requests slowest-first order (the preview shows a notice when it cannot apply that sort); an eval cell opens the failing-eval subset. The source bar explains where the link came from, provides a way back, and switches to the paired before/after window. Changing filters removes the source bar so it cannot describe a different cohort.

**No recorded load** is not proof of no read in an uninstrumented app. If nothing appears, follow the [no-load diagnosis](/docs/skills/troubleshooting#no-loads-recorded), rather than treating fetched or linked skills as loaded. A saved view keeps its chosen columns; adding skill tracing does not rewrite it. See the [filter reference](/docs/observe/reference/filters#skills-filter-group) for field names and correlation rules.

## Write it as a query

For conditions the Basic builder can't express, switch to the **Query** tab and type the expression. Query mode uses symbolic operators (`=`, `!=`, `>`, `<`, `contains`).

```text
scores.context_adherence < 0.8                          # ungrounded answers
user.id = cust_42                                       # one customer's traces
fi.span.kind = LLM AND scores.context_adherence < 0.8   # low-adherence LLM spans
```

The last query is the one the cookbook uses to surface its single ungrounded turn. To follow one customer across conversations, filter on `user.id`; to replay a full conversation, open the **Sessions** tab.

For every filterable field and operator, see [Filter syntax](/docs/observe/reference/filters).
