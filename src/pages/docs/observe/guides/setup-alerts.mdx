A slow model call can get lost among hundreds of [traces](/docs/observe/concepts/traces). Monitor the latency of model-call [spans](/docs/observe/concepts/spans) in one project and check both the alert history and the notification when a threshold is crossed.

<Prerequisites title="Before you start">
- An Observe project receiving model calls. The screenshots use the [LangGraph support agent](/docs/cookbook/observe-langgraph-agent-and-obtain-insights).
- An email address you can check for the test notification. For Slack delivery instead, you need an incoming webhook for the destination channel.
</Prerequisites>

## Choose the project and metric

1. Open **Alerts** in the sidebar.

   The landing page shows the three parts of a monitor: metric, conditions and notification.

<img src="/images/docs/observe/alerts-landing.png" alt="The Observe Alerts page describing Define Your Metric, Set Alert Conditions, and Configure Notifications, with the Start creating alerts button" style={{ borderRadius: '5px' }} />

2. Click **Start creating alerts** (or **New Alert** if a monitor already exists).
3. In **Choose a project**, select `support-agent`.

<img src="/images/docs/observe/alerts-choose-project.png" alt="Choose a project modal with support-agent selected and a Next button" style={{ borderRadius: '5px' }} />

4. Click **Next**.
5. In **Select Alert Type**, choose **Span response time**.

<img src="/images/docs/observe/alerts-select-type.png" alt="Select Alert Type step listing Application performance alerts and Metric alerts, with Span response time selected and a configuration preview on the right" style={{ borderRadius: '5px' }} />

6. Click **Next**.

   You should see **Set Alert Configuration**. An alert watches one project.

**Choosing another metric?** Application performance alerts include error counts, span or LLM response time, and API failure rates. Metric alerts include evaluation metrics, token usage, and daily or monthly spend. To monitor an eval score such as [groundedness](/docs/evaluation/builtin/groundedness), choose **Evaluation Metrics** instead.

## Choose the spans to measure

1. Enter `Slow span time` in **Name**.
2. Under **Define Metrics & Interval**, check that **Metric** is **Span response time**.
3. Set **Interval** to 5 minutes.
4. Under **Filter Events**, set **Span Type** to `LLM`.

   The monitor now measures model-call latency on a five-minute interval. The time selector above the chart changes the preview window.

<img src="/images/docs/observe/alerts-configure.png" alt="Set Alert Configuration step with a Name field reading Slow span time, a Span response time metric on a 5 minute interval, and a Filter Events row of Span Type is LLM" style={{ borderRadius: '5px' }} />

## Set the thresholds

1. Under **Define Alert**, choose **Static Value**.

   Use a fixed value for a latency target; **Percentage Change** compares against a previous period instead.

2. Set the **Critical** direction to **Above**.
3. Set the critical value to `200` ms.
4. Set the **Warning** direction to **Above**.
5. Set the warning value to `100` ms.

   With two levels, a bad spike escalates differently from an early warning. Both levels can also use **Below** for metrics where a drop matters.

## Choose delivery

1. Under **Define Notification**, select **Email**.

   Choose **Slack** instead to send the alert through your incoming webhook.

2. Add the recipient for your test.

<img src="/images/docs/observe/alerts-thresholds-notify.png" alt="Define Alert with Static Value selected, Critical above 200 and Warning above 100, and Define Notification with Email chosen and a recipient added, next to the Create Alert button" style={{ borderRadius: '5px' }} />

3. Click **Create Alert**.

   In the example, the **Alerts** table shows `Slow span time` as **Healthy**, with **Span response time**, no **Last Triggered** time and zero triggers.

<img src="/images/docs/observe/alerts-table.png" alt="The Alerts table showing the Slow span time alert with Healthy status, Span response time type, no Last Triggered time, and zero triggers" style={{ borderRadius: '5px' }} />

A new alert reads **Healthy** with no triggers yet. When the metric crosses a threshold, the status changes to **Warning** or **Critical**, **Last Triggered** is set, and the notification is sent.

## Test that the alert fires

1. Set a threshold that the project’s recent model-call latency will cross.
2. Wait one evaluation interval with matching traffic.
3. Check the monitor's alert history for a breach.

   Look for **Warning** or **Critical**, a trigger count and a **Last Triggered** time that matches the alert entry.

4. Check the recipient's inbox for the same monitor name and alert type.

   If history shows a trigger but no message arrived, check the address or Slack webhook. If there is no trigger, check the interval, filter, threshold direction and mute state.

5. Restore the intended threshold after the test.
