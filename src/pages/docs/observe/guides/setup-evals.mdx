## About

An Observe evaluation task applies a check to matching data in one project. Ridgeline Outfitters' support agent sends JSON to its returns service. You'll check two handoff spans with the built-in `is_json` evaluator, then open a failed check to see exactly what the agent sent.

## Set up the task in Observe

Start with a [traced project](/docs/observe/features/quickstart) that has at least two handoff spans. In this example, each span records the payload in `output.value`. Use your own attribute path if your agent records it elsewhere.

1. Open the project's **Spans** view. Choose **Evaluate > Add evaluators**. Enter `Check return handoffs` under **Task Name** and confirm the project. Under **Run evaluations on**, choose **Spans** to score each handoff separately. **Traces** scores a whole request; **Sessions** scores a conversation.

{/* MEDIA: The Spans view's Evaluate menu with Add evaluators, followed by the task form with the project and Spans selected. */}

2. Under **Evaluations**, click **Add Evaluation**, search for `is_json`, and click **Add**. Map the template's required `text` input to the span's `output.value`, then click **Add Evaluation** to save the mapping. This asks “is the payload valid JSON?”, not “are the order details correct?”

{/* MEDIA: is_json configured with its text variable mapped to the selected span's output.value. */}

   For nested data, use dot-separated keys and numeric positions. For example, if `output.value` contains a JSON-encoded model response, `output.value.choices.0.message.content` selects the first choice's message instead of grading the whole response envelope. Use `.0`, not `[0]`.

3. Under **Filters**, narrow the task to the handoffs you want to check. Under **When to run**, select **Historical data** and a time window containing those spans. Under **Data to evaluate**, select **A percentage of matching spans**, choose **All**, then set **Custom limit > Matching rows to process** to `2`. To check future handoffs instead, choose **New incoming data** and a percentage of matching arrivals.

4. In **Matching row**, select a span and click **Test on this row**. Check that the evaluator received the payload, not the surrounding span. For example, `{"order":"R-1042","action":"return"}` should pass; `Return approved` is plain text and should fail. This test checks the mapping on one row, not which rows sampling will select. Choose **Create task** when you're ready to schedule the evaluations.

{/* MEDIA: Historical data selected, a two-row processing limit, and Test on this row showing the JSON check for one handoff. */}

## Create the same task with the platform SDK

You need three different IDs: the **template ID** identifies the check, the **config ID** binds the check to this project's fields, and the **task ID** identifies the scheduled work. In particular, `evals` takes config IDs, not template IDs.

| Task setting | For the two handoffs |
| --- | --- |
| `project` | The Observe project ID, not its display name. Use the same project when creating the config and the task. |
| `row_type` and `filters` | Use `spans` and select the two existing span IDs. Choose spans in the same trace to follow the count example below. |
| `run_type` | `historical` runs over existing rows. `continuous` follows new matching data rather than backfilling history. |
| `sampling_rate` | A percentage from `1` to `100`. Use `100` for both selected spans. |
| `spans_limit` | For a historical task using percentage sampling, supply a processing limit from `1` to `1000000`. It is not a guaranteed number of scores or a spending limit. Omit it for continuous tasks. |

Set `FI_API_KEY` and `FI_SECRET_KEY` for your workspace. Set `OBSERVE_PROJECT_ID` to the project ID and `OBSERVE_SPAN_IDS` to the two span IDs separated by a comma. Install the platform client with `python -m pip install futureagi==0.7.0` or `npm install @future-agi/sdk@0.2.0`. Run **one** of the following. Leave `EVAL_CONFIG_ID` unset the first time; for a later run, set it to the printed config ID to reuse the same check and mapping.

<CodeGroup titles={["Python", "TypeScript"]}>

```python Python
import os
from fi import Client

project = os.environ["OBSERVE_PROJECT_ID"]
spans = [s.strip() for s in os.environ["OBSERVE_SPAN_IDS"].split(",") if s.strip()]
if not 1 <= len(spans) <= 2:
    raise ValueError("Select one or two handoff spans")

with Client() as client:
    config_id = os.getenv("EVAL_CONFIG_ID")
    if not config_id:
        matches = client.evals.templates.list(search="is_json", owner_filter="system")
        template = next(t for t in matches.items if t.name == "is_json")
        mapping = {"text": "output.value"}
        config_id = client.evals.configs.create(
            project=project, eval_template=template.id, name="Return handoff JSON",
            mapping=mapping, config={"mapping": mapping},
        ).id
    task = client.evals.tasks.create(
        project=project, name="Check return handoffs" if len(spans) == 2 else "Regrade return handoff",
        evals=[config_id],
        row_type="spans", filters={"span_id": spans}, run_type="historical",
        sampling_rate=100, spans_limit=len(spans),
    )
    print("Config:", config_id, "Task:", task.id)
    print("Status:", client.evals.tasks.get(task.id).status)
```

```typescript TypeScript
import { Client } from "@future-agi/sdk";

const project = process.env.OBSERVE_PROJECT_ID;
const spans = (process.env.OBSERVE_SPAN_IDS ?? "").split(",").map(s => s.trim()).filter(Boolean);
if (!project || spans.length < 1 || spans.length > 2) {
  throw new Error("Set OBSERVE_PROJECT_ID and select one or two handoff spans");
}

const client = new Client();
let configId = process.env.EVAL_CONFIG_ID;
if (!configId) {
  const matches = await client.evals.templates.list({ search: "is_json", owner_filter: "system" });
  const template = matches.items?.find(t => t?.name === "is_json");
  if (!template?.id) throw new Error("is_json template not found");
  const mapping = { text: "output.value" };
  const config = await client.evals.configs.create({
    project, eval_template: template.id, name: "Return handoff JSON",
    mapping, config: { mapping },
  });
  if (!config.id) throw new Error("No config ID returned");
  configId = config.id;
}
const task = await client.evals.tasks.create({
  project, name: spans.length === 2 ? "Check return handoffs" : "Regrade return handoff",
  evals: [configId],
  row_type: "spans", filters: { span_id: spans }, run_type: "historical",
  sampling_rate: 100, spans_limit: spans.length,
});
if (!task.id) throw new Error("No task ID returned");
console.log("Config:", configId, "Task:", task.id);
console.log("Status:", (await client.evals.tasks.get(task.id)).status);
```

</CodeGroup>

Creating the task queues work. The returned ID does **not** mean that scoring has finished: workers move the task from `pending` to `running` and finish a historical task once they have processed its rows.

### Use MCP instead

In a [connected MCP client](/docs/falcon-ai/guides/use-the-mcp-server), ask for each step separately so you can check the mapping before scheduling work:

1. **Find the template.** Use `list_projects` to identify your project and `list_eval_templates` to find the system `is_json` template.
2. **Test one payload.** Call `test_evaluation` with that `template_id`, `name="is_json"`, `template_type="Function"`, `eval_type_id="CustomCodeEval"`, `output_type="Pass/Fail"`, `required_keys=["text"]`, and `config={"mapping":{"text":"Return approved"}}`. Here `text` is a **literal sample**: expect a failing JSON check. This executes one evaluation but doesn't create a task.
3. **Save the field mapping.** Use `list_eval_configs` to look for a matching project config. If there isn't one, call `create_eval_config` with the project ID, the template ID in `eval_template`, a name, and the **path mapping** `{"text":"output.value"}`.
4. **Schedule and inspect.** Pass the config ID in `evals` to `create_eval_task` with the same settings as the SDK example. Save the task ID for `get_eval_task`, `pause_eval_task`, `update_eval_task`, or `resume_eval_task`.

## Inspect a failed check

1. Open **Tasks**, select **Check return handoffs**, then open **Usage**. Pick the run with a failing **Result**. A failed *verdict* means the evaluator ran successfully and found invalid JSON. If the evaluator itself errored or skipped the row, look in **Logs**, not **Usage**.
2. In the run panel, click **Open trace**. The trace drawer opens on the evaluated span with **Evals** selected. Compare the score and explanation with the span's output. For a voice project the same button opens the call drawer; a session-level run has no **Open trace** button.
3. In the trace drawer press `j` for the next different trace on the current page or `k` for the previous one. Runs on the same trace are skipped. Press `Esc` to return to the run panel for the trace you're viewing, then `Esc` again to close the panel. You stay on **Usage**.

{/* MEDIA: Open a failed JSON check from Usage, inspect the selected span on Evals, step to another trace, and press Esc back to the run panel. */}

To retrieve the same run rows with cURL and `jq`, set `EVAL_TASK_ID` to the printed task ID. This reads one page of successful executions in the past seven days. An empty page immediately after creation can mean the workers haven't produced a result yet.

```bash
curl --fail --silent --show-error --get \
  "${FI_BASE_URL:-https://api.futureagi.com}/tracer/eval-task/get_usage/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  -H "X-Workspace-Id: ${FI_WORKSPACE_ID:-}" \
  --data-urlencode "eval_task_id=${EVAL_TASK_ID:?Set EVAL_TASK_ID}" \
  --data 'period=7d' --data 'page=1' --data 'page_size=25' --data 'include_summary=false' \
  | jq '.result.logs.results[] | {span_id, result, score, reason}'
```

## Reconcile attempts with the trace count

In the project's trace or span list, each eval has one column. **S** means the evaluator targets spans and **T** means it targets traces, regardless of which list you're viewing. A pass/fail cell counts verdicts; a choices cell counts each label separately. Click the cell to open **Evals** for the breakdown.

Suppose two spans in the same trace produce these results. To regrade the second span without discarding the first task's results, rerun the SDK example with `EVAL_CONFIG_ID` set to the first config ID and only the second span in `OBSERVE_SPAN_IDS`. This starts a separate one-span task.

| Handoff span | First task | Second task | Counted on this trace |
| --- | --- | --- | --- |
| Return authorization, with valid JSON | Pass | Not evaluated | Pass |
| Return label, with plain text | Fail | Fail | Fail |

That's **three completed attempts**, but the trace cell shows **one pass and one fail**, not two fails. Both the count tile and the detail rollup (`eval_rollup`) use the latest completed result per span for this config. In the trace detail response, each span's `eval_scores` array contains its individual score records. Use those records or the two tasks' **Usage** tabs to inspect the separate attempts.

{/* MEDIA: The trace's S column with one pass and one fail, and the expanded Evals breakdown showing one current verdict per handoff span. */}

## Pause, edit, or resume

| What you want to do | What to do |
| --- | --- |
| Stop launching work | Click **Pause** on a `running` task, or call `client.evals.tasks.pause(eval_task_id=...)`. Evaluations already in flight can still finish and consume credits. |
| Continue without changes | Click **Resume** on a `paused` or `failed` task, or call `client.evals.tasks.resume(eval_task_id=...)`. This queues the remaining work; it doesn't return new scores immediately. |
| Change the configuration | Pause a running task first. Open **Details**, change the settings, and click **Save**. Choose **Edit & Re-run Existing Evals** (`edit_type="edit_rerun"`) to reuse valid results, or **Delete Past Data & Start Fresh** (`fresh_run`) to remove previous results and score again. Saving a rerun schedules it; don't also resume it. To change the row type, create a new task. |

For example, a two-span historical task might finish before you click **Pause**. A pause request then returns `Cannot pause eval task with status 'completed'. Only running tasks can be paused.` Read the status again instead of retrying the same transition.
