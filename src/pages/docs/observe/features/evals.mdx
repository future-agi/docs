A support request can finish with **OK** and still fail a [toxicity check](/docs/evaluation/builtin/toxicity). Evals run automated quality checks on your production traces in [Observe](/docs/observe), scoring LLM responses for hallucination, tone, bias, toxicity, and more, so you catch that failure without reading traces one by one.

You configure which checks to run, filter which spans they apply to, and choose whether to evaluate historical data or new spans as they arrive. Results appear per span in the Observe dashboard and can trigger alerts when quality drops. This page covers what an eval task is configured with, how to read its results, and what to check when a score is missing. For the click-by-click setup, follow [Set up evals in Observe](/docs/observe/guides/setup-evals).

## When to use

- **Scoring production output quality**: Run historic evals after a release to check for hallucinations, bias, or unsafe content across real traffic.
- **Catching regressions in production**: Set up a continuous eval task so new spans are scored automatically and you see quality drops before users report them.
- **Spot-checking a specific time window**: Filter by date range or session to evaluate only the spans from an incident or a specific user flow.
- **Controlling eval cost**: Use sampling rate and span limits to evaluate a representative subset instead of every span.
- **Running multiple quality checks at once**: Attach several evals to one task so each span gets scored for tone, safety, and accuracy in a single run.

<Prerequisites title="Before you start">
- An Observe project that already has traces.
- An eval task on that project, or the setup guide linked above to create one.
</Prerequisites>

## Choose the level one verdict covers

An eval task scores one level of your data. The level decides what you can map to the eval's inputs.

## Task settings

These are the settings an eval task carries, whether you create it in the UI or through the API.

### Filters

Define filters so the task runs only on the spans you care about.

![The New Task form with the Filters section open: a Property menu offering Span Type and Attributes, and Observation Type set to Tool.](/images/docs/observe/1.png)

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Filter | Description |
|--------|-------------|
| `observation_type` | Node/span type (e.g. `llm`, `chain`, `agent`). |
| `date_range` | Time range: `[start_date, end_date]` applied to `created_at`. |
| `created_at` | Minimum creation time (spans at or after this value). |
| `project_id` | Restrict to a specific Observe project. |
| `session_id` | Restrict to traces in a given session. |
| `span_attributes_filters` | List of span-attribute conditions. |

</div>

Filters are stored in the task's `filters` field and applied when the task runs.

### Run type

![The Scheduled Run section with the Run on menu open: Run on historic data, or Run continuously on new incoming data.](/images/docs/observe/2.png)

- **Historical**: Run on existing spans matching the filters, up to the sampling cap and span limit. The task completes after processing.
- **Continuous**: Run on new spans as they arrive. Each run only processes spans created after the last run; the task stays active for ongoing evaluation.

### Sampling rate and span limit

![A required Max Spans field above a Sampling rate slider labeled from 1 to 100.](/images/docs/observe/3.png)

- **sampling_rate**: Percentage of matching spans to evaluate. For example, `50` evaluates 50% of filtered spans per run. The slider and the [create eval task reference](/docs/api/eval-tasks/create-eval-task) both run from 1 to 100.
- **spans_limit**: Maximum number of spans to process per run. The task stops when either the sampled count or this limit is reached. The API requires it for a historical task and ignores it for a continuous one.

### Evals to run

Attach one or more eval configs to the task. The task runs each selected eval on every span it processes. For evals that need an input (e.g. [Bias Detection](/docs/evaluation/builtin/bias-detection)), set the **input key** to a span attribute path (e.g. `gen_ai.output.messages.0.message.content`) so the eval reads the right field from each span. See [built-in evals](/docs/evaluation/builtin) for supported evaluations and their required inputs.

### Create and run the task

![The Evals & Tasks tab listing one task with its filters, evals applied, sampling rate, run status of Pending and last run.](/images/docs/observe/4.png)

Create or update the eval task via the API or UI, then run it. You can test the configuration before saving. Task status values: `pending`, `running`, `completed`, `failed`, `paused`, `deleted`.

<Note>
Eval tasks are processed asynchronously. Status and results update as runs complete. For continuous tasks, new spans are picked up on subsequent runs.
</Note>

## Read a scored request

1. Open the trace table for the task's project.
2. Find the eval's column. Scores land as a new column, one result per row.

   In the `support-agent` project below, every row's **Status** is **OK**, but the toxicity column reads **Fail**. The request completed; the reply did not pass the check.

   ![The support-agent trace table with OK in the Status column and Fail in the toxicity eval column on every row.](/images/docs/observe/evals-results-column.png)

3. Open a trace for its per-span score.

You can reuse the eval in [filters](/docs/observe/guides/explore-dashboard/filters) (`scores.<name>`) and in [alerts](/docs/observe/guides/setup-alerts).

## When a score is missing

A row with no score was not necessarily read by the task. Check these before you treat it as a quality problem:

- **The row is outside the task's filters.** A span of type `chain` gets no score from a task filtered to `llm`.
- **The run type doesn't cover it.** A historical task scores existing spans and then completes. A continuous task only processes spans created after its last run.
- **Sampling or the span limit left it out.** At a sampling rate of `50`, half of the filtered spans are evaluated, and the task stops at its span limit.
- **The eval read the wrong field.** Check the input key or variable mapping, then test the configuration before saving.
- **The task hasn't finished.** Eval tasks are processed asynchronously, so a `pending` or `running` task may not have reached the row yet. Check whether the status is `failed` or `paused` instead.

## Edit a task without losing results

1. [Get the task](/docs/api/eval-tasks/get-eval-task) and check its status, filters and evals.
2. If it is `running`, [pause it](/docs/api/eval-tasks/pause-eval-task) first. An update is rejected while the task is running.
3. [Update the task](/docs/api/eval-tasks/update-eval-task) with the `edit_type` you want: `edit_rerun` preserves existing results and runs missing evals only, and `fresh_run` clears all previous results.

   When the task finishes processing, check a matching row in the trace table again.
