When a customer reports a bad answer, look up their [user](/docs/observe/concepts/users) row to find the [trace](/docs/observe/concepts/traces) for the request and the [session](/docs/observe/concepts/sessions) around it. The same row brings together activity from later conversations if you keep the customer's ID stable.

<Prerequisites title="Before you start">
- Use an [instrumented Observe project](/docs/observe/features/quickstart) that sends [spans](/docs/observe/concepts/spans).
- Choose a stable, non-sensitive customer identifier, such as `cust_42` or a hashed customer ID. `user.id` is exported in span data, so never use a raw email address or phone number.
</Prerequisites>

## Look up the user

1. Open the project that received the customer's spans.
2. Select **Users**.
3. Search for the user ID. Apply filters if you need to narrow the results.
4. Open the matching row.

   The detail view has **Summary** metrics, a **Traces** tab and a **Sessions** tab for that customer.

The Users table has one row per user, with these columns: user_id, activation date, last active, trace count, error count, session count, avg latency, LLM calls, eval pass rate, guardrail triggers, tokens and cost. In the example below, `cust_77` has two traces in one session. `cust_42` is a separate user, not a second session for `cust_77`.

![Users in the support-agent project: cust_77 has two traces in one session and cust_42 has three traces in one session.](/images/docs/observe/users-list.png)

## Choose what to inspect

| Question | Where to look |
| --- | --- |
| Which request went wrong? | Check error count, then open **Traces** for trace ID, session, latency, input, output, evals, cost and annotations. |
| Which conversation contained the request? | Open **Sessions** for session ID, time range, trace count, evals and cost. The [session walkthrough](/docs/observe/features/session) explains the table. |
| Who is driving cost? | Sort users by cost or tokens; compare LLM calls and average latency to distinguish normal activity from a possible loop. |
| Is someone still using the product? | Compare activation date, last active, active days, trace count and session count. |
| Does quality vary across customers? | Filter by eval pass rate and inspect traces for lower-scoring users. The dashboard also counts guardrail triggers. |

## Make spans appear under the right ID

When an Observe project ingests a span with `user.id`, it creates or finds an `EndUser` in that project and organization using the ID and its optional type. Spans with the same `(user_id, user_id_type)` contribute to one row. Changing the ID or type splits later spans from that row; changing only the session ID starts a different conversation for the same user.

<Mermaid chart={`flowchart TD

There are two ways to attach the ID: set attributes on an individual span, or apply the same ID to every span in a block. [Set session and user IDs](/docs/sdk/tracing/set-session-user-id) covers the second approach in more depth. The sample code uses a person's name and the `email` type. Replace them with your own non-sensitive ID and its matching type before you send data.

### Set attributes on one span

Set `user.id` on the span. It is required. You can also set `user.id.type` (`email`, `phone`, `uuid` or `custom`), `user.id.hash` and `user.metadata` (JSON) for display or filtering.

<CodeGroup>

```python Python
from fi_instrumentation import register, FITracer
from fi_instrumentation.fi_types import ProjectType
from opentelemetry.trace import Status, StatusCode

trace_provider = register(
    project_type=ProjectType.OBSERVE,
    project_name="PROJECT_NAME",
)
tracer = FITracer(trace_provider.get_tracer(__name__))

with tracer.start_as_current_span("SPAN_NAME") as span:
    span.set_status(Status(StatusCode.OK))
    span.set_attribute("user.id", "vivek.gupta")
    span.set_attribute("user.id.type", "email")  # email | phone | uuid | custom
    span.set_attribute("user.id.hash", "<hash_for_the_user.id>")  # optional
    span.set_attribute("user.metadata", {})  # optional
    span.set_attribute("input.value", "input")
    span.set_attribute("output.value", "output")
```

```javascript JS/TS
const { register, ProjectType } = require("@traceai/fi-core");

const traceProvider = register({
    projectType: ProjectType.OBSERVE,
    projectName: "FUTURE_AGI"
});
const tracer = traceProvider.getTracer("manual-instrumentation-example");

tracer.startActiveSpan("SPAN_NAME", {}, (span) => {
    span.setAttribute("user.id", "vivek.gupta");
    span.setAttribute("user.id.type", "email");
    span.end();
});
```

</CodeGroup>

### Apply an ID to every span in a block

To tag all spans in a block with the same user, use a context that sets the ID for you. With the Python SDK, `using_attributes` takes a `user_id` and, optionally, a `session_id`; the [context helpers](/docs/sdk/tracing/context-helpers) page lists the other helpers. The fragment below assumes `client` is your instrumented model client. Send the same `user_id` on later requests and a new `session_id` for each conversation.

<CodeGroup>

```python Python
from fi_instrumentation import using_attributes

with using_attributes(user_id="newuser@example.com", session_id="new-session"):
    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": "Write a haiku."}],
        max_tokens=20,
    )
```

</CodeGroup>

## Troubleshooting

- **No user row:** inspect a span in the same project for `user.id`. A trace can arrive without one: in the tracing view below, **User Id** is empty. Send another request with the identifier attached and look up the ID again.
- **One customer has multiple rows:** compare both the ID and type on the spans, not just the displayed name. Reuse the same pair on subsequent requests.
