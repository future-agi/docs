AutoEval proposes metrics and scanners based on your app's category, risk level, and domain. A recommendation is a starting point, not a score. This example checks two things about a Ridgeline Outfitters reply: does it address the shopper's question, and does it fit on one line?

Use a fresh environment. These examples create local Python objects and files, not a hosted evaluation. Only the optional OpenAI analysis at the end needs a provider key.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install agent-learning-kit==0.3.7
```

Run `python` and use the same session for the snippets below.

## From a description

`from_description` uses rules when you don't pass an LLM provider. Describe the agent's job, not the answer to one test question. `explain()` shows what the kit recommends and why.

```python
from fi.evals.autoeval import AutoEvalPipeline

description = "A Ridgeline customer support chatbot retrieves return policies and answers questions about unworn hiking boots."
proposal = AutoEvalPipeline.from_description(description, name="ridgeline-support")
print(proposal.explain())
```

## From a template

If you know what kind of app you have, start with a named configuration instead. These are the checks **configured** in each template, before customization.

| Template | Metrics | Scanners | Risk |
| --- | --- | --- | --- |
| `customer_support` | answer_relevancy | Jailbreak, Toxicity, PII | Medium |
| `rag_system` | faithfulness, groundedness, answer_relevancy | Jailbreak | Medium |
| `code_assistant` | answer_relevancy | CodeInjection, Secrets, Jailbreak | Medium |
| `content_moderation` | None | Toxicity, Bias, InvisibleChar, MaliciousURL | High |
| `agent_workflow` | action_safety, reasoning_quality | Jailbreak, CodeInjection | High |
| `healthcare` | faithfulness, answer_relevancy | PII, Secrets, Toxicity, Jailbreak | High |
| `financial` | factual_consistency, answer_relevancy | PII, Secrets, Jailbreak | High |

```python
from fi.evals.autoeval import get_template, list_templates

for name in sorted(list_templates()):
    print(name, get_template(name).risk_level)

pipeline = AutoEvalPipeline.from_template("rag_system")
```

## Customize the checks

For the chat widget, keep the relevance check and add `one_line` and an invisible-character scanner. Disable `groundedness` and remove `faithfulness` for this example. The resulting pipeline does **not** verify the return policy; run a separate grounding check if that matters to your release.

```python
from fi.evals.autoeval import EvalConfig, ScannerConfig

pipeline.disable("groundedness")
pipeline.remove("faithfulness")
pipeline.add(EvalConfig(name="one_line", threshold=1.0))
pipeline.add(ScannerConfig(name="InvisibleCharScanner", action="block"))
pipeline.set_threshold("answer_relevancy", 0.7)
```

## Run the pipeline

Scanners run first, on `response` by default. A blocking scanner can stop the run before any metrics execute. Inspect the per-check results: a missing score isn't evidence that a reply passed.

```python
question = "Can I return unworn hiking boots?"
reply = "You can return unworn hiking boots within 30 days with a receipt."

def score_reply(text):
    result = pipeline.evaluate({"query": question, "response": text})
    scans = result.scan_result.results if result.scan_result else []
    if {s.scanner_name for s in scans} != {"jailbreak", "invisible_chars"} or any(
        (s.reason or "").startswith("Scanner error:") for s in scans
    ):
        raise RuntimeError("Not all configured scanners ran successfully")
    if result.blocked_by_scanner:
        raise ValueError(f"Blocked by: {result.scan_result.blocked_by}")
    scores = {m.eval_name: m.score for m in result.metric_results if m.status == "completed" and m.score is not None}
    if set(scores) != {"answer_relevancy", "one_line"}:
        raise RuntimeError(f"Incomplete metric results: {result.metric_results}")
    print("Passed:", result.passed, "scores:", scores)
    return scores

single = score_reply(reply)
wrapped = score_reply(reply.replace(" within", "\nwithin"))
assert single["one_line"] == 1.0 and wrapped["one_line"] == 0.0
```

The line break changes the formatting score from `1.0` to `0.0` without changing the policy. The overall decision also depends on the relevance score and the configured pass rate. Neither score establishes that 30 days is the correct return window.

## Export and reload configs

Export before loading: these files contain the configuration, not past inputs or scores. Commit the config to version control if you want CI to run the same checks.

```python
pipeline.export_yaml("eval_config.yaml")
pipeline.export_json("eval_config.json")
```

```python
from fi.evals.autoeval import load_json

from_yaml = AutoEvalPipeline.from_yaml("eval_config.yaml")
from_json = AutoEvalPipeline.from_config(load_json("eval_config.json"))
assert from_yaml.config.to_dict() == from_json.config.to_dict() == pipeline.config.to_dict()
```

## Optional: analyze the description with OpenAI

Setting `OPENAI_API_KEY` alone does not enable model-based analysis. With your key set, pass an LLM provider to `AppAnalyzer`. Here the provider returns the text from an OpenAI chat completion. Only the **app description** is analyzed, not the shopper's reply. If the provider fails or its answer can't be parsed as JSON, the analyzer falls back to rules.

```python
from openai import OpenAI
from fi.evals.autoeval import AppAnalyzer

client = OpenAI()

def analyze_with_openai(prompt, system_prompt):
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "system", "content": system_prompt}, {"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
    )
    return response.choices[0].message.content

analysis = AppAnalyzer(llm_provider=analyze_with_openai).analyze(description)
print(analysis.category.value, analysis.risk_level.value, analysis.domain_sensitivity.value)
print(analysis.explanation)
```
