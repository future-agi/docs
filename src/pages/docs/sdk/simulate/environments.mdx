Script what you would otherwise click through on an [environment](/docs/environments/concepts/understanding-environments): change its cast of actors, prove or archive scenarios, check that a pairing of versions is ready, start a run with a fixed seed, and read who did what in a multi-agent trial. Each section below is one task, in the order you'd use them.

<Note>
You need an environment in **Ready** status, and an API key and secret key from your workspace settings. Set `FI_API_KEY`, `FI_SECRET_KEY` and `FI_WORKSPACE_ID` in your shell. Actors, drafts and the scenario lifecycle need environment versioning on your workspace. These methods need a Future AGI SDK release that includes them; the [Simulation reference](/docs/sdk/reference/simulation) lists the methods of the release you have.
</Note>

## Connect the SDK

Install the SDK and create a client. It reads your keys from the environment, and every environment action takes the environment's ID, the last part of its address in the app.

<Tabs>
  <Tab title="Python">
```python
# pip install futureagi
from fi import Client

client = Client()
env_id = "YOUR_ENVIRONMENT_ID"
```


## Read and change the actors

An environment's **actors** are the people and systems your agent deals with in its scenarios, such as `caller`, `coworker` and `manager` in a sales desk. A change to an actor goes into the environment's draft; runs keep using the saved version until you save the draft, so you can try a change without affecting runs in progress.

```python
cast = client.simulation.environments.actors.list(env_id)
seen = client.simulation.environments.actors.get(env_id, "coworker")

change = {"name": "Dispatcher", "side": "world"}
check = client.simulation.environments.actors.validate(env_id, op="create", changes=change, new_id="dispatcher")
if not check.problems:
    client.simulation.environments.actors.create(env_id, changes=change, new_id="dispatcher", expected_revision=cast.revision)
```

- **validate**: what a create, change or removal would say, writing nothing. It names the field at fault, for example an `id` with a hyphen, since actor IDs take lowercase letters, digits and underscores
- **create**, **update** and **delete**: change one actor. Pass `expected_revision` from the last list so a draft someone changed since is refused instead of overwritten
- **set_limits**: replace the actor limits, such as `{"max_active": 3}`; a limit you leave out takes the channel's default
- **accept_unresolved**: accept the cast as written for one point the builder could not model, named exactly as the list returns it under `unresolved`

In TypeScript the same calls are `actors.list`, `actors.validate`, `actors.create`, `actors.update`, `actors.delete`, `actors.setLimits` and `actors.acceptUnresolved`, with the actor's new ID passed as `id`. Save the draft once the cast is right. Where your environment can prove its scenarios, a changed cast is validated before it is saved, as **Validate** does before **Save** in the app: `drafts.list` says so with `validation_required`, and a plain save is refused with `validation_required`.

```python
import time

drafts = client.simulation.environments.drafts

def validate():
    listed = drafts.list(env_id)
    review = drafts.review(env_id)
    started = drafts.validate(env_id, expected_revisions={"environment": listed.environment.revision}, expected_review_digest=review.review_digest)
    return review, started.validation.state

review, state = validate()
tries = 1
while state in ("validating", "retry", "outdated", "superseded"):
    if state == "validating":  # still running
        time.sleep(20)
        listed = drafts.list(env_id)
        state = listed.validation.state if listed.validation else "unavailable"
    elif tries < 3:  # nothing proved this draft yet, or it moved: validate again
        review, state = validate()
        tries += 1
    else:
        break

listed = drafts.list(env_id)
if state in ("ready", "check_unavailable"):
    drafts.save(
        env_id,
        candidates={"environment_version_id": listed.candidates.environment_version_id, "suite_version_id": listed.candidates.suite_version_id},
        expected_review_digest=review.review_digest,
        name="Add dispatcher",
        idempotency_key="add-dispatcher",
    )
elif state == "unavailable":  # this environment can't validate: save the draft itself
    drafts.save(env_id, drafts=[{"piece": "environment", "expected_parent_id": listed.environment.parent_id}], idempotency_key="add-dispatcher")
else:
    print("Not saved:", state, listed.validation and listed.validation.error)
```

Validation runs in a build sandbox and makes model calls, and takes a few minutes. While it runs, the state is `validating`. `ready` means the changed cast passed; `check_unavailable` means the check could not run for a reason on our side, and the save may go ahead unchecked, as a run may. `retry` means nothing has proved this draft yet (a validation ended before any check ran, or the agent was certified on other versions), `outdated` means the draft changed after you validated it, and `superseded` means the environment's versions moved under it: validate again for each. `failed` means the agent failed the check, so fix the change first. `unavailable` means this environment can't validate, so you save the draft itself.

## Check scenarios and change their lifecycle

Every scenario has a **lifecycle**: `draft`, `validated`, `active`, `archived`, `source_changed` (an environment version changed something it cites) or `kept_as_written`. The scenario list returns each scenario's state and how many are in each.

```python
page = client.simulation.jobs.scenarios.list(env_id, lifecycle="archived", group_by="")  # "" lists them flat, not by goal
started = client.simulation.environments.scenarios.validate(env_id, keys=["apply-permitted-discount-standard"])
status = client.simulation.environments.scenarios.validation_status(env_id, job_id=started.job_id)

client.simulation.environments.scenarios.archive(env_id, "apply-permitted-discount-standard", reason="duplicate")
client.simulation.environments.scenarios.restore(env_id, "apply-permitted-discount-standard")
```

Validation proves scenarios again in a build sandbox and makes model calls, so name the scenarios you changed rather than the whole suite; see the Usage page in the app for what it counts toward. It returns a `job_id` straight away; `validation_status` reports `validating` until it finishes, then how many it proved. Archiving takes a scenario out of future runs and keeps its runs and evidence; restoring brings it back at once when the saved suite still holds it, or as a draft to save. `revisions` lists a scenario's content across saved suite versions, and `records` returns the seeded rows of one table, to pick a real record for a scenario; where the world can't list its rows, it answers with `available` false and no rows.

## Check run readiness before a run

**Run readiness** says whether a pairing of agent, environment and suite versions is ready to run, computed now. Leave a version out to use the environment's default.

```python
report = client.simulation.environments.readiness.get(env_id, keys=["apply-permitted-discount-standard"], trials=1)
print(report.answer.kind, report.blockers)
for row in report.rows:
    print(row)
```

The answer is `ready`, `blocked`, `stale`, `unchecked` or `validating`, with `blockers`, how many checks and participants hold the pairing back, and `rows`, one per readiness check (such as **Agent starts**) with its status and why. `readiness.cases` pages through the scenarios in one bucket (`eligible`, `blocked`, `stale` or `untested`), `readiness.recheck` validates the pairing again without a run (a pairing not certified yet runs its check in a build sandbox and makes model calls), and `readiness.history` lists the pairings already certified.

## Start a run with a fixed seed

A **seed** draws the same personas and variations again, so two runs with one seed differ only by what you changed. Each run carries an idempotency key, a new one for every call unless you pass your own. Pass the same `idempotency_key` again, for example when you retry after a timeout, and you get the same run back, not a second one.

```python
run = client.simulation.environments.run(
    env_id, scenario_ids=["lookup-deal-and-post-channel"], trials=1, seed="7",
    idempotency_key="nightly-run-2026-11-27",
)
```

A run plays your agent and simulated people, so it may incur usage charges. Read each trial with `calls.get`, which includes what the trial changed in the World, as [Read run results](/docs/environments/guides/read-run-results) describes in the app.

## See who did what in a multi-agent trial

When your agent is a multi-agent app, `calls.workers` returns which of its participants (workers) acted in one trial, read from the traces the app sent.

```python
workers = client.simulation.calls.workers(call_id)
```

It returns the workers and what each did. While the traces are still being collected it returns `pending` and `next_read_at`, so read it again after that time; for a trial that handed nothing to another agent it returns `None` in Python and nothing in TypeScript.
