An **environment** supplies the services and data your agent can use during a test. ALK's **reference harness** can start those services from a Compose file or read your agent's source and generate scenarios for it. Try starting a disposable Redis service to see where ALK records its connection details. Use the source-authoring workflow when you have an agent of your own to test.

<Note>
Install ALK using the [Python quickstart](/docs/sdk/agent-learning-kit) and keep that virtual environment active. The Redis exercise requires Docker with Compose and access to the `redis:7-alpine` image. Docker may download the image on first use. You can complete the exercise without a model account.
</Note>

## Start a disposable test service

In an empty working directory, create a folder named `redis-source`. Save the following as `redis-source/compose.yml`. The health check asks Redis to respond to `ping`, so ALK can wait until the service accepts connections.

```yaml
services:
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 1s
      timeout: 3s
      retries: 60
```

From the directory that contains `redis-source`, start Redis and inspect its recorded status:

```bash
agent-learn harness environment up --path redis-source --out redis-session
agent-learn harness environment status --out redis-session
```

Look for `redis` in the startup output. Open `redis-session/environment.json` and find the `external_address` under `service_endpoints`. Use that address to connect from your machine. ALK records the host port it assigned to this service.

When you're finished, remove the example's runtime and test volumes:

```bash
agent-learn harness environment down --out redis-session
```

## Generate scenarios from your agent

For this workflow, supply the path to your own agent repository. For example, if your support agent looks up orders, the harness reads the source to identify its tools, builds test data, then writes scenarios and checks for those tools.

Run authoring in an isolated development environment with test credentials. The harness can read configuration from the submitted repository, call models and execute generated checks. Model calls can incur charges even if you stop before running the scenarios.

For example, to use Gemini through Vertex AI, configure Google Application Default Credentials for a project with Vertex AI access. If you use the Google Cloud CLI on your laptop, `gcloud auth application-default login` sets up those credentials. Set `GOOGLE_CLOUD_PROJECT` if they don't identify the project.

If you approve using Google ADK for this run, select the backend in the same shell:

```bash
export ALK_HARNESS=vertex-gemini
export ALK_GOOGLE_ADK_EXPLICITLY_APPROVED_BY_USER=1
```

To choose a model other than the backend default, set `ALK_HARNESS_MODEL` to a compatible Gemini model available to your project.

Replace `../support-agent` with the repository path. Choose a fresh output directory. Request one scenario to review before running it:

```bash
agent-learn harness author --path ../support-agent \
  --name support_agent --count 1 --out support-author
```

After the command reports `automatic authoring complete`, open these files in `support-author`:

- `contract.json` describes the agent and tools ALK identified. Check that the tool names and arguments match the agent you submitted
- `scenarios.json` lists the generated cases. Open the corresponding `scenarios/<name>/scenario.json` to see what a particular case asks the agent to do
- `cost.json` records the model usage and cost information available to the harness. The scenario count controls how many cases you request, while the number of model calls can vary

## Generate and run scenarios together

Choose `auto` when you want ALK to generate scenarios and execute them against the agent in one attempt. This starts a fresh authoring run and can provision the services your source declares.

Before running it, check your shell and the agent repository's `.env.local` and `.env` files. The harness reads missing settings from those files. If it finds a platform URL, API key and secret key, it also sends scenario results and transcripts to that platform. For local-only results, leave the reporting credentials unset in both places. The harness checks `HARNESS_PLATFORM_URL`, `HARNESS_PLATFORM_API_KEY` and `HARNESS_PLATFORM_SECRET_KEY`, with `FI_BASE_URL`, `FI_API_KEY` and `FI_SECRET_KEY` as respective fallbacks.

Use a separate output directory:

```bash
agent-learn harness auto --path ../support-agent \
  --name support_agent --count 1 --out support-run
```

During simulation, the harness prints how many scenarios passed and the run directory under `support-run/runs/`. Open `run.json` there for the counts of passed and unrunnable scenarios. In each scenario's subdirectory, `result.json` holds its verdict, `transcript.txt` holds the conversation and `calls.json` holds the recorded calls.

If ALK reports that the authoring destination already contains files, keep that directory for inspection and choose a new `--out`. If the service fails to start, check that Docker is running and can access the images in the source's Compose file.

If you already know the services, scenarios and agent interface you want, [build a Python environment plugin](/docs/sdk/agent-learning-kit/build-an-environment-plugin) to define the interaction in code. To manage hosted jobs and read results in the dashboard, use [Platform Environments](/docs/environments).
