## What a guardrail pipeline is

A **guardrail pipeline** is the path a live request takes through every enabled guardrail on a gateway, pre-stage checks first, then post-stage checks, with each check working out its own verdict. A [guardrail](/docs/protect/concepts/understanding-protect) wraps a check and adds an action, a stage, and a confidence threshold.

## Where a guardrail sits on the request

Every guardrail has a stage: **pre**, **post**, or **both**. A pre-stage guardrail runs before the model sees the request. A post-stage guardrail runs before the response reaches the caller. A guardrail whose stage is **both** isn't a special third mode. It's the same check running twice: once on the way in, once on the way out.

This is what makes the stage a property of the guardrail, not of the check itself. A gateway, the Agent Command Center surface that holds your guardrails, can hold a mix of guardrails, some looking only at what the caller sent, others only at what the model sent back, others watching both directions.

## Settings shared across the gateway

The pipeline carries three settings, under **Pipeline Settings**, that apply across every guardrail on the gateway rather than to any one guardrail:

| Setting | Options | What it does |
|---|---|---|
| **Mode** | Parallel or Sequential | Whether the guardrails on the gateway run at the same time or one after another (Parallel by default) |
| **Fail Open** | on or off | What happens when a check doesn't return a verdict before Timeout runs out. On lets the request through unchecked, trading safety for availability; off applies the check's configured action instead, trading availability for safety |
| **Timeout (ms)** | a millisecond value | How long a check is given to return a verdict before Fail Open decides what happens next |

See [Turn on a guardrail](/docs/protect/guides/turn-on-a-guardrail) for how to change them.

## From confidence to an action

Confidence is how sure a check is that the content matches what it looks for. Each check compares that confidence score against its own threshold to decide whether it fires. Leave the threshold untouched and it defaults to **0.8**. Moving it up narrows what counts as a match; moving it down widens it, so the same check can run stricter or looser depending on where the threshold sits.

When a check fires, its **action** decides what happens next. A check can be set to **Block**, **Warn**, **Mask**, or **Log**: Block and Warn change the response status the caller gets back, and Log records that the check fired without changing anything. Leave the action untouched and it defaults to **Block**. Naming a check's action here isn't the same as choosing which checks exist: that list lives in [Guardrail checks](/docs/protect/reference/guardrail-checks).

## What the caller sees

The action a fired check takes maps directly to the response status the caller gets back:

| Outcome | Status |
|---|---|
| Blocked | HTTP `403` or `446` |
| Warned | HTTP `246` |
| Anything else | The normal response status |

Both `403` and `446` mean the same thing: the check blocked the request, so a caller can handle either the same way.

In the product UI, [testing a guardrail](/docs/protect/guides/test-a-guardrail) shows the same three outcomes as a result chip instead of status codes: `BLOCKED (446)`, `WARNING (246)`, or `OK` with the status code the call returned for everything that didn't block or warn. The chip always reads `BLOCKED (446)` for a block, so a `403` block shows `446` on screen too.

## A request through the pipeline

Take a single check, left at its defaults: threshold `0.8`, action `block`. A request comes in and the check scores it `0.92`. That score is above the threshold, so the check fires. Its action is `block`, so the caller gets back status `403` or `446`, and the result chip reads `BLOCKED (446)`. Change the action to `warn` instead and the same fired check produces `246` and the `WARNING (246)` chip, nothing about the threshold or the score changes, only the action does.

This is why it matters: threshold and action are separate knobs. Loosening a threshold makes a check fire more often on the same traffic, but what a caller actually experiences, blocked, warned, or unaffected, is controlled entirely by the action. Mixing up the two is the most common way a guardrail ends up behaving differently than expected.
