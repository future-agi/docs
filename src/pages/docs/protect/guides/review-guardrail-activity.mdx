A spike in blocks tells you which [guardrail](/docs/protect/concepts/understanding-protect) to investigate, not whether the blocks were justified. Follow one check from Analytics to the [request drawer](/docs/command-center/features/guardrails#guardrail-feedback), then see how your verdict contributes to that check's feedback summary.

<Prerequisites title="Before you start">
- [Agent Command Center](/docs/command-center/quickstart) set up with at least one [provider](/docs/command-center/features/providers) connected. Protect's guardrails live there, under **Gateway**.
- An [enabled guardrail](/docs/protect/guides/turn-on-a-guardrail) that has fired on a request. Until it fires, the trends chart, rules table, **Logs** tab and **Feedback** tab all show empty states.
</Prerequisites>

## Choose a check in Analytics

1. Open **Gateway > Guardrails > Analytics**.
2. Select **24h**, **7d**, or **30d**.

   The window applies to the whole tab, including **Guardrail Triggers Over Time**.

<div class="sdk-ref-table">

| Metric | What to read |
| --- | --- |
| **Trigger Rate** | Share of requests where any guardrail triggered. A few blocks over a month can still round to 0.0%. |
| **Blocked** | Number of blocking checks. Two checks that block on the same request count twice. |
| **Warned** | Number of warning checks, also counted per check rather than per request. |
| **Avg Latency** | Average time the guardrail check added, not total request time. |

</div>

![The 30d Analytics view shows Trigger Rate, Blocked, Warned and Avg Latency above the trigger-volume chart and Top Triggered Rules.](/images/docs/protect/guides/review-guardrail-activity.png)

3. Find the check of interest in **Top Triggered Rules**.

   Compare its share of triggers with its block and warn counts. A rule with a large share is a useful place to start.

## Find a request that fired the check

1. Open **Logs** under **Gateway > Guardrails**.

   Logs lists recent triggered requests across the gateway. It does not inherit the rule you were inspecting in Analytics.

2. Select a row to go to the request in the gateway's full request log.
3. Open that request's detail drawer.
4. Select **Guardrails**.

   You should see separate feedback controls for each check that fired. A request on which nothing fired has no **Guardrails** tab.

## Save your verdict

1. For the matching check, choose **Correct**, **False Positive**, **False Negative**, or **Unsure**.
2. Optionally add a comment explaining your choice.
3. Select **Submit Feedback**.

   You should now see **Edit**. Each reviewer has one answer per request and check, so you can amend yours rather than submitting another.

4. Open **Gateway > Guardrails > Feedback**.
5. Find the same check in **Feedback Summary by Check**.

   The totals and accuracy include submitted feedback for that check. Marking a false positive records the mistake; it does not change the rule or prevent another block.
