Check how a [guardrail](/docs/protect/concepts/understanding-protect) behaves before any traffic from your app reaches it. The **Test** tab runs a single prompt through your active guardrail configuration on the [gateway](/docs/command-center) and shows you the verdict immediately.

In this guide you run two prompts against the same guardrail: the result chip tells you whether the call went through, and the headers tell you whether a check triggered.

<Prerequisites title="Before you start">
- A guardrail that is already turned on. With nothing configured, every prompt just passes through. If you haven't set one up yet, [turn on a guardrail](/docs/protect/guides/turn-on-a-guardrail) first.
- For the comparison below, **PII Detection** with **Block** as its action, as in the PII example from that guide. PII means personally identifiable information.
</Prerequisites>

## Run a safe prompt

1. Open **Gateway > Guardrails > Test**.

   You should see the **Test Guardrails** panel.

2. Click **Safe prompt**.

   The chip drops a ready-made prompt into the box. The other example chips are **PII test**, **Injection test**, **Secrets test**, and **Toxic content**. You can also skip the chips and type your own prompt into the box.

3. Optionally enter a model name under **Model (optional)**.

   The placeholder reads "e.g. gpt-4o-mini". It names the model the test request runs against.

4. Click **Run Test**.

   The button stays disabled until there's a prompt in the box, and reads **Running...** while a test is in flight. Note the result chip and its status code before the second run.

## Run the PII test

The **PII test** chip carries the kind of data a PII Detection guardrail is built to catch. Use this built-in example, not anyone's real details.

<img src="/images/docs/protect/guides/test-a-guardrail.png" alt="PII test has filled the prompt box and Run Test is available. No result chip is visible yet." style={{ borderRadius: '5px' }} />

*The **PII test** chip fills the box for you, so Run Test is live without typing anything. The screenshot shows the panel before the run.*

1. Click **PII test**, leaving the model and the guardrail unchanged.
2. Click **Run Test** again.

   With PII Detection set to **Block**, expect **BLOCKED**.

## Read the result

When the test finishes, a result chip reports the outcome:

| What you see | What it means |
| --- | --- |
| **BLOCKED** | A guardrail stopped the request. A blocked call returns `403`. |
| **OK** with a status code | The call passed, and the chip shows the status code it returned. A check set to Warn or Log never stops the call, so it comes back `200` and shows as OK. |
| An error alert instead of a chip | The test call itself couldn't complete. This is not a guardrail verdict. |

The panel's helper text also mentions `446` and `246`. Go by the status code your run returns. [Guardrail checks](/docs/protect/reference/guardrail-checks#response-statuses) lists the status each action produces.

Below the chip, two sections show what the call returned. Open them when you're wiring your own client to react to blocked or warned responses and need the exact shape it will get, not just the summarized chip.

1. Open **Guardrail Headers**.

   After a Warn or Log trigger, the response carries the header `x-agentcc-guardrail-triggered: true`. **OK** alone does not mean that nothing triggered.

2. Open **Response Body** to see the body your client would receive.
3. Compare the two runs in **Recent Tests**.

   **Recent Tests** keeps your last 20 runs and clears when you reload the page.

## If the verdict was wrong

A chip that doesn't match what you expected, for example a prompt you thought would block coming back **OK**, points back to the guardrail's configuration rather than the panel. See [Guardrail fires on the wrong requests](/docs/protect/troubleshooting/guardrail-fires-on-the-wrong-requests) to fix it.
