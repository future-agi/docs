---
title: "Guardrail changes not taking effect"
description: "Check whether a Rules drawer edit was saved and applied, whether the gateway pipeline is on, and which side of the exchange the check reads."
---

You changed a guardrail's action or settings, but requests still come back exactly like they did before. **Rules** has one editor: open the saved rule's row to edit its drawer. **Save** sends an edit immediately; a new rule uses **Add check**. There is no separate **Save & Activate** step or Overview editor.

## Check the save result

Go to **Gateway** > **Guardrails** > **Rules** and open the rule. Confirm that you saved the drawer, then read the result. **Saved, but the gateway did not apply it** means the configuration was stored but the gateway did not confirm the change; the drawer stays open with the warning. Follow the reason in that warning rather than assuming the saved rule is live. A request error is shown separately and is not a successful save.

If the page says **Guardrails are off on this gateway**, no check runs even though you can save rules. Ask the gateway operator to enable the pipeline in the gateway configuration. If the save applied and the pipeline is on, move on to the next check.

## Check the guardrail's Stage

Open the rule's row in **Rules** and read the stage description in its drawer. It tells you whether the check reads the request or the model's answer; it is not a selector. **PII Detection** reads requests only. **Hallucination Detection** and **Data Leakage Prevention** read responses. You cannot move an organization check to post or both by editing its rule. Choose and test a check that reads the side you need covered. See [Understanding Protect](/docs/protect/concepts/understanding-protect).

## If the toggle failed

Use the rule's switch in **Rules**. A successful change reports that the check was **turned on** or **turned off**. If you see an error, check the saved state before retrying. A **Saved, but the gateway did not apply it** warning is different: the saved state changed, but enforcement has not been confirmed. Only an organization Owner or Admin can change the rule.

## Confirm with a Test tab run

The fastest way to know whether any of these fixes worked, rather than waiting on real traffic, is one run in [**Gateway** > **Guardrails** > **Test**](/docs/protect/guides/test-a-guardrail). Send a prompt that should trigger the check and read the result chip in the Result card: it reads **BLOCKED** when a check with the Block action stopped the call, which the gateway returns as `403`, or **OK** with the status code when the call went through. Checks set to Warn or Log never stop a call, so they show as OK on `200`.

## If the test still doesn't fire

If the save applied, the pipeline is on, the rule is on, and you're testing the side it reads, inspect the rule's settings next. Contact support@futureagi.com with the guardrail's name, its stage and action, and the prompt you tested with if the behavior is still unexplained.
