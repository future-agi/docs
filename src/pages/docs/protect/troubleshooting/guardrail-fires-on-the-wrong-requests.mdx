---
title: "Guardrail fires on the wrong requests"
description: "Tune a check's supported settings or match threshold, re-test the change, and record feedback. Default PII matches have no threshold slider."
---

A guardrail check can go wrong in two directions: it blocks or warns on requests that were fine, or it lets through content it should have caught. Either way, the fix is the same set of levers, worked in order on the one check that's causing it.

Go to **Gateway** > **Guardrails**. **Rules**, **Analytics**, **Feedback**, **Test**, and **Logs** are the tabs in that section; **Analytics** is where you diagnose which check is misfiring, and **Rules** is where you open that check's row to edit it.

## Find the check that's firing

Checks show up under **Rule** in the **Top Triggered Rules** table alongside **Triggers**, **Block**, and **Warn** counts. Open **Gateway** > **Guardrails** > **Analytics** to see it:

- **Over-blocking:** a high Block count points to the check to look at first, not proof on its own that it's firing on requests that were fine
- **Letting through:** if a specific kind of content, like PII or a prompt injection, is getting through, open the check meant to catch it

## Switch Action to Warn or Log while you tune

Switch **Action** from Block to Warn or Log before tuning, so a check you're still tuning doesn't stop real traffic. As an organization Owner or Admin, go to **Gateway** > **Guardrails** > **Rules** and open the check's row to edit its drawer (see [Turn on a guardrail](/docs/protect/guides/turn-on-a-guardrail) for the setup walkthrough). In the drawer's **Action** select:

- **Block** stops the request, and counts toward that check's Block total in Top Triggered Rules
- **Warn** lets the request through, and counts toward that check's Warn total in Top Triggered Rules
- **Log** lets the request through too, and still counts toward Triggers, but the check's Block and Warn totals stay flat, for a quieter pass while you compare several changes

**Mask** is offered only for checks that can rewrite the request, and serves a different use case. Set **Action** back to Block once you're satisfied with the check's behavior.

## Tune the settings the check supports

### Checks with a Match threshold

If the drawer shows **Match threshold**, it runs from 0.0 to 1.0 in steps of 0.05; a new rule starts at 0.8. A match scoring at or below the threshold is ignored. For checks whose match scores vary, raising the threshold can reduce matches and lowering it can include lower-scoring matches. Try a change of 0.05 to 0.1 and re-test before adjusting further; a threshold change will not affect examples whose scores remain on the same side of it.

### Fixed-score checks

Default **PII Detection** has no Match threshold slider. Its `max_entities` defaults to 1, and its score is the detected entity count divided by that maximum, capped at 1. Any detected entity therefore scores 1. Raising a threshold from 0.8 to 0.9 would not change which requests match.

The same limitation applies to default **Secret Detection** and **Keyword Blocklist**. Their sliders appear only if a saved `max_secrets` or `max_matches` exceeds 1; PII's slider similarly depends on a saved `max_entities` above 1. **Topic Restriction** and **Language Detection** always score 1 on a match and have no threshold slider. A threshold of 1 ignores these fixed-score matches rather than selectively reducing false positives.

For fixed-score checks, edit the rule-specific **Settings** that the drawer actually offers:

- **Keyword Blocklist**: adjust **Blocked keywords**.
- **Topic Restriction**: adjust `forbidden_topics` or `allowed_topics` and their keywords.
- **Language Detection**: adjust **Allowed scripts**.
- **PII Detection** and **Secret Detection**: the drawer does not expose detector-specific tuning fields. Change the action or choose a different check rather than looking for a sensitivity slider.

**Future AGI Eval** also hides the threshold slider, and stored-only integrations such as Presidio PII are not editable in this console. See [Guardrail checks](/docs/protect/reference/guardrail-checks) for availability and [Understanding Protect](/docs/protect/concepts/understanding-protect) for actions and stages.

Click **Save** in the drawer to send the change immediately. There is no second activation step. If you see **Saved, but the gateway did not apply it**, or re-testing shows no change, see [Guardrail changes not taking effect](/docs/protect/troubleshooting/guardrail-changes-not-taking-effect) before assuming the edit is enforced.

## Re-test after each change

After each change, switch to **Gateway** > **Guardrails** > **Test** (see [Test a guardrail](/docs/protect/guides/test-a-guardrail) for what it shows) and click the example chip that matches the case you're chasing, whether that's PII, an injection attempt, secrets, or toxic content, then run it. The result chip in the Result card reads BLOCKED, which the gateway returns as `403`, or OK with the status code the call came back on; that's the verdict to check against what you meant to happen. Re-running that chip after every settings, threshold, or Action change is how you confirm the change did what you meant, instead of stacking up several changes and losing track of which one mattered.

## Record the verdict as feedback

<Note>
Feedback is a record, not a control. Submitting a False Positive or False Negative doesn't retune the check. Marking one here without changing the rule's action or supported settings leaves the check exactly as it was.
</Note>

From **Gateway** > **Guardrails** > **Logs**, open the request the check got wrong in its detail drawer. The drawer's **Guardrails** tab only appears when at least one check fired on that request; a request that nothing caught has no feedback controls at all, so it can't be marked False Negative from its own drawer. On the drawer's **Guardrails** tab, one set of feedback controls appears for each check that fired on that request; find the set for the check you're tuning and mark it **False Positive** if it fired on a request that was fine, or **False Negative** if it let through something it should have caught, then press **Submit Feedback**. That verdict rolls up into **Gateway** > **Guardrails** > **Feedback** alongside every other correction submitted for that check.

## If it still fires wrong

If the check still fires wrong after tuning its supported settings and re-testing, the fix may be more than this check can offer on its own. Check whether a different check in the **Top Triggered Rules** table above is the actual source, or contact support@futureagi.com with the check's name, the action and settings you tried, and an example request it still gets wrong.
