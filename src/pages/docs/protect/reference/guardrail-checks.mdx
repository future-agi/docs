## PII entities

The gateway's `pii-detection` check (also stored under the rule alias `pii-detector`) accepts the following **case-sensitive** identifiers in `config.entities`. For example, `["email", "ssn", "credit_card"]` selects those three detectors. Omitting `entities` uses all supported detectors.

| Entity id | Pattern detected |
|---|---|
| `email` | Email address |
| `phone` | US phone number |
| `ssn` | US Social Security number |
| `credit_card` | Credit card number |
| `ipv4` | IPv4 address |
| `ipv6` | Full eight-group IPv6 address |
| `dob` | Date of birth pattern |
| `passport` | Passport number following a passport keyword |
| `drivers_license` | Driver's license number following a license keyword |
| `iban` | International Bank Account Number |
| `zip_code` | US ZIP+4 code |
| `aws_key` | AWS access key identifier |
| `api_key` | API key / secret pattern |
| `url_credentials` | URL containing credentials |
| `mac_address` | Colon-separated MAC address |
| `ein` | US Employer Identification Number |
| `mrn` | Medical record number with an MRN prefix |
| `bitcoin` | Bitcoin address pattern |

Uppercase legacy reference-data labels such as `EMAIL` and `SSN` are not gateway configuration identifiers and are not translated. `ADDRESS` and `NAME` have no detector in this check. Use the exact identifiers above rather than lowercasing the legacy list: for example, IP addresses use `ipv4` and `ipv6`, and medical record numbers use `mrn`.

A `topic-restriction` check groups its topics under 8 categories, most with their own subcategories; Custom ships with none.

## Configuration fields

Open an editable check's row in **Rules** to change its drawer. Check-specific fields appear under **Settings**, such as **Blocked keywords** for Keyword Blocklist. The [availability restrictions](#provider-backed-checks) apply before these fields: stored-only checks do not expose an editable provider-settings form.

### Rules dialog

The Rules editor is a drawer. Click **Add check** for a new rule or **Save** for an existing rule; either sends the change without a second activation step.

| Field | Values | New-rule default |
|---|---|---|
| On / Off | Toggle | On |
| Action | Block, Warn, Log; Mask where the check supports request rewriting | Block |
| Match threshold | Slider from 0.0 to 1.0, where applicable | 0.8 |
| Settings | Fields specific to the check, when it has them | Check-specific |

Fixed-score checks, including default PII Detection, have no Match threshold slider. Future AGI Eval also hides it. See [threshold tuning](/docs/protect/troubleshooting/guardrail-fires-on-the-wrong-requests).

### Overview dialog

There is no separate Overview editor. Legacy Overview links open Rules. The drawer describes the check's fixed request or response stage; it does not offer a pre/post/both selector.

### Pipeline settings

The **Pipeline** section in Rules separates the organization's editable timeout from gateway/operator-owned behavior. Organization checks run one at a time and stop at the first block; an organization `pipeline_mode` value does not enable parallel execution.

| Field | Organization control | What it does |
|---|---|---|
| Mode | Read-only; sequential | Shows how the gateway runs organization checks, not an organization-selectable mode |
| Fail Open | Read-only; set by the gateway operator | For a check that does not rewrite the request, a timeout or recovered panic skips the check when on; when off, it produces a failed result evaluated against the check's threshold and action |
| Check timeout (ms) | Editable by Owner/Admin, 100–60000 ms; the UI starts at 5000 ms when unset | Limits each organization check's runtime; click **Save timeout** to save it. Without an organization timeout, execution uses the gateway's default |

A request-rewriting check that times out or panics blocks the request rather than sending an unfinished rewrite. Remote-service errors returned as failed check results follow the check's threshold and action. Setting organization `guardrails.fail_open` in an update-config request does not change the gateway's failure handling; ask the gateway operator about that behavior.

## Response statuses

These are the statuses the [Agent Command Center](/docs/command-center) gateway returns on a guardrail decision. For non-streamed responses, Block from either stage returns `403`; Warn and Log let the call through. On a streamed response the status and headers are sent when the stream starts, so only a pre-stage check can change them; see [Streaming Guardrails](/docs/command-center/features/guardrails#streaming-guardrails).

| Action | Status | What the caller gets |
|---|---|---|
| Block, pre-stage check | `403` | An error body with `"type": "guardrail_error"` and `"code": "content_blocked"`, returned before the model is ever called |
| Block, post-stage check | `403` (non-streamed) | The model response is withheld. On a stream the HTTP status is already sent; see Streaming Guardrails above. Organization checks `data-leakage-prevention` and `hallucination-detection` have a fixed post-stage |
| Warn | `200` | The normal response, plus the header `x-agentcc-guardrail-triggered: true` |
| Log | `200` | The normal response, plus the header `x-agentcc-guardrail-triggered: true` |

<Note>`protect()` from the SDK is a different surface and does not use these statuses. It returns a normal `200` with the verdict in the response body; see [Run Protect from the SDK](/docs/protect/guides/run-protect-from-the-sdk).</Note>
