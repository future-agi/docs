A teammate needs to edit staging projects but doesn't need access to production. Put the environments in separate workspaces and grant membership only in staging.

<Prerequisites title="Before you start">
- To create a workspace, you need the [organization role](/docs/roles-and-permissions#organization-roles) of Owner or Admin. A workspace admin can manage settings in their own workspace.
- Use an existing [organization member](/docs/admin-settings/user-management) for the access check. Owners and organization Admins automatically have admin access to every workspace, so they cannot demonstrate the boundary.
</Prerequisites>

<Mermaid chart={`flowchart LR
  accTitle: Limit an organization member to staging
  accDescr: An organization Member belongs to staging with a workspace role. Without membership in production, the same Member has no access there.
  M["Organization Member"] --> S["Workspace Member in staging"] --> E["Can edit staging resources"]
  M --> N["No production membership"] --> P["No production access"]`} />

The same arrangement works for separate teams or projects.

## Create the staging workspace

1. Open **Settings > Workspace**.
2. Select **Create Workspace**.
3. Enter a name that distinguishes staging from production.
4. Select **Create**.

   You should see the staging workspace in the list.

## Give the member access to staging

1. Open the staging workspace from the list.
2. Open **Members**.
3. Add the organization member to this workspace.
4. Assign the member the `workspace_member` role.

   You should see the member and their role under staging's **Members** tab.

The [workspace role](/docs/roles-and-permissions#workspace-roles) controls what a member can do here: `workspace_member` can edit resources, `workspace_viewer` is for viewing, and `workspace_admin` can also manage members. An organization Member can be a workspace admin in staging without becoming an organization Admin.

## Check the boundary

1. Open the production workspace from the list.
2. Open **Members**.

   The member should not be listed. An organization Member with no membership in a workspace has no access to that workspace, so this member can work in staging only.

If the member can reach more than you intended, check their organization role and their membership in production. Before changing any settings, check the workspace name under **General**. To withdraw access to just one workspace, remove the member from that workspace's **Members** tab, not from the organization.

## Inspect workspace settings

Each workspace has its own settings page with these sections.

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Section | What to check in staging |
| --- | --- |
| **General** | The workspace name. |
| **Members** | Who belongs to staging and which workspace role each person holds. |
| **Integrations** | The [external connections](/docs/admin-settings/integrations) configured for this workspace. |
| **AI Providers** | The [provider configuration](/docs/admin-settings/ai-providers) for staging. |
| **Usage** | [Usage metrics](/docs/admin-settings/usage-summary) for this workspace. |

</div>

The [workspaces SDK reference](/docs/sdk/reference/workspaces) lists two read operations in Python and TypeScript: `workspaces.list` lists the caller's available workspaces, and `workspaces.get` looks one up by ID. The corresponding MCP tools are `list_workspaces` and `get_workspace`. Both only read workspaces: neither creates a workspace or grants a role.
