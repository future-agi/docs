If the UI loads but requests fail or new traces don't appear, a running container isn't enough evidence that the stack is healthy. Check the container, backend, and collector in order, then follow the signal that matches the failure.

<Prerequisites title="Before you start">
- For Compose, use a shell on the Docker host with access to the installation's Compose project. With the [production overlay](/docs/self-hosting/production/checklist#start-distributed-with-the-production-overlay), include its `--env-file` and `-f` flags on **every** Compose command below.
- For Helm, use a Kubernetes context with permission to run the release's chart tests; see [Check the install](/docs/self-hosting/helm#check-the-install). The Compose commands and host ports below are not Helm probes.
</Prerequisites>

## Container health

1. Inspect the service status for your Compose project.

```bash
docker compose ps        # STATUS shows healthy / unhealthy per service
docker stats             # live CPU and memory per container
```

   Long-running application images and data stores declare health checks. Use the live resource usage to investigate a container that cycles through `Restarting`.

2. Check the startup signal for your topology:

<div class="sdk-ref-table">

| Topology | Expected signal | If it doesn't appear |
| --- | --- | --- |
| Standalone | The `app` check probes the API (`/health/`), collector, [LLM gateway](/docs/command-center), UI, and object storage every 15 seconds. Its 3600-second start period allows a first migration to take over half an hour; a passing probe marks it healthy immediately. | `docker compose logs -f app` begins with configuration (setup, version, URLs, integrations, [telemetry](/docs/self-hosting/configuration/telemetry)) and ends with `Future AGI is ready in ...`. A failed startup step logs its error and retries after 30 seconds. |
| Distributed | `backend`, `frontend`, `fi-collector`, `agentcc-gateway`, `serving`, and `code-executor` probe their own endpoints. One-shot setup jobs should exit with code 0 in `docker compose ps -a`. | Workers report healthy without probing. Read `docker compose logs worker`. Watch `clickhouse` and `worker` in particular for memory pressure. |

</div>

A container that cycles through `Restarting` in `docker compose ps` often ran out of memory. Size the Docker VM as the [hardware requirements](/docs/self-hosting/requirements#hardware) say.

## Backend health

1. From the host, query the API's unauthenticated `/health/` endpoint.

```bash
curl -sf http://localhost:8000/health/
```

   This is the application check that `./bin/install` polls, not just a container status.

2. If the backend returns 503, check the startup logs before proceeding.

   The backend returns 503 while its embedded Temporal worker is down, so on Standalone this check covers the worker too. During a Standalone first boot, a 503 with `{"status": "starting", "phase": "..."}` indicates that a startup step is still in progress. Repeat the check after that step finishes.

## Collector health

1. **Distributed:** query the collector on its host-only admin port, `127.0.0.1:9464` (`FI_COLLECTOR_ADMIN_PORT`).

```bash
curl -s http://localhost:9464/healthz
```

   Read the insert counters in the JSON response. After more than 100 insert batches since startup, a failure rate above half produces HTTP 503. Alert on this signal: [spans](/docs/observe/concepts/spans) that fail to reach ClickHouse land in the dead-letter file in `futureagi_fi-collector-data` instead of appearing in queries.

2. **Standalone:** use the `app` health check rather than the host's port 9464.

   Standalone doesn't publish the admin port. Its dead-letter file is in `futureagi_app-data`; preserve that [volume](/docs/self-hosting/production/backups-restore#the-named-volumes).

After recovery, [send a new span](/docs/self-hosting/configuration/launch-mode#send-your-first-trace) and check that it arrives in Observe. A responding collector alone doesn't prove ingestion or replay of previously failed inserts.

## Setup checks

1. On an open-source installation, inspect the [first-run setup checks](/docs/self-hosting/configuration/launch-mode) for databases, cache, storage, gateway, task engine, ingestion, sandbox, and TLS.
2. Read `.result.status` in the API's unauthenticated JSON answer:

```bash
curl -s http://localhost:8000/api/setup-checks/ | jq -r .result.status   # ok, or issues
```

<div class="sdk-ref-table">

| Reading | Decision |
| --- | --- |
| `.result.status` is `ok` | Required checks passed. If the symptom is specific to requests or stale analytics, check the gateway or replication below. |
| `.result.status` is `issues` | A required check failed. Use the topology-specific fix on the setup screen and repeat the check. |
| Top-level `status` is `true` | This is true on every HTTP 200 response, even with failed checks. Don't use it for readiness. |
| HTTP 404 with `EE_LICENSE_KEY` | The Enterprise Edition install does not expose this endpoint. Use the service probes instead. |

</div>

## LLM gateway metrics

1. Enable `prometheus.enabled` in the gateway configuration file named by `AGENTCC_CONFIG_PATH` (a copy of `agentcc-gateway/config.example.yaml`, as for adding providers). On Helm the setting is `agentccGateway.config.prometheus.enabled`.
2. After changing the Compose configuration file, restart the gateway with `docker compose restart app` on Standalone (Distributed: `agentcc-gateway`).
3. Query `/-/metrics` with the gateway admin token.

```bash
TOKEN=$(docker compose exec -T app printenv AGENTCC_ADMIN_TOKEN)   # Distributed: backend instead of app
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8090/-/metrics
```

   Look for Prometheus metrics in the response. The API and collector don't expose Prometheus endpoints; monitor the data stores with their own exporters.

## PeerDB replication

1. **Distributed only:** with the `peerdb` or `all` profile, sign in to the [PeerDB console](/docs/self-hosting/troubleshooting#peerdb-errors-distributed) at [localhost:3001](http://localhost:3001).
2. Inspect the mirrors' state and lag.

   A mirror that isn't `running` means the dashboard is reading stale data. Re-running PeerDB init does not restart or resync it. Follow [Analytics data is stale](/docs/self-hosting/troubleshooting#analytics-data-is-stale), then recheck mirror state and lag.

Standalone and Helm use the app's outbox to sync Postgres to ClickHouse; neither runs PeerDB.

## Helm

On Kubernetes, run `helm test` to check that the API, UI, collector, and gateway answer. The setup screen gives `kubectl` fixes; after a fix, repeat the chart test. The chart does not include a ServiceMonitor.
