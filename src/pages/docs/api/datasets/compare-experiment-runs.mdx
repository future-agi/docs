## About

Compare two existing runs against the same dataset version, example/trial plan, and evaluator binding. The response includes case-level improvements and regressions, completeness counts, and execution trace references.

`POST /model-hub/experiment-runs/compare/`

This POST reads recorded results. It does not run a task or score outputs. Add the optional [release gate](/docs/api/datasets/release-gate) to derive a case-level pass/fail verdict for CI; without it, the response is descriptive comparison only.

## Request

Authenticate with `X-Api-Key` and `X-Secret-Key` headers and send a JSON object:

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `baseline_run_id` | UUID | Yes | Reference run. |
| `candidate_run_id` | UUID | Yes | Run to compare with the baseline. |
| `metric_id` | UUID | Yes | Evaluator binding pinned in both runs. |
| `passing_score` | number or `null` | No | Optional finite threshold for descriptive pass counts. Default `null`. |
| `higher_is_better` | boolean | No | Whether a larger score improves the result. Default `true`. |
| `include_trial_stability` | boolean | No | Include per-example repeated-trial counts and score distributions. Default `false`; omit it to keep the ordinary response. |
| `metadata_equals` | object | No | Exact JSON metadata conditions, maximum 20 keys. A case/trial identity is selected when either side matches all conditions. |
| `split_name` | string | No | Exact split selector. It selects whole identities and preserves both run sides. |
| `release_gate` | object | No | Optional [case-level policy](/docs/api/datasets/release-gate). Omit it for ordinary comparison. |

Organization and workspace access come from authentication. This read-only POST is available to authenticated workspace viewers. Do not send tenant or workspace fields in the body; unknown fields are rejected. The selected evaluator binding must match completely across the runs, including its version and configuration. Matching metric names alone is insufficient.

Set `BASE_URL` to the deployment under test and replace the example UUIDs with accessible run and metric IDs:

```bash
BASE_URL="https://your-deployment.example.com"
curl --request POST "${BASE_URL}/model-hub/experiment-runs/compare/" \
  --header 'X-Api-Key: YOUR_API_KEY' \
  --header 'X-Secret-Key: YOUR_SECRET_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "baseline_run_id": "11111111-1111-4111-8111-111111111111",
    "candidate_run_id": "22222222-2222-4222-8222-222222222222",
    "metric_id": "33333333-3333-4333-8333-333333333333",
    "passing_score": 0.8,
    "higher_is_better": true
  }'
```

Each run may contain at most 10,000 planned and recorded case/trial items. Excess evidence is rejected rather than silently truncated. There is no pagination or filter parameter on this comparison endpoint.

### Select a metadata cohort

Use `metadata_equals` for exact JSON matching or `split_name` for a single exact
split. A selector includes an entire case/trial identity when either run side
matches; the comparison keeps both sides so missing and duplicate evidence stay
visible. The server caps `metadata_equals` at 20 keys and does not interpret
operators, ranges, or expressions. Omit both fields to preserve the ordinary
response shape.

```json
{
  "baseline_run_id": "11111111-1111-4111-8111-111111111111",
  "candidate_run_id": "22222222-2222-4222-8222-222222222222",
  "metric_id": "33333333-3333-4333-8333-333333333333",
  "metadata_equals": {"cohort": "support", "language": "en"},
  "split_name": "holdout"
}
```

The response adds `result.selection` with `total_plan_count`,
`selected_count`, `metadata_equals`, and `split_name`. Counts, trial summaries,
output diffs, and a supplied release gate apply to the selected identities. An
empty selection is valid and reports zero selected cases; it does not invent a
pass.

## Response

A successful response has `status: true` and a `result` object:

| Result field | Meaning |
| --- | --- |
| `baseline_run_id`, `candidate_run_id` | Compared run IDs. |
| `dataset_version_id` | Shared pinned dataset version. |
| `metric_id`, `evaluator_version_id` | Selected binding and its pinned evaluator version. |
| `comparison` | Aggregate summaries, per-case comparisons, outcome counts, and comparable-case count. |
| `baseline_counts`, `candidate_counts` | Whole-run expected, recorded, missing, completed, failed, and assessed counts. |
| `missing_by_side` | Baseline and candidate arrays of `{example_id, trial_number}` identities with no recorded result. |
| `trace_refs` | Each planned identity with nullable baseline/candidate references containing `run_item_id`, `trace_id`, and `root_span_id`. |
| `trial_stability` | Present only when `include_trial_stability: true`. Per-example trial counts, observed score distributions, and paired score deltas. |
| `selection` | Present only when a metadata or split selector is supplied. Reports total plan count, selected count, and the normalized selector. |

`comparison.baseline` and `comparison.candidate` contain:

- `item_count`, `completed_count`, `failed_count`, and `score_count`;
- `score_average`, `score_min`, and `score_max`, which are `null` without assessed numeric evidence;
- `pass_count` and `pass_rate`, which are `null` without a passing threshold; and
- `status_counts` and `score_status_counts`.

Pass rate uses assessed scores as its denominator. Read it alongside expected and missing counts; an average or pass rate does not establish run completeness.

Each entry in `comparison.cases` contains `example_id`, `trial_number`, `status`, baseline/candidate evidence statuses and scores, `score_delta`, and nullable `missing_side`. The delta is candidate minus baseline. `higher_is_better` changes whether that delta is an improvement or regression; it does not reverse the delta's sign.

Possible case outcomes are `improved`, `regressed`, `tie`, `missing`, `duplicate`, `invalid`, `error`, `unknown`, `unsupported`, and `not_assessed`. Failed execution, malformed evidence, or a missing evaluator result cannot become a numeric pass. Invalid references, including malformed unrelated metric references on an item, make that item's evidence invalid.

`comparison.status_counts` counts those outcomes, and `comparison.comparable_count` counts numeric improved/regressed/tie pairs. A planned case absent from both runs appears in both `missing_by_side` arrays and has null trace references; it does not create a synthetic scored case in `comparison.cases`.

## Inspect repeated trials

Set `include_trial_stability: true` on the existing comparison call after recording repeated trials for each example. The Python method is `client.experiment_runs.compare`; the TypeScript method is `client.experimentRuns.compare`.

Set `FI_API_KEY`, `FI_SECRET_KEY`, and `FI_BASE_URL` for your compatible test deployment. Set `BASELINE_RUN_ID`, `CANDIDATE_RUN_ID`, and `METRIC_ID` to accessible UUIDs. The SDK snippets require the test builds pinned above; they are not install instructions for a published package.

<CodeGroup titles={["Python", "TypeScript", "cURL"]}>

```python
import os

from fi import FutureAGIClient
from fi.generated.openapi_client.models.run_comparison_request import RunComparisonRequest

with FutureAGIClient(
    api_key=os.environ["FI_API_KEY"],
    secret_key=os.environ["FI_SECRET_KEY"],
    base_url=os.environ["FI_BASE_URL"],
) as client:
    report = client.experiment_runs.compare(RunComparisonRequest.from_dict({
        "baseline_run_id": os.environ["BASELINE_RUN_ID"],
        "candidate_run_id": os.environ["CANDIDATE_RUN_ID"],
        "metric_id": os.environ["METRIC_ID"],
        "include_trial_stability": True,
    }))
    for example in report.result.trial_stability or []:
        spread = example.candidate.score_stddev
        print(example.example_id, {
            "expected": example.expected_trial_count,
            "assessed": example.candidate.assessed_trial_count,
            "spread": "fewer than two assessed trials" if spread is None else spread,
        })
```

The response adds `result.trial_stability`, sorted by `example_id`, with one entry for every example in the pinned plan, including examples absent from both runs. The option does not schedule more trials or change the release-gate verdict. When the flag is omitted or `false`, the response does not contain `trial_stability`; the Python model represents the omitted field as `UNSET`, and TypeScript exposes it as `undefined`. Omission and explicit `false` are preserved in SDK requests.

The snippets check `None` or use `??` so a standard deviation of `0` remains a number. A truthiness check would incorrectly treat observed zero spread as missing data.

| Field in each entry | Meaning |
| --- | --- |
| `example_id` | Example whose repeated trials are summarized. |
| `expected_trial_count` | Number of trial identities pinned for this example. |
| `baseline`, `candidate` | The per-side counts and score statistics below. |
| `paired.paired_trial_count` | Same-trial pairs with finite assessed scores on both sides and a finite candidate-minus-baseline delta. |
| `paired.delta_average` | Average paired delta, or `null` without an eligible pair. |
| `paired.delta_stddev` | Population standard deviation of paired deltas, or `null` with fewer than two eligible pairs. |

Each `baseline` and `candidate` object contains:

| Field | Meaning |
| --- | --- |
| `recorded_trial_count` | Planned trial identities with a recorded item, including failed, invalid, or unassessed items. A duplicate identity counts once. |
| `missing_trial_count` | Expected trials without a recorded item. |
| `assessed_trial_count` | Trials with one completed item and a finite assessed score. Failed, invalid, duplicate, and unassessed evidence contributes no score. |
| `score_average`, `score_min`, `score_max` | Statistics over assessed scores, or `null` when none are assessed. |
| `score_stddev` | Population standard deviation over assessed scores, or `null` when fewer than two trials are assessed. |

The counts keep incomplete evidence visible. For example, one assessed score from a three-trial plan has `expected_trial_count: 3` and `assessed_trial_count: 1`, with `score_stddev: null`. If the other two trials were never recorded, `missing_trial_count` is `2`; if they failed, it is `0`.

Two trials can have the same mean and different observed spread:

| Recorded scores for one example | Mean | Population standard deviation |
| --- | --- | --- |
| Baseline: `0`, `1` | `0.5` | `0.5` |
| Candidate: `0.5`, `0.5` | `0.5` | `0` |

Both sides have two expected, recorded, and assessed trials and zero missing trials. Matching trial 1 to trial 1 and trial 2 to trial 2 gives deltas `0.5` and `-0.5`, so `paired_trial_count` is `2`, `delta_average` is `0`, and `delta_stddev` is `0.5`. Deltas always mean candidate minus baseline; `higher_is_better` does not reverse their sign.

These numbers describe the recorded scores. They do not establish statistical significance, independent trials, future reliability, or a confidence interval. Keep safety and tool-behavior assertions as separate required checks even when score spread is zero.

## Failure example

With valid authentication, an invalid UUID produces HTTP `400`:

```bash
curl --request POST "${BASE_URL}/model-hub/experiment-runs/compare/" \
  --header 'X-Api-Key: YOUR_API_KEY' \
  --header 'X-Secret-Key: YOUR_SECRET_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "baseline_run_id": "not-a-uuid",
    "candidate_run_id": "22222222-2222-4222-8222-222222222222",
    "metric_id": "33333333-3333-4333-8333-333333333333"
  }'
```

| Status | Meaning |
| --- | --- |
| `400` | Invalid body, non-finite threshold, incompatible dataset/plan/evaluator binding, or comparison size limit exceeded. |
| `401` | Authentication is missing or invalid. |
| `403` | The authenticated caller does not have access to the requested workspace. |
| `404` | A run is missing, deleted, or outside the authenticated data scope, or authentication has no organization context. |
