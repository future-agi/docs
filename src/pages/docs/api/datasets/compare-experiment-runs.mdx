## About

Compare two existing runs against the same dataset version, example/trial plan, and evaluator binding. The response includes case-level improvements and regressions, completeness counts, and execution trace references.

<Note>
  Draft API reference. Use a test deployment containing the comparison API change. Hosted availability and public SDK methods are not established by this draft.
</Note>

`POST /model-hub/experiment-runs/compare/`

This POST only reads recorded results. It does not run a task, score outputs, create a comparison record, or decide whether a release should pass CI.

## Request

Authenticate with `X-Api-Key` and `X-Secret-Key` headers and send a JSON object:

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `baseline_run_id` | UUID | Yes | Reference run. |
| `candidate_run_id` | UUID | Yes | Run to compare with the baseline. |
| `metric_id` | UUID | Yes | Evaluator binding pinned in both runs. |
| `passing_score` | number or `null` | No | Optional finite threshold for descriptive pass counts. Default `null`. |
| `higher_is_better` | boolean | No | Whether a larger score improves the result. Default `true`. |

Organization and workspace access come from authentication. This read-only POST is available to authenticated workspace viewers. Do not send tenant or workspace fields in the body; unknown fields are rejected. The selected evaluator binding must match completely across the runs, including its version and configuration. Matching metric names alone is insufficient.

Set `BASE_URL` to the deployment under test and replace the example UUIDs with accessible run and metric IDs:

```bash
BASE_URL="https://your-deployment.example.com"
curl --request POST "${BASE_URL}/model-hub/experiment-runs/compare/" \
  --header 'X-Api-Key: YOUR_API_KEY' \
  --header 'X-Secret-Key: YOUR_SECRET_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "baseline_run_id": "11111111-1111-4111-8111-111111111111",
    "candidate_run_id": "22222222-2222-4222-8222-222222222222",
    "metric_id": "33333333-3333-4333-8333-333333333333",
    "passing_score": 0.8,
    "higher_is_better": true
  }'
```

Each run may contain at most 10,000 planned and recorded case/trial items. Excess evidence is rejected rather than silently truncated. There is no pagination or filter parameter on this comparison endpoint.

## Response

A successful response has `status: true` and a `result` object:

| Result field | Meaning |
| --- | --- |
| `baseline_run_id`, `candidate_run_id` | Compared run IDs. |
| `dataset_version_id` | Shared pinned dataset version. |
| `metric_id`, `evaluator_version_id` | Selected binding and its pinned evaluator version. |
| `comparison` | Aggregate summaries, per-case comparisons, outcome counts, and comparable-case count. |
| `baseline_counts`, `candidate_counts` | Whole-run expected, recorded, missing, completed, failed, and assessed counts. |
| `missing_by_side` | Baseline and candidate arrays of `{example_id, trial_number}` identities with no recorded result. |
| `trace_refs` | Each planned identity with nullable baseline/candidate references containing `run_item_id`, `trace_id`, and `root_span_id`. |

`comparison.baseline` and `comparison.candidate` contain:

- `item_count`, `completed_count`, `failed_count`, and `score_count`;
- `score_average`, `score_min`, and `score_max`, which are `null` without assessed numeric evidence;
- `pass_count` and `pass_rate`, which are `null` without a passing threshold; and
- `status_counts` and `score_status_counts`.

Pass rate uses assessed scores as its denominator. Read it alongside expected and missing counts; an average or pass rate does not establish run completeness.

Each entry in `comparison.cases` contains `example_id`, `trial_number`, `status`, baseline/candidate evidence statuses and scores, `score_delta`, and nullable `missing_side`. The delta is candidate minus baseline. `higher_is_better` changes whether that delta is an improvement or regression; it does not reverse the delta's sign.

Possible case outcomes are `improved`, `regressed`, `tie`, `missing`, `duplicate`, `invalid`, `error`, `unknown`, `unsupported`, and `not_assessed`. Failed execution, malformed evidence, or a missing evaluator result cannot become a numeric pass. Invalid references, including malformed unrelated metric references on an item, make that item's evidence invalid.

`comparison.status_counts` counts those outcomes, and `comparison.comparable_count` counts numeric improved/regressed/tie pairs. A planned case absent from both runs appears in both `missing_by_side` arrays and has null trace references; it does not create a synthetic scored case in `comparison.cases`.

## Failure example

With valid authentication, an invalid UUID produces HTTP `400`:

```bash
curl --request POST "${BASE_URL}/model-hub/experiment-runs/compare/" \
  --header 'X-Api-Key: YOUR_API_KEY' \
  --header 'X-Secret-Key: YOUR_SECRET_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "baseline_run_id": "not-a-uuid",
    "candidate_run_id": "22222222-2222-4222-8222-222222222222",
    "metric_id": "33333333-3333-4333-8333-333333333333"
  }'
```

| Status | Meaning |
| --- | --- |
| `400` | Invalid body, non-finite threshold, incompatible dataset/plan/evaluator binding, or comparison size limit exceeded. |
| `401` | Authentication is missing or invalid. |
| `403` | The authenticated caller does not have access to the requested workspace. |
| `404` | A run is missing, deleted, or outside the authenticated data scope, or authentication has no organization context. |
