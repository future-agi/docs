<TLDR>
Adding tracing is the easy half. Knowing it worked is the half that gets skipped, because a trace that arrives looking fine can still be missing cost, sessions, users, or half its spans. This guide instruments an app that has none, then runs `fi_verify.py`, which checks ten gates against the spans your app really produced and exits 0 or names the gate that failed.
</TLDR>

## What a verified integration means

These failures all produce a trace list that looks populated, and reading the dashboard cannot tell them apart from a correct integration:

- Cost and tokens are missing everywhere, because the LLM spans carry neither a model nor a token count and nothing can price them
- One request appears as three traces, and each piece looks valid on its own
- Sessions and users are blank, so conversations do not group and per-customer spend cannot be read
- Evals report nothing, which looks identical to an eval that found no problems
- Nothing arrives at all, and the client stays healthy because the collector refused the batch quietly

So the result is decided by a checker rather than by looking. Ten gates, each tied to the step that closes it:

| Gate | Holds when | Step |
|---|---|---|
| G1 | the probe succeeded and the exporter reported success for the real batch | 1 |
| G2 | the resource has a project name; the checker also displays its type | 2 |
| G3 | one request is one trace, one root, no orphans | 2 |
| G6 | one `session.id`, identical across the trace | 3 |
| G7 | `user.id` is present | 3 |
| G4 | every span is typed, and at least one is an LLM span | 4 |
| G5 | prompt and completion on every LLM span | 4 |
| G8 | the model name is on every LLM span | 4 |
| G9 | each LLM span has model and input-token data, or an explicit numeric cost | 4 |
| G10 | no scanned environment credential value occurs in the captured attributes | 4 |

Nine gates read a local capture of your spans. G1 reads two receipts written during the run, because a capture says nothing about whether anything arrived.

A successful export is not a database read. After the gates pass, find the printed trace ID in the app and inspect the stored spans. G9 checks the inputs to pricing, not whether the platform has a rate for that model. G10 checks for matching environment-secret values, not all possible sensitive content.

## Tutorial

<Steps>
<Step title="Prove the keys before writing code that depends on them">

Three values: `FI_API_KEY` and `FI_SECRET_KEY` from the console, and `FI_PROJECT_NAME`, the name this app appears under. Tracing never needs your model provider key.

```bash
python observability/futureagi/fi_verify.py preflight
```

`preflight` sends one real span, then three deliberately broken variants. If any broken variant is accepted, nothing is proven and it fails.

| Answer | Means |
|---|---|
| `200` | keys, route and payload all valid. Go to Step 2 |
| `401 authentication failed` | the keys arrived and were refused: wrong keys, or keys from another environment |
| `401 missing credentials` | the `X-Api-Key` and `X-Secret-Key` headers never arrived: unset, or a proxy strips them |
| `400 no project_name` | keys fine, payload not. It belongs on the resource, not the span |
| `404` | wrong path. It ends `/tracer/v1/traces`, with no trailing slash |

</Step>
<Step title="Make one request arrive as one tree">

Use one provider per process. A CLI or job needs a root span around its work and a flush before it exits. For a thread pool, copy the context in the caller and run the worker in that context. For a message broker, propagate the trace context across the boundary; see [Distributed Tracing](/docs/cookbook/quickstart/distributed-tracing).

Save the setup module for your chosen track. Each exposes a tracer and a request scope for Step 3. Capture is opt-in; do not leave `FI_VERIFY=1` enabled for real customer traffic.

<Tabs>
<Tab title="Future AGI SDK">

Save as `observability/futureagi/setup_sdk.py`.

```python
import os

from fi_instrumentation import FITracer, register, using_attributes
from fi_instrumentation.fi_types import ProjectType
from . import fi_verify

provider = register(project_name=os.environ["FI_PROJECT_NAME"],
                    project_type=ProjectType.OBSERVE, verbose=False)
tracer = FITracer(provider.get_tracer("support"))


def request_scope(session_id, user_id):
    return using_attributes(session_id=session_id, user_id=user_id)


if os.getenv("FI_VERIFY") == "1":
    fi_verify.attach(provider)
```

</Tab>
<Tab title="OpenTelemetry">

Save as `observability/futureagi/setup_otel.py`.

```python
import os
from contextlib import contextmanager
from contextvars import ContextVar

from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import SpanProcessor, TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from . import fi_verify

provider = TracerProvider(resource=Resource.create({
    "project_name": os.environ["FI_PROJECT_NAME"], "project_type": "observe",
}))
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(
    endpoint=os.environ["FI_ENDPOINT"],
    headers={"X-Api-Key": os.environ["FI_API_KEY"],
             "X-Secret-Key": os.environ["FI_SECRET_KEY"]},
)))
_scope = ContextVar("support_scope", default={})


class ScopeProcessor(SpanProcessor):
    def on_start(self, span, parent_context=None):
        span.set_attributes(_scope.get())


@contextmanager
def request_scope(session_id, user_id):
    token = _scope.set({"session.id": session_id, "user.id": user_id})
    try:
        yield
    finally:
        _scope.reset(token)


provider.add_span_processor(ScopeProcessor())
tracer = provider.get_tracer("support")
if os.getenv("FI_VERIFY") == "1":
    fi_verify.attach(provider)
```

</Tabs>

<Step title="Carry session and user from the edge">

Save as `observability/futureagi/request.py`. Open the scope **outside** the root so the root and its children get the same session and user. Use an internal user ID, not an email address. Reuse a session ID for related requests, but create a new root for each request.

```python
from contextlib import contextmanager


@contextmanager
def support_turn(setup, question, session_id, user_id):
    with setup.request_scope(session_id, user_id):
        with setup.tracer.start_as_current_span("support.turn", attributes={
            "gen_ai.span.kind": "CHAIN", "input.value": question,
        }) as root:
            yield root
```

</Step>
<Step title="Write the model, messages and usage where they belong">

Save as `support.py`. The synthetic policy comes from a local lookup. The SDK track instruments only the OpenAI client; do not add another LLM span around it. The plain OpenTelemetry track opens a child span around that same call and copies the actual counts from its response. Both tracks record the lookup as a `TOOL` span and put the final answer on the root.

```python
import os
import sys
from contextlib import nullcontext

from openai import OpenAI
from observability.futureagi.request import support_turn

if sys.argv[1:] == ["sdk"]:
    from observability.futureagi import setup_sdk as setup
    from traceai_openai import OpenAIInstrumentor
    OpenAIInstrumentor().instrument(tracer_provider=setup.provider)
    manual = False
elif sys.argv[1:] == ["otel"]:
    from observability.futureagi import setup_otel as setup
    manual = True
else:
    raise SystemExit("Choose a tracing track: sdk or otel")

question = "Can I return an unused tent after two weeks?"
model = "gpt-4o-mini"
with support_turn(setup, question, os.environ["FI_SESSION_ID"], "shopper-demo") as root:
    with setup.tracer.start_as_current_span("policy.lookup", attributes={
        "gen_ai.span.kind": "TOOL", "input.value": "tent returns",
    }) as tool:
        policy = {"tent returns": "Unused tents can be returned within 30 days."}["tent returns"]
        tool.set_attribute("output.value", policy)
    context = setup.tracer.start_as_current_span("support.reply", attributes={
        "gen_ai.span.kind": "LLM", "gen_ai.request.model": model,
        "gen_ai.provider.name": "openai", "input.value": question,
    }) if manual else nullcontext()
    with context as span, OpenAI() as client:
        response = client.chat.completions.create(model=model, messages=[
            {"role": "system", "content": "Answer in one sentence using this policy: " + policy},
            {"role": "user", "content": question},
        ])
        answer = response.choices[0].message.content
        if not answer:
            raise ValueError("Expected a text reply")
        if manual:
            usage = response.usage
            span.set_attributes({"output.value": answer,
                                 "gen_ai.usage.input_tokens": usage.prompt_tokens,
                                 "gen_ai.usage.output_tokens": usage.completion_tokens,
                                 "gen_ai.usage.total_tokens": usage.total_tokens})
    root.set_attribute("output.value", answer)
    trace_id = f"{root.get_span_context().trace_id:032x}"
setup.provider.force_flush()
print(answer)
print(f"Trace ID: {trace_id}")
```

Use the model and usage from the model call, not estimates from prompt length. If you stream Chat Completions, request usage on the final chunk and keep the span open until the stream finishes. If your deployment supplies its own cost, put `gen_ai.cost.total` on the LLM span. Do not copy the same charge or token counts onto the parent: summing parent and child would count the call twice.

</Step>
<Step title="Run the ten gates">

Run `python support.py sdk` or `python support.py otel`, depending on the setup module you saved. Note the trace ID printed after the answer. Then run:

```bash
python observability/futureagi/fi_verify.py check
```

Expect `GREEN LIGHT achieved` only if all ten gates pass. In Observe, open `ridgeline-traced-support` and find the same trace ID. Expand `support.turn` to see `policy.lookup` and the model call. Check that the root has the shopper's question and answer, and that the model span has nonzero token counts. This distinguishes a locally well-formed span from one stored in the app.

</Step>
<Step title="Bind evals to attributes the trace carries">

A trace-scoped eval can bind to `input.value` and `output.value` on `support.turn`: these are the shopper's question and the answer they saw. For a span-scoped eval, select the LLM spans and bind the model output instead. Check the attribute names in your trace before binding; not every span represents a model call. See [Setup evals](/docs/observe/guides/setup-evals).

</Step>
</Steps>

## The same steps on an existing repository

The [OpenAI Agents customer-service example](https://github.com/openai/openai-agents-python/tree/v0.25.0/examples/customer_service) runs an airline triage agent with a handoff to a FAQ agent and a local lookup tool. You can trace a single request without editing its interactive entry point. This section uses the **Future AGI SDK** setup module above, but a different instrumentor: the Agents instrumentor observes framework events, including tools and handoffs, rather than just HTTP model calls.

From your original directory, install the matching SDK and clone the example at the corresponding release. Keep `run_traced.py` beside `support.py`, **outside** the clone.

```bash
python -m pip install openai-agents==0.25.0 traceai-openai-agents==0.1.8
git clone --depth 1 --branch v0.25.0 https://github.com/openai/openai-agents-python.git openai-agents-python
```

Save as `run_traced.py`. Chat Completions is selected explicitly. The Agents instrumentor installs its own tracing processor; the script does not also instrument the underlying OpenAI client.

```python
import asyncio
import os

from agents import RunConfig, Runner, set_default_openai_api
from traceai_openai_agents import OpenAIAgentsInstrumentor
from examples.customer_service.main import AirlineAgentContext, triage_agent
from observability.futureagi import setup_sdk as setup
from observability.futureagi.request import support_turn


async def main():
    OpenAIAgentsInstrumentor().instrument(tracer_provider=setup.provider)
    set_default_openai_api("chat_completions")
    question = "What is the baggage allowance for my flight?"
    with support_turn(setup, question, os.environ["FI_SESSION_ID"], "shopper-demo") as root:
        result = await Runner.run(triage_agent, question, context=AirlineAgentContext(),
                                  run_config=RunConfig(model="gpt-4o-mini"))
        answer = str(result.final_output)
        root.set_attribute("output.value", answer)
        trace_id = f"{root.get_span_context().trace_id:032x}"
    setup.provider.force_flush()
    print(answer)
    print(f"Trace ID: {trace_id}")


if __name__ == "__main__":
    asyncio.run(main())
```

Run `PYTHONPATH="$PWD/openai-agents-python" python run_traced.py` and then `python observability/futureagi/fi_verify.py check`. Each app run replaces the local capture, so check it before starting the next request. In Observe the requests remain separate traces; `FI_SESSION_ID` groups them under one session.

## If your app is not Python

Use an OTLP HTTP exporter with the two authentication headers, `project_name` and `project_type` on the **resource**, and one typed root per request. Carry the session, user and model fields across in the same way. The local capture hook `fi_verify.attach()` is Python-specific. For a non-Python app, verify the stored trace tree, messages and token counts in Observe rather than running `check` against an empty capture.

## Troubleshooting

| Symptom | What to check |
|---|---|
| Preflight says `400 no project_name` | Put the project name on the resource, not the span. |
| `check` reports no spans | Export `FI_VERIFY=1` before starting the app. Run all commands in one directory and flush the provider after ending the root. |
| G3 reports orphans or multiple roots | Keep the request scope around the entire run; explicitly propagate context over a thread or service boundary. |
| Session or user is missing from the root | Open the request scope before the root, not inside it. |
| G8 or G9 fails | Inspect the LLM span for a model and usage. For a manual span, copy the counts before ending it. A pricing gate does not prove a billed dollar amount. |
| More model spans than model calls | Instrument either the framework or the underlying client, not both. |

Keep one trace across a service boundary with [Distributed Tracing](/docs/cookbook/quickstart/distributed-tracing).
