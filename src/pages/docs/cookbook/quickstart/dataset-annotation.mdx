<TLDR>
**What you'll build:** A project-scoped [annotation](/docs/annotations) view with categorical, numeric and text labels for human review, plus a bulk write that uses the same label names and recorded span IDs to push judgments from Python with `Annotation.log_annotations()`.
</TLDR>

## The problem

A reviewer may have judged the right response, but the SDK won't attach `sentiment` to a label named `Sentiment`. Even an exact label name isn't enough if the span ID doesn't belong to the target project. A write count alone doesn't tell you which response received the judgment.

## What you'll build

A review view with categorical, numeric and text [labels](/docs/annotations/concepts/labels), plus a bulk annotation workflow that checks the target project before writing to its [spans](/docs/observe/concepts/spans).

<Mermaid chart={`

    accTitle: Connect a human judgment to the right span
    accDescr: A project trace provides the review context. The reviewer applies a label. The bulk write uses the same project's label name and span ID, and you check the write counts against the rows you sent.
    T["Project trace"] --> V["Review view"] --> L["Reviewer label"] --> B["Project, label and span ID"] --> S["Check write counts"]
`} />

You'll:

1. Create a view from a [trace](/docs/observe/concepts/traces), not a standalone dataset.
2. Give annotators context, an output to judge and three label types.
3. Match the project, label names and span IDs before sending a bulk write.
4. Check the write counts against the rows you sent.

<Prerequisites title="Before you start">
- A [Future AGI account](https://app.futureagi.com) and [workspace API key and secret key](/docs/admin-settings/api-keys).
- A [dataset with a few rows](/docs/cookbook/quickstart/dataset-management) and a tracing project with recorded spans. Follow [Manual tracing](/docs/cookbook/quickstart/manual-tracing) if you need a project.
- Python 3.11 or later for the SDK steps. This intermediate walkthrough takes about 15 minutes and uses `futureagi` and `pandas`.
</Prerequisites>

## Create the review view from the project

1. Open **Tracer** under **Observe**.
2. Choose the project that contains the spans you intend to annotate.
3. Open a trace from that project.
4. Open its annotation drawer.
5. Click **Create New View**.
6. Name the view, for example `Response Quality Review`.

   You should see the view editor open with **Static Fields**, **Response Fields** and **Labels** ready to configure.

Starting from the project matters. A view created from a project-scoped trace carries that project with it; a view created outside a project doesn't. `get_labels(project_id=...)`, which `log_annotations()` calls under the hood, only returns labels attached to a project, so labels created without one are invisible to the SDK.

## Give reviewers the fields they need

1. Under **Static Fields**, select context columns such as `user_query` and `context`.

   Reviewers can read these fields but cannot edit them.

2. Under **Response Fields**, select the output to judge, such as `response`.

   Both the reference context and response should now appear in the layout preview.

## Define the labels

Create one label for each judgment you want annotators to make. Each label needs a name, an annotation type, and (for non-categorical types) a min/max range and a step size.

1. Click **Create New Label**.
2. Enter the label's name.
3. Choose its [annotation type](/docs/annotations/reference/label-types-and-values).
4. Enter guidance under **Description**.
5. Configure the values for that type using the tables below.
6. Click **Save**.
7. Repeat for the remaining labels.

   You should see all three under **Labels** in the editor.

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Field | Description |
|---|---|
| **Name** | The label's name, shown to annotators and used to reference it from the SDK |
| **Annotation Type** | **Categorical** (predefined options), **Numeric** (a score on a scale), or **Text** (free-form feedback) |
| **Description** | Required guidance shown to annotators on how to apply the label |
| **Display Options** | Numeric labels only: currently offers a single option, **Slider** |
| **Min / Max Value** | Required for Numeric and Text labels: the lower and upper bounds of the score (for Text, these map to minimum/maximum character length) |
| **Step Size** | Numeric labels only, required: the increment the slider moves by |

</div>

Use these three labels in the example:

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Label name | Annotation Type | Description | Min | Max | Step Size |
|---|---|---|---|---|---|
| Sentiment | Categorical | Overall tone of the response | N/A | N/A | N/A |
| Relevance Score | Numeric | How well the response addresses the query | 1 | 5 | 0.5 |
| Reviewer Notes | Text | Free-form feedback or corrections | 0 | 500 | N/A |

</div>

Use `Positive`, `Negative` and `Neutral` as the categories for Sentiment.

<Tip>
For categorical labels, enable **Auto Annotate** during label creation. Annotate a handful of rows manually first, then review, accept, or override the labels it suggests for the remaining rows.
</Tip>

## Collect one human judgment

1. Under **Annotators**, add the workspace members who will review rows.
2. Click **Create**.
3. As an assigned annotator, open the view.
4. Apply a label to a row using its read-only context and response.

   Changes save automatically, and the row's status updates as annotators work through the rows.

## Identify your project before using the SDK

Before pushing annotations programmatically, confirm the exact label names and the project you're targeting. `Annotation.log_annotations()` matches label names by exact string, so a typo or case mismatch raises a `ValueError` and aborts the call.

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Variable | What to set | Where to find it |
| --- | --- | --- |
| `FI_API_KEY` | The workspace API key | **Settings > API Keys** |
| `FI_SECRET_KEY` | The matching secret | Shown when you create the key pair |

</div>

1. Install the packages.

```bash
pip install futureagi pandas
```

2. Set the workspace credentials.

```bash
export FI_API_KEY="your-api-key"
export FI_SECRET_KEY="your-secret-key"
```

3. List the projects using the first part of the example below.
4. Match the project name and ID to the project you reviewed in the UI.
5. Run the label lookup for **that** project ID.

   The snippet uses `projects[0].id` as an example. Don't assume the first returned project is yours; substitute the ID you matched before running the lookup.

```python
import os
from fi.annotations import Annotation

client = Annotation(
    fi_api_key=os.environ["FI_API_KEY"],
    fi_secret_key=os.environ["FI_SECRET_KEY"],
)

projects = client.list_projects()
for p in projects:
    print(f"  {p.name} (id: {p.id}, type: {p.project_type})")

labels = client.get_labels(project_id=projects[0].id)
for label in labels:
    print(f"  {label.name}: type {label.type} (id: {label.id})")
```

Example output format, not IDs to use in your project:

```
  My Tracing Project (id: proj_abc123, type: observe)
  Sentiment: type categorical (id: lbl_001)
  Relevance Score: type numeric (id: lbl_002)
  Reviewer Notes: type text (id: lbl_003)
```

## Write judgments to recorded spans

For bulk annotation or CI pipelines, push a pandas DataFrame with `Annotation.log_annotations()`. Each row references a traced span by its `context.span_id`.

1. Copy the actual `context.span_id` values from the spans you intend to annotate in the project.
2. Replace the three example span IDs in the DataFrame below with those values.
3. Set the project name in `log_annotations()` to the exact name from your lookup.
4. Match each column's label name and type against the labels returned for that project.

   Annotation columns use `annotation.{label_name}.{type}`. Case and spaces matter; `annotation.notes` is a separate, optional notes column.

5. Run the bulk write with judgments that correspond to those spans.

```python
import os
import pandas as pd
from fi.annotations import Annotation

client = Annotation(
    fi_api_key=os.environ["FI_API_KEY"],
    fi_secret_key=os.environ["FI_SECRET_KEY"],
)

# Column format: annotation.{label_name}.{type}
# Types: label (categorical), score (numeric), text, rating (1-5 stars), thumbs (True/False)
df = pd.DataFrame({
    "context.span_id": ["span_abc123", "span_def456", "span_ghi789"],
    "annotation.Sentiment.label": ["Positive", "Negative", "Neutral"],
    "annotation.Relevance Score.score": [4.5, 2.0, 3.5],
    "annotation.Reviewer Notes.text": [
        "Accurate and well-structured response",
        "Hallucinated a date that wasn't in the context",
        "Correct but could be more concise",
    ],
    "annotation.notes": [
        "Reviewed by QA team",
        "Flagged for retraining",
        None,
    ],
})

result = client.log_annotations(df, project_name="My Tracing Project")

print(f"Annotations created: {result.annotationsCreated}")
print(f"Annotations updated: {result.annotationsUpdated}")
print(f"Notes created:       {result.notesCreated}")
print(f"Errors:              {result.errorsCount}")
```

Example result format (your counts may differ):

```
Annotations created: 9
Annotations updated: 0
Notes created:       2
Errors:              0
```

6. Check `annotationsCreated`, `annotationsUpdated`, `notesCreated` and `errorsCount` against the rows you sent.

   The counts tell you how many annotations and notes were written, not which span received them. A project label list confirms a label exists, not that a particular span received it, so confirm that the span IDs you sent belong to the project you named.

## Recognize a label mismatch

On test data, change just the case of the Sentiment column as shown below. Use the same project name as the successful call.

```python
df_bad = df.rename(columns={"annotation.Sentiment.label": "annotation.sentiment.label"})
client.log_annotations(df_bad, project_name="My Tracing Project")
```

The mismatch raises a `ValueError` and aborts the call. With the example name the error reads:

```
ValueError: No annotation label found for name 'sentiment' and type 'label' in project 'My Tracing Project'
```

Copy `Sentiment` exactly as returned by the project label lookup and retry with the original DataFrame.

## Troubleshooting

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Symptom | Cause | Fix |
|---|---|---|
| `ValueError: No annotation label found for name '{name}' and type '{value_type}' in project '{project_name}'` | The DataFrame column's `{label_name}` segment doesn't exactly match a label name in the project (matching is case-sensitive) | Run `get_labels(project_id=...)` and copy the label name verbatim into the column, including case and spaces |
| `log_annotations()` succeeds but `annotationsCreated` is lower than expected | Some `context.span_id` values don't correspond to a span in the target project | Verify span IDs against the tracing project before building the DataFrame, and check `errorsCount` in the response |
| An annotation column is ignored with no error | The column name has more or fewer than three dot-separated segments (a label name containing a dot does this) | Keep the column as `annotation.{label_name}.{type}` with no extra dots in the label name |
| Auto Annotate never suggests labels | No manual annotations exist yet for the platform to learn from, or the label isn't Categorical | Annotate a handful of rows manually first; Auto Annotate only applies to Categorical labels |
| Annotator can't see the view | The workspace member wasn't added to the view's Annotators section | Open the view, add the member under Annotators, and click Save |
| `client.list_projects()` doesn't include the expected project | `project_name` passed to `log_annotations()` doesn't match a project's exact name | Print `p.name` for each project returned by `list_projects()` and use that literal string |

</div>
