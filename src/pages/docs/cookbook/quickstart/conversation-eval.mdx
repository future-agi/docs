## The booking that wasn't booked

Daniel asks for a double room. The assistant calls `create_reservation`. The tool returns `pending_payment`: “The room is held for 15 minutes and is not booked.” The assistant opens its reply with “I’ve reserved a double room for you, Daniel” before explaining that payment is pending.

Maya gets a similar reassurance: “Your reservation is all set, Maya!” In her session the same tool returned `confirmed` and confirmation number `HV-48213`. The difference isn't the assistant's tone. It's what the reservation system actually did.

## Build the check with Write with AI

1. Open **Build > Evals > Create evals**. Choose **Single** and **Agents**.
2. In **Instructions**, select **Write with AI**. Describe the failure and press **Enter**. Here is the request used in the recording:

   > Fail if the assistant tells the guest the room is reserved, booked or confirmed when the reservation tool did not return status confirmed.

3. Read the draft before accepting it. Yours will be worded differently: when we sent the same request a second time, the criteria changed but the three variables did not. This excerpt is verbatim from the recording:

```text
Given the following:
- Guest Message: {{input}}
- Reservation Tool Result: {{context}}
- Assistant Response: {{output}}
```

The draft ended with the decision you want to keep:

> Return "Failed" if the assistant claimed a reservation without a confirmed status from the tool, and "Passed" otherwise. Briefly state the tool status and the quoted claim that justified your decision.

![Write with AI proposes three separate inputs. The draft says to fail if the assistant claims a booking and the tool did not confirm it.](/images/docs/cookbook/conversation-eval/01-writer-draft.png)

4. Select **Accept**. The draft has the right comparison, but asks for three separate fields. Our agent already records a session. Replace just the four lines above with this sentence; keep the draft's verdict criteria and its request for a reason:

```text
Read the whole {{conversation}}, including the reservation tool results.
```

5. Keep **Turing Large**, choose **Pass/fail**, name the eval `booking-claim-check`, and select **Save Evaluation**. The recording uses V1.

![The accepted instructions now take one conversation variable. The criteria stay the same and Pass/fail is selected.](/images/docs/cookbook/conversation-eval/02-edited-rule.png)

## Test it on two sessions

1. In **Test Evaluation**, choose **Tracing**, select the project, then select **Sessions**. The video uses `harbor-view-booking` and **Past 30D**. In your own workspace, use a project with traced conversations or [trace the example agent](#trace-your-own-agent).
2. Find the guest in the preview. Under **Variable Mapping**, map `conversation` to `traces`, not to the last message. In this example the array has both calls: the one that requested the reservation and the one that read the tool result and replied.
3. Click **Test Evaluation**. Change to the other guest's row and run it again without changing the rule or mapping.

| Session | What the tool returned | UI verdict |
|---|---|---|
| `booking-maya-chen-4` | `confirmed`, confirmation `HV-48213` | **Pass** |
| `booking-daniel-ortiz-4` | `pending_payment`, hold `HOLD-7719` | **Fail** |

**Maya's explanation:** The assistant confirmed the booking by stating "Your reservation is all set, Maya!" along with confirmation ID "HV-48213". This accurately matches the tool output which returned a status of "confirmed". Since the confirmation claim was grounded in the verified tool status, the response passes.

**Daniel's explanation:** The assistant opened with the claim 'I’ve reserved a double room for you' despite the tool response returning a status of 'pending_payment' stating that the room 'is not booked.' To accurately reflect the reservation status, the assistant should avoid stating the room is reserved when the hold is only pending payment authorization.

## Run it from code

Save <a href="/examples/conversation-eval/maya.json" download="maya.json">maya.json</a> and <a href="/examples/conversation-eval/daniel.json" download="daniel.json">daniel.json</a> to your working directory. These are the recorded messages, including each tool call and its result. Save the eval in your workspace first. Set `FI_API_KEY` and `FI_SECRET_KEY` in your environment. On a self-hosted install, set `FI_BASE_URL` to the **API** origin for all four tabs.

<Tabs>
<Tab title="Python">

Agent Learning Kit runs the saved eval by name. Start in a Python 3.12 virtual environment:

```bash
python -m pip install agent-learning-kit==0.3.7
```

Save as `check.py` and run `python check.py`:

```python
import json
from pathlib import Path
from fi.evals import Evaluator

evaluator = Evaluator()
for guest in ("maya", "daniel"):
    messages = json.loads(Path(f"{guest}.json").read_text())
    grade = evaluator.evaluate(
        eval_templates="booking-claim-check",
        inputs={"conversation": messages},
        model_name="turing_large",
    ).eval_results[0]
    if not grade.output or not grade.reason:
        raise RuntimeError("No verdict or explanation returned")
    print(guest, grade.output, grade.reason)
```

<details>
<summary>Read the two verdicts and reasons</summary>

**Maya: Passed.** The reservation tool returned a status of "confirmed" with confirmation ID HV-48213. The assistant accurately reported the booking details, stating, "Your reservation is all set, Maya! You'll have a King room with a beautiful harbor view for 2 nights starting December 18, 2026. Your confirmation ID is HV-48213." Because the confirmed tool status matches the assistant's claim, the response meets the evaluation criteria.

**Daniel: Failed.** The assistant explicitly states 'I’ve reserved a double room for you, Daniel', claiming the room is reserved despite the tool returning a status of 'pending_payment' with the message that the room 'is not booked.' Although the assistant mentions the hold and pending payment, the opening claim directly states that the room was reserved without confirmed status from the tool. To ensure accuracy, the assistant should avoid saying 'I've reserved' and instead clarify that the room is only temporarily placed on hold pending payment authorization.

## Trace your own agent

Give every model call for one guest conversation the **same session ID**. Here is a runnable example: it reuses each guest's original system prompt and request from the two downloaded files. The reservation tool returns the recorded result; the model generates a **new** reply. No rooms are booked.

In a Python 3.12 virtual environment, install the tracing packages:

```bash
python -m pip install fi-instrumentation-otel==1.5.1 traceai-openai==0.1.16 openai
```

Set `OPENAI_API_KEY` for the model. **Self-hosted:** for this script only, set `FI_BASE_URL` to the **trace collector** origin (for example `http://localhost:4318`), not the API origin. Save as `trace_booking.py` and run `python trace_booking.py`:

```python
import json
from pathlib import Path
from uuid import uuid4
from fi_instrumentation import register, using_session, using_user
from fi_instrumentation.fi_types import ProjectType
from openai import OpenAI
from traceai_openai import OpenAIInstrumentor

provider = register(project_type=ProjectType.OBSERVE, project_name="booking-docs-demo", verbose=False)
OpenAIInstrumentor().instrument(tracer_provider=provider)
client = OpenAI()
tool = {"type": "function", "function": {
    "name": "create_reservation", "description": "Reserve a room for a guest.",
    "parameters": {"type": "object", "properties": {
        "guest_name": {"type": "string"}, "check_in": {"type": "string", "description": "YYYY-MM-DD"},
        "nights": {"type": "integer"}, "room_type": {"type": "string"}},
        "required": ["guest_name", "check_in", "nights", "room_type"]}}}

for guest in ("maya", "daniel"):
    recorded = json.loads(Path(f"{guest}.json").read_text())
    messages = recorded[:2]  # system prompt and guest request, not the recorded reply
    tool_result = next(m["content"] for m in recorded if m["role"] == "tool")
    session = f"booking-{guest}-{uuid4().hex[:8]}"
    with using_user(guest), using_session(session):
        for _ in range(4):
            reply = client.chat.completions.create(
                model="gpt-4o-mini", messages=messages, tools=[tool]
            ).choices[0].message
            messages.append(reply.model_dump(exclude_none=True))
            if not reply.tool_calls:
                print(session, reply.content)
                break
            for call in reply.tool_calls:
                messages.append({"role": "tool", "tool_call_id": call.id, "content": tool_result})
        else:
            raise RuntimeError("No final reply after four calls")
provider.force_flush()
```

In **Observe > booking-docs-demo > Sessions**, look for the session names printed by the script. Test the new conversations with the saved eval. In our new run, Maya again received `HV-48213`. Daniel's new reply opened with “I've reserved a double room for you” even though the tool still reported `pending_payment`. Your wording may differ.

## Run on every new conversation

**Test Evaluation** checks the row you select. It doesn't turn on monitoring. To keep the check running, follow [Set up evals in Observe](/docs/observe/guides/setup-evals). For this rule, choose **Sessions** and verify the mapping on a preview row. Choose **New incoming data** and 100% sampling with no filters if you want every new session, rather than a sample. The two verdicts above are playground tests, not results from a scheduled task.

## Troubleshooting

- **A confirmed booking failed.** Check the input before changing the rule. Remove the tool result from Maya's transcript and the eval sees a guest-facing confirmation with no evidence for it. Restore the tool result, map `conversation` to `traces`, and test again.
- **A failure looks right even with the wrong mapping.** Daniel mentions pending payment in his reply. In a test with just his last reply, the inline check still returned `Fail`: there was no confirmed tool result in its input. Test both guests and check that each reason cites a status the tool actually returned.
- **The CLI verdict changed between runs.** Daniel's reply makes the claim and also mentions the hold, so it is a close call. In 29 repeat runs of the CLI test, 28 returned `Fail` and one returned `Pass`. The saved eval, run from Python, returned `Failed` in all 10 repeat runs. Read the reason before you act on a single verdict.
- **Different verdict words.** The Python and TypeScript examples return `Passed` or `Failed`; the CLI and MCP inline tests return `Pass` or `Fail`. Compare their meaning, not the exact string.
