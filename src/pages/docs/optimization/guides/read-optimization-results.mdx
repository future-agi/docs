The best-ranked [optimization trial](/docs/optimization/concepts/understanding-optimization#a-trial-is-one-candidate-prompt-scored-row-by-row) need not improve the eval you care about. Compare it with the baseline, then use the prompt diff and the scored rows to decide whether to keep the change.

<Prerequisites title="Before you start">
- A [dataset](/docs/dataset) with a completed run. If you don't have one, [run an optimization](/docs/optimization/guides/run-an-optimization) first.
</Prerequisites>

## Open the completed run

1. Open the dataset's **Optimization** tab.
2. Select a **Completed** run.

   You should see the score graph, the result bar with its improvement note and **View Column**, and the trial list below it.

<div class="sdk-ref-table">

| Run status | What the run detail page shows |
| --- | --- |
| **Queue** or **Running** | A stepper tracks the run's four steps (onboarding, running the baseline eval, starting trials, and finalizing), and a “Please wait while we complete the optimization...” loader shows. The comparison below reads the run once it is **Completed**. |
| **Failed** | The loader area shows an error instead of results. |
| **Cancelled** | The **Optimization Stopped** panel and a **Re-Run Optimization** button replace the whole view, with no trial list. [Restart a stopped run](/docs/optimization/guides/run-an-optimization#restart-a-stopped-run) covers what that button does. |

</div>

## Compare the scores

1. Use **Evaluations** above the graph to select the eval lines to show.

   The **Evaluation Score** axis runs from 0 to 100. Each line represents one eval, with the baseline and then each numbered trial along the horizontal axis.

2. Compare each candidate with **Baseline** on the eval that matters to you.

   The baseline is the run's starting point, and every candidate is measured against it. The more a trial's line pulls above the baseline on that eval, the more the run improved on it. Lines that stay bunched around the baseline mean the run plateaued and didn't find a meaningfully better prompt.

### The trial list

1. Find the flagged row in the **Trial** column.

   Rows appear in run order, not score order; the baseline appears on the graph but has no row in the list.

![Completed GEPA run: Trial 2 scores 10% on cold_message_check, while Trial 1 and the other candidates show 0%.](/images/docs/optimization/run-detail-trial-list.png)

In this run, Trial 1 stays at the baseline on `cold_message_check`. Trial 2 is the flagged winner at 10%, up 10 points. The bump at Trial 2 on the graph and the flagged row under it are the same trial, read two ways. The average is over the rows the run scored, at most 50, not necessarily the whole dataset. On a run with several evals, a lower-ranked trial can still do better on the one you need.

2. If the list is wide, open **View Column** on the result bar.
3. Select the eval columns you want to compare.

   Each eval column shows the trial's score and its change from baseline.

## Check what changed in the prompt

1. Open the winning trial's row, **Trial 2** in the example.

   The **Prompt** tab initially shows only the candidate prompt.

2. Turn on **Show Diff**.

   Compare the baseline on the left with the trial on the right. In Trial 2, a first message and a follow-up became an instruction to “Write exactly ONE phase-one cold outreach message.”

![Trial 2 replaces the baseline first message and follow-up with a one-message instruction and a list of runtime inputs.](/images/docs/optimization/trial-detail-show-diff.png)

3. Open **Trial Items**.
4. Inspect one scored row.

   Compare the input, generated output and each eval's score. For Trial 2, check whether the output is one first message rather than a sequence. The prompt diff shows what was asked; the row shows what the model actually did.
