---
title: "Quickstart"
description: "Install the fi CLI, build an environment from your agent's folder, push a change as a new agent version, and fail a run on a low pass rate"
---

Install the CLI, sign in, build an [environment](/docs/environments/concepts/understanding-environments) from your agent's folder, push a change to your agent as a new agent version, check it, run the environment's suite (its set of test scenarios) against it, and wait for the pass rate. The last run command exits non-zero when fewer than 80% of the measured calls pass, which is the same command you put in CI.

## In this page

You go through twelve steps in order. Some steps print an ID that a later command needs. Those commands show it as a placeholder in capitals, such as `ENV_ID`, and the step says which output to copy it from.

## Prerequisites

- Go 1.24 or later, and git
- GitHub access to the private `future-agi/futureagi-cli` repository over SSH. Check it with `ssh -T git@github.com`, which greets you by your GitHub username
- A Future AGI account and a personal API key pair from [API Keys](https://app.futureagi.com/dashboard/keys) (on a self-hosted install, the API Keys page of your own dashboard, `/dashboard/keys`)
- Your agent's code in a folder on your machine, here `./my-agent`. This guide was tested with a Python agent folder (an `agent.py` and a `requirements.txt`)

<Note>
`fi` is a reserved word in bash and zsh, so these steps install the binary as `futureagi` as well and every command uses that name. [CLI Overview](/docs/cli) explains why. The CLI's own error and hint lines name commands as `fi ...`; type `futureagi` in their place.
</Note>

## Steps

<Steps>
<Step title="Install the CLI">

The repository is private and has no release yet, so install from source. The `git config` line makes Go fetch GitHub modules over SSH; skip it if your git already does.

```bash
git config --global url."git@github.com:".insteadOf "https://github.com/"
GOPRIVATE='github.com/future-agi/*' GOBIN="$(go env GOPATH)/bin" go install github.com/future-agi/futureagi-cli/cmd/fi@fi-cli-commands
ln -sf "$(go env GOPATH)/bin/fi" "$(go env GOPATH)/bin/futureagi"
PATH="$(go env GOPATH)/bin:$PATH"
futureagi version
```

The `PATH` line lasts only for this shell. To keep `futureagi` on your PATH in new terminals, add it to `~/.zshrc` (zsh) or `~/.bashrc` (bash).

`@fi-cli-commands` is the branch that holds the simulation commands. A binary installed this way reports its version as `dev`. If the `go install` output includes `Permission denied (publickey)`, your SSH key is not authorized for the repository, and the `ln` and `futureagi version` lines then fail too: add the key to your GitHub account or ask for access, then run the block again. To undo the `git config` line later, run `git config --global --unset url.git@github.com:.insteadof`.

</Step>
<Step title="Sign in">

```bash
futureagi auth login
```

It asks for your personal API key and secret key without echoing them, and saves the pair in your OS keychain under the active profile (`default` on a first login). Login does not contact the server; the next step checks the keys. If it exits 3 with `cannot write OS keychain`, unlock your keychain or see [Install and auth](/docs/cli/install-and-auth#sign-in) for the `--insecure-file-store` fallback; if you log in with it, add `--insecure-file-store` to every command below. If login hangs with no output after the second prompt, look for a keychain access dialog; with none, press Ctrl-C and log in again with `--insecure-file-store`.

For a self-hosted install, add `--base-url` with your platform's API URL, not the dashboard URL, such as `--base-url https://api.futureagi.example.com`; the profile remembers that URL. To sign in without a terminal, such as in CI, see [Install and auth](/docs/cli/install-and-auth#sign-in).

</Step>
<Step title="Check the setup">

```bash
futureagi doctor
```

```text
profile       default
base_url      https://api.futureagi.com
base_url_src  default
api_key       a1b2…9f3c
reachable     true
signed_in     true
user          you@example.com
```

`reachable false` exits 6 and `signed_in false` exits 3. A key pair the server rejects currently also shows `reachable false` (exit 6), so if the URL is right, check the keys. [Install and auth](/docs/cli/install-and-auth#troubleshooting-by-exit-code) says what to do for each.

</Step>
<Step title="Choose a workspace">

```bash
futureagi api context workspaces list
```

```text
ID                                    NAME               DISPLAY_NAME
4c1d2e3f-5a6b-4c7d-8e9f-0a1b2c3d4e5f  Default Workspace  Default Workspace
7e8f9a0b-1c2d-4e3f-9a5b-6c7d8e9f0a1b  support-team       Support team
```

Save the workspace in the CLI's user config file, `~/.config/fi/config.toml`, so every later command acts in it. Create the folder with `mkdir -p ~/.config/fi`, then create the file with these lines, replacing `WORKSPACE_ID` with a value from the `ID` column above, usually the one for `Default Workspace`:

```toml
[profiles.default]
workspace_id = "WORKSPACE_ID"
```

Without a workspace, the list commands below warn and come back empty. To use a workspace for one command only, pass `--workspace WORKSPACE_ID` instead. If you signed in to another profile, name its table after it, such as `[profiles.self-hosted]`.

</Step>
<Step title="Build an environment">

```bash
futureagi sim env create --repo ./my-agent --wait
```

The folder is uploaded and the cloud builder turns it into an environment: it works out how to reach your agent, writes the world it acts in, and writes the suite the later steps run. Nothing runs on your machine. The build is charged, so it asks you to confirm; in a script, pass `--yes`. `--dry-run` in place of `--wait` asks the server whether the build could start, including which credentials are missing, and lists the uploaded files: it uploads the folder, because the server's check scans it, but creates no environment.

`--wait` exits 0 when the build completed, 8 when the builder asks you a question, was canceled or failed, and 6 on an infrastructure failure or when `--wait-timeout` (default 60m) ends the wait. The output's `environment_id` row is the new environment's ID; the commands below show it as `ENV_ID`. While it waits, stderr also shows `environment ENV_ID: state/stage`, which is the place to copy it from when the wait stops early (exit 6), because nothing is then printed on stdout. A stopped wait does not cancel the build; resume with `futureagi sim env status ENV_ID --wait`, or stop the build with `futureagi sim env cancel ENV_ID --yes`.

If it asks a question (exit 8), answer the builder with `futureagi sim env chat ENV_ID`, approve a design it proposes with `futureagi sim env approve ENV_ID`, then resume the wait. [Environments](/docs/cli/environments#build-an-environment) covers the builder's questions and the other flags.

Steps 6 to 12 need a build that completed. If it does not complete, the environment has no suite: stop here and fix the build before you push, because push still succeeds on an environment whose build failed.

<Tip>
Already have an environment? Run `futureagi sim env list --limit 100` (it shows 10 rows without `--limit`) and use the `ID` of a row whose `SOURCE_KIND` is `archive` (built from an uploaded folder) and whose `STATUS` is `completed`. Only archive environments take a pushed version, and only a completed build has a suite to run and lets the pushed version become the default.
</Tip>

</Step>
<Step title="Push a change to your agent">

Make a change to your agent's code, such as its prompt, then push the folder:

```bash
futureagi agents push --repo ./my-agent --env ENV_ID --wait
```

```text
environment_id                       2d7e4b91-6c3a-4f58-9e21-b0a4c7d3e865
agent_id                             -
version_id                           b84e2d1c-7a9f-4c36-8e05-3f6a1d9c2b74
label                                v2
status                               active
connection_check.state               passed
connection_check.activation_outcome  applied
source.kind                          archive
source.path                          /home/you/my-agent
source.name                          my-agent
source.source_id                     5e2c8a17-9d4b-4f31-b6a0-7c3e1d9f2b85
source.file_count                    38
source.total_bytes                   48213
source.upload_digest                 sha256:3f9a...c41e
source.resolved_commit_sha           -
source.dirty                         -
source.skipped                       [.env]
dry_run                              -
```

The folder is uploaded and becomes the environment's next agent version. The `version_id` row is that version's ID; the commands below show it as `VERSION_ID`. A folder identical to the current default is refused (exit 1), which is why you change something first. In a git checkout, push sends the git-tracked and unignored files; elsewhere, every file except `.git`, `node_modules`, virtualenvs and `__pycache__`. It never sends symlinks or files that may hold secrets, such as `.env` files (`.env.example`, `.env.sample` and `.env.template` are uploaded), `.fi`, `.ssh` and `.aws` folders and private keys. [What push uploads](/docs/cli/agents#what-push-uploads) has the full rules.

`--wait` waits for the server's check: exit 0 when it passed, and a failed check exits 5. Push sends no retry key, so pushing again makes another version: after exit 6, list the versions with `futureagi sim env versions list ENV_ID` before you push again. On stderr, push prints `agent version VERSION_ID: check pending` while it waits.

The version becomes the environment's default only when `connection_check.activation_outcome` is `applied`. Another value, such as `environment_busy` or `-`, means it did not move: a build or run is in progress, or the environment's build did not complete. Wait for a running build or run to end, or rebuild the environment, then run `futureagi sim env agent set-default ENV_ID VERSION_ID`; `set-default` is refused (exit 1) until then. The run steps below pass `--agent-version`, which pins the pushed version either way. Push may also print a hint that the platform can suggest rebuilding the environment for this version; `futureagi sim env nudges list ENV_ID` lists those suggestions.

</Step>
<Step title="Check the agent version">

```bash
futureagi agents test VERSION_ID --env ENV_ID
```

It reports the check of that agent version. The server runs the source, credentials and provider checks; checks it can't report yet show as `unknown`, never as passed. Checks that do not apply to this agent, such as provider checks on an uploaded agent, show as `skipped` and do not fail the check. Exit 0 when it passed, 5 when it failed, with the failing check named. A re-check that passes makes the version the environment's default, as push does.

</Step>
<Step title="Pick the suite">

```bash
futureagi sim suites list --env ENV_ID
```

```text
ID                                    LABEL  STATUS  IS_DEFAULT  SCENARIO_COUNT  ORIGIN     CREATED_AT                 SUMMARY
c3e9a7f1-4b2d-4f60-8a1e-5d7c9b3e2f48  v2     active  true        12              manual     2026-11-02T14:10:00+00:00  1 scenario changed
e1f4b8d2-9c6a-4e37-b5f0-2a8d6c4e1b93  v1     active  false       11              authoring  2026-10-30T08:00:00+00:00  First version
```

The `ID` of the row whose `IS_DEFAULT` is `true` is the suite version ID that `--suite` takes; the commands below show it as `SUITE_VERSION_ID`. Discarded versions have no label and show `STATUS` `discarded`; skip them.

An empty list, only the header, means the environment's build never completed, so it has no suite. Build the environment first, as in step 5.

</Step>
<Step title="Preview the run">

```bash
futureagi sim run --env ENV_ID --suite SUITE_VERSION_ID --agent-version VERSION_ID --dry-run
```

Without `--agent-version`, a run tests the environment's saved default agent version, which is not the one you pushed when push did not apply it. Check that `versions.agent.id` in the preview is your `VERSION_ID`. The preview shows the agent, environment and suite versions the run would pin, each scenario, the server's warnings and `blocked`. It starts nothing and costs nothing. It exits 0 even when the selection is blocked, so read `blocked` and the warnings before you go on.

</Step>
<Step title="Run and wait for the pass rate">

```bash
futureagi sim run --env ENV_ID --suite SUITE_VERSION_ID --agent-version VERSION_ID --yes --wait --fail-under 0.8
```

`--yes` confirms the run, which is charged like any run. The command prints `started run RUN_ID` on stderr, waits until the run and its grading end, then prints the run's final status, whose `id` row is the same Run ID. The commands below show it as `RUN_ID`. Don't use the `run_id` row: it is a different platform ID that `futureagi sim runs` commands reject.

| Exit | Meaning |
|---|---|
| 0 | Every scenario was measured and at least 80% of the measured calls passed |
| 5 | The pass rate, passed / (passed + failed), is below 0.8, even if some calls were not measured |
| 6 | `--wait-timeout` ended the wait, or a network or server error |
| 8 | The run failed, was canceled or is partial at or above 0.8, or no call was measured |

Ctrl-C stops the waiting, never the run. `--wait-timeout` bounds the whole wait (default 60m); in CI, set it longer than the run takes, such as `--wait-timeout 90m`. When the wait times out (exit 6), nothing is printed on stdout: copy the Run ID from the `started run` line on stderr, or, with `--json`, from `job_id` in the error object on stderr. Don't run the same command again to resume: that starts a second charged run. To retry it, rerun it with `--idempotency-key` set to the `Idempotency-Key` value it printed on stderr, and the server returns the run it already started.

To keep waiting, run `futureagi sim runs status RUN_ID --wait`. To stop the run itself, use `futureagi sim runs cancel RUN_ID --yes`.

</Step>
<Step title="Read the results">

```bash
futureagi sim runs results RUN_ID
```

The header counts the whole run's outcomes, and each row is one call with its scenario key, outcome and `result_state`. `futureagi sim runs trial show RUN_ID CALL_ID` prints one call's transcript, tool calls and checks, where `CALL_ID` is a row's `ID` value from the results table.

</Step>
<Step title="Open the run in the dashboard">

```bash
futureagi sim runs status RUN_ID
```

Build the run's page path from the `environment_id` (your `ENV_ID`), `run_test_id` and `test_execution_id` rows of the output:

```text
/dashboard/simulate/environments/ENV_ID/runs/RUN_TEST_ID/TEST_EXECUTION_ID/call-details
```

The `web_url` row is a legacy path (`/dashboard/simulate/test/...`) that can show a not-found page, so use the path you built. The page lists every call with its recording or transcript. On Cloud, open `https://app.futureagi.com` followed by the path. On a self-hosted install, prefix the path with your dashboard (frontend) URL, not the API base URL.

</Step>
</Steps>
