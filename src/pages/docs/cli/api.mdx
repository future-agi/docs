`fi api` is a set of commands generated from the platform's API catalog, for the reads and writes that have no hand-written command yet. Each one maps to one endpoint, takes its parameters as flags, and prints the response as a table, JSON or JSON Lines, with the same sign-in, workspace and exit codes as every other command.

## In this page

How the commands are grouped, how to find one and read its help, and how reads, writes, pagination and request bodies behave.

## Find a command

The commands are grouped by product area, then by resource:

| Group | Covers |
|---|---|
| `fi api context` | Who you are signed in as, and your workspaces |
| `fi api agents` | Agent definitions, their versions, runs and test executions |
| `fi api datasets` | Datasets, their evaluations, knowledge bases and prompt stats |
| `fi api evaluations` | Evaluators, evaluation templates and the evaluation playground |
| `fi api observability` | Projects, traces, spans, sessions, properties, eval tasks, eval configs, alert rules and alerts |
| `fi api prompts` | Prompt templates, their versions and prompt runs |
| `fi api simulation` | Environments and their drafts, versions, suites, rebuild offers (`nudges`) and evaluations; jobs (environment builds and runs); personas; run tests (`run-tests`); test executions and call executions |

Walk down with `--help`: each level lists the commands under it.

```bash
futureagi api --help
futureagi api simulation --help
futureagi api simulation environments --help
futureagi api simulation environments list --help
```

In the API a run is a job, so `fi api simulation jobs` takes the Run ID (`job_id`); the help text calls it a harness job.

A command's help gives its endpoint description, its flags (path, query and body parameters, with their limits), examples, and for a write, how it is sent:

```text
Request cancellation of a harness job. Completed work is kept; cleanup may still be pending.

Only explicitly supplied parameters are sent. Use --json to retain the full response and pagination metadata.

Write: sent once and never auto-retried; this endpoint takes no idempotency key, so after a timeout read the resource before repeating. Destructive: asks for confirmation on a TTY; pass --yes with --no-input or without a TTY.

Usage:
  fi api simulation jobs cancel [flags]
```

## Read

Choose a workspace first, with `--workspace` or a saved `workspace_id` (see [Choose a workspace](/docs/cli/install-and-auth#choose-a-workspace)). Without a workspace, `fi api` lists don't warn; they just come back empty.

```bash
futureagi api context whoami
futureagi api context workspaces list --json
futureagi api observability projects list
futureagi api observability traces search --project-id PROJECT_ID --page-size 50 --json
futureagi api simulation environments run-plan --id ENV_ID --json
```

`PROJECT_ID` is the `ID` column of `futureagi api observability projects list`, and `ENV_ID` is the `ID` column of `futureagi sim env list`. Only the parameters you pass are sent. Reads retry transient failures up to three attempts, so a read is always safe to repeat.

Pagination is explicit: a list returns one page, and you pass the page or cursor flag the endpoint takes (such as `--page`, `--page-number` or `--cursor`; check the command's help) to get the next. Use `--json` to keep the full response with its next-page metadata; the CLI never follows pages on its own.

```bash
futureagi api observability properties list --cursor-mode --page-size 50 --json
futureagi api observability properties list --cursor-mode --page-size 50 --cursor NEXT_CURSOR --json
```

`NEXT_CURSOR` is the `result.next_cursor` field of the previous page's JSON; `result.has_more` is `false` on the last page.

## Write

Writes are sent once and never retried on their own. A write whose endpoint honors an idempotency key sends one. The key is a new UUID unless you pass `--idempotency-key`. The CLI prints it to stderr before sending and includes it as `idempotency_key` in a JSON error. After a timeout or a network error (exit 6), rerun with the same key. A write without a key has no `--idempotency-key` flag, so read the resource before you repeat it.

A write that takes a body has `--body`: inline JSON, `@FILE`, or `-` for stdin. It defaults to `{}` when the body is optional. Destructive writes ask for confirmation on a terminal: deletes and cancels, and writes that start or spend charged work, such as starting a run, extending a suite or re-running calls. Without a terminal, or with `--no-input`, they need `--yes`. The command's help says Destructive when this applies.

```bash
futureagi api simulation jobs cancel --id RUN_ID --yes --no-input
```

`RUN_ID` is the Run ID that `futureagi sim run` prints (`job_id`); see [Runs](/docs/cli/runs).

<Tip>
Prefer the hand-written command when there is one, such as `fi sim runs cancel` over `fi api simulation jobs cancel`: it checks the run's state first, takes the Run ID as an argument, prints a readable result and documents its exit codes. Use `fi api` for what has no hand-written command, or for the raw response, such as `fi api simulation jobs get --id RUN_ID --json` for a run's full record, with its events.
</Tip>

## Exit codes in fi api

The [shared exit codes](/docs/cli/install-and-auth#exit-codes) apply, with one addition: an HTTP 400 that names a flag or body field also exits 2, and the message names the flag. Any other 400 exits 1.
