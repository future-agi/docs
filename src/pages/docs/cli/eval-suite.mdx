## About

Use `fagi eval test` to see how a judge grades one reply. Use `fagi eval suite` when you want CI to fail if too few verdicts match your expectations. In this example, Ridgeline Outfitters promises a 30-day return window. You supply the support agent's replies; neither command runs the agent for you.

## Preview one judgment

Install the CLI with `npm install -g @future-agi/cli@0.2.2`. On Linux and macOS the npm wrapper requires Node.js `^22.15.0` or `>=23.11.0`. Start with a dry run. You don't need Python, platform credentials or a provider key for the preview.

```bash
MODEL=gpt-4.1-mini
RUBRIC='Pass only if the reply gives the exact return window in days. Policy: {{days}} days. Reply: {{reply}}'

fagi eval test --criteria "$RUBRIC" \
  --var-json days=30 --var 'reply=You can return the jacket within 30 days.' \
  --model "$MODEL" --output-type pass-fail --dry-run --json
```

Look for `dry_run: true` and inspect `request.config.mapping`: `days` should be the number `30`, and `reply` should be the sentence you supplied. `--var` takes a literal string; `--var-json` takes one JSON value, including a number, array or object. You can repeat either flag, but each key must be unique.

If you omit `--var-json days=30`, the CLI reports `criteria token {{days}} has no matching variable; add --var days=VALUE or remove the token` and exits `2` without calling the judge. Restore the mapping before continuing. This placeholder check applies when you supply inline criteria or variables.

## Run one reply and read the verdict

For a live run, set `FI_BASE_URL` first if you use a self-hosted API. Run `fagi auth login` and enter a matching platform API key and secret key, or provide them through `FI_API_KEY` and `FI_SECRET_KEY` in CI. These keys authenticate the CLI, not the judge. For `gpt-4.1-mini`, your organization needs an [OpenAI provider key](/docs/admin-settings/ai-providers). If you use a different configured judge, change `MODEL` in your shell. A dry run checks neither set of credentials.

Save the rubric as a JSON request so you can reuse it for the suite. Supply each example's reply separately. In the same shell, run:

```bash
cat > return-policy.json <<'JSON'
{
  "template_type": "Llm",
  "name": "ridgeline-return-window",
  "criteria": "Pass only if the reply gives the exact return window in days. Policy: {{days}} days. Reply: {{reply}}",
  "config": {"mapping": {"days": 30}},
  "output": "Pass/Fail",
  "reason_column": true
}
JSON

fagi eval test --data-file return-policy.json \
  --var 'reply=You can return the jacket within 30 days.' \
  --model "$MODEL" --output-type pass-fail --json
```

Read `output` for the verdict and `reason` for the explanation, if supplied. **Exit `0` means the evaluation completed, not that the reply passed.** For example, a verdict of `"Failed"` can still exit `0`. Check the actual JSON value and type before you write your suite expectations. If the CLI reports an invalid response instead, see [Limits and errors](#limits-and-errors) before running a suite.

`--data-file` accepts one JSON object, or `-` for standard input. `--criteria` and `--name` override file fields; `--var` and `--var-json` add or replace individual keys in `config.mapping`. Use a file rather than putting sensitive text in shell history. Both commands require `--model` and `--output-type`. The flags set `model`, `config.model` and `output_type`. They do not overwrite the separate `output` field. Keep `"output": "Pass/Fail"` in this template so the platform formats the verdict as pass/fail. Accepted output types are `pass-fail`, `score`, `numeric`, `choices` and `reason`; use one your judge supports.

## Label two cases and check the call count

The gate requires both support replies to follow the same return policy. The pack reply deliberately promises 90 days so you can see which case breaks the gate. Save one JSON object per line:

```bash
cat > returns.jsonl <<'JSONL'
{"id":"jacket-return","reply":"You can return the jacket within 30 days.","expected":"Passed"}
{"id":"pack-return","reply":"You can return the pack within 90 days.","expected":"Passed"}
JSONL

fagi eval suite --template return-policy.json --cases returns.jsonl \
  --id-column id --expect-column expected --min-match-rate 1 \
  --model "$MODEL" --output-type pass-fail --dry-run --json
```

Check that `planned_calls` is `2`. Each previewed request should contain the template's `days` and that row's `reply`. With these flags, `id` names the case in reports and `expected` stays local for comparison. Use a unique ID for each row. All other row keys become judge inputs and override template mappings of the same name.

## Gate CI and inspect a mismatch

In CI, install the same CLI version, check out `return-policy.json` and `returns.jsonl`, and set the same model and platform environment variables as in your live test. Use a fresh report directory for each job: if validation or authentication fails before the suite starts, an old report can remain on disk. Use the command's exit code as the job result and collect `reports/returns.xml` even on failure.

```bash
: "${MODEL:?Set MODEL to your configured judge model in the CI job}"
mkdir -p reports
fagi eval suite --template return-policy.json --cases returns.jsonl \
  --id-column id --expect-column expected --min-match-rate 1 \
  --model "$MODEL" --output-type pass-fail \
  --junit-file reports/returns.xml -o jsonl
```

`-o jsonl` prints one `case` event per evaluated row, then `suite_finished`. If the judge returns `"Passed"` for the jacket and `"Failed"` for the pack, only one of two expectations matches. The match rate is `0.5`, below the required `1`, so the command exits `5`. In JUnit, look for the testcase named `pack-return`, with a `failure` message of `output did not match the expected value`. To print just the mismatches from the report:

```python
import json
from xml.etree import ElementTree

for case in ElementTree.parse("reports/returns.xml").findall("testcase"):
    if case.find("failure") is not None:
        result = json.loads(case.findtext("system-out"))
        print(f"{case.get('name')}: expected {result['expected']!r}, got {result['output']!r}")
```

For those verdicts, the line is `pack-return: expected 'Passed', got 'Failed'`. If you're testing the agent, fix the 90-day promise. If you're testing the *judge's ability to spot a bad reply*, label the pack row `"Failed"` instead: rejecting that reply is then a match.

| Gate setting | How it affects the result |
| --- | --- |
| `--expect-column expected` | Uses the row's JSON value, even `null`. To supply a default for rows without that key, add `--expect '"Passed"'`. Without either expectation, a row still makes a judge call but doesn't count toward the rate. |
| `--min-match-rate` | Matches divided by cases with expectations. The range is `0` to `1`, inclusive; equality passes. A gate needs at least one scored case. Without a threshold, a completed suite reports mismatches but exits `0`. |
| `--junit-file` | A mismatch is a failed testcase even if the overall gate passes. A request error is an `error`, not a mismatch; unscored cases and cases left after a stop are `skipped`. |

Matching is JSON equality, not a second model judgment. Strings are case-sensitive, array order matters, and numeric `1` matches `1.0` but not the string `"1"`. A match-rate threshold is not a minimum judge score. The suite compares the current outputs with your labels, not two stored experiment runs.

## Limits and errors

- **Call budget:** The suite defaults to `--max-cases 20`. You can set it from `1` to `500`. A file with more cases than the cap is rejected in full before credentials or network calls, not truncated. For example, adding `--max-cases 1` to the two-row command exits `2` without grading either reply. The template and cases files are limited to 16 MiB each, and a JSONL line to 1 MiB.
- **Billing and timeouts:** Budget for one model call per case. The CLI sends requests one at a time and never retries them automatically. `--timeout` defaults to `2m` per call. A timeout does not cancel server work or refund a completed call; check what ran before retrying.
- **Missing provider key:** If the single test returns HTTP `400` with `API key not configured for openai`, the CLI exits `2`. Use a model whose provider is configured. A suite that hits this error on the jacket stops before grading the pack; the report contains an `error` and a `skipped` case, not a quality mismatch.
- **Request or response errors:** The suite stops on the first API, network or invalid-response error. Check `stop_reason` in the partial report. For example, platform v1.59.1 can return HTTP `200` with `result.metadata` encoded as a string. CLI 0.2.2 expects an object there: it reports `invalid evaluation response` and exits `1`, not `5`. Check the evaluation log rather than rerunning the suite or lowering the threshold. You can also [test a single reply in the eval builder](/docs/evaluation/guides/custom-evals#test-the-eval) to inspect the judge's verdict without the CLI.
