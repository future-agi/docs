## The two levels

Every Future AGI account has an **organization**. Inside it sit one or more **workspaces**, and every workspace holds the same kinds of thing.

<img src="/images/docs/rbac/access-levels.svg" alt="Access has two levels. The organization holds members and roles, the plan and billing, and organization settings. Under it sit workspaces, and every workspace holds the same kinds of thing: traces, datasets, evaluations, prompts, annotation queues and knowledge bases." style={{ border: 'none', width: '100%', maxWidth: '660px', margin: '1.75rem auto', display: 'block' }} />

*The organization is the billing boundary. The workspace is the data boundary*

The organization is where billing lives. The workspace is where the data lives. Each has its own set of roles, so you hold one role in the organization and one in each workspace you belong to.

Every organization is created with one workspace, called **Default Workspace**. Workspace names are unique inside an organization, and reusing one gives you **Workspace with this name already exists**.

## What is scoped where

This boundary decides what a teammate in another workspace can see.

<CardGroup cols={2}>
  <Card title="Lives in a workspace" icon="layer-group">
    Datasets, traces and Observe projects, the evaluations and evaluation templates you create, prompts and prompt folders, annotations and annotation queues, knowledge bases, custom models, agent playground graphs, optimization runs, and integration and AI Provider connections
  </Card>
  <Card title="Lives in the organization" icon="database">
    Members, roles and invites, the plan, billing, invoices and wallet balance, resource and rate limits, gateway API keys and gateway request logs, organization settings, MCP server settings, and the Settings pages for AI Providers, Integrations and Falcon AI Connectors
  </Card>
</CardGroup>

Integrations and AI Providers appear on both sides because there are two of each: an organization Settings page, and a tab inside every workspace holding that workspace's own connections. Reaching one does not give you the other.

Switching workspace changes the work. Datasets and prompts are completely separate lists per workspace. Your Settings list stays the same, and the only sidebar entry that moves is **Build > Keys**, which appears where your workspace role allows it.

Future AGI's built-in evaluations are available in every workspace of every organization. An evaluation template you build yourself belongs to the workspace you built it in, so rebuild it in the second workspace, or keep shared evaluations in a workspace everyone belongs to.

## What the boundary does not cover

Separating teams into workspaces separates their work. Four things stay shared across the whole organization.

| Not separated | What that means |
|---|---|
| The gateway | Every role opens every page under **Gateway**, and the request logs are stamped with the organization rather than a workspace |
| Where a key can send | A key always writes to its own organization, whichever one you have open in the dashboard |
| What a key can be aimed at | Traces are fixed to the key's workspace, but other SDK and API calls can name any workspace you have access to in the same organization |
| Usage and billing | One plan, one balance, one invoice. **Usage Summary** is open to every role and breaks consumption down by workspace |

Three consequences follow:

- Anyone who can sign in sees every team's gateway traffic, so keep a team's traffic off the gateway if it has to stay private
- Every role can see what every team is using on **Usage Summary**
- A key is scoped by who holds it, not by where it was made

<Warning>
**Gateway** is in the sidebar for everyone, including a Viewer, and every page under it opens: Providers, API Keys, Guardrails, Fallbacks, the request logs, budgets and webhooks. Treat gateway configuration as visible to your whole organization.

Only reading is open to everyone. Writing is still checked, just later than elsewhere. The gateway leaves its create buttons live instead of greying them out, then refuses on submit with **Write access denied to this workspace**. If you cannot create in a workspace, you cannot create here either.
</Warning>

## Where a key lands

A [platform API key](/docs/admin-settings/api-keys) belongs to one organization for good, and inside it to one workspace. The key takes whichever workspace you had open when you created it. Nothing in the **Add API Key** dialog says so and there is no field to change it, so switch into the workspace before you create the key.

Traces always land in the workspace the key was created in. The one exception is the starter `system_org_key`, which was never created in a workspace and lands in the organization's default one. A workspace header on a trace export is ignored, so a trace cannot be redirected afterwards.

Other SDK and API calls can override the key, in this order:

1. An `X-Workspace-Id` header or a `workspace_id` query parameter takes precedence, provided that workspace is in the same organization and you have access to it
2. Otherwise the workspace the key was created in
3. Otherwise the workspace you last used in that organization, then the first workspace you belong to, and if you belong to none, the organization's default workspace

<Tip>
Data in the wrong place is almost always the key. Make one key per workspace, name it after the workspace, and create each one while you are inside it.
</Tip>

## One person, many organizations

One person can belong to several organizations, with a different role in each. Owner in one, Member in another, Viewer in a third.

Organizations share nothing: separate workspaces, separate members, separate plan, separate billing, separate keys. Two teams that genuinely need separate gateway logs or separate invoices need separate organizations, because neither splits by workspace.

Move between them from the switcher at the top of the sidebar. Hover **Organization** to see the list. Future AGI remembers where you were, so the organization and workspace you last used are where you land next time, on any device.

## Why it matters

The workspace is the thing you reach for when one group must not see another group's work, and it does that job completely for datasets, traces, prompts and evaluations. What it does not do is contain a credential, a gateway log or a bill, and those three are exactly where an isolation promise tends to be made. Read the four rows above before you promise a customer that two teams are separated.
