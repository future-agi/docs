## About

A **guardrail** is an [evaluation](/docs/evaluation) applied inline to live traffic, where an input or output is checked against a rule and an action is taken based on the result, such as blocking or flagging. Unlike batch evals that score responses after they are generated, guardrails run on the request path itself, in the [Protect gateway](/docs/protect), so decisions can be enforced in real time.

Guardrails reuse the same eval templates as batch evals (Toxicity, Groundedness, PII Detection, and custom rules), but apply them differently: synchronously at the gateway, with a choice of three outcomes instead of a score. This lets you check both inputs and outputs in one place, while keeping the same eval definitions across your system.

---

## How guardrails differ from evals

Both use the same templates and judge models, but they answer different questions and run at different times.

| Aspect | Batch eval | Guardrail |
|---|---|---|
| **When** | After the response is generated | Before the request reaches the provider, or before the response is returned |
| **Where** | Dataset, simulation, or CI/CD | Protect gateway (inline request path) |
| **Result** | Score (0–1), category, or pass/fail | Action (block, warn, or log) |
| **Use case** | Measure quality, understand patterns | Enforce policy in production |

---

## Guardrail structure

A guardrail policy groups one or more checks and controls how they run.

Each policy sets:

- **Checks**: the safety rules to run, each with a type (Toxicity, PII, Prompt Injection, custom, and others) and a threshold
- **Mode**: `enforce` lets checks act on the request, `monitor` records violations without blocking
- **Scope**: where the policy applies, `global` (all keys), `project` (all keys in a project), or `key` (a single virtual key)

Each check runs at a **stage**, `pre` before the provider call or `post` after it, and resolves to an **action** when it triggers.

---

## Actions

When a guardrail check triggers (the input or output violates the rule), one of three actions happens:

| Action | Behavior | Use case |
|---|---|---|
| **Block** | Reject the request with 403 Forbidden | Enforce hard boundaries, such as never allowing prompt injection attempts |
| **Warn** | Add a warning header to the response, allow it through | Flag suspicious content without blocking, such as high-toxicity responses |
| **Log** | Record the violation in audit logs, no change to request or response | Passive monitoring for compliance or analysis |

---

## Runtime vs batch

Guardrails run at the Protect gateway during request and response processing, so they can make real-time decisions. Batch evals run offline on datasets or after responses are collected.

Running evals at the gateway means:

- Responses flagged at the input stage never reach the provider
- Outputs flagged at the output stage are blocked before they are returned
- All decisions are audit-logged for compliance
- Latency is predictable and measured in milliseconds

The trade-off is that guardrails must evaluate quickly. Complex evals that require extensive reasoning may not be practical as guardrails; simpler rule-based checks and fast scanning work best.
