Context is the grounding you give an eval. It is the facts, retrieved documents, tool outputs, or conversation history that a response should stay true to. Without context, an eval can judge whether an answer reads well; with context, it can judge whether the answer is actually supported by the source it was meant to use.

You pass context as an input to the eval, the same way you pass the response. It is a `string` or a `list[string]`: one document, or the set of chunks your retrieval returned for that query.

## Evals that use context

Context is what the RAG and retrieval family of evals reads:

- **Groundedness** checks that the response only claims things the context supports
- **Context adherence** checks that the response follows what the context says
- **Context relevance** checks that the retrieved context actually addresses the query
- **Chunk attribution** traces each claim back to the chunk it came from
- **Chunk utilization** checks whether the retrieval returned the chunks the answer needed

An eval that needs context declares it as a required input. If you do not map it, the eval has nothing to ground against.

## Knowledge base and context

A **knowledge base** is the full set of sources your app can retrieve from, like all of your product or support documentation. **Context** is the slice of it that retrieval pulls for a single query. An eval scores against the context that was actually used for that response, not the whole knowledge base, so it measures the retrieval you really ran.

## Context in an agent

An agent often retrieves more than once, refining its query as it goes. Each retrieval hop carries its own context, and the final answer draws on the accumulated set. On a traced agent run, each retrieval hop's context lives on its own retriever span, so once the eval is pointed at the attribute that holds it, both each hop's retrieval quality and the sufficiency of the final context can be scored hop by hop.

## Providing context

You give an eval its context wherever the eval runs. In a dataset, map the column that holds your context to the template's `context` input. In the SDK, pass it as the `context` input alongside the response. On a traced run, the context arrives in the trace as a span attribute, and you map that attribute to the template's `context` input yourself, since its name depends on how your app is instrumented.
