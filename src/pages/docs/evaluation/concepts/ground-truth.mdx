## About

**Ground truth** is a collection of expected or reference values that reference-based evals compare model outputs against. Instead of measuring subjective qualities like tone or safety, a reference-based eval checks whether the generated output matches the known-correct answer. You upload ground truth as a dataset, then attach it to specific [eval templates](/docs/evaluation/concepts/eval-templates) so those templates can compare each model output to its reference at eval time.

---

## When to use ground truth

Ground truth is the right choice when you have a clear, correct answer to compare against. Common cases:

- A question answering system where the correct answer is known in advance
- A code generation tool where you know what the correct code should produce
- A data extraction pipeline where the expected fields and values are labeled
- A classification task where the correct label is on file
- Any task where correct means matching a specific reference output

If you do not have known-correct answers yet, or correctness is subjective like tone or helpfulness, use a [judge model](/docs/evaluation/concepts/judge-models) eval instead.

---

## Evals that use ground truth

Several built-in templates compare against a reference value:

- [Ground Truth Match](/docs/evaluation/builtin/ground-truth-match): pass or fail on whether the output matches the reference value semantically
- Answer Similarity: a similarity score between the output and a reference answer
- Fuzzy Match: approximate string matching with configurable tolerance
- Retrieval metrics such as Recall@K and Mean Average Precision: measure whether a retrieved set contains the expected items

Each template documents the input keys it expects. When you attach ground truth to a template, you map your dataset columns to those keys.

---

## How ground truth data is structured

Ground truth is stored as a dataset with named columns, where each row is one example. At minimum it needs:

- **Input columns**: the data the model receives, such as the question column for a question-answering eval
- **Expected output column**: the correct answer the eval compares against. Every row must have one
- **Optional explanation column**: any extra context the eval can use, such as the reasoning behind the answer

The platform stores the dataset as JSON rows with named columns.

---

## Mapping ground truth to eval inputs

When you attach ground truth to an eval template, you configure two mappings:

**Variable mapping** connects each eval template input to a ground truth column. For example, if the template needs a `question` input, you map it to the `prompt` column. At eval time the platform uses this mapping to pull the right column value for each row.

**Role mapping** designates which column is the expected output, and optionally which column carries an explanation. It tells the eval which ground truth value to compare against.

The platform validates these mappings when you save them, so every mapped column must exist in your dataset.

---

## Retrieval and few-shot injection

Ground truth can also calibrate the judge by injecting similar examples into the eval prompt, called **few-shot grounding**. When enabled, the platform:

1. Embeds your ground truth dataset so similar examples can be found
2. At eval runtime, finds the ground truth rows most similar to the current input
3. Includes those rows in the judge prompt as reference calibration

This helps the judge apply your correctness criteria without you rewriting the prompt.

Retrieval requires the embedding status to be `Completed`. The platform embeds ground truth asynchronously after you save a mapping, and once embedding finishes, retrieval starts on the next eval run. If you change the variable mapping, the embeddings are marked stale and re-embedded automatically.
