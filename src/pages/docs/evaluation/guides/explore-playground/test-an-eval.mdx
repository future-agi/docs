Before you attach an eval to your data, test it on one example whose answer you know. Every eval has a **Test Evaluation** panel on its page, so you can run it on a bit of data and read the result and the reason first.

This guide tests [Detect Hallucination](/docs/evaluation/builtin/detect-hallucination), where the question is whether the reply makes a claim that its context doesn't support.

<Prerequisites title="Before you start">
- An eval you can open from the [Evaluations list](/docs/evaluation/guides/explore-playground).
- A sample with the fields the eval expects. Use **Custom** if you don't have a saved row.
</Prerequisites>

## Select an eval

1. Search or filter the Evaluations list for `hallucination`.
2. Open `detect_hallucination`.

   You should see **Test Evaluation** on the right of **Eval Details**.

<img src="/images/docs/evaluation/explore-playground/test-an-eval/select-eval.png" alt="The Evaluations list filtered to hallucination shows three matching evals, including detect_hallucination." style={{ borderRadius: '5px' }} />

## Choose the source

1. Select a source tab in **Test Evaluation**.

   Choose **Tracing** to check a claim from your app, or **Custom** to supply the example yourself.

2. Select the example to test, or enter your values in the JSON editor for **Custom**.

| Tab | What the eval reads |
|---|---|
| **Dataset** | A row from a [dataset](/docs/dataset). |
| **Tracing** | A [span](/docs/observe/concepts/spans) or [trace](/docs/observe/concepts/traces) from a project in [Observe](/docs/observe), so you test on real production data. The recording below selects **Sessions** on this tab to test a whole [session](/docs/observe/concepts/sessions). |
| **Simulation** | A call from a [simulation](/docs/environments). |
| **Custom** | Your own test data as JSON, one value per variable the eval needs. |

<img src="/images/docs/evaluation/explore-playground/test-an-eval/custom-test.png" alt="Custom mode shows the JSON editor and the input, output and context variables." style={{ borderRadius: '5px' }} />

## Map the claim and its evidence

An eval declares the variables it needs, and this hallucination eval needs `input`, `output`, and `context`. In **Custom**, those variables are the JSON keys, so they are already mapped and you fill in the values directly.

For a real data source such as a trace, use **Variable Mapping** to point each variable at a field in your data. The attribute names depend on how your app is instrumented.

1. Map `input` to the question.
2. Map `output` to the reply you want to check.
3. Map `context` to the field that contains the source material.

   In the captured example, `input` maps to `input`, `output` to `output`, and `context` to `input.value`.

## Compare the verdict with the evidence

1. Select **Test Evaluation**.
2. Read **Explanation** alongside **Result**.

   In the trace below, the reply says API keys can be managed at the organization level. The result is **Pass**: the explanation says that statement appears verbatim in the supplied context.

<img src="/images/docs/evaluation/explore-playground/test-an-eval/tracing-result.png" alt="The tracing test maps context to input.value. The Pass explanation says the reply about organization-level API keys matches the context exactly." style={{ borderRadius: '5px' }} />

3. Select a second example with a claim its context does not support.
4. Run **Test Evaluation** again without changing the rule.

   Look for **Fail** and an explanation that identifies the unsupported claim. For example, the eval's own criteria distinguish naming a CEO when the context confirms the name from naming one when the context mentions no CEO.

## Troubleshooting

- **A variable is missing.** In **Custom**, check the JSON for a key matching the variable name. In **Tracing**, inspect the selected row for a field with the required value and map it. If the row lacks the evidence, select a different row before testing again.
- **The verdict looks wrong.** Compare the explanation with the actual `output` and `context` values. Check that `context` points to the source material rather than the claim being judged.
