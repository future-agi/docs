---
title: "Set up guardrails"
description: "Turn on real-time safety checks for your AI, through the gateway or directly in code with the Protect SDK"
---

A [guardrail](/docs/evaluation/concepts/guardrails) screens a request or response and acts on it right away, block it, warn, or just log it, instead of scoring it after the fact like a standard eval. There are two ways to run one, and both operate in milliseconds:

- **Through the gateway**: turn on checks for all traffic passing through Agent Command Center, no code changes.
- **Through the Protect SDK**: call guardrail checks directly in your application code.

This guide walks through both.

## Through the gateway

In the sidebar, go to **Gateway → Guardrails**. The **Overview** tab shows your guardrail count and, once you have any configured, a table of each one's type, action, and stage. Click **Rules** to configure checks.

### Pick a check

Checks are grouped into **AI-Powered Checks**, external ML models and services such as Future AGI Eval, Llama Guard, Azure Content Safety, Presidio PII, Lakera Guard, AWS Bedrock Guardrails, HiddenLayer, and Aporia Guardrails, and **Rule-Based Checks**, structural checks like PII Detection, Content Moderation, Prompt Injection, Keyword Blocklist, Secret Detection, and Topic Restriction. This example uses **Prompt Injection**, a rule-based check.

<img src="/images/docs/evaluation/guides/guardrails/rules-full-catalog.png" alt="Guardrails Rules tab scrolled to show the full AI-Powered Checks catalog: Future AGI Eval, Llama Guard, Azure Content Safety, Presidio PII (Custom, action block, threshold 0.80), Lakera Guard, AWS Bedrock Guardrails, HiddenLayer, and Aporia Guardrails, each with a toggle and an edit pencil, with a callout pointing at the Future AGI Eval check's toggle" style={{ borderRadius: '5px' }} />
*The AI-Powered Checks catalog. Rule-Based Checks, including Prompt Injection, sit further down the same page*

### Configure the check

Click the pencil icon on the check's row. In the dialog, toggle **Enabled**, pick an **Action**, `Block`, `Warn`, or `Log`, and set the **Confidence Threshold**, from 0.0 to 1.0, that decides how sure the check must be before it fires.

<img src="/images/docs/evaluation/guides/guardrails/configure-check.png" alt="Configure Prompt Injection dialog with an Enabled toggle, an Action dropdown set to Block, and a Confidence Threshold slider set to 0.80" style={{ borderRadius: '5px' }} />
*Enable the check, choose what it does when it fires, and how sure it needs to be*

- **Block** rejects the request before it reaches the provider
- **Warn** lets the request through and flags it
- **Log** records the violation with no change to the request or response

Click **Save** on the dialog.

### Save and activate

Back on Rules, a banner reads **You have unsaved changes. Save to push guardrail config to the gateway.** Click **Save & Activate** to push the change live.

<img src="/images/docs/evaluation/guides/guardrails/save-activate.png" alt="Guardrails Rules tab with an unsaved-changes banner and the Save and Activate button highlighted at the top right" style={{ borderRadius: '5px' }} />
*Nothing reaches the gateway until you click Save & Activate*

### Confirm it's live

Back on **Overview**, the guardrails table lists everything configured on this gateway, including the one you just turned on: its type, whether it's enabled, its action, and its stage, `Before LLM` for a check that runs before the provider call.

<img src="/images/docs/evaluation/guides/guardrails/live.png" alt="Guardrails Overview tab with summary cards for Total Guardrails, Active, Disabled, and Types, and a table listing each configured guardrail with its type, enabled state, action, and stage" style={{ borderRadius: '5px' }} />
*Type, action, and stage all show in the Overview table for every guardrail you've configured*

<Note>
This dashboard configures one shared set of checks for your whole organization. For a policy scoped to a single project or virtual key, with its own `mode` (`enforce` or `monitor`), use the `/agentcc/guardrail-policies/` API described in [Guardrails](/docs/evaluation/concepts/guardrails#guardrail-structure).
</Note>

## Through the SDK (Protect)

Protect is the in-code path: the same safety dimensions as the gateway, called directly where your application produces output, so the check runs inline without a round trip to the dashboard.

It covers four dimensions: `content_moderation`, `bias_detection`, `security` (prompt injection, adversarial manipulation), and `data_privacy_compliance` (PII, GDPR/HIPAA).

<Note>
Requires `pip install ai-evaluation` and `FI_API_KEY` + `FI_SECRET_KEY` in your environment.
</Note>

```python
from fi.evals import Protect

protect = Protect()

result = protect.protect(
    inputs="How do I hack into my neighbor's WiFi?",
    protect_rules=[
        {"metric": "content_moderation"},
        {"metric": "security"},
    ],
)

print(result["status"])          # "passed" or "failed"
print(result["failed_rule"])     # which rule tripped, if any
print(result["messages"])        # action message, or the original input if it passed
```

Check inputs before they reach your LLM, or outputs before they reach your user, same method, either side:

```python
result = protect.protect(
    inputs=llm_output,
    protect_rules=[
        {"metric": "bias_detection"},
        {"metric": "data_privacy_compliance"},
    ],
    reason=True,
)

if result["status"] == "failed":
    print(f"Output blocked: {result['reasons']}")
```
