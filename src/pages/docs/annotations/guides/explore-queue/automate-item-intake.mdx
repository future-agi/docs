When reviewers need new items that meet the same conditions, use an intake rule instead of selecting each batch by hand. Run the rule once and inspect the matches in your [queue](/docs/annotations/concepts/queues-and-items) before relying on a schedule.

<Prerequisites title="Before you start">
- An existing queue, such as `Support quality review` from [Create a queue](/docs/annotations/guides/create-queue).
- Manager access on the queue. Organization and workspace admins also have [manager-level access](/docs/annotations/troubleshooting#roles-and-permissions). The **Rules** tab is manager-only; creating, editing, deleting, and running rules need that access.
</Prerequisites>

## Create the rule

1. Open **Rules** in `Support quality review`.
2. Select **Add Rule**.
3. Give the rule a name.
4. Choose a **Source type**: [Dataset Row](/docs/dataset/concepts/understanding-datasets), [Trace](/docs/observe/concepts/traces), [Span](/docs/observe/concepts/spans), [Session](/docs/observe/concepts/sessions), or [Simulation](/docs/environments).
5. Set the **Trigger** using the scan behavior below.
6. Select the target dataset, project, or agent definition for that source.

   If the queue is already scoped to a dataset or project, the field reads “Locked by this queue”.

7. Under **Conditions**, specify what should match.

   The source type determines which fields and operators are available.

8. Select **Create Rule**.

   The button stays disabled until the rule has a name and a source. The saved rule appears on **Rules**.

## Choose a scan schedule

<div class="sdk-ref-table">

| Trigger | First run | Later runs |
| --- | --- | --- |
| **Manually** | Scans the backlog against the conditions. | **Run Now** rescans the full backlog each time. It never runs unattended. |
| **Every hour**, **Daily**, **Weekly**, or **Monthly** | Scans the backlog, whether started by the schedule or by **Run Now**. | Scans what is new since the last run, including when you use **Run Now**. Allow about an hour around the scheduled time rather than expecting an exact minute. |

</div>

## Run it once and inspect the matches

1. Turn on **Enabled** in the rule's row.

   If **Run Now** is disabled, its tooltip says “Enable this rule before running it”.

2. Select **Run Now**.

   The toast either reports what was added or says “We're preparing your data” while the work finishes in the background.

3. Open **Items** after the run finishes.
4. Compare the new rows with your conditions.

   Check that a source you expect to match was added, and that one you expect not to match was not.

If another run is still active, a second **Run Now** returns “A run is already in progress for this rule”. Wait for that run to finish. If you see “Only queue managers can manage automation rules.”, check your access rather than changing the conditions.

## Edit the rule or remove it

Select the rule's row to open **Edit Automation Rule**. You can change the name, source type, conditions, or trigger. To remove the rule, select the **x** at the end of the row, then confirm.

## Know who gets notified

- When a manual **Run Now** finishes in the background, the person who ran it, its creator, and the queue managers get an email. Scheduled runs don't send that completion email.
- New-item notifications are separate. Annotators get at most one new-item email per hour and a daily summary at their local digest hour unless they've snoozed notifications. Whatever a rule adds reaches them on both, so a rule that fires while you're not watching still gets to the people who work the items.
