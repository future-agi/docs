## What a score is

A **score** is one answer, from a person or a system, to one [label](/docs/annotations/concepts/labels) about one [source](/docs/annotations/concepts/understanding-annotation). It's the single record type behind every judgment in Annotation, whether it came from working a [queue item](/docs/annotations/concepts/queues-and-items) or from scoring a single item on the spot.

A score carries the label's [value](/docs/annotations/reference/label-types-and-values), who or what produced it, and where it came from, and it looks the same regardless of which surface wrote it.

## What makes a score unique

What decides whether a new judgment becomes its own score or lands on an existing one is a key made of four fields. Change any one of them and you get a different score, not an update to an old one.

- **Source**: the trace or item the score is about
- **Label**: the label being answered
- **Annotator**: the person account that submitted it, whether they worked a queue item or scored a single item directly
- **Queue item**: the queue item the score was submitted through, if any

Say `priya@yourteam.com` scores a trace's **Response quality** while working the `Support quality review` queue. The same trace later lands in a second queue, `Escalation audit`, and she scores it again with the same label. Source, label, and annotator all match, but the queue item doesn't, so the two submissions produce two independent scores instead of one overwriting the other. The same person's judgment through two different campaigns is two separate pieces of evidence, not a correction. Score that trace on the same label again herself, this time with no queue item involved on either submission, and all four fields match: the second write lands on the existing score instead of creating a new one.

### Scores with no annotator

A score written without an annotator, through the API or an import rather than by a person, uses a narrower key: source and label alone, with no queue item and no annotator in it. Only one such score can exist for a given source and label, so writing another one there lands on that same record instead of creating a second. That second write counts as an edit, not a fresh record: the earlier value is kept in the score's history alongside it.

## What a score remembers

Editing a score's value doesn't erase what was there before. The prior value is appended to the score's history before the new one is written, so the current answer and the trail of what it used to be both live on the same record, visible wherever the source appears and in every [export](/docs/annotations/guides/export-annotations).

Every score also carries a `score_source` tag recording where it came from: `human`, `api`, `auto`, or `imported`. It's a record of origin you can read back the same way, not a setting you choose.

## A score outlives its queue item

Delete the queue item, or the queue itself, and the score stays: only the provenance link goes with it. The link from a score to a queue item is optional, telling you which campaign produced the score rather than owning it: a score's existence was never bound to a queue item in the first place. That's why an inline judgment, one with no queue item at all, and a queue judgment show up side by side wherever the source appears, and in every export. They're the same kind of record; only the provenance differs.

## Why it matters

- Scoring the same source in more than one queue never collides, so a support audit and a compliance audit can run over the same traces independently
- Correcting a score is safe: the old value doesn't disappear, it's superseded on the same record
- Every view of a source, and every export, shows one list of scores no matter which surface wrote them
