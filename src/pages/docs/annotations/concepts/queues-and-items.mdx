## A queue is the campaign, an item is what's inside it

A **queue** is the campaign. It carries:

- a status
- the [labels](/docs/annotations/concepts/labels) it's collecting answers for
- the people working it and the role each one holds
- a rule for how many independent submissions each item needs before it counts as done

An **item** is one thing inside that campaign: a trace, a span, a session, a dataset row, a prototype run, or a call from a simulation, pulled in for review. It carries a status of its own as it moves from untouched to answered, and it lands in the queue when someone adds it there (see [Add items](/docs/annotations/guides/explore-queue/add-items)).

A queue starts out in **draft**, and it only accepts annotations once someone flips it to **active**. Once every item inside it is done, an active queue completes itself, no one has to flip that switch by hand.

[Create a queue](/docs/annotations/guides/create-queue) covers that setup. This page is about what a queue and its items actually are, and how an item gets from waiting to done.

An item moves through four statuses:

- **pending**: waiting to be picked up
- **in_progress**: being worked on, and reserved for whoever opened it, so a second annotator can't pick up the same item while it's active. Reserved isn't a status of its own, it's a lock that only applies within `in_progress`
- **pending review**: submitted, but held for a reviewer's decision before it counts as done
- **completed**: done

Once every label the queue requires has been scored by enough annotators, the item is done, unless the queue calls for review, in which case it lands in pending review instead of completing outright. From there, a reviewer's approval moves it to completed, and sending it back moves it to `in_progress` so the annotator can act on the feedback.

## Roles decide who can do what

Everyone on a queue holds one or more of three roles. An **annotator** submits [scores](/docs/annotations/concepts/scores). A **reviewer** approves or sends back submissions when the queue requires it. A **manager** configures the queue and its people. Only annotators and managers can actually submit an annotation: holding the reviewer role by itself doesn't grant that.

Two shortcuts save you from adding people by hand. Whoever creates a queue is added to it as a manager the moment it's saved, and org and workspace admins act as managers on every queue automatically, without ever being added as members.

## The default queue you meet before you build one

You'll run into a queue before you ever set one up yourself. Future AGI creates a default queue automatically for every project, dataset, and agent definition, so there's always somewhere for an item to land before anyone builds a purpose-built one. It follows the same rules as any other queue, with one exception: because it's meant to keep collecting whatever lands in it indefinitely, it never auto-completes the way an ordinary queue does.

## Why it matters

The queue is what makes annotation a managed workflow instead of something one person does off to the side. The item is what keeps that workflow honest one row at a time, holding its own status so a single stuck item never quietly skews the read on how the whole batch is progressing. It's also why the same completion rule works whether one annotator is enough or five have to agree: the queue sets the bar, and every item is measured against it independently.
