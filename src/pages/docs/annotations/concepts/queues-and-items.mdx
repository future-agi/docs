## A queue is the campaign, an item is what's inside it

A **queue** is the campaign. It carries a status, the [labels](/docs/annotations/concepts/labels) it's collecting answers for, the people working it and the role each one holds, and a rule for how many independent submissions each item needs before it counts as done. An **item** is one thing inside that campaign, the actual source waiting on those answers, and it carries a status of its own as it moves from untouched to answered.

A queue starts out in draft, and it only accepts annotations once someone flips it to active. [Create a queue](/docs/annotations/guides/create-queue) covers that setup; this page is about what a queue and its items actually are, and how an item gets from waiting to done.

An item is reserved for whoever opens it, so a second annotator can't pick up the same item while the first one is still working it. It stays reserved through `in_progress`, and once every label the queue requires has been scored by enough annotators, it's done, unless the queue calls for review. In that case it lands in a pending review state instead of completing outright.

## Roles decide who can do what

Everyone on a queue holds one or more of three roles. An **annotator** submits [scores](/docs/annotations/concepts/scores). A **reviewer** approves or sends back submissions when the queue requires it. A **manager** configures the queue and its people. Only annotators and managers can actually submit an annotation: holding the reviewer role by itself doesn't grant that.

Two shortcuts save you from adding people by hand. Whoever creates a queue is added to it as a manager the moment it's saved, and org and workspace admins act as managers on every queue automatically, without ever being added as members.

## The default queue you meet before you build one

You'll run into a queue before you ever set one up yourself. Future AGI creates a default queue automatically for every project, dataset, and agent definition, so there's always somewhere for an item to land before anyone builds a purpose-built one. It follows the same rules as any other queue, with one exception: because it's meant to keep collecting whatever lands in it indefinitely, it's the one queue that never auto-completes just because everything currently inside it is done.

## Why it matters

The queue is what makes annotation a managed workflow instead of something one person does off to the side: it has an owner list, a rule for when an item counts as finished, and a status someone can flip once the batch is done. The item is what keeps that workflow honest one row at a time, holding its own status so a single stuck item never quietly skews the read on how the whole batch is progressing. It's also why the same completion rule works whether one annotator is enough or five have to agree: the queue sets the bar, and every item is measured against it independently.
