## A reusable question with a fixed answer type

A **label** is a reusable question plus the answer type it accepts. Attach it to a [queue](/docs/annotations/concepts/queues-and-items) and every annotator working that queue answers the same question, the same way, and each answer lands as a [score](/docs/annotations/concepts/scores). The full object model connecting labels, queues, and scores lives in [Understanding Annotation](/docs/annotations/concepts/understanding-annotation); this page is about the label on its own.

A few things follow from that definition.

**A label's type is locked the moment you create the label** and can't be changed afterward, though you can still edit its name, description, or settings. You can't turn a numeric label into a categorical one, for example: the type fixes the control the annotator sees, whether that's radio buttons, a number slider, a text box, stars, or a thumbs toggle, and the shape of the value written into every resulting score.

**Labels are organization-scoped.** A label belongs to the org, optionally narrowed to a [workspace](/docs/roles-and-permissions) (a grouping of projects, datasets, and queues within the org), not to any single queue.

**Editing a label changes every queue it's attached to.** A queue attaches an existing label rather than copying it, so editing a label's name, description, or settings changes what every attached queue shows and validates against from that point on, because every queue is pointing at the same row. Scores already submitted aren't touched: validation runs at submit time, so the edit only affects submissions made after it.

**A queue needs at least one label to exist.** You can't create or save a queue with zero labels attached. The label is what turns a pile of items into something answerable.

## Five types, five kinds of judgement

- **Categorical** offers a predefined set of options to choose from: a defect category, a sentiment, an escalation reason
- **Numeric** collects a score within a range: relevance from 1 to 10, a quality score out of 100
- **Text** collects free-text feedback: a correction, a rewrite, an explanation in the annotator's own words
- **Star Rating** collects a star-based rating
- **Thumbs Up/Down** collects binary pass/fail feedback

The settings each type requires and the exact validation applied to a submitted value live on [Label types & values](/docs/annotations/reference/label-types-and-values).

## Picking a type

Match the type to the shape of the judgement, not the topic:

- The answer is one of a fixed set of outcomes → Categorical
- The answer is a position on a scale → Numeric
- The answer is open-ended, in the annotator's own words → Text
- The answer is a fast quality gut-check → Star Rating
- The answer is a single yes/no call → Thumbs Up/Down

`Response quality`, for instance, is a categorical label with three options: `Good`, `Needs work`, `Wrong`. Once you know the type you want, [create a label](/docs/annotations/guides/create-label) with that type and its settings.

If an item needs more than one kind of judgement, attach more than one label to the queue rather than stretching a single label to cover two jobs.

## Why it matters

Standardizing on a small set of labels (one for quality, one for tone) keeps scores comparable across teams and projects: everyone answering "Response quality" is answering the exact same categorical question, with the exact same options.
