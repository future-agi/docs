## Label, queue, item, score

A [label](/docs/annotations/concepts/labels) is a reusable question with a fixed answer type: text, a number, a category, a star rating, thumbs up or down. Define it once and reuse it wherever you want that same question answered.

A [queue](/docs/annotations/concepts/queues-and-items) attaches one or more labels and holds the items waiting to be judged against them. A queue can't exist with zero labels; the labels are what an annotator sees when they open an item.

Each item a queue holds points at exactly one **source**: a trace, a span, a session, a call execution, a prototype run, or a dataset row. Point an item at a trace and it stays a trace, nothing else. There's no such thing as an item pointing at two sources, or none.

Every answer to a label, whether it came from working an item or from judging a source directly, becomes one [score](/docs/annotations/concepts/scores) row.

The source FK is enforced where the item and the score are written, not just assumed by convention: set an item's `trace` field and its `span`, `session`, `call_execution`, `prototype_run`, and `dataset_row` fields all stay unset, and trying to populate a second one is rejected. Whichever one kind is set is the item's source, permanently.

A score follows the same one-of-six pattern, but it doesn't need an item to exist. Work an item through a queue and the answer you submit is written as a score pointing at the item's source, with a pointer back to the item itself. Open that same source somewhere else, with no queue involved, and answer the same question directly: that's a score too, on the same source and the same label, just without the pointer back to an item, because there wasn't one to point to. It's the identical kind of record either way, so wherever a source's judgements are shown, the queue-produced ones and the directly-produced ones sit side by side.

Take a trace from the `support-agent` project. Route it into the `Support quality review` queue, and it becomes an item with only its `trace` field set. An annotator opens the item, answers the queue's `Response quality` label, and that answer lands as a score referencing the trace, the label, and the item. The same trace also turns up in a trace explorer, and someone answers `Response quality` on it there, with no queue in sight. That's a second score, same trace, same label, no item behind it. Both scores belong to the trace, and both show up wherever the trace's judgements are read back.

## Why it matters

- The source FK invariant means an item's source is unambiguous by construction. Nothing downstream has to guess or resolve which of six possible sources an item was actually about
- A score not needing an item means judging something inline is never a lesser path: it produces the same record a queue would, so filtering, exporting, or displaying judgements never has to special-case where they came from
- A label defined once and attached wherever it's needed means the same question, `Response quality` in a support queue and in a compliance queue, produces answers that land in one comparable set of scores
