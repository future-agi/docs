## About

Agent Command Center is configured at the organization level. Each organization has its own providers, guardrails, routing rules, rate limits, and budgets. Changes take effect in real time with no gateway restart required.

Configuration can be set in four places. When the same setting exists in multiple places, the most specific one wins:

```
Request headers  >  Virtual key config  >  Organization config  >  Global defaults
```

- **Request headers**: Per-request overrides sent via `x-agentcc-*` headers, such as `x-agentcc-cache-ttl` or `x-agentcc-timeout`. See [headers reference](/docs/command-center/api/headers).
- **Virtual key config**: Settings attached to a specific [virtual key](/docs/command-center/concepts/virtual-keys) (e.g. allowed models and providers).
- **Organization config**: Org-level settings configured via the dashboard or the control-plane API.
- **Global defaults**: Gateway-wide defaults. For self-hosted deployments, these come from `config.yaml`. For the cloud gateway, these are platform defaults.

For example, if the org sets cache TTL to 60 seconds but a request sends `x-agentcc-cache-ttl: 5m`, that request uses a 5-minute TTL. The header takes a Go duration (`30s`, `5m`, `1h`); a bare number such as `300` is ignored.

## Example configuration

A minimal organization configuration with failover, a model fallback, caching, a per-key rate limit, and a monthly budget. Provider API keys are not part of this object: add providers under **Gateway > Providers**, and the control plane merges them into the config it sends to the gateway.

<Tabs items={["Dashboard", "cURL"]}>

<Tab title="Dashboard">

Go to **Gateway > Settings** in the Future AGI dashboard, open the **Org Config** tab, and click **Edit Config** (or **Create Custom Config** if the org has none yet). Each section (Routing, Cache, Rate Limiting, Budgets, Model Map, and others) has its own tab. Saving creates a new config version and pushes it to the gateway.

</Tab>

<Tab title="cURL">

Each `POST` to the control plane creates a new config version from the request body and makes it active:

```bash
curl -X POST https://api.futureagi.com/agentcc/org-configs/ \
  -H "X-Api-Key: YOUR_API_KEY" \
  -H "X-Secret-Key: YOUR_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "routing": {
      "failover": {
        "enabled": true,
        "max_attempts": 2,
        "on_status_codes": [429, 500, 502, 503, 504],
        "on_timeout": true
      },
      "model_fallbacks": {"gpt-4o": ["claude-sonnet-4-6"]}
    },
    "cache": {"enabled": true, "default_ttl": 3600},
    "rate_limiting": {"enabled": true, "per_key_rpm": 600},
    "budgets": {
      "enabled": true,
      "org_limit": 500.0,
      "org_period": "monthly",
      "hard_limit": true,
      "warn_threshold": 0.8
    },
    "change_description": "Failover, cache, rate limit and budget"
  }'
```

Sections you leave out of the body are reset to their defaults in the new version, so send every section you want to keep. `GET https://api.futureagi.com/agentcc/org-configs/active/` returns the current version to start from. The gateway rejects unknown keys inside a section (for example `cache.ttl_seconds`); such a save returns 400 and the previous version stays active. Cache `default_ttl` is in seconds and `warn_threshold` is a fraction (`0.8` = 80%).

</Tab>

</Tabs>

**Self-hosted config.yaml:**

```yaml
providers:
  openai:
    base_url: "https://api.openai.com"
    api_key: "${OPENAI_API_KEY}"
    api_format: "openai"
    models: ["gpt-4o", "gpt-4o-mini"]
  anthropic:
    base_url: "https://api.anthropic.com"
    api_key: "${ANTHROPIC_API_KEY}"
    api_format: "anthropic"
    headers:
      anthropic-version: "2023-06-01"
    models: ["claude-sonnet-4-6", "claude-haiku-4-5"]

routing:
  default_strategy: round-robin
  failover:
    enabled: true
    max_attempts: 2
    on_status_codes: [429, 500, 502, 503, 504]
    on_timeout: true
  model_fallbacks:
    gpt-4o: ["claude-sonnet-4-6"]

cache:
  enabled: true
  default_ttl: 1h

budgets:
  enabled: true
  default_period: monthly
  warn_threshold: 0.8
  org:
    limit: 500.00
    hard: true
```

Every provider needs `base_url` and `api_format`, or a `type` with a preset (such as `groq` or `mistral`) that fills them in. Without them the gateway refuses to start with `provider "openai": base_url is required`. Durations in `config.yaml`, such as `default_ttl`, use Go duration syntax (`1h`).

<Note>
Changes to organization configuration push to the gateway in real time. No restart or redeployment needed. A self-hosted gateway reads `config.yaml` at startup and does not watch the file: `POST /-/reload` re-reads it but applies only the `routing` section, so restart the gateway for any other change.
</Note>

## SDK configuration

The Agent Command Center SDK can attach `x-agentcc-*` headers at two levels: **client-level** (every request) and **per-request** (a single call). A `GatewayConfig` is turned into headers by `to_headers()`, but the gateway acts on only some of them today:

| `GatewayConfig` setting | Sent as | Applied by the gateway |
|---|---|---|
| `CacheConfig(namespace=...)` | `x-agentcc-cache-namespace` | Yes |
| `CacheConfig(force_refresh=True)` | `x-agentcc-cache-force-refresh: true` | Yes |
| `TimeoutConfig(total=...)` (Python) | `x-agentcc-request-timeout` in milliseconds | Yes |
| `CacheConfig(ttl=...)` | `x-agentcc-cache-ttl` as a bare number of seconds | No. The gateway needs a Go duration such as `5m`, so set the header yourself. |
| `retry`, `fallback`, `load_balance`, `routing`, `mirror`, `guardrails`, cache `strategy` | The `x-agentcc-config` JSON header (guardrails also as `x-agentcc-guardrail-policy`) | No. The gateway does not read these headers. Set retries, failover and guardrails in the org config or `config.yaml`. The routing strategy and mirroring take effect only in a self-hosted `config.yaml`. |

For retries from your application, use the SDK's own `max_retries` option, which retries 408, 429, 500, 502, 503, and 504 responses on the client side.

### Client-level config

Pass the settings to the client constructor:

<CodeGroup>
```python Python
from agentcc import AgentCC, GatewayConfig, CacheConfig

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com",
    max_retries=3,  # retried by the SDK
    config=GatewayConfig(cache=CacheConfig(namespace="prod")),
    default_headers={"x-agentcc-cache-ttl": "5m"},
)

# All requests through this client use these settings
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
)
```

```typescript TypeScript
import { AgentCC } from "@agentcc/client";

const client = new AgentCC({
  apiKey: "sk-agentcc-your-key",
  baseUrl: "https://gateway.futureagi.com",
  maxRetries: 3, // retried by the SDK
  config: { cache: { namespace: "prod" } },
  defaultHeaders: { "x-agentcc-cache-ttl": "5m" },
});

const response = await client.chat.completions.create({
  model: "gpt-4o",
  messages: [{ role: "user", content: "Hello" }],
});
```
</CodeGroup>

### Per-request overrides

Override config for a single request using `GatewayConfig.to_headers()`:

```python
from agentcc import GatewayConfig, CacheConfig

override = GatewayConfig(cache=CacheConfig(force_refresh=True))

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What time is it?"}],
    extra_headers=override.to_headers(),
)
```

You can also set individual headers directly:

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={
        "x-agentcc-cache-force-refresh": "true",
        "x-agentcc-cache-namespace": "staging",
    },
)
```

### Using with other clients

If you're not using the Agent Command Center SDK, use `create_headers()` to generate `x-agentcc-*` headers for any OpenAI-compatible client (OpenAI SDK, LiteLLM, LangChain, cURL, etc.):

```python
from openai import OpenAI
from agentcc import create_headers

headers = create_headers(
    cache_namespace="prod",
    trace_id="trace-abc",
    metadata={"team": "ml", "env": "production"},
)
headers["x-agentcc-cache-ttl"] = "10m"  # Go duration; create_headers(cache_ttl=...) sends bare seconds, which the gateway ignores

client = OpenAI(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com/v1",
    default_headers=headers,
)
```

See [Request & response headers](/docs/command-center/api/headers) for the full list of `x-agentcc-*` headers.

## Model mapping

Model mapping pins a model name to a provider. When a request asks for `gpt-4o`, the gateway sends it to the provider you mapped it to, under the same model name. Use it when more than one provider serves a model, or to route a model the provider's model list doesn't declare.

<Tabs items={["Dashboard", "API"]}>

<Tab title="Dashboard">

Go to **Gateway > Settings**, open the **Org Config** tab, click **Edit Config**, and add model-to-provider pairs on the **Model Map** tab.

</Tab>

<Tab title="API">

Add a `model_map` section to the body of the `POST https://api.futureagi.com/agentcc/org-configs/` call in [Example configuration](#example-configuration). The call replaces every section, so send it together with the sections you already have:

```json
{
  "model_map": {
    "gpt-4o": "openai",
    "claude-sonnet-4-6": "anthropic"
  }
}
```

</Tab>

</Tabs>

**Self-hosted config.yaml:**

```yaml
model_map:
  gpt-4o: openai
  claude-sonnet-4-6: anthropic
```

Requests keep using the model name:

```python
response = client.chat.completions.create(
    model="gpt-4o",  # served by the provider "openai"
    messages=[{"role": "user", "content": "Hello"}],
)
```

<Note>
If you send a model name that doesn't match any configured provider or model map entry, the gateway returns a 404 with the message: `model "X" not found in any configured provider. Configure model_map or use 'provider/model' format.`
</Note>

## GatewayConfig reference

The `GatewayConfig` dataclass groups the SDK's per-request config objects:

| Field | Type | Description |
|---|---|---|
| `cache` | `CacheConfig` | Cache strategy, TTL, namespace, force refresh |
| `retry` | `RetryConfig` | Max retries, backoff settings, status codes |
| `fallback` | `FallbackConfig` | Fallback model targets and trigger conditions |
| `load_balance` | `LoadBalanceConfig` | Load balancing strategy and targets |
| `guardrails` | `GuardrailConfig` | Input/output guardrail policies and settings |
| `routing` | `ConditionalRoutingConfig` | Conditional routing rules |
| `mirror` | `TrafficMirrorConfig` | Shadow traffic configuration |
| `timeout` | `TimeoutConfig` | Connect, read, write, and total timeouts |

`GatewayConfig.to_headers()` serializes the entire config to `x-agentcc-config` as a JSON header, plus individual headers for cache, guardrail, and timeout settings. The gateway does not read `x-agentcc-config`, so only the settings marked "Yes" in the [SDK configuration](#sdk-configuration) table take effect.
