## About

Agent Command Center is configured at the organization level. Each organization has its own providers, guardrails, routing rules, rate limits, and budgets. A saved organization config takes effect with no gateway restart.

Configuration can be set in four places. When the same setting exists in multiple places, the most specific one wins, except for the settings listed after the example below:

```
Request headers  >  Virtual key config  >  Organization config  >  Global defaults
```

- **Request headers**: Per-request overrides sent via `x-agentcc-*` headers or `GatewayConfig.to_headers()`. See [headers reference](/docs/command-center/api/headers).
- **Virtual key config**: Settings attached to a specific [virtual key](/docs/command-center/concepts/virtual-keys) (e.g. rate limits, allowed models, guardrails).
- **Organization config**: Org-level settings configured via the dashboard or admin API.
- **Global defaults**: Gateway-wide defaults. For self-hosted deployments, these come from `config.yaml`. For the cloud gateway, these are platform defaults.

For example, on a self-hosted gateway with the response cache on, if the org sets cache TTL to 60 seconds but a request sends `x-agentcc-cache-ttl: 300`, that request uses a 300-second TTL.

These settings do not follow that order:

- **Request-log content mode**: the most restrictive value applies, of the organization's `privacy.content_mode`, the key's `log_content`, the request's `x-agentcc-log-content` header, and the gateway's default. See [Is my data stored?](/docs/command-center#frequently-asked-questions).
- **Retries and timeouts**: a request's retry headers (`x-agentcc-max-attempts`, `x-agentcc-retry-delay-ms`, `x-agentcc-backoff`) can only tighten the organization's retry settings, never loosen them, and a request's timeout header is held at the gateway's maximum request timeout.
- **Rate limits**: a key's own limit is used in place of the organization's per-key limit, and the organization's other limits still count the key's requests: a request is refused when any limit that applies to it is reached. See [Rate limiting](/docs/command-center/features/rate-limiting).
- **Guardrails**: an organization's checks run as the organization set them, except a check that shares its name with a rule in a self-hosted gateway's `config.yaml`, which runs as that rule. A request header or a key's overrides change only the rules in a self-hosted gateway's own `config.yaml`, such a rule included. See [Guardrails](/docs/command-center/features/guardrails#per-request-guardrail-overrides).

## Configuration sections

| Section | What it controls | Feature page |
|---|---|---|
| `providers` | Which LLM services are available and their credentials | [Supported providers](/docs/command-center/features/providers) |
| `routing` | How requests are distributed across providers | [Routing](/docs/command-center/features/routing) |
| `cache` | Whether the organization's responses are cached (`enabled`), and their default TTL in seconds (`default_ttl`) | [Caching](/docs/command-center/features/caching) |
| `rate_limiting` | Maximum request rate per key or organization | [Rate limiting](/docs/command-center/features/rate-limiting) |
| `budgets` | Spending limits per period and alert thresholds | [Rate limiting & budgets](/docs/command-center/features/rate-limiting) |
| `guardrails` | Safety checks on requests and responses | [Guardrails](/docs/command-center/features/guardrails) |
| `cost_tracking` | Cost calculation and attribution settings | [Cost tracking](/docs/command-center/features/cost-tracking) |
| `tool_policy` | Which tool and function calls are permitted | [Virtual keys](/docs/command-center/concepts/virtual-keys) |
| `ip_acl` | Which source IP addresses are allowed | [Virtual keys](/docs/command-center/concepts/virtual-keys) |
| `model_map` | Which of the organization's providers serves a model name, and aliases (see [below](#model-mapping)) | - |
| `alerting` | Email or webhook alerts for budget events and errors | - |
| `privacy` | Request-log content mode (`privacy.content_mode`) and retention days (`privacy.retention`) | [Overview FAQ: Is my data stored?](/docs/command-center#frequently-asked-questions) |
| `mcp` | Model Context Protocol integration settings | - |
| `audit` | Audit log configuration and retention | - |

Sections with a feature page are described there. The rest of this page covers the config hierarchy and how to set config from code.

## Example configuration

A minimal organization configuration with two providers, a model fallback chain, retries, and caching:

<Tabs items={["Dashboard", "Organization config", "Self-hosted config.yaml"]}>

<Tab title="Dashboard">

Go to **Gateway > Settings** in the Future AGI dashboard and open the **Org Config** tab. Each section (providers, guardrails, routing, cache, rate limiting, budgets, model map, and more) has its own tab. (**Full Config (Read-Only)**, the tab next to **Org Config**, shows the gateway's own config, not the organization's.) A save is pushed to the gateway, with no restart. On Future AGI's hosted gateway, the **Cache** tab is read-only, because the response cache is off there.

</Tab>

<Tab title="Organization config">

```json
{
  "providers": {
    "openai": {
      "api_key": "sk-...",
      "base_url": "https://api.openai.com",
      "api_format": "openai",
      "models": ["gpt-4o", "gpt-4o-mini"],
      "enabled": true
    },
    "anthropic": {
      "api_key": "sk-ant-...",
      "base_url": "https://api.anthropic.com",
      "api_format": "anthropic",
      "models": ["claude-sonnet-4-6", "claude-haiku-4-5"],
      "enabled": true
    }
  },
  "routing": {
    "model_fallbacks": {
      "gpt-4o": ["claude-sonnet-4-6"]
    },
    "retry": {
      "enabled": true,
      "max_retries": 2
    }
  },
  "cache": {
    "enabled": true,
    "default_ttl": 3600
  }
}
```

A provider serves requests only while `enabled` is `true`, and it is called at its `base_url` in its `api_format`. The `cache` section takes effect only on a self-hosted gateway whose config file turns the response cache on. For budgets, see [Rate limiting & budgets](/docs/command-center/features/rate-limiting).

</Tab>

<Tab title="Self-hosted config.yaml">

```yaml
providers:
  openai:
    base_url: "https://api.openai.com"
    api_format: "openai"
    api_key: "${OPENAI_API_KEY}"
    models: ["gpt-4o", "gpt-4o-mini"]
  anthropic:
    base_url: "https://api.anthropic.com"
    api_format: "anthropic"
    api_key: "${ANTHROPIC_API_KEY}"
    models: ["claude-sonnet-4-6", "claude-haiku-4-5"]

routing:
  model_fallbacks:
    gpt-4o:
      - claude-sonnet-4-6
  retry:
    enabled: true
    max_retries: 2

cache:
  enabled: true
  default_ttl: 1h
```

</Tab>

</Tabs>

<Note>
A saved organization config is pushed to the gateway, with no restart or redeployment. A self-hosted gateway does not watch its config file: `POST /-/reload` with the admin token re-reads the file and reloads its routing settings.
</Note>

## SDK configuration

The Agent Command Center SDK lets you set config at two levels: **client-level** (applies to every request) and **per-request** (overrides for a single call).

### Client-level config

Pass a `GatewayConfig` to the client constructor:

<CodeGroup>
```python Python
from agentcc import AgentCC, GatewayConfig, CacheConfig

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="http://localhost:8080",
    config=GatewayConfig(
        cache=CacheConfig(ttl=300, namespace="prod"),
    ),
)

# All requests through this client send these settings
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
)
```

```typescript TypeScript
import { AgentCC } from "@agentcc/client";

const client = new AgentCC({
  apiKey: "sk-agentcc-your-key",
  baseUrl: "http://localhost:8080",
  config: {
    cache: { ttl: 300, namespace: "prod" },
  },
});

const response = await client.chat.completions.create({
  model: "gpt-4o",
  messages: [{ role: "user", content: "Hello" }],
});
```
</CodeGroup>

The gateway applies the cache section's `ttl`, `namespace` and `force_refresh` when it runs the response cache (a self-hosted gateway with the cache on; the hosted gateway runs none). It does not apply a `retry` or `fallback` section: it names such sections in the `x-agentcc-config-ignored` response header. Set retries and fallbacks in your organization's [routing config](/docs/command-center/features/routing) instead. The [GatewayConfig reference](#gatewayconfig-reference) says what the gateway does with each section.

### Per-request overrides

Override config for a single request using `GatewayConfig.to_headers()`:

```python
from agentcc import GatewayConfig, CacheConfig

override = GatewayConfig(cache=CacheConfig(force_refresh=True))

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What time is it?"}],
    extra_headers=override.to_headers(),
)
```

You can also set individual headers directly:

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={
        "x-agentcc-cache-force-refresh": "true",
        "x-agentcc-cache-namespace": "staging",
    },
)
```

### Using with other clients

If you're not using the Agent Command Center SDK, use `create_headers()` to generate `x-agentcc-*` headers for any OpenAI-compatible client (OpenAI SDK, LiteLLM, LangChain, cURL, etc.):

```python
from openai import OpenAI
from agentcc import create_headers, GatewayConfig, CacheConfig

headers = create_headers(
    config=GatewayConfig(cache=CacheConfig(ttl=600)),
    trace_id="trace-abc",
    metadata={"team": "ml", "env": "production"},
)

client = OpenAI(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com/v1",
    default_headers=headers,
)
```

See [Request & response headers](/docs/command-center/api/headers) for the full list of `x-agentcc-*` headers.

## Model mapping

`model_map` sends a model name to a provider you choose: each entry maps a model name to a provider ID.

For your organization's API keys, a mapped name goes only to the provider it names, and only when that is one of your organization's own providers, enabled and with a key. An entry that names any other provider is not used. When that provider lists exactly one model and not the requested name, a chat completion is sent as that model, so the name works as an alias. Otherwise the request is sent under the name it used. Embeddings, images, audio, rerank, `/v1/completions`, and `/v1/responses` use a mapped provider only when they can send the requested name unchanged.

A name with no entry goes to the first of your providers that lists it, in provider-ID order, unless a [routing strategy](/docs/command-center/features/routing#routing-strategies) chooses among them.

<Tabs items={["Dashboard", "Organization config", "Self-hosted config.yaml"]}>

<Tab title="Dashboard">

Go to **Gateway > Settings > Org Config** and open the **Model Map** tab to add model-to-provider pairs: a model name and the ID of one of your providers. For an alias, first add a provider under **Gateway > Providers** that lists only the model the alias should call, then map the alias to that provider.

</Tab>

<Tab title="Organization config">

```json
{
  "providers": {
    "openai-mini": {
      "api_key": "sk-...",
      "base_url": "https://api.openai.com",
      "api_format": "openai",
      "models": ["gpt-4o-mini"],
      "enabled": true
    }
  },
  "model_map": {
    "my-fast-model": "openai-mini"
  }
}
```

The provider `openai-mini` lists only `gpt-4o-mini`, so a chat completion for `my-fast-model` is sent to it as `gpt-4o-mini`. To point the alias at another model, change the model that provider lists, or map the alias to another provider.

</Tab>

<Tab title="Self-hosted config.yaml">

In the gateway's `config.yaml`, `model_map` maps a model name to the ID of one of the gateway's providers, and the request is sent under the name it used: it is not an alias. For an alias, give the name a routing target with a `model_override`:

```yaml
providers:
  openai:
    base_url: "https://api.openai.com"
    api_format: "openai"
    api_key: "${OPENAI_API_KEY}"
    models: ["gpt-4o", "gpt-4o-mini"]

routing:
  targets:
    my-fast-model:
      - provider: openai
        model_override: gpt-4o-mini
```

These settings apply to the providers in `config.yaml`, which serve the gateway's internal keys. See [Self-hosted models](/docs/command-center/features/self-hosted-models) for which keys each kind of provider serves.

</Tab>

</Tabs>

Then use the alias in requests:

```python
response = client.chat.completions.create(
    model="my-fast-model",  # sent to the provider as gpt-4o-mini
    messages=[{"role": "user", "content": "Hello"}],
)
```

<Note>
With your organization's API key, a model name that none of your providers lists, and that `model_map` does not send to one of them, is refused with 403 (`permission_denied`): `model "X" is not available for this API key`. A request served by the providers in a self-hosted gateway's `config.yaml`, on a gateway with more than one provider, gets 404 (`model_not_found`) for a name that no provider, `model_map` entry, or routing target knows: `model "X" not found in any configured provider. Configure model_map or use 'provider/model' format.`
</Note>

## GatewayConfig reference

The `GatewayConfig` dataclass groups per-request config. `GatewayConfig.to_headers()` serializes the entire config to `x-agentcc-config` as a JSON header, plus individual headers for the cache, guardrail, and timeout settings. This is what the gateway does with each section:

| Field | Type | What the gateway does with it |
|---|---|---|
| `cache` | `CacheConfig` | Applies `ttl`, `namespace`, and `force_refresh` as the cache headers, on a gateway that runs the response cache. The other cache fields (`strategy`, `semantic_threshold` and the rest) are not read |
| `timeout` | `TimeoutConfig` | `total` (seconds) is sent as `x-agentcc-request-timeout` and sets the request's timeout, up to the gateway's maximum. `connect`, `read`, `write`, and `pool` are not applied |
| `guardrails` | `GuardrailConfig` | Leave it unset. The SDK sends its guardrail names in `x-agentcc-guardrail-policy`, which takes a mode (`log-only`, `disabled`, or `strict`), not names, so where guardrail checks run for the request it is refused (403, or 400 `invalid_policy`) |
| `retry`, `fallback`, `load_balance`, `routing`, `mirror` | | Not read. The gateway names them in the `x-agentcc-config-ignored` response header |
