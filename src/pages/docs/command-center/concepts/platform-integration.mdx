## About

Agent Command Center can run standalone or connect to a Future AGI control plane. Configured request-log and telemetry export paths connect eligible gateway traffic to the platform.

---

## Agent Command Center → Observe

With OpenTelemetry enabled and sampling permitting export, gateway spans can carry available model, provider, latency, token, cost and guardrail fields. Model prompt/completion attributes additionally require deployment body capture; request logs are a separate path. On self-hosted gateways these trace switches are `otel.enabled` and `otel.include_bodies`, and the configured collector determines the export destination.

From Observe you can:
- View exported request traces with the metadata retained by their capture controls
- Monitor latency percentiles (p50, p95, p99) per model and provider
- Track cost breakdown by model, provider, team, or custom metadata dimension
- See provider health trends and error rate history
- Drill into sessions (`x-agentcc-session-id`) to trace conversation-level patterns

**How to tag requests for attribution:**

```python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-...",
    base_url="https://gateway.futureagi.com",
    metadata={"team": "search", "feature": "query-expansion", "env": "production"},
)
```

Metadata retained in enabled, sampled spans successfully delivered to Observe can appear as filterable dimensions, subject to the span metadata controls.

## Agent Command Center → Evaluate

Agent Command Center's guardrails are backed by the Future AGI evaluation engine. When you configure a **Future AGI Evaluation** guardrail, Agent Command Center sends each request/response pair to the evaluation engine in real time. The engine runs model-level checks — not just regex — to detect hallucinations, quality regressions, and policy violations.

This is the key differentiator from guardrail products that rely on pattern matching: evaluation guardrails score outputs using the same models and metrics you use in offline eval.

The `futureagi` guardrail type connects Agent Command Center to Evaluate:

```python
config = client.guardrails.configs.create(
    name="Production quality gate",
    rules=[
        {
            "name": "futureagi",          # Future AGI evaluation engine
            "stage": "post",
            "mode": "sync",
            "action": "warn",
            "threshold": 0.7,
        }
    ],
)
```

Available guardrail scores and decisions can be retained in eligible gateway request logs when request logging is enabled and control-plane delivery succeeds.

## Shadow experiments (self-hosted)

For eligible self-hosted traffic, configure gateway-level `routing.mirror` with mirroring enabled and matching sampling rules. Storing production/shadow comparison data additionally requires `routing.mirror.capture_results: true` (off by default); mirroring alone does not store results.

Captured results can be sent to the control plane's `/agentcc/webhook/shadow-results/` endpoint when `control_plane.url` is configured. Ingestion also requires accepted webhook authentication, valid results and matching, non-deleted experiment records; delivery can fail. A per-request SDK option alone does not enable capture or establish synchronization with Evaluate. See [Self-hosted shadow experiments](/docs/command-center/features/shadow-experiments) for configuration.

## Metadata as the connective tissue

The `x-agentcc-metadata` header (or `metadata=` parameter in the SDK) is how you connect Agent Command Center data to your application's dimensions. Caller-supplied metadata is omitted from request logs in content mode `none`; span metadata uses separate controls and requires enabled, sampled export. Tags are not automatically present in every connected product:

| Tag | Use in Observe (retained, queryable span metadata) |
|-----|---------------------------------------------------|
| `metadata.team` | Cost breakdown by team |
| `metadata.feature` | Latency per feature |
| `metadata.user_id` | Per-user cost |
| `metadata.env` | Separate prod/staging metrics |

For shadow experiments, the shadow-result webhook stores comparison fields and an experiment ID, not caller-supplied request metadata. These tags do not automatically provide experiment scoping, segmentation or isolation through that path.
