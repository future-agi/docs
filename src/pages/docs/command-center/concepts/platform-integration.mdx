## About

Agent Command Center can run standalone or as the data collection and enforcement layer of the Future AGI platform. Request logging is on by default, so requests are recorded in the gateway's request log, and configured export paths can feed Observe, Evaluate, and Protect.

---

## Agent Command Center → Observe

With request logging on (the default), each model/API request through Agent Command Center is recorded in the gateway's **request log**: request, response metadata, latency, token counts, cost, provider used, routing decision, and guardrail outcomes. Prompt and response bodies are kept only when `logging.request_logging.include_bodies` is on (off by default). The request log is stored by Agent Command Center itself, not in Observe. View it under **Agent Command Center > Logs** and **Sessions**, where you can:
- Inspect each request with its recorded metadata
- Track cost by model, provider, or custom metadata dimension
- Drill into sessions (`x-agentcc-session-id`) to trace conversation-level patterns

Gateway requests appear in **Observe** as [traces](/docs/observe/concepts/traces) only when the gateway's OpenTelemetry export is on and pointed at the Future AGI collector. The export is a self-hosted gateway setting, and none of the bundled configs (Docker Compose, Helm, or `config.example.yaml`) turn it on. With it on, each request becomes one [span](/docs/observe/concepts/spans) in the Observe project you name, and can nest under your application's [traceAI](/docs/observe/concepts/traceai) spans. See [OpenTelemetry export](/docs/command-center/features/observability#opentelemetry-export) for the `otel` block, and [Send gateway spans to self-hosted Observe](/docs/command-center/features/observability#send-gateway-spans-to-self-hosted-observe) for the setup.

**How to tag requests for attribution:**

```python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-...",
    base_url="https://gateway.futureagi.com",
    metadata={"team": "search", "feature": "query-expansion", "env": "production"},
)
```

These metadata fields are recorded with each request in the request log, and you can filter **Agent Command Center > Logs** by any metadata key and value. When OpenTelemetry export is on and a request is sampled, they're also written to the span as `agentcc.metadata.<key>` (controlled by `otel.metadata_attributes`), so you can filter and group on them in Observe too.

## Agent Command Center → Evaluate

Agent Command Center's guardrails are backed by the Future AGI evaluation engine. When you configure a **Future AGI Evaluation** guardrail, Agent Command Center sends each request/response pair to the evaluation engine in real time. The engine runs model-level checks — not just regex — to detect hallucinations, quality regressions, and policy violations.

This is the key differentiator from guardrail products that rely on pattern matching: evaluation guardrails score outputs using the same models and metrics you use in offline eval.

The `futureagi` guardrail type connects Agent Command Center to Evaluate:

```python
config = client.guardrails.configs.create(
    name="Production quality gate",
    rules=[
        {
            "name": "futureagi",          # Future AGI evaluation engine
            "stage": "post",
            "mode": "sync",
            "action": "warn",
            "threshold": 0.7,
        }
    ],
)
```

Guardrail scores and decisions are recorded in the gateway [request log](/docs/command-center/features/observability#which-requests-are-logged).

## Shadow experiments (self-hosted)

For eligible self-hosted traffic, configure gateway-level `routing.mirror` with mirroring enabled and matching sampling rules. Storing production/shadow comparison data additionally requires `routing.mirror.capture_results: true` (off by default); mirroring alone does not store results.

Captured results can be sent to the control plane's `/agentcc/webhook/shadow-results/` endpoint when `control_plane.url` is configured. Ingestion also requires accepted webhook authentication, valid results and matching, non-deleted experiment records; delivery can fail. A per-request SDK option alone does not enable capture or establish synchronization with Evaluate. See [Self-hosted shadow experiments](/docs/command-center/features/shadow-experiments) for configuration.

## Metadata as the connective tissue

The `x-agentcc-metadata` header (or `metadata=` parameter in the SDK) is how you connect Agent Command Center data to your application's dimensions. Tags set on requests are stored in the request log and, when OpenTelemetry export is on, on the span in Observe. They are not automatically present in every connected product:

| Tag | Use in Observe (retained, queryable span metadata) |
|-----|---------------------------------------------------|
| `metadata.team` | Cost breakdown by team |
| `metadata.feature` | Latency per feature |
| `metadata.user_id` | Per-user cost |
| `metadata.env` | Separate prod/staging metrics |

For shadow experiments, the shadow-result webhook stores comparison fields and an experiment ID, not caller-supplied request metadata. These tags do not automatically provide experiment scoping, segmentation or isolation through that path.
