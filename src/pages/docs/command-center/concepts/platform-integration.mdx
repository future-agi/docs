## About

This page covers two places where Agent Command Center meets the rest of Future AGI. A **Future AGI Evaluation** guardrail check runs your Future AGI evaluations on each request before the provider is called. And the metadata you set on requests lets you filter **Gateway > Request Logs** by any of its keys and group **Gateway > Analytics** by the `application` and `service` keys.

---

## Future AGI evaluations as a guardrail

```
Your application
        │
        ▼
┌───────────────┐   message text   ┌────────────────┐
│ Agent Command │ ───────────────→ │ Future AGI     │
│ Center        │ ←─────────────── │ evaluation API │
│               │   eval result    └────────────────┘
└───────────────┘
        │  request, unless blocked
        ▼
  LLM provider
```

Agent Command Center's guardrails can call the Future AGI evaluation engine. A **Future AGI Evaluation** guardrail check sends the text of each request's messages to Future AGI's evaluation API before the provider is called, and runs the evaluations you choose on it, by eval ID (in the dashboard, your Protect templates). Unlike the pattern-based checks, it uses Future AGI's evaluation models.

When an evaluation fails, the check triggers like any other: with the action `warn`, the request goes on and the response says so in its guardrail headers; with `block`, the request is refused with 403 `content_blocked`.

The check is an entry in your organization's guardrail checks whose `config` has `"provider": "futureagi"` (in the dashboard, **Gateway > Guardrails > Rules**, **Future AGI Eval**):

```json
{
  "guardrails": {
    "checks": {
      "futureagi-eval": {
        "enabled": true,
        "action": "warn",
        "config": {
          "provider": "futureagi",
          "eval_ids": ["your-eval-id"],
          "api_key": "your-fi-api-key",
          "secret_key": "your-fi-secret-key"
        }
      }
    }
  }
}
```

`api_key` and `secret_key` are your Future AGI API keys. Without them, or without an eval ID, the check cannot run and triggers on every request. See [Guardrails](/docs/command-center/features/guardrails) for actions and the other check types.

Guardrail decisions are recorded with each request in the request log (**Gateway > Request Logs**).

## Request metadata

Tag requests with metadata: the `x-agentcc-metadata` header, or in the SDK `metadata=` on the client (every request it sends) or `request_metadata=` on one request.

```python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-...",
    base_url="https://gateway.futureagi.com",
    metadata={"application": "search", "service": "query-expansion", "team": "search"},
)
```

The gateway keeps these keys with each request in the request log, with the exceptions listed under [Cost attribution](/docs/command-center/features/cost-tracking#cost-attribution). In the console:

- **Gateway > Request Logs**, **Filters**: **Application** and **Service** match the `application` and `service` keys, and **Custom Tags** matches any key you type as `key:value` (for example `team:search`).
- **Gateway > Analytics**: the **Usage**, **Cost** and **Errors** tabs group requests by application and service, as well as by model and provider.
