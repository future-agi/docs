## About

Agent Command Center is not a standalone gateway. It's the data collection and enforcement layer of the Future AGI platform. Every request through Agent Command Center is recorded in its request log, and can feed Observe, Evaluate, and Protect.

---

## Agent Command Center → Observe

Every request through Agent Command Center is recorded in the gateway's **request log**: request, response metadata, latency, token counts, cost, provider used, routing decision, and guardrail outcomes. The request log is stored by Agent Command Center itself, not in Observe. View it under **Gateway > Request Logs** and **Gateway > Sessions**, where you can:
- Inspect each request with its full metadata
- Track cost by model, provider, or custom metadata dimension
- Drill into sessions (`x-agentcc-session-id`) to trace conversation-level patterns

Gateway requests appear in **Observe** as [traces](/docs/observe/concepts/traces) only when the gateway's OpenTelemetry export is on and pointed at the Future AGI collector. The export is a self-hosted gateway setting, and none of the bundled configs (Docker Compose, Helm, or `config.example.yaml`) turn it on. With it on, each request becomes one [span](/docs/observe/concepts/spans) in the Observe project you name, and can nest under your application's [traceAI](/docs/observe/concepts/traceai) spans. See [OpenTelemetry export](/docs/command-center/features/observability#opentelemetry-export) for the `otel` block, and [Send gateway spans to self-hosted Observe](/docs/command-center/features/observability#send-gateway-spans-to-self-hosted-observe) for the setup.

**How to tag requests for attribution:**

```python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-...",
    base_url="https://gateway.futureagi.com",
    metadata={"team": "search", "feature": "query-expansion", "env": "production"},
)
```

These metadata fields are recorded with each request in the request log, and you can filter **Gateway > Request Logs** by any metadata key and value. When OpenTelemetry export is on, they're also written to the span as `agentcc.metadata.<key>`, so you can filter and group on them in Observe too.

## Agent Command Center → Evaluate

Agent Command Center's guardrails are backed by the Future AGI evaluation engine. When you configure a **Future AGI Evaluation** guardrail, Agent Command Center sends each request to the evaluation engine in real time, before the model call. The engine runs model-level checks, not just regex, to detect hallucinations, quality regressions, and policy violations.

This is the key differentiator from guardrail products that rely on pattern matching: evaluation guardrails score outputs using the same models and metrics you use in offline eval.

A Future AGI Evaluation check connects Agent Command Center to Evaluate. Add it under **Gateway > Guardrails**, or as a check in the org config's `guardrails.checks` with `"provider": "futureagi"` in its `config`. The SDKs do not have a guardrail management API. See [Guardrails](/docs/command-center/features/guardrails) for the check settings.

Guardrail scores and decisions are logged in both Agent Command Center (for traffic analysis) and Evaluate (for quality trend tracking).

## Agent Command Center → Evaluate (shadow experiments)

Shadow experiments in Agent Command Center generate comparison data that feeds directly into Evaluate.

When you configure traffic mirroring, Agent Command Center collects:
- Production model responses
- Shadow model responses
- Latency and token deltas for each request pair

These paired results appear in Evaluate, where you can:
- Run automated scoring on response pairs using evaluation metrics
- Calculate win rates across hundreds or thousands of production requests
- Make evidence-based migration decisions before switching providers

**Enabling shadow experiments:**

Mirroring runs from the gateway's own config, not from the request. The SDK's `GatewayConfig(mirror=...)` travels in the `x-agentcc-config` header, which the gateway does not read, so it mirrors nothing. On a self-hosted gateway, add mirror rules to `config.yaml`:

```yaml
routing:
  mirror:
    enabled: true
    capture_results: true   # store shadow results and send them to the control plane
    rules:
      - source_model: "gpt-4o"
        target_provider: "anthropic"
        target_model: "claude-sonnet-4-6"
        sample_rate: 0.1    # mirror 10% of gpt-4o traffic
```

Mirror rules saved in an org config (`routing.mirror`) are accepted but not applied by the gateway today; only the gateway-level `routing.mirror` mirrors traffic. Streaming requests are not mirrored.

With `capture_results: true` and `control_plane.url` set, the gateway sends shadow results to the control plane for analysis.

## Metadata as the connective tissue

The `x-agentcc-metadata` header (or `metadata=` parameter in the SDK) is how you connect Agent Command Center data to your application's dimensions. Tags set on requests are stored in the request log and, when OpenTelemetry export is on, on the span in Observe:

| Tag | Use in Observe | Use in Evaluate | Use in Evaluate (experiments) |
|-----|---------------|-----------------|-------------------|
| `metadata.team` | Cost breakdown by team | Quality trends per team | Experiment scoping by team |
| `metadata.feature` | Latency per feature | Regression alerts per feature | A/B test segmentation |
| `metadata.user_id` | Per-user cost | User-level quality flags | User cohort experiments |
| `metadata.env` | Separate prod/staging metrics | Different quality thresholds | Shadow test isolation |
