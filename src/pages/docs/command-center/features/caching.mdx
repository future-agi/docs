## About

Agent Command Center caches LLM responses server-side. A cache hit returns the stored response without calling the provider. The `X-AgentCC-Cache` response header shows cache status (`hit_exact`, `hit_semantic`, or `miss`), and `X-AgentCC-Cost` is not sent on exact cache hits, since no provider tokens were consumed.

No client-side cache logic needed. Caching works for all providers through the same configuration.

<Note>
The response cache is off on Future AGI's hosted gateway (`gateway.futureagi.com`), for every organization: no request is served from cache there, and the dashboard shows the cache settings as not enforced on this gateway. The rest of this page applies to a self-hosted gateway.
</Note>

A response is cached only when the gateway's config file sets `cache.enabled: true` and the caller's organization has its own cache setting turned on.

On a self-hosted gateway, send requests with an API key that belongs to an organization, and turn that organization's cache on with `"cache": {"enabled": true}` in its config (see [Organizations](/docs/command-center/admin/organizations)). A key with no organization is never served from the cache.

---

## When to use

- **Repeated queries**: FAQ bots, common customer questions, template-based prompts
- **Development and testing**: Avoid burning API credits on the same test prompts
- **High-traffic endpoints**: Reduce provider costs for popular queries

## Exact match vs semantic cache

| | Exact match | Semantic cache |
|---|---|---|
| **How it matches** | Identical request parameters (same messages, model, temperature) | Cosine similarity between character n-gram vectors of the last user message, for the same model (see [How semantic matching works](#how-semantic-matching-works)) |
| **Example** | Same prompt, character for character | "What is the capital of France?" matches "What's the capital of France?" (similarity 0.905). "Tell me today's weather" does not match "What's the weather today?" (0.542) |
| **Lookup** | A hash lookup | The message is vectorized and compared with stored entries |
| **Use case** | Deterministic queries, templates | Near-identical wording: differences in case, punctuation, or a word or two |
| **Cost on hit** | Not calculated (the cost plugin is skipped) | The cost plugin still runs |

<Note>
Streaming requests bypass cache entirely - both on read and write. Cache only applies to non-streaming completions.
</Note>

<Note>
Guardrails that check the request run before the cache lookup, so a request they refuse gets their error and no cached response. Guardrails that check the response still run on what is served.
</Note>

### How semantic matching works

The semantic cache does not call an embedding model. For each cacheable request, the gateway takes the text of the last user message, lowercases it, and turns every run of characters that are not letters or digits into one space. It counts the text's character 3-grams and 4-grams into a fixed-length vector (256 dimensions by default) by hashing each n-gram with FNV-1a, then scales the vector to unit length. With the in-memory and Qdrant backends, and with Pinecone on an index that uses the cosine metric, a stored response is served when the cosine similarity between the two vectors is at or above the threshold (`0.85` by default) and the stored entry is for the same model and the same organization. The closest such entry wins.

Only the last user message is compared: the system prompt, earlier messages, and parameters such as `temperature` are not. Because the comparison is on spelling, not meaning, a paraphrase in different words usually misses, and two questions that differ in one important word can score close to the threshold: "What is the capital of France?" and "What is the capital of Spain?" score 0.826.

## Configuration

| Setting | Description | Default |
|---|---|---|
| `enabled` | Enable or disable caching | `false` |
| `default_ttl` | Time-to-live for cached entries (e.g. `5m`, `1h`) | `5m` |
| `max_entries` | Maximum number of cached entries (LRU eviction) | `10000` |
| `semantic.enabled` | Add the semantic cache after the exact-match lookup | `false` |
| `semantic.threshold` | Cosine similarity, 0 to 1, that a stored entry needs to be served | `0.85` |
| `semantic.dimensions` | Length of the n-gram vector | `256` |
| `semantic.backend` | `memory`, `qdrant`, or `pinecone` | `memory` |

The `semantic` settings are read only from the gateway's config file. An organization's config turns its cache on or off and sets its default TTL; it cannot turn on the semantic cache.

From the SDK's cache settings, the gateway reads `ttl`, `namespace`, and `force_refresh` for each request. Whether a response is cached is decided by the gateway's and the organization's settings: `enabled` and `strategy` sent with a request are not applied, and the response names them in the `x-agentcc-config-ignored` header.

**Self-hosted config.yaml:**

```yaml
cache:
  enabled: true
  default_ttl: 5m
  max_entries: 10000
  semantic:              # optional
    enabled: true
    threshold: 0.85
    dimensions: 256
    backend: memory      # or qdrant, pinecone
```

## Cache namespaces

Partition the exact-match cache into isolated buckets. Each namespace keeps its own exact-match entries. Semantic matching is per organization and model.

Use the `x-agentcc-cache-namespace` request header or set it in the SDK config:

```python
# Per-request namespace
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={"x-agentcc-cache-namespace": "staging"},
)
```

Common namespace patterns:
- **Environment isolation**: `prod`, `staging`, `dev`
- **A/B testing**: different namespaces per experiment variant

## Per-request cache control

Override cache behavior on individual requests using headers:

| Header | Value | Effect |
|---|---|---|
| `x-agentcc-cache-force-refresh` | `true` | Bypass cache, fetch fresh response, update cache |
| `Cache-Control` | `no-store` | Disable caching for this request entirely |
| `x-agentcc-cache-ttl` | seconds | Override TTL for this specific response |
| `x-agentcc-cache-namespace` | string | Route to a specific cache namespace |

## Cache backends

**Exact match backends:**

| Backend | Use case |
|---|---|
| In-memory (default) | Single-instance deployments, development |
| Redis | Multi-instance deployments, shared cache across replicas |

**Semantic cache backends** (vector stores):

| Backend | Notes |
|---|---|
| In-memory | Development and small-scale deployments |
| Qdrant | Self-hosted vector search. The gateway creates its collection with the cosine distance if it does not exist |
| Pinecone | Managed vector database. The gateway does not create the index: create it with the cosine metric and as many dimensions as `semantic.dimensions` |

Each backend stores the gateway's n-gram vectors and finds the closest one. None of them computes embeddings.

<Note>
Backend configuration is set at the gateway level in `config.yaml`. The hosted gateway at `gateway.futureagi.com` does not run the response cache.
</Note>
