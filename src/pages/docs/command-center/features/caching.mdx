## About

Agent Command Center caches LLM responses server-side. A cache hit returns an instant response without calling the provider. The `x-agentcc-cache` response header shows the cache status, and `x-agentcc-cost` is left out of exact cache hits, since no provider tokens were consumed.

| `x-agentcc-cache` | Meaning |
|---|---|
| `hit_exact` | Served from the exact match cache |
| `hit_semantic` | Served from the semantic cache |
| `hit_conditional` | Reserved for edge cache conditional requests (`If-None-Match`, with `cache.edge` on). The gateway does not pass `If-None-Match` to the cache today, so you won't see this value |
| `miss` | Not in the cache (or `x-agentcc-cache-force-refresh` / `Cache-Control: no-cache` skipped the lookup); the provider was called |
| `skip` | Caching is on but the request is not cacheable: a streaming request, `Cache-Control: no-store`, or an endpoint the cache does not cover |
| `skip_org_disabled` | Caching is not turned on in the organization's config |

No client-side cache logic needed. Caching works for all providers through the same configuration.

---

## When to use

- **Repeated queries**: FAQ bots, common customer questions, template-based prompts
- **Development and testing**: Avoid burning API credits on the same test prompts
- **High-traffic endpoints**: Reduce provider costs for popular queries

---

## Exact match vs semantic cache

| | Exact match | Semantic cache |
|---|---|---|
| **How it matches** | Identical request parameters (same messages, model, temperature) | Similar wording of the last user message. Everything else in the request (model, other messages, tools, parameters) must match exactly |
| **Example** | Same prompt, character for character | "What is the capital of France?" matches "What's the capital of France?" (similarity 0.91) |
| **Latency** | Fastest: hash lookup | Slightly higher: the gateway builds a vector from the text and searches for the closest entry |
| **Use case** | Deterministic queries, templates | Small wording changes: punctuation, case, contractions |
| **Cost on hit** | No cost recorded (the cost and credits plugins are skipped, and `x-agentcc-cost` is not set) | Priced from the model catalogue on the cached response's token usage |

The semantic cache does not use an embedding model. The gateway turns the text into a vector of hashed character 3-grams and 4-grams (256 dimensions by default) and compares vectors by cosine similarity, so it matches text that is spelled alike, not text that means the same thing. "What's the weather today?" and "Tell me today's weather" score 0.54 and do not match at the default threshold of 0.85, while "What is the capital of France?" and "What is the capital of Germany?" score 0.79. Raise the threshold if near-identical questions with different answers share a cache.

<Note>
Streaming requests bypass cache entirely - both on read and write. Cache only applies to non-streaming completions.
</Note>

<Warning>
The cache lookup runs before [guardrails](/docs/command-center/features/guardrails). An exact or semantic hit returns the stored response without a provider call, and guardrails that check the request (Pre stage) do not run on that request, so a guardrail you enable after an entry is cached does not apply to it until the entry expires. Guardrails that check the response (Post stage) still run on what is served.
</Warning>

## Configuration

There is no `strategy` setting. The exact match cache is always on when caching is on, and the semantic cache is a second layer you turn on with `cache.semantic.enabled` in a self-hosted `config.yaml`; a request that misses the exact cache is then looked up in the semantic cache. In the organization's config, only `enabled` and `default_ttl` take effect; `max_entries` and the `semantic` settings below apply only in `config.yaml`.

| Setting | Description | Default |
|---|---|---|
| `enabled` | Enable or disable caching | `false` |
| `default_ttl` | Time-to-live for cached entries (e.g. `5m`, `1h`). The organization's config also accepts `5m` and stores it as seconds (`300`) | `5m` |
| `backend` | Exact-match backend: `memory`, `redis`, `disk`, `s3`, `azure-blob`, or `gcs` | `memory` |
| `max_entries` | Maximum number of cached entries (LRU eviction) | `10000` |
| `semantic.enabled` | Turn on the semantic cache layer | `false` |
| `semantic.threshold` | Minimum cosine similarity (0 to 1) for a semantic hit | `0.85` |
| `semantic.dimensions` | Size of the n-gram vector | `256` |
| `semantic.backend` | `memory`, `qdrant`, `weaviate`, or `pinecone` | `memory` |
| `semantic.max_entries` | Maximum number of entries in the in-memory semantic cache | `50000` |

Caching is also opt-in per organization: the gateway skips the cache (`x-agentcc-cache: skip_org_disabled`) for any request whose organization config does not turn caching on. A gateway with only `config.yaml` and no organization config gives `skip_org_disabled` on every request, so also enable caching in the organization's config.

<Tabs items={["Dashboard", "Self-hosted config.yaml"]}>

<Tab title="Dashboard">

Go to **Gateway > Settings**, open the **Org Config** tab, and select the **Cache** tab. Turn on caching, set the default TTL, and save. The organization's config accepts a duration such as `5m` or a number of seconds, and stores it as seconds (for example `300`).

</Tab>

<Tab title="Self-hosted config.yaml">

```yaml
cache:
  enabled: true
  default_ttl: 5m
  max_entries: 10000
  semantic:
    enabled: true
    threshold: 0.85
    dimensions: 256
    backend: memory
```

</Tab>

<Note>
The SDK's `CacheConfig` does not configure the gateway cache. Its `enabled` and `strategy` fields travel in the `x-agentcc-config` header, which the gateway does not read, and its `ttl` is sent as a bare number of seconds, which the gateway ignores (see the `x-agentcc-cache-ttl` header below). Only its `namespace` and `force_refresh` take effect.
</Note>

## Cache namespaces

Partition cache into isolated buckets. Each namespace maintains its own entries, so entries from one environment don't leak into another.

Use the `x-agentcc-cache-namespace` request header, or set `namespace` in the SDK's `CacheConfig`, which sends the same header:

```python
# Per-request namespace
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={"x-agentcc-cache-namespace": "staging"},
)
```

Common namespace patterns:
- **Environment isolation**: `prod`, `staging`, `dev`
- **Multi-tenant isolation**: one namespace per customer
- **A/B testing**: different namespaces per experiment variant

## Per-request cache control

Override cache behavior on individual requests using headers:

| Header | Value | Effect |
|---|---|---|
| `x-agentcc-cache-force-refresh` | `true` | Bypass cache, fetch fresh response, update cache |
| `Cache-Control` | `no-store` | Disable caching for this request entirely |
| `x-agentcc-cache-ttl` | duration, e.g. `300s`, `10m` | Override TTL for this specific response. A bare number such as `300` is ignored, and the default TTL applies |
| `x-agentcc-cache-namespace` | string | Route to a specific cache namespace |

<Tabs items={["Python (Agent Command Center SDK)", "Python (OpenAI SDK)", "cURL"]}>

<Tab title="Python (Agent Command Center SDK)">

```python
# Force a fresh response (bypass cache)
response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What is AI?"}],
    extra_headers={"x-agentcc-cache-force-refresh": "true"},
```

## Cache backends

**Exact match backends:**

| Backend | Use case |
|---|---|
| In-memory (`memory`, default) | Single-instance deployments, development |
| Redis (`redis`) | Multi-instance deployments, shared cache across replicas |
| Disk (`disk`) | Single instance, cache survives restarts |
| Amazon S3 (`s3`) | Shared cache in an S3 bucket |
| Azure Blob Storage (`azure-blob`) | Shared cache in an Azure Blob container |
| Google Cloud Storage (`gcs`) | Shared cache in a GCS bucket |

**Semantic cache backends** (vector stores):

| Backend | Notes |
|---|---|
| In-memory | Development and small-scale deployments |
| Qdrant | Production-grade self-hosted vector search |
| Weaviate | Self-hosted or managed vector database |
| Pinecone | Managed vector database |

<Note>
Backend configuration is set at the gateway level in `config.yaml`. If you're using the cloud gateway at `gateway.futureagi.com`, the backend is managed for you.
</Note>
