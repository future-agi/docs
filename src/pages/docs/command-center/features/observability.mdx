When one gateway request is slow, costly or blocked by a guardrail, you need to find that request again. Agent Command Center logs every request and response and propagates a [trace](/docs/observe/concepts/traces) ID you can follow from your application to the gateway log. A [self-hosted gateway](/docs/self-hosting) can also export each request as a [span](/docs/observe/concepts/spans) to [Observe](/docs/observe) and serve Prometheus metrics.

Request logging is on by default, with no extra setup. Prometheus metrics and [OpenTelemetry](/docs/tracing/concepts/otel) export are off until you turn them on.

<Prerequisites title="Before you start">
- A configured model provider and a [Command Center gateway key](/docs/command-center/quickstart) for the request. For a Python example, initialize the appropriate client as shown in the quickstart.
- For export to your own Observe install, a separate [workspace API key and secret key](/docs/admin-settings/api-keys) from that install and access to the gateway configuration.
</Prerequisites>

## Request logging

Every request through Agent Command Center is logged with:

- Request ID, trace ID, [session](/docs/observe/concepts/sessions) ID
- Model requested and model actually used
- Provider that handled the request
- Input/output token counts
- Cost
- Latency
- Cache status (hit/miss/skip)
- Guardrail results
- Any errors or fallback events

Logs sync to the Future AGI dashboard automatically. View them in **Agent Command Center > Logs**.

### Log levels

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Level | What's logged |
|---|---|
| `error` | Failed requests, provider errors, guardrail blocks |
| `warn` | Fallbacks, slow requests, budget warnings |
| `info` | Every request (default) |
| `debug` | Full request/response bodies, header details |

</div>

For self-hosted deployments, set the log level in `config.yaml`:

```yaml
logging:
  level: info
```

## Distributed tracing

For cURL, substitute your gateway key for the placeholder. When testing your own deployment, also replace the hosted URL with your gateway's chat completions URL. For Python, start with the initialized client from the quickstart.

1. Send one request through the gateway with `x-agentcc-trace-id` set.

   The gateway propagates the ID to downstream provider calls and logs. If you omit it, the gateway generates one.

<Tabs items={["Agent Command Center SDK", "OpenAI SDK", "cURL"]}>

<Tab title="Python (Agent Command Center SDK)">

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    trace_id="trace-from-my-app-abc123",
    user_id="user-42",
)

print(response.agentcc.trace_id)    # trace-from-my-app-abc123
print(response.agentcc.provider)    # openai
print(response.agentcc.latency_ms)  # 342
print(response.agentcc.cost)        # 0.00015
```

</Tab>

<Tab title="Python (OpenAI SDK)">

```python
raw = client.chat.completions.with_raw_response.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={
        "x-agentcc-trace-id": "trace-from-my-app-abc123",
        "x-agentcc-user-id": "user-42",
    },
)
print(raw.headers.get("x-agentcc-trace-id"))
print(raw.headers.get("x-agentcc-cost"))
```

</Tab>

<Tab title="cURL">

```bash
curl -i https://gateway.futureagi.com/v1/chat/completions \
  -H "Authorization: Bearer sk-agentcc-your-key" \
  -H "x-agentcc-trace-id: trace-from-my-app-abc123" \
  -H "x-agentcc-user-id: user-42" \
  -H "Content-Type: application/json" \
  -d '{"model": "gpt-4o", "messages": [{"role": "user", "content": "Hello"}]}'
# Look for x-agentcc-trace-id in response headers
```

</Tab>

</Tabs>

2. Read the trace ID in the response.

   The Agent Command Center SDK returns it as `response.agentcc.trace_id`. With the OpenAI SDK or cURL, read the `x-agentcc-trace-id` [response header](/docs/command-center/api/headers).

3. Open **Agent Command Center > Logs**.
4. Find the request with that ID. Use the same ID to correlate it with your application logs.

   A gateway log entry doesn't imply that an Observe span was exported. To check that second destination, configure export below and send a new request.

## OpenTelemetry export

Self-hosted gateways can emit one OpenTelemetry span per request to any OTLP-compatible backend. Span attributes follow the `gen_ai.*` semantic conventions, and each span carries the gateway's trace ID as `agentcc.trace_id`, so you can match it to its row in the request log above. The `otel` block in the gateway's `config.yaml` turns export on; it's off by default. Export never waits on the collector, so a slow or unreachable one doesn't slow requests down.

Sending to your own Future AGI install? Go to [Send gateway spans to self-hosted Observe](#send-gateway-spans-to-self-hosted-observe).

```yaml
otel:
  enabled: true
  exporter: otlp
  endpoint: "http://otel-collector:4318" # /v1/traces is appended when the URL has no path
  protocol: "http/protobuf"
  service_name: "agentcc-gateway"
  headers:                               # sent on every export request
    Authorization: "${OTEL_AUTH_HEADER}" # for example "Bearer <token>"
```

<Warning>
The gateway speaks OTLP over **HTTP with protobuf** only, so point it at your collector's OTLP/HTTP port (usually **4318**), not the gRPC port 4317. Setting `enabled: true` without `exporter: otlp` prints spans to stdout instead of exporting them.
</Warning>

With `enabled: true` and `exporter: otlp`, the gateway refuses to start when:

- `endpoint` is missing, or isn't an absolute `http(s)` URL
- a header value is empty (usually a `${VAR}` that isn't set)
- `protocol` is `grpc` or `http/json`

### Export settings

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Key | Default | Description |
|---|---|---|
| `enabled` | `false` | Turns span creation on |
| `exporter` | `stdout` | `stdout` or `otlp` |
| `endpoint` | none | Collector base URL; required for `otlp` |
| `protocol` | `http/protobuf` | The only supported value |
| `headers` | none | Headers sent with every export, for collector authentication. Use `${VAR}` to keep credentials out of the file |
| `service_name` | `agentcc-gateway` | `service.name` resource attribute |
| `sample_rate` | `1.0` | Fraction of requests that get a span. `0` or unset is treated as `1.0`; to stop spans, set `enabled: false` |
| `attributes` | none | Extra OTLP resource attributes |
| `include_bodies` | `false` | Attach the prompt and completion (`input.value` / `output.value`), redacted with the organization's privacy settings like the request log |
| `trace_propagation` | `false` | Honor an inbound W3C `traceparent` so the gateway span nests under the caller's span |
| `metadata_attributes` | `true` | Also emit each caller metadata key as `agentcc.metadata.<key>`, next to the `metadata` JSON object |
| `body_attributes` | `true` | Emit unknown scalar request-body fields as `agentcc.body.<key>` attributes |
| `capture_headers` | none | Allowlist of request headers to copy onto the span. Well-known credential headers (`Authorization`, `Cookie`, `x-api-key` and similar) are never copied |

</div>

### Send gateway spans to self-hosted Observe

When you self-host Future AGI alongside the gateway, point the `otel` block at your install's `fi-collector`, the service that receives traces for Observe.

Add the block to the gateway's config file:

- **Docker Compose:** the file `AGENTCC_CONFIG_PATH` in `.env` names, relative to the repository root. If it's still the bundled `agentcc-gateway/config.example.yaml`, copy it to `agentcc-gateway/config.yaml` and set `AGENTCC_CONFIG_PATH=agentcc-gateway/config.yaml` first (see [LLM gateway](/docs/self-hosting/configuration/system#llm-gateway))
- **[Helm](/docs/self-hosting/helm):** under `agentccGateway.config.otel`, or in your own ConfigMap if you set `agentccGateway.existingConfigMap`

Create the API key and set its two variables (step 2) before you restart anything: the gateway won't start while a `${VAR}` in the block is unset.

```yaml
otel:
  enabled: true
  exporter: otlp
  endpoint: "http://127.0.0.1:4318"   # see step 1 for your setup
  protocol: "http/protobuf"
  headers:
    X-Api-Key: "${AGENTCC_OTEL_API_KEY}"
    X-Secret-Key: "${AGENTCC_OTEL_SECRET_KEY}"
  attributes:
    project_name: "my-chatbot"        # Observe project the spans land in
  include_bodies: false               # see step 4
  trace_propagation: false            # see step 5
```

1. **Endpoint.** `fi-collector` takes OTLP/HTTP on port 4318. Use the address the gateway can reach it on:

   | Setup | `endpoint` |
   |---|---|
   | Standalone (`docker-compose.yml`) | `http://127.0.0.1:4318` |
   | Distributed (`docker-compose.distributed.yml`) | `http://fi-collector:4318` |
   | Helm | `http://<fullname>-fi-collector:4318` |

   In Standalone the gateway runs in the same `app` container as the collector. With Helm, `<fullname>` is `futureagi` for a release named `futureagi`, and `kubectl get svc` shows the exact Service name.

2. **API keys.** The collector refuses an export without an API key pair. Create one in your own install (not app.futureagi.com) under **Build > Keys**, which Owners, Admins and workspace Admins can see. You get an API key and a secret key, and the secret key is shown only once, so copy both. Set them as `AGENTCC_OTEL_API_KEY` and `AGENTCC_OTEL_SECRET_KEY`:

   - Docker Compose: in `.env`
   - Helm: in a Secret listed under `agentccGateway.extraEnvFrom`

   Don't reuse the names `FI_API_KEY` and `FI_SECRET_KEY`. Every service in the install reads `.env`, and the API and the simulation runner read those two names too, so they'd start using your key.

3. **Project.** Spans land in the Observe project named by the `project_name` resource attribute, in the workspace the API key belongs to. If no project has that name yet, it's created on the first export. Pick a name no other project in that workspace uses: projects are matched by name, so an existing project with that name gets the spans. Without a `project_name`, the collector refuses the export.

4. **Prompt and completion bodies.** `include_bodies` is off by default, so spans carry metrics and metadata but no message content. Turning it on sends prompts and completions to Observe, redacted with your organization's privacy settings, the same way the request log is. The request log has its own switch, `logging.request_logging.include_bodies`.

5. **Nesting under traceAI spans.** If your application is instrumented with [traceAI](/docs/observe/concepts/traceai), sends its spans to the same `project_name`, and passes a W3C `traceparent` header on its calls to the gateway, set `trace_propagation: true`. The gateway span then nests under your application's span instead of starting a second trace. Leave it off otherwise: any OpenTelemetry instrumentation in your application can send a `traceparent`, and the gateway span would then point at a parent Observe never receives, so the trace isn't listed. Only a `traceparent` marked as sampled is honored.

6. **Apply and check.** The gateway reads its config once, at startup, so restart it after every change:

   - Docker Compose, first time or after editing `.env`: `docker compose up -d` (`docker compose restart` doesn't re-read `.env`)
   - Docker Compose, after editing only the config file: `docker compose restart app` in Standalone, or `docker compose restart agentcc-gateway` in Distributed (`docker compose up -d` doesn't pick up a config-file change)
   - Helm: `helm upgrade`. If you use `existingConfigMap`, or changed only the Secret, also run `kubectl rollout restart deployment/<fullname>-agentcc-gateway`

### Match the exported span to the request

1. Send a new tagged request through the restarted gateway.
2. Find its trace ID in **Agent Command Center > Logs**.
3. Open the `my-chatbot` project in Observe, in the workspace the API key belongs to.

   The request shows up as a trace.

4. Compare the span's `agentcc.trace_id` with the ID from the log.

   You should see the same gateway ID in both places. With `include_bodies: false`, the span can match even though it has no prompt or completion.

### If the request succeeds but no span arrives

If nothing arrives, check the gateway's logs: `docker compose logs app` in Standalone, `docker compose logs agentcc-gateway` in Distributed, or `kubectl logs deployment/<fullname>-agentcc-gateway` with Helm. A refused export never fails the request, so the logs are where it shows:

- `otlp exporter: collector rejected the credentials, dropping spans`: the key pair is wrong, expired or disabled
- `otlp exporter: collector rejected batch, dropping spans`: another refusal, such as a missing `project_name`
- `otlp exporter: max retries exceeded, dropping spans`: the gateway can't reach the endpoint, or the collector kept answering with a 5xx or 429 (the line's `reason` says which)

<Warning>
In Standalone the gateway runs in the same `app` container as the API, the UI and the collector. If the gateway refuses to start (an unset variable or an invalid value), the whole container stops and restarts in a loop, and the UI goes down with it. `docker compose logs app` shows a `failed to load config` line naming the `otel` setting. Fix or remove the block, then run `docker compose up -d` again.
</Warning>

## Session tracking

Group related requests into sessions for conversation-level analytics. Set `x-agentcc-session-id` on each request in a conversation:

```python
session_id = "user-123-conversation-456"
messages = []

# Each turn in the conversation shares the same session_id
messages.append({"role": "user", "content": "What's the capital of France?"})
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    session_id=session_id,
    user_id="user-123",
)
messages.append({"role": "assistant", "content": response.choices[0].message.content})

messages.append({"role": "user", "content": "What's its population?"})
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    session_id=session_id,
    user_id="user-123",
)
```

Sessions appear in the dashboard under **Agent Command Center > Sessions** and show:
- Total requests in the session
- Cumulative cost
- Models and providers used
- Timeline of requests

## Metrics

Self-hosted gateways can serve Prometheus metrics on the `/-/metrics` endpoint. Metrics are off by default.

### Turn on metrics

Add a top-level `prometheus` block to the gateway's `config.yaml`, then restart the gateway:

```yaml
prometheus:
  enabled: true
```

- The route is always `/-/metrics`; a `path` key is accepted but ignored
- The endpoint needs the gateway's admin token, set as `admin.token` in `config.yaml` or the `AGENTCC_ADMIN_TOKEN` environment variable, sent as `Authorization: Bearer <token>`
- With no admin token set, the endpoint answers `401` to every request

For where the config file lives on the self-hosted platform, the restart command, and a `curl` check, see [LLM gateway metrics](/docs/self-hosting/production/monitoring#llm-gateway-metrics).

### Available metrics

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Metric | Type | Labels | Description |
|---|---|---|---|
| `agentcc_requests_total` | Counter | `model`, `provider`, `status` (`ok` or `error`) | Requests processed |
| `agentcc_errors_total` | Counter | `model`, `provider` | Requests that ended in an error |
| `agentcc_tokens_input_total` | Counter | `model`, `provider` | Input tokens |
| `agentcc_tokens_output_total` | Counter | `model`, `provider` | Output tokens |
| `agentcc_cost_microdollars_total` | Counter | `model`, `provider` | Cost in millionths of a US dollar; divide by 1,000,000 for USD |
| `agentcc_cache_hits_total` | Counter | `type` (`exact` or `semantic`) | Cache hits |
| `agentcc_cache_misses_total` | Counter | None | Cache misses |
| `agentcc_request_duration_ms` | Histogram | `model`, `provider` | Request latency in milliseconds |
| `agentcc_uptime_seconds` | Gauge | None | Seconds since the gateway started |

</div>

Each `agentcc_*` series except uptime appears on its first event, for example `agentcc_errors_total` after the first failed request. The endpoint also carries `video_*` series for video generation jobs.

### Scrape configuration

```yaml
# prometheus.yml
scrape_configs:
  - job_name: "agentcc-gateway"
    scrape_interval: 15s
    metrics_path: "/-/metrics"
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/agentcc-admin-token   # holds the gateway's admin token
    static_configs:
      - targets: ["agentcc-gateway:8080"]   # the gateway's host and port
```

## Alerting

Configure alerts to get notified about issues. See [Cost tracking > Budget alerts](/docs/command-center/features/cost-tracking#budget-alerts) for alert configuration.

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| Event | When it fires |
|---|---|
| Budget threshold crossed | Spend exceeds configured percentage |
| Error rate spike | Error rate exceeds threshold over a time window |
| Latency spike | P95 latency exceeds threshold |
