## About

Agent Command Center speaks six provider APIs natively (OpenAI, Anthropic, Google Gemini including Vertex AI, AWS Bedrock, Azure OpenAI, and Cohere) and connects any other endpoint that implements the OpenAI API, cloud or self-hosted, by its base URL. Add a provider once with its API key, then switch between providers by changing the model name in your request.

## Cloud providers

| Provider | Type | `api_format` | Auth | Notes |
|---|---|---|---|---|
| OpenAI | `openai` | `openai` | API key | Native format |
| Anthropic | `anthropic` | `anthropic` | API key | Auto-translated to OpenAI format |
| Google Gemini | `gemini` | `gemini` | API key | Auto-translated to OpenAI format |
| Google Vertex AI | `vertexai` | `gemini` | Bearer token | Uses GCP project/location headers |
| AWS Bedrock | `bedrock` | `bedrock` | SigV4 | Requires AWS region, cross-region failover supported |
| Azure OpenAI | `azure` | `azure` | API key | Requires `api_version`, supports Azure AD bearer auth |
| Cohere | `cohere` | `cohere` | API key | Auto-translated to OpenAI format |
| Groq | `groq` | `openai` | API key | OpenAI-compatible |
| Mistral AI | `mistral` | `openai` | API key | OpenAI-compatible |
| Together AI | `together` | `openai` | API key | OpenAI-compatible |
| Fireworks AI | `fireworks` | `openai` | API key | OpenAI-compatible |
| DeepInfra | `deepinfra` | `openai` | API key | OpenAI-compatible |
| Perplexity | `perplexity` | `openai` | API key | OpenAI-compatible |
| Cerebras | `cerebras` | `openai` | API key | OpenAI-compatible |
| xAI (Grok) | `xai` | `openai` | API key | OpenAI-compatible |
| OpenRouter | `openrouter` | `openai` | API key | OpenAI-compatible |
| Hugging Face | `huggingface` | `openai` | API key | Inference API |
| Anyscale | `anyscale` | `openai` | API key | OpenAI-compatible |
| Replicate | `replicate` | `openai` | API key | OpenAI-compatible |

In the gateway's `config.yaml`, a `type` field has no effect: every provider needs its own `base_url` and `api_format`.

Providers marked "OpenAI-compatible" use the same wire format as OpenAI. No translation needed. Providers with native formats (Anthropic, Gemini, Bedrock, Cohere) are automatically translated by Agent Command Center - your code stays identical regardless of which provider handles the request.

<Tip>
Agent Command Center supports all models from each provider, including new releases. Use any model name your provider supports.
</Tip>

## Self-hosted providers

Ollama, vLLM, LM Studio, HuggingFace TGI, LocalAI and any other server that implements the OpenAI API connect the same way: set `api_format: "openai"` and point `base_url` at the server. Agent Command Center has no preset for these servers, so a `type` value such as `ollama` or `vllm` has no effect. In the gateway's `config.yaml`, a provider without a `models` list gets its models from the server's `/v1/models` endpoint when the gateway starts. [Self-hosted models](/docs/command-center/features/self-hosted-models) has configuration examples.

<Note>
Your self-hosted endpoint must be reachable from the Agent Command Center. Use a tunnel (ngrok, Cloudflare Tunnel), a cloud VM with a public IP, or deploy behind a reverse proxy.

On a self-hosted Future AGI install, a provider you add in the dashboard can use a private or LAN address only after you set `AGENTCC_ALLOW_PRIVATE_PROVIDER_URLS=true`. Loopback addresses such as `localhost` are never allowed. See [Private and local provider URLs](/docs/command-center/features/self-hosted-models#private-and-local-provider-urls).
</Note>

## Adding a provider

<Tabs items={["Dashboard", "Organization config"]}>

<Tab title="Dashboard">

1. Go to **Gateway > Providers** in the Future AGI dashboard
2. Click **Add Provider**
3. Select the provider from the list
4. Enter your API key and any required settings
5. Click **Save**

</Tab>

<Tab title="Organization config">

The same providers in the `providers` section of the organization's config (in the dashboard, **Gateway > Settings > Org Config**, **Providers** tab). The key of each entry is the provider ID:

```json
{
  "providers": {
    "openai": {
      "api_key": "sk-your-openai-key",
      "base_url": "https://api.openai.com",
      "api_format": "openai",
      "models": ["gpt-4o", "gpt-4o-mini"],
      "enabled": true
    },
    "anthropic": {
      "api_key": "sk-ant-your-key",
      "base_url": "https://api.anthropic.com",
      "api_format": "anthropic",
      "models": ["claude-sonnet-4-6", "claude-haiku-4-5"],
      "enabled": true
    }
  }
}
```

A provider serves your organization's keys only while `enabled` is `true` and it has credentials. A request goes to one of your providers that lists the requested model, unless the [model map](/docs/command-center/concepts/configuration#model-mapping) names another.

</Tab>

</Tabs>

<Warning>
Provider API keys are stored encrypted and never exposed in API responses.
</Warning>

## Switching providers at request time

Change the model name to route to a different provider. Same code, same API, different LLM.

<Tabs items={["Python (Agent Command Center SDK)", "Python (OpenAI SDK)", "LiteLLM", "cURL"]}>

<Tab title="Python (Agent Command Center SDK)">

```python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com",
)

# OpenAI
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}]
)

# Anthropic - same code, different model
response = client.chat.completions.create(
    model="claude-sonnet-4-6",
    messages=[{"role": "user", "content": "Hello"}]
)

# Google Gemini
response = client.chat.completions.create(
    model="gemini-2.0-flash",
    messages=[{"role": "user", "content": "Hello"}]
)
```

</Tab>

<Tab title="Python (OpenAI SDK)">

```python
from openai import OpenAI

# Works with the OpenAI SDK - just swap base_url and api_key
client = OpenAI(
    base_url="https://gateway.futureagi.com/v1",
    api_key="sk-agentcc-your-key",
)

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}]
)
```

</Tab>

<Tab title="LiteLLM">

```python
import litellm

response = litellm.completion(
    model="openai/gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com/v1",
)
```

</Tab>

<Tab title="cURL">

```bash
curl -X POST https://gateway.futureagi.com/v1/chat/completions \
  -H "Authorization: Bearer sk-agentcc-your-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```

</Tab>

</Tabs>

## Self-hosted setup

Connect models running on your own infrastructure.

<Tabs items={["Dashboard", "Organization config"]}>

<Tab title="Dashboard">

1. Go to **Gateway > Providers**
2. Click **Add Provider**
3. For **Provider**, select **Custom / Self-hosted**
4. Enter your model server's endpoint URL as the **Base URL**
5. Enter an API key. For a server that checks no key, such as Ollama or a vLLM server started without one, enter any placeholder, such as `ollama`
6. Select the models from the list the dialog fetches
7. Click **Add Provider**

<Note>
On a self-hosted Future AGI install, the endpoint can also be a private or LAN address, such as `http://host.docker.internal:11434/v1` for Ollama on the Docker host, once you set `AGENTCC_ALLOW_PRIVATE_PROVIDER_URLS=true`. Loopback addresses such as `localhost` are never allowed. See [Private and local provider URLs](/docs/command-center/features/self-hosted-models#private-and-local-provider-urls).
</Note>

</Tab>

<Tab title="Organization config">

```json
{
  "providers": {
    "ollama": {
      "base_url": "https://your-ollama.example.com",
      "api_format": "openai",
      "api_key": "ollama",
      "models": ["llama3.1"],
      "enabled": true
    },
    "vllm": {
      "base_url": "https://your-vllm.example.com",
      "api_format": "openai",
      "api_key": "your-vllm-api-key",
      "models": ["meta-llama/Llama-3.1-8B-Instruct"],
      "enabled": true
    }
  }
}
```

For a server that checks no key, such as Ollama, `api_key` can be any value: a provider needs one to serve requests.

</Tab>

</Tabs>

## Provider health

Agent Command Center records each provider's response times, request and error counts, and success rate from the requests it serves. It sends no probe requests of its own. What happens when a provider keeps failing depends on your routing settings:

1. With the [circuit breaker](/docs/command-center/features/routing#circuit-breaking) turned on, a provider that keeps failing for a model stops getting that model's requests until its cooldown ends
2. With [failover](/docs/command-center/features/routing#failover) turned on, a failed request moves to another of your providers that serves the same model
3. After the cooldown, requests reach the provider again, and enough successes in a row close the circuit

See [Routing](/docs/command-center/features/routing) for these settings.
