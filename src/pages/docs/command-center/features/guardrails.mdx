## About

Guardrails are safety checks that run on every request and response flowing through Agent Command Center. They catch dangerous or unwanted content before it reaches the LLM (pre-processing) or before it reaches your users (post-processing; for streamed responses, see [Streaming Guardrails](#streaming-guardrails)).

<Warning>
When [caching](/docs/command-center/features/caching) is on and a request is served from an exact match hit, guardrails that check the request (Pre stage) do not run on that request. Guardrails that check the response (Post stage) still run on the cached response before it is returned. Disable caching for traffic that must be screened on every request.
</Warning>

---

## When to use

- **Compliance and privacy**: Detect and redact PII (emails, SSNs, credit cards) before sending to LLM providers
- **Security**: Block prompt injection attempts and prevent system prompt extraction
- **Content safety**: Filter hate speech, threats, sexual content, and other harmful outputs
- **Data protection**: Detect secrets (API keys, passwords, tokens) in messages
- **Custom rules**: Enforce business-specific policies with blocklists and expression rules

---

## Built-in Guardrail Types

Agent Command Center includes 16 guardrail types covering common safety scenarios. The Stage column is the stage each type runs at when you set it up in the dashboard; today the gateway uses it whatever stage the guardrail is set to. A rule in `config.yaml` runs at the `stage` the rule sets.

| Guardrail Type | Stage | What it detects |
|---|---|---|
| PII Detection | Pre | Emails, SSNs, credit cards, phone numbers, addresses |
| Prompt Injection | Pre | Attempts to override system prompts or extract instructions |
| Content Moderation | Pre | Hate speech, threats, sexual content, violence |
| Secret Detection | Pre | API keys, passwords, tokens, credentials |
| Hallucination Detection | Post | Factually incorrect or fabricated information |
| Topic Restriction | Pre | Blocks requests on restricted topics |
| Language Detection | Pre | Enforces allowed languages |
| Data Leakage Prevention | Post | Prevents sensitive data from being processed |
| Blocklist | Pre | Custom word/phrase blocklists |
| System Prompt Protection | Pre | Prevents system prompt extraction attempts |
| Tool Permissions | Pre | Validates tool/function call permissions |
| Input Validation | Pre | Validates input format and structure |
| MCP Security | Pre | Validates MCP protocol security |
| Custom Expression Rules | Pre | Custom logic via expressions |
| Webhook (BYOG) | Pre | Custom guardrails via webhook |
| Future AGI Evaluation | Pre | Future AGI's proprietary evaluation models |

## Enforcement Modes

Choose how Agent Command Center handles guardrail violations.

| Mode | HTTP Status | Behavior |
|---|---|---|
| Enforce | 403 (pre-stage checks) | Request blocked, error returned to client. A block from a post-stage check does not return 403 today; see [Guardrail blocked (403)](/docs/command-center/concepts/api-reference#guardrail-blocked-403) |
| Monitor | 200 | Request proceeds, warning logged |
| Log | 200 | Request proceeds, violation logged silently |

<Tip>
Start with Monitor mode to understand traffic patterns before switching to Enforce.
</Tip>

### Fail-open vs fail-closed

What happens when a guardrail service itself errors (timeout, crash)?

- **Fail-open** (default): the request proceeds. Use this when availability matters more than safety enforcement.
- **Fail-closed** (`fail_open: false`): the request is blocked. Use this when safety is non-negotiable, even at the cost of occasional false rejections during outages.

## Score thresholds

Guardrails return confidence scores from 0.0 (safe) to 1.0 (maximum violation). Set thresholds to control sensitivity.

Example response with score:

```json
{
  "guardrail": "pii-detector",
  "score": 0.87,
  "entities": ["EMAIL", "CREDIT_CARD"],
  "threshold": 0.5,
  "action": "blocked"
}
```

| Threshold | Sensitivity | Use case |
|---|---|---|
| 0.3 | High | Strict enforcement, catch edge cases |
| 0.5 | Medium | Balanced approach |
| 0.8 | Low | Only catch obvious violations |

## Setting Up Guardrails

Configure guardrails via the dashboard or SDK.

<Tabs items={["Dashboard", "Python (Agent Command Center SDK)", "TypeScript (Agent Command Center SDK)"]}>
  <Tab title="Dashboard">

    1. Go to **Agent Command Center > Guardrails** in the Future AGI dashboard
    2. Click **Add Guardrail Policy**
    3. Select guardrail type (e.g., PII Detection)
    4. Choose enforcement mode: Enforce or Monitor
    5. Configure type-specific settings (entities, thresholds, etc.)
    6. Set scope: globally, to project, or to API key
    7. Click Save
  </Tab>

  <Tab title="Python (Agent Command Center SDK)">

from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com",
    control_plane_url="https://api.futureagi.com",
)

config = client.guardrails.configs.create(
    name="Production Safety",
    rules=[
        {
            "name": "pii-detector",
            "stage": "pre",
            "mode": "enforce",
            "threshold": 0.5,
            "config": {
                "entities": ["EMAIL", "SSN", "CREDIT_CARD", "PHONE"]

        },
        {
            "name": "injection-detector",
            "stage": "pre",
            "mode": "monitor",
            "threshold": 0.6
        },
        {
            "name": "content-moderation",
            "stage": "pre",
            "mode": "enforce",
            "threshold": 0.7
        },
        {
            "name": "secrets-detector",
            "stage": "pre",
            "mode": "enforce",
            "threshold": 0.5

## PII Remediation Modes

Choose how to handle detected PII.

| Mode | Behavior | Example |
|---|---|---|
| Block | Reject request | Request blocked with 403 |
| Mask | Replace with asterisks | alice@***.com |
| Redact | Remove entirely | [REDACTED] |
| Hash | Replace with hash | #a1b2c3d4 |

Configure redact mode in Python SDK:

```python
config = client.guardrails.configs.create(
    name="PII Redaction",
    rules=[
        {
            "name": "pii-detector",
            "stage": "pre",
            "mode": "monitor",
            "remediation": "redact",
            "config": {
                "entities": ["EMAIL", "SSN", "CREDIT_CARD"]
            }
        }
    ],
)
```

<Tip>
Use Redact or Mask to sanitize sensitive data while allowing the request to proceed.
</Tip>

## Streaming Guardrails

When you stream a chat completion (`"stream": true` on `/v1/chat/completions`), Agent Command Center sends the response headers first, then the response in chunks as the model generates it. A guardrail's stage decides what it can still do:

| Stage | When it runs on a stream | Effect |
|---|---|---|
| Pre (checks the request) | Before the stream opens | A `block` returns the 403 `content_blocked` error instead of a stream. A `warn` or `log` adds `x-agentcc-guardrail-triggered: true` to the stream's headers |
| Post (checks the response) | After the last chunk of response text, before `data: [DONE]` | Cannot stop or take back anything, because the headers and the response text have already gone out. `data: [DONE]` waits until these checks finish or time out. The result is recorded in the request log |

The table applies to guardrails set up in the dashboard and to `config.yaml` rules, except a `config.yaml` rule with `mode: "async"`: it runs in the background, so it cannot block the request, add the header, or delay `data: [DONE]`, and it reports a failure only in the gateway's own log output. Guardrails set up in the dashboard or through the SDK always run synchronously, whatever `mode` they carry.

Post-stage guardrails see the streamed text only on `/v1/chat/completions` and `/v1/completions`, and on a self-hosted gateway only when it records request and response bodies (`logging.request_logging.include_bodies: true`, or `otel.include_bodies: true` with `otel.enabled: true`). Otherwise they have no response text to check.

To act on a response while it streams, run a self-hosted gateway and [check the stream as it is generated](#check-the-stream-as-it-is-generated).

<CodeGroup>
```python Python
from agentcc import AgentCC

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com",
    control_plane_url="https://api.futureagi.com",
)

# A pre-stage block raises here, before any chunk arrives
for chunk in client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Tell me about security."}],
    stream=True,
):
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
```

```typescript TypeScript
import { AgentCC } from "@futureagi/agentcc";

const client = new AgentCC({
  apiKey: "sk-agentcc-your-key",
  baseUrl: "https://gateway.futureagi.com",
});

// A pre-stage block throws here, before any chunk arrives
const stream = await client.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [{ role: "user", content: "Tell me about security." }],
  stream: true,
});

for await (const chunk of stream) {
  const content = chunk.choices[0]?.delta?.content;
  if (content) process.stdout.write(content);
}
```
</CodeGroup>

### Check the stream as it is generated

On a self-hosted gateway, the post-stage rules in [`config.yaml`](/docs/command-center/deployment/self-hosted#configuration-file) (`guardrails.rules`) can check a `/v1/chat/completions` response while the model is still generating it. This is off by default. Turn it on with `guardrails.streaming`:

```yaml
guardrails:
  enabled: true
  rules:
    - name: "content-moderation"
      stage: "post"
      mode: "sync"
      action: "block"
      threshold: 0.7
  streaming:
    enabled: true
    check_interval: 100     # Bytes of new response text between checks (default: 100)
    failure_action: "stop"  # "stop" (default) or "disclaimer"
```

Each time another `check_interval` bytes of text have arrived, the gateway holds the chunk that completes the interval and runs these rules on the whole response so far. It runs them once more when the model finishes, if text has arrived since the last check. Chunks in between are sent without waiting for a check, so up to `check_interval` bytes of text can reach the client before a check catches it, and a response shorter than `check_interval` is checked only after all of it has been sent. The stream waits while a check runs, so a smaller interval catches content sooner but runs more checks. Only `sync` rules whose action is `block` affect the stream:

| `failure_action` | When a check fails |
|---|---|
| `stop` (default) | If a check during the stream fails, the gateway sends an error event instead of the chunk it held and ends the stream without `data: [DONE]`. If the check at the end fails, the whole response has already been sent: the error event follows it, and the stream still ends with `data: [DONE]` |
| `disclaimer` | The stream continues. If the check at the end fails, the gateway sends one more content chunk after the one with `finish_reason`: two newlines followed by `[Content warning: <guardrail message>]`. A check that fails during the stream adds no notice |

With `disclaimer`, the check at the end runs only if text arrived after the last interval check. If the last chunk of text completes an interval, the response gets no notice, even when that check fails.

The error event that `stop` sends:

```text
data: {"error":{"message":"Content moderation triggered: violence (score: 1.00)","type":"guardrail_error","param":null,"code":"stream_blocked"}}
```

The HTTP status stays 200, because it was sent with the headers, and the chunks sent before the check are not taken back.

<Note>
Streaming checks use only the rules in `config.yaml`. Guardrails set up in the dashboard run only before the stream opens and after the response text has been sent, as described in [Streaming Guardrails](#streaming-guardrails), even when `guardrails.streaming.enabled` is `true`.
</Note>

## Per-request guardrail overrides

Apply guardrail policies to individual requests without changing your org-level config. Pass policy IDs via `GatewayConfig`:

<CodeGroup>
```python Python
from agentcc import AgentCC, GatewayConfig, GuardrailConfig

client = AgentCC(
    api_key="sk-agentcc-your-key",
    base_url="https://gateway.futureagi.com",
    config=GatewayConfig(
        guardrails=GuardrailConfig(
            input_guardrails=["pii-detection", "prompt-injection"],
            output_guardrails=["toxicity-check"],
            deny=True,       # block on violation
            fail_open=False, # fail closed: block if guardrail errors
        )
    ),
)

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
```

```typescript TypeScript
import { AgentCC } from "@futureagi/agentcc";

const client = new AgentCC({
  apiKey: "sk-agentcc-your-key",
  baseUrl: "https://gateway.futureagi.com",
  config: {
    guardrails: {
      input_guardrails: ["pii-detection", "prompt-injection"],
      output_guardrails: ["toxicity-check"],
      deny: true,
      fail_open: false,
    },
  },
});

const response = await client.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [{ role: "user", content: "What is the capital of France?" }],
});
```
</CodeGroup>

<Tip>
Use `input_guardrails` and `output_guardrails` to reference guardrail policy IDs created via the dashboard or SDK. Per-request config layers on top of your org-level defaults.
</Tip>

## Custom Blocklists

Create custom blocklists to block specific words, phrases, or patterns.

Dashboard steps:
1. Navigate to Guardrails → Blocklists
2. Click Create Blocklist
3. Enter name and description
4. Add blocked terms (one per line)
5. Click Save

Python SDK:

<Tabs>
  <Tab title="Python (Agent Command Center SDK)">
```python
blocklist = client.guardrails.blocklists.create(
    name="Restricted Topics",
    words=["confidential", "secret", "internal"],
)

config = client.guardrails.configs.create(
    name="Blocklist Policy",
    rules=[
        {
            "name": "blocklist",
            "stage": "pre",
            "mode": "sync",
            "action": "block",
            "config": {
                "blocklist_id": blocklist["id"]
            }
        }
    ],
)
```
  </Tab>
