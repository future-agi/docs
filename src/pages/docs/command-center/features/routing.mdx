## About

Agent Command Center's routing layer distributes requests across multiple providers and models for reliability and performance. With provider failover turned on, a chat completion that fails on one provider moves to another provider that serves the same model, and circuit breakers stop sending requests to a provider that keeps failing.

---

## When to use

- **High availability**: Move a failed request to another of your providers that serves the same model when one is down or rate-limited
- **Cost optimization**: Route to the cheapest provider that supports the requested model
- **Latency reduction**: Route to the fastest provider based on recent response times
- **Traffic distribution**: Split traffic across providers by weight for capacity management

---

## Key concepts

| Term | Definition |
|------|-----------|
| **Failover** | Moving a failed request to another of your providers that serves the same model, on the status codes you choose (429, 500, 502, 503 and 504 unless you set others) |
| **Retries** | Repeated attempts on the same provider after a failure, with exponential backoff and random jitter between them |
| **Circuit breaking** | Stops sending a model's requests to a provider after repeated failures, then lets requests through again after a cooldown |
| **Timeouts** | How long a request for a model may take (`model_timeouts`), and how long each provider tried may take (`failover.per_attempt_timeout`) |
| **Routing strategy** | The algorithm Agent Command Center uses to select which provider handles each request (e.g., round robin, weighted, latency-based) |

### Configuration parameters

These are fields of the `routing` section of your organization's config, which the dashboard's **Fallbacks** page and **Routing** tab edit. A self-hosted gateway's `config.yaml` takes the same fields under `routing:`. Durations are strings such as `"500ms"` or `"30s"` (in `config.yaml`, plain durations such as `30s`). For your organization's API keys, failover, retries, the circuit breaker, and the routing strategy apply to chat completions. `model_timeouts` also sets the timeout of requests to the other endpoints.

**Failover** (`routing.failover`):

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn provider failover on |
| `max_attempts` | number | `3` | Most providers tried for one request, the first one included |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | Status codes that move the request to another provider |
| `on_timeout` | boolean | `false` | Also move the request when the provider times out |
| `per_attempt_timeout` | duration | none | Time limit for each provider tried, its retries included |

**Retries** (`routing.retry`):

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn retries on |
| `max_retries` | number | `2` | Retries after the first call to a provider |
| `initial_delay` | duration | `"500ms"` | Longest wait before the first retry |
| `max_delay` | duration | `"10s"` | Longest wait between retries |
| `multiplier` | number | `2` | How much the longest wait grows after each retry |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | Status codes that are retried |
| `on_timeout` | boolean | `false` | Also retry when the provider times out |

**Circuit breaker** (`routing.circuit_breaker`):

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn circuit breaking on |
| `failure_threshold` | number | `5` | Failures, with no success between them, that open the circuit |
| `success_threshold` | number | `2` | Successes after the cooldown that close the circuit again |
| `cooldown` | duration | `"30s"` | How long an open circuit refuses requests |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | Status codes that count as failures. A provider timeout always counts |

**Timeouts** (`routing.model_timeouts`):

| Parameter | Type | Description |
|-----------|------|-------------|
| `model_timeouts` | object | Model name to duration, e.g. `{"o1": "300s"}`. Sets the timeout of a request for that model, up to the gateway's maximum request timeout |

## Routing strategies

| Strategy | Org config value | `config.yaml` value | How it works |
|----------|------------------|---------------------|-------------|
| Round Robin | `round_robin` | `round-robin` | Evenly across providers in rotation (the default in the gateway's config file) |
| Weighted | `weighted` | `weighted` | Based on each provider's weight (e.g., 70% to one, 30% to another) |
| Least Latency | `least_latency` | `least-latency` | Routes to the fastest provider based on recent response times |
| Cost Optimized | `cost_optimized` | `cost-optimized` | Cheapest provider that supports the requested model |
| Adaptive | `adaptive` | `adaptive` | Prefers the provider that has recently served the model fastest and with the fewest errors (see [Adaptive strategy details](#adaptive-strategy-details)) |

A strategy chooses among your organization's providers that serve the requested model. An organization with no strategy set sends each request to the first of those providers, by provider ID. Both spellings name the same strategy.

  <Tab title="Dashboard">

    2. Select a strategy and set the routing options the tab shows
    3. Click **Save**

    **Fallbacks, retries, and circuit breaking:**
    1. Go to **Gateway > Fallbacks**
    2. Expand the section you want (Provider Failover, Retry, Circuit Breaker, or Model Timeouts)
    3. Toggle it on, set your values, and click **Save**

  </Tab>
  <Tab title="Organization config">

    The strategy is `routing.strategy`. The weighted strategy reads each provider's `weight` in the `providers` section; a provider with no weight counts as 1. Here `openai` and `azure` both list `gpt-4o`, and 70% of its requests go to `openai`:

    ```json
    {
      "providers": {
        "openai": { "weight": 70 },
        "azure": { "weight": 30 }

      "routing": {

    }
    ```

  </Tab>
  <Tab title="Self-hosted config.yaml">

    ```yaml
    routing:
      default_strategy: "weighted"
      targets:
        gpt-4o:
          - provider: openai
            weight: 70
          - provider: azure
            weight: 30
    ```

  </Tab>

## Failover

With failover turned on, a chat completion that fails with one of `on_status_codes` (or times out, with `on_timeout`) moves to another of your organization's providers that serves the same model. It keeps moving until a provider succeeds or `max_attempts` providers have been tried. The routing strategy picks each provider; with no strategy, the providers are tried in provider-ID order.

```json
{
  "routing": {
    "failover": {
      "enabled": true,
      "max_attempts": 3,
      "on_status_codes": [429, 500, 502, 503, 504],
      "on_timeout": true
    }
  }
}
```

<Note>
Failover moves a request to another provider of the same model. To move a request to a different model, add a [model fallback](#model-fallbacks) chain.
</Note>

## Retries

Retries repeat a failed call on the same provider. Agent Command Center waits longer before each retry: the longest wait starts at `initial_delay` and is multiplied by `multiplier` after each retry, up to `max_delay`, and each wait is a random time up to that longest wait. With the defaults, the waits are up to 500ms, then up to 1s. This gives struggling providers time to recover instead of flooding them with rapid retry requests.

```json
{
  "routing": {
    "retry": {
      "enabled": true,
      "max_retries": 2,
      "initial_delay": "500ms",
      "max_delay": "10s",
      "multiplier": 2,
      "on_status_codes": [429, 500, 502, 503, 504]
    }
  }
}
```

## Circuit breaking

Circuit breaking stops sending requests to a provider that is failing repeatedly. There is one circuit for each provider and model. After `failure_threshold` failures with no success between them, the circuit opens and the provider is skipped for that model. After the cooldown, requests reach it again: `success_threshold` successes close the circuit, and any failure opens it again. This prevents a single failing provider from degrading your entire application.

The circuit breaker has three states:

| State | Behavior |
|-------|----------|
| Closed | Normal operation, requests pass through |
| Open | The provider is skipped for this model, with no call to it |
| Half-Open | After the cooldown, requests pass through again until the circuit closes or opens |

```json
{
  "routing": {
    "circuit_breaker": {
      "enabled": true,
      "failure_threshold": 5,
      "success_threshold": 2,
      "cooldown": "30s"
    }
  }
}
```

<Tip>
Circuit breaking works with failover: a provider whose circuit is open is skipped, and the request goes to another of your providers that serves the model. When every one of them has an open circuit, the request gets a 503 error without a call to any provider.
</Tip>

## Timeouts

Set a timeout per model, and a time limit for each provider a request tries.

```json
{
  "routing": {
    "model_timeouts": {
      "o1": "300s",
      "gpt-4o": "60s"
    },
    "failover": {
      "enabled": true,
      "per_attempt_timeout": "25s"
    }
  }
}
```

## Example: High-availability setup

This organization config combines weighted routing, failover, retries, circuit breaking, and a model timeout. `openai` and `azure` both list `gpt-4o`; only the fields this example sets are shown.

```json
{
  "providers": {
    "openai": { "weight": 60 },
    "azure": { "weight": 40 }
  },
  "routing": {
    "strategy": "weighted",
    "failover": {
      "enabled": true,
      "max_attempts": 2,
      "on_status_codes": [429, 500, 502, 503, 504],
      "on_timeout": true,
      "per_attempt_timeout": "25s"
    },
    "retry": {
      "enabled": true,
      "max_retries": 2,
      "initial_delay": "500ms",
      "max_delay": "10s",
      "multiplier": 2
    },
    "circuit_breaker": {
      "enabled": true,
      "failure_threshold": 5,
      "success_threshold": 2,
      "cooldown": "30s"
    },
    "model_timeouts": {
      "gpt-4o": "60s"
    }
  }
}
```

To choose among providers, use a [routing strategy](#routing-strategies). To send a model name to one provider, use a [model map](/docs/command-center/concepts/configuration#model-mapping). To move a failed request to another model, use [model fallbacks](#model-fallbacks).

## Real-world patterns

### Gradual provider migration

Move a model's traffic from one provider to another without a big-bang switch. Here `openai` and `azure` both list `gpt-4o`; start with 10% of its traffic on `azure` and increase it over time:

```json
{
  "providers": {
    "openai": { "weight": 90 },
    "azure": { "weight": 10 }
  },
  "routing": {
    "strategy": "weighted"
  }
}
```

Increase the `azure` weight over days or weeks. If issues arise, dial it back immediately.

### Cost optimization across tiers

To send each request to the cheapest of your providers that serves the requested model, use the cost-optimized [routing strategy](#routing-strategies).

### Rate limit absorption

Spread load across providers so a single rate limit doesn't block your application. Here `openai` and `azure` both list `gpt-4o`:

```json
{
  "routing": {
    "strategy": "round_robin",
    "failover": {
      "enabled": true,
      "on_status_codes": [429, 500, 502, 503, 504]
    }
  }
}
```

When one provider rate-limits you, the request moves to another of your providers that serves the same model. To move to a different model, add a [model fallback](#model-fallbacks) chain.

## Model fallbacks

Configure per-model fallback chains for automatic failover when a specific model is unavailable:

```yaml
routing:
  model_fallbacks:
    gpt-4o:
      - claude-sonnet-4-6
      - gemini-2.0-pro
    claude-sonnet-4-6:
      - gpt-4o
      - gemini-2.0-pro
```

When `gpt-4o` fails, Agent Command Center automatically tries `claude-sonnet-4-6`, then `gemini-2.0-pro`.

In an organization config, the same chains go under `routing.model_fallbacks`. They run when a request fails with one of the failover status codes (429, 500, 502, 503 and 504 unless you set others), and on a provider timeout when there is no `routing.failover` section or it sets `on_timeout: true`. `routing.fallback_enabled: false` keeps them stored but off.

## Complexity-based routing

Route requests to different models based on prompt complexity. Agent Command Center scores each request on 8 signals and maps it to a tier.

**Scoring signals:**

| Signal | Default weight | What it measures |
|---|---|---|
| `token_count` | 0.15 | Total input tokens |
| `message_count` | 0.10 | Number of messages in the conversation |
| `system_prompt_length` | 0.10 | Length of the system prompt |
| `tool_count` | 0.15 | Number of tools/functions provided |
| `multimodal` | 0.15 | Whether the request contains images or audio |
| `keyword_heuristics` | 0.15 | Presence of reasoning keywords ("analyze", "step by step", "compare", etc.) |
| `structured_output` | 0.10 | Whether `response_format` is set |
| `max_tokens` | 0.10 | Requested output length |

Each signal produces a 0-100 score. The weighted sum maps to a tier:

```yaml
routing:
  complexity:
    enabled: true
    default_tier: "moderate"
    tiers:
      simple:
        max_score: 30
        model: "gpt-4o-mini"
        provider: "openai"
      moderate:
        max_score: 70
        model: "gpt-4o"
        provider: "openai"
      complex:
        max_score: 100
        model: "claude-sonnet-4-6"
        provider: "anthropic"
```

A simple classification request scores low and routes to `gpt-4o-mini`. A multi-tool reasoning task scores high and routes to `claude-sonnet-4-6`.

You can override the tier per request with the `x-agentcc-complexity-override` header. Pass the tier name (e.g., `simple`, `moderate`, `complex` - matching your configured tier names).

## Provider lock (sticky routing)

Force a request to a specific provider, bypassing the routing strategy. Useful for stateful workflows where you need consistency across multiple calls.

Set it via the `x-agentcc-provider-lock` header or `provider_lock` in request metadata:

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={"x-agentcc-provider-lock": "openai"},
)
```

Configure which providers can be locked to:

```yaml
routing:
  provider_lock:
    enabled: true
    allowed_providers: ["openai", "anthropic"]
    deny_providers: ["groq"]  # never lock to Groq
```

If `allowed_providers` is empty, all providers are allowed (except those in `deny_providers`).

## Adaptive strategy details

The adaptive strategy reads how each provider has recently served the requested model every time it selects one. It runs no background job:

1. **Learning phase**: Until the providers have `learning_requests` responses between them (default: 20), it uses round-robin so each one is measured.
2. **Scoring**: Each provider's score is its latency relative to the slowest provider's, times the latency weight (default: 0.5), plus its odds of an error (error rate divided by success rate), times the error-rate weight (default: 0.4). The lowest score wins.
3. **Exploration**: A share of the selections (`min_weight`, default: 0.05, per other provider) goes to one of the other providers, so a provider that recovers is noticed.

```yaml
routing:
  default_strategy: "adaptive"
  adaptive:
    enabled: true
    learning_requests: 20
    min_weight: 0.05
    signal_weights:
      latency: 0.5
      error_rate: 0.4
```

In an organization config, `routing.adaptive.enabled: true` selects the adaptive strategy, whatever `routing.strategy` says. The `update_interval` and `smoothing_factor` settings and the `cost` signal weight are not read.
