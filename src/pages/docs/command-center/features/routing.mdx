## About

Agent Command Center's routing layer distributes requests across multiple providers and models for reliability and performance. If one provider is down or slow, traffic automatically shifts to healthy alternatives. This ensures your application stays responsive even when individual providers experience outages or rate limiting.

---

## When to use

- **High availability**: Automatic failover to backup providers when primary is down or rate-limited
- **Cost optimization**: Send traffic to the provider you rank first, such as your cheapest one, and use the others only when it fails
- **Latency reduction**: Route to the fastest provider based on recent response times
- **Traffic distribution**: Split traffic across providers by weight for capacity management

---

## Key concepts

| Term | Definition |
|------|-----------|
| **Failover** | Automatic rerouting of requests to a backup provider when the primary provider fails or returns errors (429, 5xx) |
| **Retries** | Repeated attempts to send a request after a failure, using exponential backoff to avoid overwhelming the provider |
| **Circuit breaking** | A protection mechanism that stops sending requests to a failing provider entirely, then gradually tests recovery before resuming full traffic |
| **Timeouts** | Maximum duration Agent Command Center waits for a provider response before treating the request as failed |
| **Routing strategy** | The algorithm Agent Command Center uses to select which provider handles each request (e.g., round robin, weighted, latency-based) |

### Configuration parameters

These parameters sit under `routing` in the gateway's `config.yaml` and in the `routing` section of your org config. The **Gateway > Fallbacks** page edits the org config ones. Durations are strings such as `"500ms"`, `"30s"` or `"2m"`.

**Failover (`routing.failover`):**

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn failover on or off |
| `max_attempts` | number | `3` | Providers to call in total, counting the first one |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | HTTP status codes that trigger failover |
| `on_timeout` | boolean | `false` | Also fail over when a provider call times out |
| `per_attempt_timeout` | duration | none | Time limit for each provider call, so a slow first provider leaves time for the next |

**Retries (`routing.retry`):**

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn retries on or off |
| `max_retries` | number | `2` | Retries on the same provider before failing over |
| `initial_delay` | duration | `500ms` | Wait before the first retry |
| `max_delay` | duration | `10s` | Upper limit on the wait between retries |
| `multiplier` | number | `2` | Multiplier applied to the wait after each retry (500ms, 1s, 2s) |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | HTTP status codes that are retried |
| `on_timeout` | boolean | `false` | Also retry when a provider call times out |

Retries run inside failover: they only happen when failover is also enabled.

**Circuit breaker (`routing.circuit_breaker`):**

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `enabled` | boolean | `false` | Turn circuit breaking on or off |
| `failure_threshold` | number | `5` | Failures in a row that open the circuit |
| `success_threshold` | number | `2` | Successes in a row, after the cooldown, that close it again |
| `cooldown` | duration | `30s` | How long the circuit stays open before requests are let through again |
| `on_status_codes` | number[] | `[429, 500, 502, 503, 504]` | HTTP status codes that count as failures |

**Timeouts:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `routing.model_timeouts` | map of model to duration | Time limit for requests to one model, e.g. `{"o3": "120s"}` |
| `x-agentcc-timeout` header | duration | Time limit for one request. Takes precedence over `model_timeouts` |

Without either, a request gets the gateway's `server.default_request_timeout` (60s by default). The time limit covers the whole request, including retries and failover.

## Routing strategies

| Strategy | `config.yaml` value | Org config value | How it works |
|----------|-------------|-------------|-------------|
| Round Robin | `round-robin` | `round_robin` | Evenly across providers in rotation (default) |
| Weighted | `weighted` | `weighted` | Based on each target's `weight` (e.g., 70% OpenAI, 30% Anthropic) |
| Least Latency | `least-latency` | `least_latency` | Routes to the provider with the lowest recent response times |
| Cost Optimized | `cost-optimized` | `cost_optimized` | Routes to the target with the lowest `priority` value, rotating between ties. It does not read prices, so give your cheapest provider the lowest `priority` |
| Adaptive | `adaptive` | none | Dynamically adjusts weights based on real-time performance |
| Race | `fastest` | none | Sends to several providers at once and returns the first response. You are billed for every call made, including those whose responses are discarded |

A strategy chooses among the providers that serve the requested model, listed per model under `routing.targets` in `config.yaml`.

<Warning>
The gateway does not apply the org config `routing.strategy` yet. It saves the value and records it on each request, but when several of your organization's providers serve the same model, the gateway always picks the first one by provider name. The strategies take effect through `routing.default_strategy` on a gateway you run yourself.
</Warning>

## Configuring a routing strategy

<Tabs items={["Dashboard", "config.yaml (self-hosted gateway)"]}>
  <Tab title="Dashboard">

    1. Go to **Gateway > Providers** and open the **Routing** tab
    2. Choose a **Default Strategy** and click **Save Routing Config**. The org config editor (**Gateway > Settings > Org Config > Edit Config > Routing**) edits the same `routing.strategy` value. See the warning above: the gateway does not apply it yet

    **Fallbacks, retries, and circuit breaking:**
    1. Go to **Gateway > Fallbacks**
    2. Expand the section you want (Model Fallback Chains, Provider Failover, Retry, Circuit Breaker, or Model Timeouts)
    3. Toggle it on, set your values, and click **Save & Apply**

  </Tab>
  <Tab title="config.yaml (self-hosted gateway)">
    ```yaml
    routing:
      default_strategy: "weighted"
      targets:
        gpt-4o:
          - provider: "openai"
            weight: 70
          - provider: "azure-openai"
            weight: 30
    ```
  </Tab>
</Tabs>

<Note>
The Agent Command Center SDK has no routing methods, and routing policies created through the control plane's `routing-policies` API never reach the gateway: the org config they would be merged into fails validation, so the merge is rolled back and the API reports `gateway_synced: false`. Set routing in the dashboard or in `config.yaml`.
</Note>

## Failover

Failover triggers on the status codes in `on_status_codes` (429 and 5xx by default) and, with `on_timeout: true`, on timeouts. When a provider fails, Agent Command Center sends the request to another provider that serves the same model, skipping the ones already tried and any whose circuit is open, until one succeeds or `max_attempts` providers have been called.

```json
{
  "routing": {
    "failover": {
      "enabled": true,
      "max_attempts": 3,
      "on_status_codes": [429, 500, 502, 503, 504],
      "on_timeout": true,
      "per_attempt_timeout": "20s"
    }
  }
}
```

<Note>
Failover moves between providers of the same model. To fall back to a different model, such as `claude-sonnet-4-6` when `gpt-4o` fails, use [model fallbacks](#model-fallbacks).
</Note>

## Retries

Agent Command Center uses exponential backoff for retries. This means it waits progressively longer between each retry attempt: with the defaults, 500ms before the first retry and 1s before the second, never more than `max_delay`. This gives struggling providers time to recover instead of flooding them with rapid retry requests. Retries stay on the same provider; once they run out, failover moves to the next provider.

```json
{
  "routing": {
    "retry": {
      "enabled": true,
      "max_retries": 2,
      "initial_delay": "500ms",
      "max_delay": "10s",
      "multiplier": 2
    }
  }
}
```

## Circuit breaking

Circuit breaking stops sending requests to a provider that is failing repeatedly. After `failure_threshold` failures in a row the circuit opens. After the `cooldown`, Agent Command Center lets requests through again, and `success_threshold` successes in a row close the circuit. This prevents a single failing provider from degrading your entire application.

The circuit breaker has three states:

| State | Behavior |
|-------|----------|
| Closed | Normal operation, requests pass through |
| Open | Requests rejected immediately, no calls to provider |
| Half-Open | Requests allowed again to test if the provider recovered |

```yaml
routing:
  circuit_breaker:
    enabled: true
    failure_threshold: 5
    success_threshold: 2
    cooldown: 30s
```

<Tip>
Circuit breaking works with failover. When a circuit opens, Agent Command Center automatically routes to the next available provider.
</Tip>

<Note>
The gateway applies the circuit breaker from its own `config.yaml`. Circuit breaker values saved in an org config, for example on **Gateway > Fallbacks**, are stored but not used yet.
</Note>

## Timeouts

Set a time limit per model with `routing.model_timeouts`, or per request with the `x-agentcc-timeout` header (a duration such as `30s`). The header wins over the per-model value. Use `failover.per_attempt_timeout` to cap each provider call within that time.

```json
{
  "routing": {
    "model_timeouts": {
      "gpt-4o": "30s",
      "o3": "120s"
    }
  }
}
```

## Example: High-availability setup

This `config.yaml` combines weighted routing, failover, retries, circuit breaking and timeouts for a production setup:

```yaml
routing:
  default_strategy: "weighted"
  targets:
    gpt-4o:
      - provider: "openai"
        weight: 60
      - provider: "azure-openai"
        weight: 40
  failover:
    enabled: true
    max_attempts: 2
    on_status_codes: [429, 500, 502, 503, 504]
    on_timeout: true
    per_attempt_timeout: 25s
  retry:
    enabled: true
    max_retries: 2
    initial_delay: 500ms
    max_delay: 10s
    multiplier: 2
  circuit_breaker:
    enabled: true
    failure_threshold: 5
    success_threshold: 2
    cooldown: 30s
  model_timeouts:
    gpt-4o: 60s
```

## Conditional routing

Route requests to specific providers based on request attributes. Rules are evaluated in priority order (lower number = higher priority). First match wins.

Supported fields: `model`, `user`, `stream`, `provider`, `session_id`, `request_id`, `metadata.<key>`

Supported operators: `$eq`, `$ne`, `$in`, `$nin`, `$regex`, `$gt`, `$lt`, `$gte`, `$lte`, `$exists`

```yaml
routing:
  conditional_routes:
    - name: "enterprise-to-dedicated"
      priority: 10
      condition:
        field: "metadata.tier"
        op: "$eq"
        value: "enterprise"
      action:
        provider: "openai-dedicated"

    - name: "gpt-models-to-openai"
      priority: 50
      condition:
        field: "model"
        op: "$regex"
        value: "^gpt-"
      action:
        provider: "openai"

    - name: "streaming-to-groq"
      priority: 60
      condition:
        field: "stream"
        op: "$eq"
        value: true
      action:
        provider: "groq"
```

You can also combine conditions with `$and`, `$or`, and `$not`:

```yaml
    - name: "premium-non-streaming"
      priority: 20
      condition:
        $and:
          - field: "metadata.tier"
            op: "$eq"
            value: "premium"
          - field: "stream"
            op: "$eq"
            value: false
      action:
        provider: "openai-premium"
```

## Real-world patterns

### Gradual provider migration

Migrate from one provider to another without a big-bang switch. Start with 10% traffic to the new provider and increase over time:

```yaml
routing:
  default_strategy: "weighted"
  targets:
    gpt-4o:
      - provider: "openai"
        weight: 90
      - provider: "anthropic"
        weight: 10
        model_override: "claude-sonnet-4-6"   # model sent to this provider
```

Increase the Anthropic weight over days or weeks. If issues arise, dial it back immediately.

### Cost optimization across tiers

Use conditional routing to direct different request types to the most cost-effective provider:

```yaml
routing:
  conditional_routes:
    - name: "long-context-to-gemini"
      priority: 10
      condition:
        field: "model"
        op: "$in"
        value: ["gpt-4o", "claude-opus-4-6"]
      action:
        provider: "gemini"        # Lower cost for long-context tasks

    - name: "fast-tasks-to-groq"
      priority: 20
      condition:
        field: "metadata.task_type"
        op: "$eq"
        value: "classification"
      action:
        provider: "groq"          # High speed, low cost for simple tasks
```

### Rate limit absorption

Spread load across providers so a single rate limit doesn't block your application:

```yaml
routing:
  default_strategy: "round-robin"
  targets:
    gpt-4o:
      - provider: "openai"
      - provider: "anthropic"
        model_override: "claude-sonnet-4-6"
      - provider: "gemini"
        model_override: "gemini-2.0-flash"
  failover:
    enabled: true
    on_status_codes: [429, 500, 502, 503, 504]
```

When OpenAI rate-limits you, the request fails over to Anthropic or Gemini.

## Model fallbacks

Configure per-model fallback chains for automatic failover when a specific model is unavailable:

```yaml
routing:
  model_fallbacks:
    gpt-4o:
      - claude-sonnet-4-6
      - gemini-2.0-pro
    claude-sonnet-4-6:
      - gpt-4o
      - gemini-2.0-pro
```

When `gpt-4o` fails, Agent Command Center automatically tries `claude-sonnet-4-6`, then `gemini-2.0-pro`.

## Complexity-based routing

Route requests to different models based on prompt complexity. Agent Command Center scores each request on 8 signals and maps it to a tier.

**Scoring signals:**

| Signal | Default weight | What it measures |
|---|---|---|
| `token_count` | 0.15 | Total input tokens |
| `message_count` | 0.10 | Number of messages in the conversation |
| `system_prompt_length` | 0.10 | Length of the system prompt |
| `tool_count` | 0.15 | Number of tools/functions provided |
| `multimodal` | 0.15 | Whether the request contains images or audio |
| `keyword_heuristics` | 0.15 | Presence of reasoning keywords ("analyze", "step by step", "compare", etc.) |
| `structured_output` | 0.10 | Whether `response_format` is set |
| `max_tokens` | 0.10 | Requested output length |

Each signal produces a 0-100 score. The weighted sum maps to a tier:

```yaml
routing:
  complexity:
    enabled: true
    default_tier: "moderate"
    tiers:
      simple:
        max_score: 30
        model: "gpt-4o-mini"
        provider: "openai"
      moderate:
        max_score: 70
        model: "gpt-4o"
        provider: "openai"
      complex:
        max_score: 100
        model: "claude-sonnet-4-6"
        provider: "anthropic"
```

A simple classification request scores low and routes to `gpt-4o-mini`. A multi-tool reasoning task scores high and routes to `claude-sonnet-4-6`.

You can override the tier per request with the `x-agentcc-complexity-override` header. Pass the tier name (e.g., `simple`, `moderate`, `complex` - matching your configured tier names).

## Provider lock (sticky routing)

Force a request to a specific provider, bypassing the routing strategy. Useful for stateful workflows where you need consistency across multiple calls.

Set it via the `x-agentcc-provider-lock` header or `provider_lock` in request metadata:

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}],
    extra_headers={"x-agentcc-provider-lock": "openai"},
)
```

Configure which providers can be locked to:

```yaml
routing:
  provider_lock:
    enabled: true
    allowed_providers: ["openai", "anthropic"]
    deny_providers: ["groq"]  # never lock to Groq
```

If `allowed_providers` is empty, all providers are allowed (except those in `deny_providers`).

## Adaptive strategy details

The adaptive strategy learns from real traffic and adjusts weights over time:

1. **Learning phase**: For the first N requests (default: 100), uses round-robin to gather baseline latency and error data from all providers.
2. **Active phase**: Computes per-provider weights every 30 seconds using latency (lower is better) and error rate (fewer errors is better).
3. **Weight smoothing**: New weights are blended with old weights using a smoothing factor (default: 0.3) to prevent wild swings.
4. **Minimum weight**: No provider drops below 5% weight, ensuring all providers stay in rotation.

```yaml
routing:
  default_strategy: "adaptive"
  adaptive:
    enabled: true
    learning_requests: 100
    update_interval: 30s
    smoothing_factor: 0.3
    min_weight: 0.05
    signal_weights:
      latency: 0.5
      error_rate: 0.4
      # cost: 0.1 (parsed but not yet used in weight calculation)
```

## Race (fastest response) details

The `fastest` strategy sends the same request to all eligible providers simultaneously and returns whichever responds first. The rest are cancelled.

```yaml
routing:
  default_strategy: "fastest"
  fastest:
    max_concurrent: 3        # limit parallel calls
    cancel_delay: 50ms       # wait before cancelling losers
    excluded_providers:       # skip these in the race
      - "groq"
```

<Warning>
You are billed by every provider that receives the request, not just the winner. Use this for latency-critical requests where cost is secondary.
</Warning>
