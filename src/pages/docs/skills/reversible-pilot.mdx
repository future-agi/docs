title: "Try a reversible pilot"
description: "Trial a supported existing library, reproduce a real application failure, and update or leave without cutting over production."
---

## Before starting

**Pilot preview.** Enable only the surfaces and exact client/runtime versions qualified for the deployment. The pilot runs alongside the existing application, tracing, incident detection, and experiment CI. It is not a replacement for those systems and does not establish a measured 10x advantage.

Read [Compatibility](/docs/skills/compatibility) before issuing credentials or rebuilding the library. Use synthetic or specifically authorized, reviewed material. A working demo in a different application is not qualification of the application.

## 1. Inventory before migration

Inventory the complete source library locally: roots, linked dependencies, supporting files, binaries, nested instructions, host metadata, and sizes. Evaluate the entire compiled closure, not each leaf in isolation. Record which members are unsupported and why.

Choose an isolated pilot repository or directory and a supported subset deliberately. If the complete job requires unsupported members, stop and keep that job in the incumbent system. A successful smaller subset must not be reported as a successful full migration.

The initial supported intake is a bounded, versioned Langfuse export or local private-folder format. Check the enabled importer for its exact accepted export version; an unspecified export format is not portable by assumption. Do not upload provider secrets, hidden reasoning, or unrelated customer transcripts.

## 2. Review retained bytes and source identity

A migration preview should retain exact uploaded bytes and show every included, rejected, and skipped member; source project/resource/revision; destination; checks; and rights/NOTICE evidence. Confirmation must refer to that preview, not silently reread a changed folder or moving branch.

Copy reviewed leaves into drafts. Publish them deliberately, assemble the context with explicit accepted links, and publish the parent. Source production and existing agents stay unchanged. Retain the migration receipt that maps immutable source identities and content hashes to destination UUIDs, versions, and digests.

For public GitHub source intake, selecting a root after preview must retain the original tracked ref and resolved commit SHA. Review inherited license and NOTICE files. Existing personal drafts block replacement. Private hosted Git connectors, arbitrary URL fetching, and executing repository hooks are not pilot features.

## 3. Install the exact candidate

A first publication may have no production label. Use its returned immutable version, not a default-production command that cannot resolve yet. Follow [Safe installation](/docs/skills/safe-installation): purpose-bound credential, reviewed destination/ownership plan, exact file verification, real host discovery, and separate delivery observations.

Do not replace the pilot plan with an overlay unzip command. Do not change global instructions, application credentials, or host settings implicitly.

## 4. Reproduce an existing failure

1. Find the original failure in retained Langfuse tracing. Capture its exact external project/trace/observation and physical span identity through an authorized connector surface. A copied link is still a human handoff; it is not automatic reconstruction.
2. Select only the relevant request, tool results, and state fixture. Review redaction and workspace disclosure before saving a case. Confirm the expected behavior from approved requirements, not from the failed answer.
3. For a supported Dataset row, select the exact authorized row and revision, map fields explicitly, redact, and confirm the expectation. Missing or unsupported data stays visible; do not silently convert it into a complete native case.
4. Reproduce the failure using historical context plus pinned code, actual entrypoint, runtime, checkpoint schema/state, tools, retrieval fixtures, model configuration, and evaluator identities.
5. If the inputs are missing or the original failure does not recur, retain **Not reproduced** and the missing/confounding inputs. Do not relabel a synthetic control as a reproduced customer failure.
6. Preserve the existing draft, start the repair from the recorded version, and explicitly review the current publication head. See [historical editing](/docs/skills/agent-contexts#repair-the-historical-version-the operator-intended).
7. Run a matched native comparison for the application claim, including neighboring working requests and routing near misses. A text run is an optional diagnostic, not a required second paid run.
8. Inspect failures, missing trials, tool errors, and disagreements. Keep the incumbent regression pipeline authoritative. Record its exact external run/configuration reference and attributed decision, clearly labeled operator-recorded rather than a machine-imported Hub verdict.
9. Hand off the exact candidate through [Reviews](/docs/skills/reviewed-releases). After release, inspect a real new trace in the retained system with the changed Hub identity.

Changed Hub bytes must never masquerade as an old Langfuse skill version. Exact equality mappings apply only while verified bytes match; changed content has derivation lineage. Native test payloads must not automatically leak into production tracing. LangSmith-origin capture is outside this pilot.

## 5. Import the next source update

The second import is part of the pilot, not an optional cleanup exercise. Match by immutable source/migration identity, never by name alone. Review **Base / Source / Hub** differences against the last accepted source basis and current destination.

If the Hub diverged, choose explicitly to keep it, replace it with the reviewed source, or reconcile manually. Preserve an existing personal draft before switching. There is no automatic semantic merge. Retain per-item outcome receipts. After a lost response, recover the original operation instead of submitting a new key and creating duplicate destinations.

For safe pushes, review whether the plan is a complete snapshot or a patch. Removed files must be explicit. Omitted tags preserve metadata; an explicit empty tag list clears it. A stale destination/head invalidates the plan.

## 6. Export and leave cleanly

Export the supported changed content with its mapping receipt. Verify bytes and document which content was derived from, rather than equal to, the source version. Keep the original production source and retained tracing/CI available.

Review removal of unchanged managed pilot files, import segments, and configuration. Modified or unowned paths must remain, with manual cleanup explained. Revoke pilot credentials explicitly. Removing a binding or archiving a context does not uninstall files or erase offline copies.

A pilot is complete only when update, recovery, and exit work as well as first import. Record setup effort, handoffs, failures, human review, observed delivery, known/unknown spend, and remaining unsupported work. See [Recovery](/docs/skills/rollout-recovery) for outage and rollback decisions.
