## Current availability

As shipped, repository rollouts are **off by default**: the deployment setting `SKILLS_CONTEXT_CAMPAIGNS_ENABLED` is false unless an operator turns it on. When rollouts are off, the **Repository rollouts** navigation tab is hidden; opening the route directly shows **Repository rollouts are off**. New repository changes cannot be started, but existing rollout records stay readable. An administrator can follow **Read the rollout setup guide**; other members are directed to an administrator. Enabling the setting still requires a qualified local executor. Existing receipts remain inspectable. Persisting campaign records does not qualify the repository executor. This guide therefore does not offer an executable campaign recipe or claim that fleet rollout is enabled.

## What the registered API represents

The [sealed API reference](/docs/skills/sealed-api) includes campaign list/create/read, authorization, pause/resume/cancel, rollback preview, target listing, claims, plans, attempts, and observations. Registration is not permission to bypass an unavailable deployment capability.

A campaign records a **fixed selected inventory** of repository bindings and exact releases. Membership must not expand automatically. A plan records the reviewed destination preimages and patch. A claim or attempt is orchestration state; neither is a successful Git write, merge, install, or delivery observation.

## What the gated executor was exercised to do

For product qualification only, the isolated test stack can turn the setting on. In that stack, against a fake Git server and a synthetic forty-repository fixture, the executor was exercised through these steps:

1. Inventory the selected repositories with the installed CLI. Existing local and nested instructions are read without executing repository code, and an unavailable repository stays listed rather than being dropped.
2. Plan every fixed target with one command, then review one group of targets whose managed result is proven identical together and every exception (a local modification, a deliberate pin, an unavailable repository) individually.
3. Freeze the exact targets, review the preimage-bound plans, and authorize each exposed repository.
4. Create deterministic pull requests, pause, and reconcile an unknown Git write by repository, branch, and marker without creating a duplicate. A merged pull request, an applied plan, and a file comparison against the merged tree are separate observations.
5. Repeat for a second immutable version without advancing the held pins or excluded repositories, then review reverse plans that return to the original release.

This is evidence class **synthetic fixture + fake Git server**. It is not a real-GitHub conformance run, and the rollout checkpoint that would allow it to be advertised has not been accepted. No operator-effort ratio is claimed from these runs.

## Inspect retained evidence

For an existing authorized campaign, the operator checks the selected targets, exact release identities, plans, exceptions, pins, and attempt receipts. An unknown Git-write outcome must be reconciled by repository, deterministic branch, and marker before retry. Pausing prevents new claims but cannot retract a request already in flight.

Repository review and merge remain independent actions. A merged pull request does not prove installation, and installation does not prove that a running agent received the release. Missing observations remain unknown rather than being inferred from aggregate progress.

## Recovery remains a separate job

Cold adoption, recurring update, and recovery need separate evidence. A favorable update result cannot hide an unmeasured rollback. Recovery requires an eligible retained release, reviewed pointer transition, preimage-bound local restore, and observations of affected consumers.

Until campaign qualification is available, repository owners retain their existing review/merge workflow. [Updates and recovery](/docs/skills/rollout-recovery) distinguishes pointer rollback, restore-as-new-version, local restore, old threads, and quarantine. No automatic merge, force push, offline revocation, or fleet-wide success is promised.
