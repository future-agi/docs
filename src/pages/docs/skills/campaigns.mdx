## What the registered API represents

The [sealed API reference](/docs/skills/sealed-api) includes campaign list/create/read, authorization, pause/resume/cancel, rollback preview, target listing, claims, plans, attempts, and observations. Registration is not permission to bypass an unavailable deployment capability.

A campaign records a **fixed selected inventory** of repository bindings and exact releases. Membership must not expand automatically. A plan records the reviewed destination preimages and patch. A claim or attempt is orchestration state; neither is a successful Git write, merge, install, or delivery observation.

## Inspect retained evidence

For an existing authorized campaign, the operator checks the selected targets, exact release identities, plans, exceptions, pins, and attempt receipts. An unknown Git-write outcome must be reconciled by repository, deterministic branch, and marker before retry. Pausing prevents new claims but cannot retract a request already in flight.

Repository review and merge remain independent actions. A merged pull request does not prove installation, and installation does not prove that a running agent received the release. Missing observations remain unknown rather than being inferred from aggregate progress.

## Recovery remains a separate job

Cold adoption, recurring update, and recovery need separate evidence. A favorable update result cannot hide an unmeasured rollback. Recovery requires an eligible retained release, reviewed pointer transition, preimage-bound local restore, and observations of affected consumers.

Until campaign qualification is available, repository owners retain their existing review/merge workflow. [Updates and recovery](/docs/skills/rollout-recovery) distinguishes pointer rollback, restore-as-new-version, local restore, old threads, and quarantine. No automatic merge, force push, offline revocation, or fleet-wide success is promised.
