## Check availability first

Skill tests and context tests are separate. The Tests tab is always listed. Whether a run can start depends on the deployment: test previews and runs need `SKILLS_TESTING_ENABLED` and are refused with HTTP 503 `skills_unavailable` otherwise, models must come from `SKILLS_VERIFIED_MODELS`, and application verification additionally needs a hosted application runtime ([Compatibility](/docs/skills/compatibility#deployment-switches-at-the-sealed-head)). When there is no runtime, choosing **Test on the application** shows **Application tests are off** and explains that the workspace has no hosted application runtime. Answer checks remain available where testing is enabled; text results do not prove an application repair. A control that is unavailable is not a passing result or an invitation to call the API directly. The [API reference](/docs/skills/sealed-api) lists every registered operation.

The context's **Tests** tab holds three things in one place: the saved reviewed regression cases (`GET` and `PUT /model-hub/skills/contexts/{context_id}/tests/`), whole-context text tests, and, where a runtime is configured, application verification. Expand **App version info** to inspect the runtime and its evidence class. On the product's test stack that is a container runtime and **evidence class: synthetic fixture**.

The screenshot uses synthetic test data. It shows the state before an application target is registered, not a test result. The **Tests** tab has three views: **Results**, **Run a test**, and **Cases**. Under **Results**, a context with saved cases but no runs shows **No test runs yet**; those cases stay under **Cases**. **No tests yet** is reserved for a context with neither saved cases nor runs. Neither state means the cases passed.

## Choose the claim being tested

| Evidence | Appropriate claim | Not established |
| --- | --- | --- |
| Static checks | Saved files satisfy structural checks | Model behavior, script safety, or application success |
| Text comparison | The frozen examples, supplied text, and answer checks were compared | Native discovery or real application tool execution |
| Native application comparison | The qualified entrypoint ran against pinned application configuration | Unobserved hosts, cases, or deployments |
| Installation or delivery receipt | Specific bytes were installed or reached an observed boundary | Instruction compliance or a successful business action |

The standing `AGENTS.md` root has no activation score. A child-only test does not establish whole-context behavior. Forced selection and natural selection remain separate observations.

## Test the whole context

On a draft or a published release, open **Tests**, then **Run a test**, and choose **Check answers** to test the saved standing root and its accepted linked skills together. Use **Saved draft** or **Published version** to identify the candidate. The page states that opening tests does not publish or move production. Under **Test case**, the author either chooses **Use a saved test case** (an approved case needs no further tick) or **Write a new request**, entering a **Test request** and **Expected answer contains** text and ticking **I checked this request and its expected answer.** **Compare with** selects a published version or **Without the context**; **Task model** and **Maximum estimated cost (USD)** set the model and spend ceiling (once remembered, they collapse to one line with **Change**). **Preview answer check** shows the outbound content, the number of runs, and the upper cost before anything runs; the author ticks the inventory review under **Before this runs**. **Run answer check** is enabled only for the exact previewed candidate and test case: if either changes, the page asks for a new preview. **Cancel context test** stops new work, and **Attempt details** lists every attempt separately. A saved case can be reviewed and kept as a reviewed regression case for later runs.

The SDK exposes the same flow for several contexts as `plan-set` and `run-set` ([SDK and CLI interfaces](/docs/skills/sdk-cli#author-test-publish-and-request-release-for-a-set-of-contexts)).

## Verify on the application

With a hosted runtime, **Add application target** registers the application that consumes the context. **Pin the application configuration** shows the identities the runtime measured from its live image and mounts, and each verification launch measures them again and refuses a mismatch. The matched application run (`POST /model-hub/skills/contexts/{context_id}/native/preview/` then `POST .../native/runs/`) runs every selected example on the same pinned application with each context version: a candidate, a recorded reference, and the production version. The preview states the cells and the paid ceiling, and starting the run requires an explicit acceptance of the spend. Each cell reports four separate outcomes: the skill selected, the file delivered, the business tool, and the answer. The [repair guide](/docs/skills/repair-failing-trace) follows one failure through this flow.

## Prepare an enabled skill comparison

1. The author saves all file edits and reviews the acknowledged draft revision or immutable version.
2. In the skill's test configuration, the author records the cases and expected behavior. The suite is read or updated through `GET` or `PUT /model-hub/skills/{skill_id}/tests/`.
3. The author requests a run preview and reviews the selected model/provider, outbound content, redaction findings, planned work, and budget. A preview does not start paid execution.
4. The author resolves the preview's findings and explicitly starts the reviewed configuration. The server checks current permissions, limits, and preconditions.
5. The author inspects the run, results, and individual attempts. File reads, selection, tools, answer outcomes, missing work, and provider failures must not be collapsed into one success badge.
6. Evidence remains private until the author explicitly shares it with the declared audience.

The API exposes separate preview, start, read, results, attempts, files, cancel, and share operations for each resource kind. Request fields and response definitions are in [the sealed API contract](/docs/skills/sealed-api). Context and skill identifiers must not be substituted across these routes.

### Read estimates and technical details

Skill test previews and results display money in a readable form such as **$0.24**, **$25**, or **under $0.01**; missing estimates remain **unknown**, never zero. Hovering a displayed estimate shows its exact reported USD decimal. In the run preview, **Technical details** includes the exact upper-bound estimate, exact stop, and price source. The **Estimated-cost stop (USD)** input remains in USD; display rounding does not change the submitted limit or turn an estimate into an invoice.

Result configuration keeps harness, adapter, and evaluator versions under **Technical details**. Individual attempt details put the price source there too. Task estimates, judge estimates, reserved amounts, and unknown calls remain separate; inspect those details rather than treating a rounded total as complete usage.

## Capture a regression case

From a trace in **Observe → Tracing**, **Save as test case** starts a reviewed capture, where the deployment supports it. The operator supplies the physical source identity, reviews authorized source content and redaction, and accepts an explicit expectation. A link to an incident is not a reproduced failure. The context capture API separates source inspection, preview, and acceptance.

Historical repair starts from **Edit viewed vN**, not whichever version happens to be latest. The author preserves unrelated personal work, reviews the candidate against the current publication head, and retains the original content origin. [Agent contexts](/docs/skills/agent-contexts#repair-the-historical-version-that-was-intended) explains that workflow.

## Interpret incomplete and disputed results

Both comparison arms failing is not candidate success. Startup, parsing, tool, and provider errors remain errors. A cancelled run may still include an in-flight paid call. Missing attempts remain incomplete, and expired payloads are not inspectable evidence merely because a receipt survives.

Reviewers can record **Agree with the automatic outcome**, **Disagree with the automatic outcome**, or **Cannot assess** against evidence. An annotation is attributed and append-only; it does not replace the machine result. A new annotation can make an earlier release approval stale.

## Share only the intended evidence

Sharing includes the retained inputs, answers, and receipts visible to the selected audience. Publication does not implicitly share private runs, and sharing does not extend retention. External CI references remain operator-recorded unless an explicitly qualified import exists.

### Attach evidence to a skill publication or label move

In the skill's publication or **Move label** dialog, inspect a matching run, explicitly **Share evidence** if needed, and choose **Attach this evidence**. Only shared, current, inspectable, finished evidence that is eligible for attachment can be selected. Finished does not mean passed; review the outcomes and regressions.

The selected run appears in an **Evidence attached: test run from …** row with its case count, answer regressions, and workspace audience. **View attached results** opens that run; **Remove attachment** clears the selection. Attaching here is only a selection: publication saves it with the new version, while the **Move label** dialog states **Moving saves the attached test evidence with this label change.** The server rechecks it when the operator confirms the operation.

If the selection becomes unavailable or no longer matches, the attached confirmation is replaced by a warning. Inspect the conflict, run tests again, or deliberately choose **Continue without attachment**; it is never silently dropped. With no matching runs, **No tests run for these files. Not tested is not a pass.** is not an attached-evidence state.

[Reviewed releases](/docs/skills/reviewed-releases) binds evidence identity, visibility, expiry, and annotation revision to the exact release decision. Neither a passing comparison nor an approved request changes production by itself.
