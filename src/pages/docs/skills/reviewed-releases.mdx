## Availability and authority

**Pilot preview.** Reviews, typed native evidence, and shared spending controls require integrated qualification. Check [Compatibility](/docs/skills/compatibility) for deployment and package prerequisites. A visible component or a passing unit test is not proof that the complete review path is enabled.

Publication creates an immutable candidate. It does not move production. A writer can publish; a currently authorized administrator must move a protected label. Approval records a decision about a specific packet, not permanent permission to release future content. Existing protection and quarantine remain enforced even when new authoring or testing features are disabled.

## Submit one exact packet

1. Publish the candidate with production unchanged. Record its UUID, version, digest, content origin, and reviewed publication head.
2. Select the evidence that supports the claim. Explicitly share private evidence with the declared workspace audience before attaching it. Sharing includes frozen inputs, answers, and receipts; publication must not silently share it.
3. Name the intended label transition and the exact target environment/binding configuration revision. Include applicable text and/or native evidence and reviewed annotation revisions.
4. Include an exact external experiment/CI link and configuration reference when that pipeline is authoritative. It remains **operator-recorded / unimported** unless a separately qualified import exists.
5. Assign the reviewer and submit. The reviewer finds the request in **Skills → Reviews**, with authorized unread state. Do not rely on a global notification popover or a manually injected deep link as evidence of arrival.

Viewing a request is not approval. Losing scope, role, or evidence visibility removes inaccessible details and unread-count contribution; it does not expose private evidence to an administrator implicitly.

## Inspect evidence without a universal pass badge

| Evidence or observation | What it establishes | What it does not establish |
| --- | --- | --- |
| Static checks | Structure, path/content bounds, warnings and detected capability-related changes | Behavioral correctness or a sandbox |
| Text comparison | Exact supplied text, selected examples, delivered file ranges, and answer checks | Native host discovery, application tools, or actual business effects |
| Native comparison | Outcomes from the qualified pinned application/configuration and planned case matrix | All applications, unobserved cases, or automatic production adoption |
| Installation receipt | Verified materialized bytes for a destination/profile | Model-boundary delivery |
| External CI reference | The attributed operator's recorded handoff and decision | A Hub-imported or automatically enforced verdict |

Either text or native evidence can be selected; one does not automatically require the other. Inspect candidate identity, immutable execution configuration, visibility, payload expiry, and full case×arm×repeat coverage. Both arms failing is not candidate success. Startup, parser, and tool failures cannot become a passed negative-selection case. Preserve demonstrated failures alongside incomplete work.

For native selection, inspect required, forbidden, and optional child identities against the pinned catalog. Forced invocation may show efficacy but cannot satisfy a natural-selection assertion. The standing AGENTS root has no routing score. File delivery is not instruction compliance.

## Capability changes and human disagreement

Inspect the exact diff and deterministic execution-related deltas: declared tools/hooks, added or changed scripts, host metadata, and detected external destinations. An empty change list is not a security certification; declared permissions are not a sandbox.

Use **Agree**, **Disagree**, or **Cannot assess** on the relevant check/attempt, with bounded cited text and an attributed comment. An annotation is append-only and does not overwrite the machine grade. A new annotation advances the revision, including a disagreement added after approval.

Record a decision for the actual packet: approve or request changes. Do not treat a grouped review's final click as proof that reviewing many items took no effort.

## Execute, conflict, and re-review

At execution the server rechecks current authority, intended pointer, release/security revisions, candidate digest, relevant impact, target configuration, evidence visibility/expiry, and annotation revisions—even for a no-op transition.

If the target tools/configuration changed, an annotation was appended, evidence expired, policy changed, or the releaser lost authority, stop. The earlier approval is no longer sufficient. Inspect the conflict and explicitly submit or review a new packet. Do not automatically refresh preconditions, drop a rejected evidence reference, or use force.

After a successful move, inspect the durable event receipt. **Pre-move review currentness** and **post-move pointer state** are separate facts. Production pointing to v7 does not mean checked-in locks or old threads now contain v7. Use [consumer and recovery observations](/docs/skills/rollout-recovery).

## Provider processing, budgets, and retention

Preview must show providers, complete outbound inventory and stable redacted finding IDs, planned calls, estimated upper bound, and the explicitly configured spend stop before paid work. Resolve every finding against that preview; no client-invented finding IDs and no hidden judge or repair call. An AI judge is an explicit paid choice.

The workspace period allowance must be shared across text and native task/judge/approved charged-tool work. Existing Simulation entitlements remain additional checks, not a second remaining balance and not a license to double-bill. Unknown-priced paid tools and arbitrary application credentials are outside the pilot. No monetary default is authorized by this guide.

Known provider estimates, outstanding reservations, unknown spend, and any separately disclosed platform charges are different values. Cancellation prevents new calls; an in-flight call may finish and cost money. Period rollover does not erase an unknown reservation. A lower budget blocks new admissions rather than rewriting prior usage.

Private runs remain private until explicit sharing. Sharing does not extend payload retention. Expired payloads are unavailable even when hash/configuration/count receipts remain; an expired run is not inspectable proof. If the private native-read inventory or shared reservation bridge is unqualified, paid native execution is unavailable.

Paid assistance, automatic promotion, inherited mandatory evidence policies, and delegated service release execution are not enabled by this pilot review workflow.
