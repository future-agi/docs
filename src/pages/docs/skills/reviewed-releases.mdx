## Availability and authority

A **release request** is the version, intended label move, target configuration, and evidence sent to an independent person. **Review** is that person's decision, not publication, a test result, or the request itself. Test-case approval and **Human check** annotations do not authorize a release.

At product commit `e503da41fd21655c94b7d46e64d202c44a886a47`, request submission, the reviewer inbox, reviewer-side renewal, and durable release receipt were exercised end to end on the isolated test stack with synthetic data. That is historical evidence, not verification of the newer wording and combined acknowledgments described here. Screenshots below are from the earlier captured UI and may show older wording. Typed native evidence and paid execution retain their separate qualification requirements. Check [Compatibility](/docs/skills/compatibility) for deployment and package prerequisites. A visible component or a passing unit test is not proof that the complete path is enabled.

For an agent context, publication creates an immutable version without moving production. A writer can publish; a second person reviews the release request; execution separately checks current authority. A **protected label** can be set, moved, or removed only by a currently authorized workspace admin, organization admin, or organization owner—not automation using a system key. Approval records a decision about one exact request revision, not permission to release future content. A standalone skill's protected-label move does not require this second-person workflow; see [release rules](/docs/skills/versions-and-labels#move-a-protected-label). Existing protection and quarantine remain enforced even when new authoring or testing features are disabled.

## Submit one exact release request

1. Publish the version with production unchanged. Record its UUID, version, digest, content origin, and acknowledged publication head.
2. Select the evidence that supports the claim. Explicitly share private evidence with the declared workspace audience before attaching it. Sharing includes frozen inputs, answers, and receipts; publication must not silently share it.
3. Name the intended label transition and the exact target environment/binding configuration revision. Include applicable text and/or native evidence and reviewed annotation revisions.
4. Include an exact external experiment/CI link and configuration reference when that pipeline is authoritative. It remains **operator-recorded / unimported** unless a separately qualified import exists.
5. Assign the reviewer and submit. The reviewer finds the request in **Skills → Reviews**, with authorized unread state. Do not rely on a global notification popover or a manually injected deep link as evidence of arrival.

Viewing a request is not approval. Losing scope, role, or evidence visibility removes inaccessible details and unread-count contribution; it does not expose private evidence to an administrator implicitly.

### Read the release comparison and impact summary

The release diff identifies whose version each column shows. For a context production move, the headings are **In production (context vN)** and **This release (context vN)**, using the actual old and proposed context versions—not a linked skill's version numbers. Another label uses its own name. A first release has **No release yet** on the left; a leaf-skill comparison uses `vN` without `context`.

**Who is affected** separates apps following the moved label from apps pinned to an immutable version. When a complete small impact list has names for all apps (at most three), the summary names each app, the label/version transition it follows, or the version it is pinned to. Otherwise it uses counts, for example: **Of 3 connected apps: 2 move v1 → v2; 1 is pinned and doesn't move. 1 of the 3 hasn't reported a version yet.** That last app is part of the same three, not an additional group. If per-app reporting status cannot be attributed consistently, only the aggregate reporting count is shown.

These are expected selection consequences for registered apps the operator can access, not proof that they installed or received the release. Pinned apps do not move, and missing observations remain unknown. A missing impact read is **Application impact has not been measured.**, not zero affected apps.

## Publish, then send the request

From a saved context draft, inspect the publication comparison and the static-check warnings. Changed files and warnings are open where the author is asked to confirm them. One tick covers the changed files against the published head and, only when present, the listed warnings. For example: **I've checked the 2 changed files against v1 and the 2 check warnings**. Combining the tick does not remove head, warning, or fingerprint checks. If the draft or inspected head changes, inspect it again.

**Publish version** creates the immutable version. **Publish and request release** carries it into the release composer without moving production, with the only available target preselected. If the publication outcome is unknown, retry the same operation; do not create another operation key or silently swap the inspected head.

On a published context, **Request release for vN** opens the composer with that version and the production label selected. Choose an independent person in **Assigned reviewer**, inspect the proposed transition and evidence, then select **Continue**. The primary action is disabled with **Choose a reviewer** while nobody is selected. A sole eligible reviewer may be preselected, but the request is never submitted automatically. **No test evidence attached** is a non-blocking warning, not a passed test or permission to ignore an authoritative external pipeline.

The requester confirms **I've checked this version, where it's going and the evidence I'm attaching.** before **Send request**. The reviewer finds it in **Skills → Reviews** and chooses **Open request**. Publication, the requester's acknowledgment, and the reviewer's approval remain separate decisions; none of them moves production.

### Attach private results deliberately

**Private results are visible only to you; sharing lets the reviewer see them.** The neutral **Private** tag is not a failure status. Selecting a private row opens consent for that result. **Share and attach N selected** is the bulk action; there are no separate per-row share buttons or an **Attach all** shortcut. Consent covers the retained inputs, answers, and receipts shared with the declared workspace audience.

A result carried in from Tests is marked **From your test** and preselected, but not attached before sharing is confirmed. Otherwise the suggested result is the newest matching **Application test**, not an Answer check. Inspect every selected result and its target identity; a suggestion is not proof of suitability. Each attached result keeps its own identity in the request.

The existing release-request API supports the composer with `GET /model-hub/skills/release-requests/options/` (recipients, targets, and shareable evidence for one version), `POST /model-hub/skills/release-requests/inspection/` (a read-only inspection of a proposed request), and `POST /model-hub/skills/release-requests/native-evidence/{evidence_id}/share/`. None moves a label.

## Review and move the label

The independent reviewer opens the changed files, evidence, and **Who is affected** summary, then confirms **I've checked the changes, the evidence and what this release will affect.** Where file counts are available, the sentence names the number of changed files. Choose **Approve release** or **Request changes** for this exact revision; a test pass is not that decision.

After approval, a currently authorized releaser separately confirms **Move production to vN?**. The summary and move button remain. If that same person already ticked the decision for the same request revision and fingerprint in this session, there is no duplicate tick. Another person, a new session without that acknowledgment, or a changed identity requires confirmation again. A stale request invalidates the remembered tick. An ABA move—away from a version and back again—cannot reuse approval just because the visible version number matches.

The acknowledgment is bound to the revision and fingerprint, not just the version name. Reviewer independence, current release authority, and server-side execution checks are unchanged.

## Inspect evidence without a universal pass badge

| Evidence or observation | What it establishes | What it does not establish |
| --- | --- | --- |
| Static checks | Structure, path/content bounds, warnings and detected capability-related changes | Behavioral correctness or a sandbox |
| Text comparison | Exact supplied text, selected examples, delivered file ranges, and answer checks | Native host discovery, application tools, or actual business effects |
| Native comparison | Outcomes from the qualified pinned application/configuration and planned case matrix | All applications, unobserved cases, or automatic production adoption |
| Installation receipt | Verified materialized bytes for a destination/profile | Model-boundary delivery |
| External CI reference | The attributed operator's recorded handoff and decision | A Hub-imported or automatically enforced verdict |

Either text or native evidence can be selected; one does not automatically require the other. Inspect the version identity, immutable execution configuration, visibility, payload expiry, and coverage of every test case, compared version, and repeat. Both versions failing is not success for the proposed release. Startup, parser, and tool failures cannot become a passed negative-selection case. Preserve demonstrated failures alongside incomplete work.

For native selection, inspect required, forbidden, and optional child identities against the pinned catalog. Forced invocation may show efficacy but cannot satisfy a natural-selection assertion. The standing AGENTS root has no routing score. File delivery is not instruction compliance.

## Capability changes and human disagreement

Inspect the exact diff and deterministic execution-related deltas: declared tools/hooks, added or changed scripts, host metadata, and detected external destinations. An empty change list is not a security certification; declared permissions are not a sandbox.

Under **Human check**, use **Agree with the automatic outcome**, **Disagree with the automatic outcome**, or **Cannot assess** on the relevant check/attempt, with bounded cited text and an attributed comment. An annotation is append-only and does not overwrite the machine grade. A new annotation advances the revision, including a disagreement added after approval. Test cases use **Approved** or **Needs approval**; those statuses are not release approval.

Record a separate decision for the actual release request: approve or request changes. Do not treat a grouped review's final click as proof that checking many items took no effort.

## Execute, conflict, and re-review

At execution the server rechecks current authority, intended pointer, release/security revisions, candidate digest, relevant impact, target configuration, evidence visibility/expiry, and annotation revisions—even for a no-op transition.

If the target tools/configuration changed, an annotation was appended, evidence expired, policy changed, or the releaser lost authority, stop. The earlier approval is no longer sufficient. Inspect the conflict and explicitly submit or review a new packet. Do not automatically refresh preconditions, drop a rejected evidence reference, or use force.

After a successful move, inspect **Release receipt**. It leads with the production transition, **Before the move**, **After the move**, **Approved by**, and **Released by**. Open **Audit details** for the recorded preconditions and result: pre-move review checks and post-move pointer state are separate facts. Production pointing to v7 does not mean checked-in locks or old threads now contain v7. Use [consumer and recovery observations](/docs/skills/rollout-recovery).

## Renew a stale approval explicitly

A race can make an approved release request stale before it is released: the target's pinned application configuration changed, an annotation was appended, the release policy changed, or retained evidence expired. The release attempt is refused. **Renew request** opens the changed preconditions; it does not silently reuse the old approval.

After a rule change, the dialog explains: **The release review rules changed after this request was approved, so the approval no longer applies. Review what changed, then approve again.** The evidence summary reports how many test results are kept and that they will be rechecked when the request is renewed. Removed or expired results remain explicitly listed.

Only an assigned independent reviewer, not the author, can renew. Renewal is its own attributed operation:

1. `GET /model-hub/skills/release-requests/{request_id}/renewal/` previews the next packet revision: the `changes` (each item with its before and after values), any `removed_evidence`, the previous fingerprint, and the new fingerprint.
2. `POST` to the same route with the request `revision` and that `expected_fingerprint` (and an `Idempotency-Key`) creates the next immutable revision. It is refused with `review_current` if nothing changed, `review_stale` if preconditions moved again after the preview, and `target_retired` if the reviewed target no longer exists.
3. The new revision starts **pending**. Only a new decision on it can authorize execution. The reviewer can record that decision separately, or approve the renewed revision in the same inspected dialog when it already shows every change.

The renewed packet keeps the author's candidate, label transition, target binding, and evidence selection. Evidence that is no longer available (expired or deleted) is removed and listed in `removed_evidence`, never substituted. A transient loss of the releaser role also refuses the release, but the product does not offer renewal for a role refusal.

![Renew release review dialog with the changed security policy, retained evidence, changed-values disclosure, and explicit acknowledgment before renewed approval](/images/docs/skills/release-renewal.png)

Open **Changed values** to inspect the changed rules and their before/after values, with who changed them and when where available. If those values were not recorded or the server cannot supply them, the dialog says **Values at approval weren't recorded**. A changed revision counter alone does not establish the old policy values; do not infer them from today's settings. Changing a rule and restoring it still invalidates the prior approval.

The reviewer confirms **I've checked every change since the last approval, and it needs approving again.**, then chooses **Renew and decide later** or **Approve again**. **Cancel** leaves the request unchanged. Renewing without approval creates a pending revision; the previous approval does not carry forward. Approving again records a new decision bound to the inspected new revision; it does not move the label.

### Register the application target

For a release that names a target, a person with publish permission on the context registers the application target on its **Connected apps** tab with **Connect an app**: a target name, the label it follows, an update mode (for example **New threads only**), and a runtime manifest file produced by the application's build. The page states that registering does not move any label, and the server rejects a manifest that lacks a pinned native field. The target is registered once and reviewed packets then name its pinned configuration revision.

## Provider processing, budgets, and retention

Preview must show providers, complete outbound inventory and stable redacted finding IDs, planned calls, estimated upper bound, and the explicitly configured spend stop before paid work. Resolve every finding against that preview; no client-invented finding IDs and no hidden judge or repair call. An AI judge is an explicit paid choice.

The workspace period allowance must be shared across text and native task/judge/approved charged-tool work. Existing Simulation entitlements remain additional checks, not a second remaining balance and not a license to double-bill. Unknown-priced paid tools and arbitrary application credentials are outside the pilot. No monetary default is authorized by this guide.

Known provider estimates, outstanding reservations, unknown spend, and any separately disclosed platform charges are different values. Cancellation prevents new calls; an in-flight call may finish and cost money. Period rollover does not erase an unknown reservation. A lower budget blocks new admissions rather than rewriting prior usage.

Private runs remain private until explicit sharing. Sharing does not extend payload retention. Expired payloads are unavailable even when hash/configuration/count receipts remain; an expired run is not inspectable proof. If the private native-read inventory or shared reservation bridge is unqualified, paid native execution is unavailable.

Paid assistance, automatic promotion, inherited mandatory evidence policies, and delegated service release execution are not enabled by this pilot review workflow.
