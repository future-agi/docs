## Release prerequisite

**Pilot preview.** Use only a released, qualified SDK/CLI version advertised for the deployment and selected profile. No package version or tested context-installation command is established by this guide. Until package conformance is published, the new installer is unavailable; do not copy proposed `fi.context` methods into production scripts.

The legacy Skills ZIP recipe is a download/overlay recipe, **not a safe updater**. It can leave deleted files behind or replace local edits. Keep existing installations intact until a reviewed migration plan is available. See [Compatibility](/docs/skills/compatibility).

## Choose identity and destination together

The Use surface should show workspace, resource kind, requested selector, resolved immutable version/digest, client profile/version, project destination, and update policy together.

- A label follows future resolutions; an exact version remains pinned. Neither means hot replacement of an existing thread.
- No selector means `production`. Missing production fails; it does not fall back to latest.
- First-publish installation uses the returned immutable version when no label exists.
- A standalone skill uses the leaf consumption facade; it does not need an agent context. Legacy routes and context routes are not interchangeable.
- Project-root standing instructions and native skill directories are separate adapter outputs. No global/personal installation or implicit host-settings change is promised.

## Use one authentication mode

An administrator issues an isolated, expiring **consume** credential with explicit resource kind/UUID and allowed labels or exact version IDs. **Report** credentials are bound to declared bindings and cannot read content. A consume credential cannot author, publish, run paid tests, or become a broad API credential.

The secret is shown once. Store it in the deployment's secret mechanism, never a URL, committed lock, screenshot, support ticket, or transcript. Issuance retries return the original metadata without showing the secret again. If it is lost, issue a replacement deliberately. Rotate by creating a replacement, observing old-key use, and explicitly revoking the old credential.

Credential metadata includes `last_used_at`, the latest successful authorized consumption operation observed by the server. An absent timestamp is not evidence that offline copies do not exist. Authentication failures do not count as successful use; a successful fetch still does not prove installation or model delivery.

The wire scheme is `Authorization: Context <credential-id>.<secret>`. The dedicated context and leaf-consumption facades require this credential; a human Bearer token is not accepted on those surfaces. Broad credentials remain for separately authorized human authoring and inspection, not as a fallback to isolated consumption. Context mode ignores ambient broad-key environment variables and rejects mixed credentials or auth-header overrides; it does not use dummy broad keys. Global unrelated APIs reject Context credentials.

## Resolve once and verify the whole snapshot

A qualified transport resolves the selector once, records requested and resolved identities, enumerates every manifest page, and retrieves immutable file chunks. Both leaf and context consumption manifests identify the object with `resource_id` and `kind` (`skill` or `agent_context`), alongside `version_id`, `version`, and `digest`. Immutable chunks also carry `resource_id`; a client expecting only `context_id` or `skill_id` is incompatible with this consumption contract.

File offsets are character offsets; byte ceilings apply to UTF-8 output. A chunk may be shorter than the requested byte maximum because JSON escaping also has a response-size ceiling. Follow advancing continuation offsets until complete and verify each file hash and the complete canonical manifest digest. Never infer EOF from a short chunk.

Credential-backed resolve returns a bounded resolution lease. Every immutable page, file, download, and access check carries `X-Context-Resolution` along with the actual credential. This header is not standalone authority. A production move must not splice new files into the staged old snapshot. Revocation, expiry, scope denial, and quarantine override the lease, including cache reuse and 304 responses.

If the lease expires, renew only through a qualified eligible exact session grant or re-resolve and replan. Do not continue old staging with pages from a new resolution. Cache partitions include origin, scope, and credential identity; equal names in different workspaces cannot share authority.

## Review and apply a local plan

Before applying, inspect every addition, replacement, removal, collision, transformation, and local instruction source. A no-lock repository is not already managed. Explicitly establish ownership of the managed entrypoint segment while preserving local text and exposing nested instructions as additional context.

The plan binds source digest, adapter version, previous ownership lock, destination preimages, and output hashes. Application should:

1. Use unique staging and verify all source bytes before touching the destination.
2. Take an installation lock and recheck the approved preimages.
3. Refuse symlink/case/prefix escapes, dirty managed content, unowned collisions, and host-control outputs.
4. Journal changes and retain recoverable backups.
5. Remove only unchanged previously owned files.
6. Verify outputs and commit the lock last.

Imported content cannot quietly install settings, MCP configuration, hooks, CI workflows, or package manifests. Scripts stored in a bundle are not executed during preview/import/planning.

Repository multi-path updates are journaled, not globally atomic for arbitrary live readers. Stop or start a new client session as the qualified profile requires. An interrupted operation remains incomplete until journal recovery and verification finish; a new lock must not claim success for partial files.

## Update, restore, remove, verify, and doctor

| Operation | Review before applying |
| --- | --- |
| Update | Newly resolved follower target and exact differences. Pins must not advance. |
| Restore | Exact retained lock/release and current eligibility. Do not re-resolve historical child labels. |
| Remove | Only unchanged owned files/managed segments. Preserve modified and unowned content and explain manual cleanup. |
| Verify | Complete managed file hashes and lock identity. This verifies bytes, not behavior. |
| Doctor | Filesystem integrity, client discovery, scope/precedence, compatibility, and missing observations separately. |

Sequential standalone-skill installs must preserve a cumulative lock; concurrent installs must not exchange staging files. Local edits or a changed preimage require a new reviewed plan, not a force overwrite. The checked-in-lock CI verifier is a byte check, not behavioral regression automation. Retain the existing experiment/CI pipeline and its permissions/budgets.

## Application and MCP clients

Python sync/async and TypeScript transports must reconstruct the same immutable snapshot and enforce the same auth/lease rules. Transport parity does not certify a native JavaScript application. The qualified Python application adapter mounts approved source/context read-only while leaving conversation state and tool outputs writable in separate locations.

The pilot MCP path uses existing real human-bound MCP identities, not isolated Context-token ingress. Existing MCP configurations opt into the new group explicitly. Use the advertised release-state and release-review reads before mutation. Caller-supplied operation keys survive retries. Manifest pagination and chunk continuation must remain complete through the actual bounded-response layer.

The intended context operations are list, resolve, list immutable files, read immutable file, read release state, read exact release review, read immutable-version dependencies, publish an owned draft, and set a label. The future proposal operation is absent while disabled. Reverse dependents remains separately documented REST behavior. Reading context does not install it, issue credentials, execute its instructions, or authorize promotion.

After installation, consult [Recovery and observations](/docs/skills/rollout-recovery). Installed, discovered, and delivered are different states.
