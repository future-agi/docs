## About

A version freezes the complete file set. A label selects a version for future resolution. A resource can have versions 1, 2, and 3 while `production` still points to v2. Publication and promotion are separate decisions; an operation that also requests a label must satisfy the current label policy before changing it.

Agent-context versions also freeze the accepted linked-skill closure. A following child label records intent, not permission to refresh a published parent's bytes.

## One selection rule

| Request | Resolution |
| --- | --- |
| `version=3` | Immutable version number 3 of the selected resource. |
| `label=production` | The version currently assigned to production. |
| `label=staging` | The version currently assigned to staging. |
| `label=latest` | The highest published version; this virtual label cannot be assigned or removed. |
| Neither selector | Production, not latest. |
| Both selectors | An invalid-selector error. |

If neither selector is supplied, the default is `production`. A missing label returns HTTP 404; missing production does not fall back to latest. The first publication can be consumed by its explicit immutable version while production remains unassigned. Consumers should retain `version_id` and `digest`, not only the mutable label.

The legacy multi-skill ZIP route can include resolvable leaves while listing missing-label entries under `skipped`; that is not whole-context resolution. Context consumption must preserve the complete immutable closure.

## Drafts do not change production

Each author has one live personal draft per resource. A saved revision protects against overwriting a newer save from another tab. On conflict, the author preserves local text, compares the server revision, and explicitly chooses how to continue. Publication is not an autosave side effect.

The original leaf draft API supports its legacy stale-base workflow. **Agent contexts do not have a force-publication shortcut.** A context repair starts from **Edit viewed vN**. If latest moves, the author compares the draft against the new head and acknowledges that head without replacing the historical draft contents. Publication records both content origin and publication parent. [Agent contexts](/docs/skills/agent-contexts) describes draft preservation and head acknowledgment.

Ordinary publication with content identical to latest can return `unchanged: true`. An explicit historical restoration is different: it creates a new version even when those bytes match latest.

## Compare before promoting

The author compares the proposed version with the selected prior version and production, including added, removed, and modified files. For a context, the comparison also includes accepted dependency changes. A file diff does not establish model behavior.

A context release request records the version and digest, intended label transition, current release/security revisions, impact, target configuration when applicable, evidence visibility/expiry, and annotation revisions. Context release diffs use **In production (context vN)** and **This release (context vN)** so the parent versions are not confused with linked-skill versions. [Reviewed releases](/docs/skills/reviewed-releases) explains **Who is affected** and separates author submission, the second person's review, and authorized execution.

In a standalone skill's **Versions** tab, open the label row's **⋯** menu and choose **Move** or **History**. Version rows open their files; their **⋯** menu also offers comparisons, restoration, and label actions. A disabled action states the missing permission or precondition.

In **Move label**, **Attach this evidence** selects an eligible shared run. Its **Evidence attached** row identifies the run and offers **View attached results** or **Remove attachment**. The summary leads with test-case outcomes and sharing; model settings and attempt counts are under **Technical details**. The attachment is saved only when the label move succeeds, not when it is selected; stale or unavailable evidence needs an explicit decision. See [attaching evidence](/docs/skills/tests#attach-evidence-to-a-skill-publication-or-label-move).

## Move a protected label

**Protected label (only admins can move it)** means only a currently authorized workspace admin, organization admin, or organization owner can set, move, or remove that label. Automation using a system key cannot move it. Writers can still publish immutable versions; publishing permission does not grant protected-label authority. Protection is not a claim that the content is safe or that a second person has approved it.

The rules differ for standalone skills and agent contexts:

| Resource | Release decision |
| --- | --- |
| Standalone skill | An authorized admin can move a protected label in one inspected action, including a permitted label move requested during publication. A second person's approval is not required by this skill flow. |
| Agent context | A release request needs a second person's review because one release can change several skills. Publication leaves production unchanged; approval alone does not move it. Execution separately rechecks authority, including admin authority for a protected label. |

The action's rule note reflects the workspace's current protected-label names and review requirement. Do not assume that `production` is always protected or that an unprotected context label bypasses the context release request. An admin can use **Change rules** where offered to open **Manage label protection**. Protection survives removal of the label pointer; changing the protected-name list does not move any label. Editing rules never silently refreshes the state already inspected in another open dialog: reload and inspect before attempting the move again.

Compare-and-swap checks include the current pointer and aggregate release revision. The latter detects ABA changes such as v4 → v5 → v4 even though the pointer number again matches. Omitting `expected_version` from a legacy request is not a way to bypass required protected-release preconditions.

If authority, policy, evidence, annotation, target configuration, or relevant release state changes, stop and inspect the conflict. For a context release request, the independent reviewer uses **Renew request** and decides on the new revision; for a skill action, explicitly reload and inspect the current state before retrying. An old approval must not be made current by silently refreshing fields or dropping evidence.

Label history records the transition and actor. A reviewed context release's durable receipt distinguishes **currentness before the move** from **pointer state after the move**. Its pointer describes the execution event, not a promise that the label has never moved since.

## Choose the correct rollback operation

| Operation | Effect | Does not do |
| --- | --- | --- |
| Roll back a label | Points the label at an eligible retained immutable version after reviewed authorization | Create a new content version or update installed files |
| Restore as new version | Copies a historical complete snapshot into a new immutable version; context restoration retains its accepted lock | Move production automatically |
| Local locked restore | Applies a new preimage-bound plan for an approved exact release/lock | Reauthorize a quarantined release or rewrite existing conversation history |

The legacy leaf restore endpoint uses the default note `Restored from vN` unless supplied otherwise. Its explicit restore path allocates a new version, including when the digest matches latest. Ordinary unchanged-publish deduplication must not be applied to that operation.

A label rollback cannot replace content already installed or delivered to a conversation. A lower version number can be an intentional recovery release; consumer state must be compared by immutable identity and observation, not numeric ordering.

## Retirement and quarantine

Retirement hides a source from new direct selection. Retained published parents preserve embedded child bytes; retirement is not revocation. Quarantine blocks future managed distribution and continuation of the affected identity, subject to current checks. Neither erases offline copies or retracts a model call already sent.

### Restore an archived skill

Where archived recovery is available, a workspace or organization admin opens the Skills library's **More > Archived skills**, selects **Restore** beside the original skill, and reviews the retained label targets. Check **I've checked which labels come back with this skill.**, then select **Restore skill**; the note is optional.

This restores the original UUID with its versions, label targets, protection policy, and history. It does not create a version, move production to latest, clear quarantine, or replace installed files. A retained label can become fetchable again at its existing version, subject to current access and quarantine checks. A live namesake blocks restoration; creating another skill with the same name is not recovery of the original identity. See [recovery and conflicts](/docs/skills/rollout-recovery#restore-an-archived-skill) and the [post-seal API operations](/docs/skills/api-reference#restore-an-archived-skill).
