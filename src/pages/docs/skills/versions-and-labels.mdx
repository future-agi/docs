## About

A version freezes the complete file set. A label selects a version for future resolution. A resource can have versions 1, 2, and 3 while `production` still points to v2. Publication and promotion are separate decisions; an operation that also requests a label must satisfy the current label policy before changing it.

Agent-context versions also freeze the accepted linked-skill closure. A following child label records intent, not permission to refresh a published parent's bytes.

## One selection rule

| Request | Resolution |
| --- | --- |
| `version=3` | Immutable version number 3 of the selected resource. |
| `label=production` | The version currently assigned to production. |
| `label=staging` | The version currently assigned to staging. |
| `label=latest` | The highest published version; this virtual label cannot be assigned or removed. |
| Neither selector | Production, not latest. |
| Both selectors | An invalid-selector error. |

If neither selector is supplied, the default is `production`. A missing label returns HTTP 404; missing production does not fall back to latest. The first publication can be consumed by its explicit immutable version while production remains unassigned. Consumers should retain `version_id` and `digest`, not only the mutable label.

The legacy multi-skill ZIP route can include resolvable leaves while listing missing-label entries under `skipped`; that is not whole-context resolution. Context consumption must preserve the complete immutable closure.

## Drafts do not change production

Each author has one live personal draft per resource. A saved revision protects against overwriting a newer save from another tab. On conflict, the author preserves local text, compares the server revision, and explicitly chooses how to continue. Publication is not an autosave side effect.

The original leaf draft API supports its legacy stale-base workflow. **Agent contexts do not have a force-publication shortcut.** A context repair starts from **Edit viewed vN**. If latest moves, the author reviews the candidate against the new head and acknowledges that head without replacing the historical candidate. Publication records both content origin and publication parent. [Agent contexts](/docs/skills/agent-contexts) describes draft preservation and head review.

Ordinary publication with content identical to latest can return `unchanged: true`. An explicit historical restoration is different: it creates a new version even when those bytes match latest.

## Compare before promoting

The author compares the candidate with the selected prior version and production, including added, removed, and modified files. For a context, the review also includes accepted dependency changes. A file diff does not establish model behavior.

The review packet records candidate identity, intended label transition, current release/security revisions, impact, target configuration when applicable, evidence visibility/expiry, and annotation revisions. [Reviewed releases](/docs/skills/reviewed-releases) separates author submission, reviewer decision, and authorized execution.

## Move a protected label

An authorized administrator executes a protected transition only after reviewing the exact packet. A writer's ability to publish does not grant that authority. Approval alone does not move production, and a broad system key does not inherit a human administrator's protected-release permissions.

Compare-and-swap checks include the current pointer and aggregate release revision. The latter detects ABA changes such as v4 → v5 → v4 even though the pointer number again matches. Omitting `expected_version` from a legacy request is not a way to bypass required protected-release preconditions.

If authority, policy, evidence, annotation, target configuration, or relevant release state changes, the operator inspects the conflict and renews review. An old approval must not be made current by silently refreshing fields or dropping evidence.

Label history records the transition and actor. The durable release receipt distinguishes **currentness before the move** from **pointer state after the move**. Its pointer describes the execution event, not a promise that the label has never moved since.

## Choose the correct rollback operation

| Operation | Effect | Does not do |
| --- | --- | --- |
| Roll back a label | Points the label at an eligible retained immutable version after reviewed authorization | Create a new content version or update installed files |
| Restore as new version | Copies a historical complete snapshot into a new immutable version; context restoration retains its accepted lock | Move production automatically |
| Local locked restore | Applies a new preimage-bound plan for an approved exact release/lock | Reauthorize a quarantined release or rewrite existing conversation history |

The legacy leaf restore endpoint uses the default note `Restored from vN` unless supplied otherwise. Its explicit restore path allocates a new version, including when the digest matches latest. Ordinary unchanged-publish deduplication must not be applied to that operation.

A label rollback cannot replace content already installed or delivered to a conversation. A lower version number can be an intentional recovery release; consumer state must be compared by immutable identity and observation, not numeric ordering.

## Retirement and quarantine

Retirement hides a source from new direct selection. Retained published parents preserve embedded child bytes; retirement is not revocation. Quarantine blocks future managed distribution and continuation of the affected identity, subject to current checks. Neither erases offline copies or retracts a model call already sent.

Archived-identity recovery remains subject to the deployment's actual enabled surface. A replacement resource with the same name is not the original UUID. [Updates and recovery](/docs/skills/rollout-recovery) covers preserved identities, eligibility, interrupted applications, and unknown consumers.
