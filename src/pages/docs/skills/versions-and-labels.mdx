## About

A version freezes a skill's files. A label selects which version a consumer should fetch. For example, `support-policy` can have versions 1, 2, and 3 while `production` still points to version 2 and `staging` points to version 3. Publishing version 3 does not move `production` unless you explicitly request that label change.

## One selection rule

REST resolve, downloads, and MCP use the same rule:

| Request | Resolution |
| --- | --- |
| `version=3` | Immutable version number 3 of this skill. |
| `label=production` | The version currently assigned to `production`. |
| `label=staging` or another label | The version currently assigned to that label. |
| `label=latest` | The highest published version number. `latest` is virtual and cannot be assigned or removed. |
| Neither `version` nor `label` | `production`. |
| Both `version` and `label` | HTTP 400 `invalid_selector`. |

If you supply neither selector, the default is `production`, not `latest`. A missing label returns HTTP 404 `label_not_found`; there is no fallback. An unpublished skill is visible in the library as **Not published** but cannot be resolved. Resolution responses include the immutable `version_id` and `digest`, so record those rather than only the mutable label.

Multi-skill downloads are the exception to whole-request failure for a missing label: resolvable skills are included, and skills missing the label appear in the lock file's `skipped` array. If none resolve, the request returns `nothing_to_download`. Numeric `version` is allowed only for a download with exactly one name.

## Drafts do not change production

Each person has one draft per skill. It stores files, a note, a `base_version`, and a numeric `revision` on the server. Another person's draft is separate; the detail page can show that they have work in progress, but comparisons with `draft` use your own draft.

Saving checks the revision to avoid overwriting newer edits from another tab. A mismatch returns `draft_conflict`. Reload the server's draft, compare your unsaved work, and retry against the current revision only after deciding which content to keep.

Publishing checks whether the draft's `base_version` is still the latest version. If someone published meanwhile, `stale_base` asks you to compare before proceeding. **Publish anyway** uses `force: true`; it accepts the older base, not a bypass of file checks or warning acknowledgment.

On a successful draft publish, the draft is removed. The published version has a monotonically increasing number, starting at 1, plus a UUID and digest. Publishing content identical to the latest version returns the latest version with `unchanged: true` and creates no duplicate version.

## Compare before promoting

Open a skill's **Versions** tab. Select two versions and choose **Compare**, or use a version's menu to compare with the previous or production version. You can also compare your draft with a published version.

The comparison lists added, removed, modified, and unchanged files. Select a changed file for a side-by-side text diff. This compares file contents, not model behavior or evaluation results.

## Move a label or roll back

In **Versions**, choose **Move** for a label, select the target version, review the file changes, and confirm the move. To roll back, point `production` at an earlier reviewed version. No content is edited and no version is deleted.

![Move production dialog with target version and file-change summary](/images/docs/skills/skills-move-label.png)

Label history records the previous version, next version, actor, note, and time for promotions, rollbacks, and removals. A removal has `to_version: null`. This history does not require the licensed audit-log feature.

![Label history drawer with promotion and rollback by synthetic actors](/images/docs/skills/skills-label-history.png)

Use compare-and-set protection when changing a label with REST or MCP. `expected_version: 2` means “move it only if it still points to version 2.” `expected_version: null` means it must not exist. Omitting the field makes the change unconditional. If another writer changed it first, the server returns `label_conflict` with `current_version`.

This Bash example rolls `production` from version 3 back to version 2. It assumes both versions exist and production still points to 3.

```bash
export HOST_API="https://api.futureagi.com"
: "${FI_API_KEY:?Set FI_API_KEY}"
: "${FI_SECRET_KEY:?Set FI_SECRET_KEY}"
: "${FI_WORKSPACE_ID:?Set FI_WORKSPACE_ID}"
: "${SKILL_ID:?Set SKILL_ID to the skill UUID}"
curl -fsS -X PUT \
  -H "X-Api-Key: $FI_API_KEY" \
  -H "X-Secret-Key: $FI_SECRET_KEY" \
  -H "X-Workspace-Id: $FI_WORKSPACE_ID" \
  -H 'Content-Type: application/json' \
  --data '{"version":2,"expected_version":3,"note":"Roll back after reviewing the policy change"}' \
  "$HOST_API/model-hub/skills/$SKILL_ID/labels/production/"
```

<Note>
A label move affects later fetches. It cannot update files already installed on a machine or replace content an application has cached. Reinstall or refetch, and check the resolved version ID and digest.
</Note>

## Restore content without rewriting history

Choose **Restore as new version** on an earlier version. Restoration republishes that version's complete file set on top of the current latest version. The default note is `Restored from vN`. If its digest already matches the latest version, the unchanged-publish rule avoids a duplicate.

Restoration and rollback are different: restoration adds a version when the content differs, while rollback moves a label to an existing version. After restoring, move any labels you want consumers to use. Restoration alone does not promote `production`.

Individual published versions cannot be edited or deleted. Archiving the skill hides it from the library and makes it unavailable to consumers; it does not turn its old versions into editable drafts.
