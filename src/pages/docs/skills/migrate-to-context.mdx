## About

This guide follows one migration from start to exit: a Langfuse `langfuse-skills-v1` exchange and a private local folder reviewed as a single set, published as leaf skills, assembled into one agent context, piloted in a project, updated a second time, exported, and removed.

The screenshots come from the product's own test flows on a Future AGI test stack, which migrate a small synthetic library: a versioned exchange and a private folder holding three supported skills and one deliberately unsupported member. The complete automated runs described under [What the complete automated runs observed](#what-the-complete-automated-runs-observed) used a larger synthetic library of fifteen members, fourteen of them supported. Both show the product behavior for a fixture. It does not show a migration of any customer's data, and it does not show that a model naturally selected or followed the installed instructions.

Before starting, read [Retained migration](/docs/skills/migration) for the review model and [Compatibility](/docs/skills/compatibility) for deployment prerequisites. Migration never changes the source, issues runtime credentials, or moves a production label.

## 1. Inventory every source first

1. The operator runs the local compatibility inventory over the private folder. It produces an **inventory packet** that lists every inventoried source, its immutable origin, project, resource, revision and digest, and the proposed context.
2. The operator keeps the packet. A later import can be matched to the same source only through these identities; a skill name is not an identity.
3. The Langfuse material must already be in the `langfuse-skills-v1` exchange schema. An arbitrary Langfuse export or a remote URL is not accepted.

In the fifteen-member harness library, the packet reported the complete inventory, one member that cannot be imported, and a compiled-context check that listed that member as an `unsupported_members` diagnostic.

## 2. Review the whole set once

1. In **Skills → Import → From another tool**, the operator opens **CLI inventory** and chooses **Choose inventory packet**, which previews its sources. Alternatively, choose the source files or private folder and select **Preview import**.
2. **Review all items** lists each member with its source identity, destination, file count and size, and the decision that will apply. One decision applies to every listed item.
3. A member that cannot be imported is shown as **Left out** with its reason. In the fixture, a binary file was left out as `file_not_text`.
4. The operator acknowledges the exception with **Leave out 1 skill that can't be imported. The others import without it.** This is a supported-subset trial, not a complete migration.
5. Under **Import as**, **Published v1, no labels** is selected by default; choose drafts instead if publication is not intended. The operator explicitly checks **I confirm my rights to copy all 3 items, including their licenses and retained notices.** (the count reflects the reviewed selection) Publication warnings, if present, require their own acknowledgment.
6. **Import and publish** creates the leaf versions. The result in the screenshot's fixture was three versions published without labels; production was unchanged.

## 3. Assemble one context

Below the result, **Agent context from this migration** proposes a context from the local inventory. Each skill is pinned to the exact version that was just published. Nothing is linked or published until the operator accepts it. After acceptance, the operator reviews the complete context as described in [Agent contexts](/docs/skills/agent-contexts) and publishes it. The fixture's context was published as version 1 with no label moved.

## 4. Pilot an install, with the limits stated

1. Under **Create a read-only key**, choose the expiry and select **Create credential**. This step is offered after publishing the context in the migration dialog and on the context's **Use** tab. The key is consume-only, bound to that exact version, cannot read drafts or other versions, and shows its secret once.
2. The operator generates a reviewed install plan for the project, inspects it, and applies it. The product states that without a released package and a verified host profile, a pilot install is a preview and not delivery evidence.

![Read-only key created for context version 1 in the migration dialog, with the preview-only warning and unchanged production](/images/docs/skills/workflow-migrate-pilot-credential.png)

In the product, the check that follows an install compares checked-in bytes with the plan, and the CLI reports discovery and delivery as `not_observed`. Treat an install as a file result only. The harness's separate model-boundary observation, described below, used a scripted synthetic model response.

## 5. Take a second update without losing local work

1. The operator prepares a later import from the same inventory identities. The preview matches destinations by those identities.
2. If a destination has a personal draft, the item is held: **Preserve your draft before replacing it, then preview again.** The operator chooses **Preserve draft** for the skill, then previews again.
3. Items that can be replaced are shown as **Replace with reviewed source**. The operator reviews the new set and publishes it as new versions.

![Second import preview comparing Base, Source, and Hub, with a personal draft that blocks replacement until it is preserved](/images/docs/skills/workflow-migrate-second-update.png)

In the fixture's checks, the second update created no duplicate imports, the source mappings still matched, and the preserved local draft was kept.

## 6. Export, then remove

1. On the context's **Use** tab, expand **More ways to install** if needed. Under **Export latest linked skills**, **Export N linked skills with mapping receipts** downloads the current published version of each linked skill as its exact archive, with its source mapping receipt, in one ZIP. Export does not change the source, remove local files, or revoke credentials.
2. The operator compares the archives with the originals. In the fixture, the supported members' bytes matched the originals.
3. The operator plans local removal, inspects it, and applies it. Unchanged managed files are removed; modified or unowned local files are preserved. See [Safe installation](/docs/skills/safe-installation).
4. The operator revokes the pilot credential. The credential list then shows it as **Revoked**.

![Use tab exporting the three linked skills with their source mapping receipts](/images/docs/skills/workflow-migrate-export.png)


## What the complete automated runs observed

The whole job, from inventory through removal and revocation, was run by the product's harness four times at product commit `e503da41fd21655c94b7d46e64d202c44a886a47`: cold and configured, each inside and outside a git working tree. All four runs completed, and each passed the same eight outcome checks:

| Check | Observed |
| --- | --- |
| Complete inventory | The reviewed intake plans and the local inventory listed the same whole collection of members. |
| Migration mappings | Each import receipt mapped a source identity to a distinct destination, and the second import matched the same destinations. |
| Source and production unchanged | No leaf or context label was assigned, the retained source bytes were identical to the start of the job, and the exports reported the source unmodified. |
| No duplicate import | The library held one skill per name, with version counts and receipt counts that match the two imports. |
| Round-trip bytes | The exported archives' file contents were compared with the originals. |
| Local work preserved | The project files outside the managed paths were observed on the filesystem after the update and removal. |
| Delivered identity | The delivered content identities were derived from the requests an installed Codex CLI binary sent to a scripted synthetic model stream. |
| Credential revoked | A use of the credential before revocation succeeded, a use after revocation was refused, and the credential list showed it revoked. |

The delivered-identity observation used a scripted synthetic model stream, so it shows what the requests contained, not that a model selected or followed the content naturally. The installation used a preview plan (`--adopt-local --allow-preview`) because the host profile is unqualified. These runs did not measure a person's time, did not include a validated competitor baseline, and support no claim about relative effort.

## What this evidence does not show

- Natural discovery or selection of the installed content by a real host with a released package. The Use panel in the run reported the profile as unqualified and the package as not released, and the model stream was scripted.
- Migration of data from a live Langfuse project or a customer machine.
- Time or effort spent by a person. The run was driven by an automated harness.
