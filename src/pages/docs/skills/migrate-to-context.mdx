## About

This guide follows one migration from start to exit: a Langfuse `langfuse-skills-v1` exchange and a private local folder reviewed as a single set, published as leaf skills, assembled into one agent context, piloted in a project, updated a second time, exported, and removed.

The screenshots come from a synthetic run on a Future AGI test stack. The run used fourteen supported skills and one deliberately unsupported member. It shows the product behavior for that fixture. It does not show a migration of any customer's data, and it does not show that a model received the installed instructions.

Before starting, read [Retained migration](/docs/skills/migration) for the review model and [Compatibility](/docs/skills/compatibility) for deployment prerequisites. Migration never changes the source, issues runtime credentials, or moves a production label.

## 1. Inventory every source first

1. The operator runs the local compatibility inventory over the private folder. It produces an **inventory packet** that lists every inventoried source, its immutable origin, project, resource, revision and digest, and the proposed context.
2. The operator keeps the packet. A later import can be matched to the same source only through these identities; a skill name is not an identity.
3. The Langfuse material must already be in the `langfuse-skills-v1` exchange schema. An arbitrary Langfuse export or a remote URL is not accepted.

In the fixture, the packet reported the complete inventory, fifteen library members, one member that cannot be imported, and a compiled-context check that listed that member as an `unsupported_members` diagnostic.

## 2. Review the whole set once

1. In **Skills → Import → Retained migration**, the operator chooses **Choose inventory packet** (or source files, or a private folder) and selects **Preview retained migration**.
2. **Review all items** lists each member with its source identity, destination, file count and size, and the decision that will apply. One decision applies to every listed item.
3. A member that cannot be imported is shown as **Left out** with its reason. In the fixture, a binary file was left out as `file_not_text`.
4. The operator acknowledges the exception with **Leave out 1 blocked member. This is a supported-subset trial, not a complete migration.**
5. The operator also checks **Publish each imported draft as a new version without labels** and **I confirm my rights to copy all items, including their licenses and retained notices.**
6. **Import and publish** creates the leaf versions. The result in the fixture was fourteen versions published without labels; production was unchanged.

![Reviewed set with the left-out member, acknowledged exception, and fourteen published versions](/images/docs/skills/workflow-migrate-reviewed-set.png)

## 3. Assemble one context

Below the result, **Agent context from this migration** proposes a context from the local inventory. Each skill is pinned to the exact version that was just published. Nothing is linked or published until the operator accepts it. After acceptance, the operator reviews the complete context as described in [Agent contexts](/docs/skills/agent-contexts) and publishes it. The fixture's context was published as version 1 with no label moved.

## 4. Pilot an install, with the limits stated

1. In the context's **Use** tab, the operator issues a **pilot credential** with an expiry. It is consume-only, bound to that exact version, cannot read drafts or other versions, and shows its secret once.
2. The operator generates a reviewed install plan for the project, inspects it, and applies it. The product states that without a released package and a verified host profile, a pilot install is a preview and not delivery evidence.

![Pilot credential issued for version 1, with the preview-only warning](/images/docs/skills/workflow-migrate-pilot-credential.png)

In the fixture, the check that followed compared checked-in bytes with the plan. Discovery by a host and delivery to a model were recorded as **not observed**. Treat an install as a file result only.

## 5. Take a second update without losing local work

1. The operator prepares a later import from the same inventory identities. The preview matches destinations by those identities.
2. If a destination has a personal draft, the item is **Held**: "Your personal draft blocks replacement. Preserve it, then preview again." The operator chooses **Preserve draft for** the skill, then previews again.
3. Items that can be replaced are shown as **Replace with reviewed source**. The operator reviews the new set and publishes it as new versions.

![Second import with one held destination and one replacement](/images/docs/skills/workflow-migrate-second-update.png)

In the fixture's checks, the second update created no duplicate imports, the source mappings still matched, and the preserved local draft was kept.

## 6. Export, then remove

1. On the context's **Use** tab, **Export linked skills with mapping receipts** downloads the current published version of each linked skill as its exact archive, with its source mapping receipt, in one ZIP. Export does not change the source, remove local files, or revoke credentials.
2. The operator compares the archives with the originals. In the fixture, the supported members' bytes matched the originals.
3. The operator plans local removal, inspects it, and applies it. Unchanged managed files are removed; modified or unowned local files are preserved. See [Safe installation](/docs/skills/safe-installation).
4. The operator revokes the pilot credential. The credential list then shows it as **Revoked**.

![Export of fourteen linked skills with their source mapping receipts](/images/docs/skills/workflow-migrate-export.png)

![Credential list showing the pilot credential as revoked](/images/docs/skills/workflow-migrate-credential-revoked.png)

## What this evidence does not show

- Native discovery or model-boundary delivery for a real host and its released package. The Use panel in the run reported the profile as unqualified and the package as not released.
- Migration of data from a live Langfuse project or a customer machine.
- Time or effort spent by a person. The run was driven by an automated harness.
