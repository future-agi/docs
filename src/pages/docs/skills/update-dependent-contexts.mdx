## About

When a shared skill gets a new production version, contexts that follow it do not change by themselves. This guide follows one update: the maintainer inspects the dependents, previews and accepts the update into each follower's draft, tests each complete context, reviews and publishes each parent, and then authorizes each label move separately.

The screenshots come from a synthetic run with one shared skill and three contexts, one of which deliberately pins the old version. The run included an upstream version published while a parent was being edited, an unrelated consumer heartbeat, and a source that changed and then reverted. It shows the product behavior for that fixture and does not describe a customer's workspace.

For the concepts behind this flow, read [Agent contexts](/docs/skills/agent-contexts#follow-does-not-mean-silently-update).

## Doing this for a whole set

The Used by tab shows active and historical references on one screen, without a scope switch. From the inventory already open, the maintainer selects the followers and previews and accepts the update for all of them in one reviewed batch. Each follower still receives its own draft, its own accepted lock, its own test, its own review, and its own label decision. The whole-context test form keeps the last request, model, ceiling, and reference in the browser for that organization, workspace, and user, so a person testing several contexts in a row does not retype them. The review attestation is never prefilled. These defaults reduce retyping. They do not reduce what is reviewed.

The SDK covers the same steps for several contexts: `python -m fi.context.testing plan-set` and `run-set` for whole-context tests, `python -m fi.context.release plan-publish` and `publish-set` for publication, and `plan-release` and `request-set` for review requests. Each takes one plan digest per step and refuses a plan that changed. See [SDK and CLI interfaces](/docs/skills/sdk-cli#author-test-publish-and-request-release-for-a-set-of-contexts).

## 1. Inspect the dependents

On the shared skill's **Used by** tab, the maintainer sees every published context release that references it. The tab states that these are published references, not proof of delivery to a running agent. Each row shows the included child version, its update policy, and its state.

In the fixture, the skill's production was v8. Two contexts followed production and still included v7, shown as **Update available**. The third pinned v7 and was shown as **Pinned on purpose**. A following selector never changes an approved parent.

![Used by tab of the shared skill with two followers offered an update, one deliberate pin, and the Prepare draft updates action](/images/docs/skills/workflow-dependents-inventory.png)

## 2. Accept the update into each draft

1. The maintainer selects the followers and chooses **Prepare draft updates for N contexts** (or **Prepare draft updates for 1 context**). The pin is not selectable for an update. Preparation does not move production.
2. The preview shows each exact resolution. Accepting applies it to a separate draft for each context.
3. Each draft's **Linked skills** list shows the accepted child version. In the fixture, the accepted lock for the updated skill read v8.

![Linked skills list of an updated follower showing its accepted locks, with the shared skill included at v8](/images/docs/skills/workflow-dependents-accepted-lock.png)

If the shared skill moves again before publication, for example to v9, the draft still contains v8. Long edits, expiring previews, and unrelated label moves or consumer heartbeats do not refresh the lock. A new update is previewed and accepted explicitly.

## 3. Test the whole context

1. On the draft's **Tests** tab, the maintainer enters a request and an expected literal answer, selects a task model and a cost ceiling, and may select a historical reference version.
2. **Preview answer check** shows the outbound content and the cost before anything runs. The maintainer must confirm the request and expected answer.
3. The result lists the candidate digest, the reference version, and each attempt separately. Execution status is not a release approval, and routing is not applicable to standing instructions.

![Whole-context test result for the candidate and a historical reference, each attempt graded separately](/images/docs/skills/workflow-dependents-whole-context-test.png)

A test of the child skill alone is not evidence about the whole context.

## 4. Review and publish each parent

For each context, the maintainer opens **Continue to publish**, inspects the root, changed files and dependency changes, and checks **I reviewed these changes against the current published version.** Warnings, when present, require the separate **I've read the check warnings for this version.** acknowledgment. **Publish version** acknowledges that reviewed head and publishes in one click. Publication creates an immutable version and moves no label. If the draft or head moved after review, publication conflicts and the review must be renewed.

## 5. Authorize each label move

The label move is a separate authorized step for each parent. Afterwards the review page shows a **Release receipt**: the request and decision identities, the currentness checks before the move, and the pointer state after it. The receipt records the pointer at execution, not its current position.

![Durable release receipt showing the currentness before the move and the production pointer after it](/images/docs/skills/workflow-dependents-release-receipt.png)

## 6. Inspect consumers honestly

The **Connected apps** tab summarizes each declared consumer's **Target release**, **Last delivered**, verification state, and last report. Select **Inspect** for the individual resolved, installed, discovered, and delivered observations and their source and age. In the screenshot, **Last delivered** shows v2 reported by the client for one session, with notices for mixed sessions, an old thread that retains an earlier version, and an available update. Missing stages remain **Not observed**; they are not inferred from delivery.

![Connected apps tab showing target and last-delivered v2, Mixed sessions, Old thread retained, Update available, and an Inspect action for individual observations](/images/docs/skills/workflow-dependents-consumers.png)

Coverage is limited to declared bindings, and observations are reported by the client. Offline and unregistered consumers remain unknown.

## What this evidence does not show

- A model receiving the updated instructions in a real host. Reported delivery is client-reported.
- Behavior of a customer's contexts, which may be larger or differently pinned.
- That approval of one parent applies to another. Each parent has its own review and authorization.
