## Authentication and tenant scope

Human authoring uses an authorized JWT Bearer identity or the existing `X-Api-Key` / `X-Secret-Key` pair, with `X-Workspace-Id` selecting an accessible workspace. The original [API examples](/docs/skills/api-reference#authentication-and-example-setup) show that setup.

Isolated consumption uses `Authorization: Context <credential-id>.<secret>` on its dedicated surfaces. Report grants are binding-scoped and are not read grants. Context credentials cannot be mixed with broad credentials or substituted into authoring endpoints. Immutable consumption continuations also carry the returned `X-Context-Resolution`; this lease header is not standalone authority.

Operation tables describe operation-specific parameters; they do not waive authentication, workspace access, resource-kind checks, label protection, quarantine, or runtime capability checks. The original leaf routes are not aliases for context UUIDs.

## Mutations, retries, and examples

An operation declaring a required UUID `Idempotency-Key` requires a caller-owned key retained across retries of that same intent. After an unknown outcome, the caller reconciles the original operation receipt before creating a new intent. Draft revisions, source revisions, preview IDs, reviewed head identities, and release/security revisions are preconditions, not values to refresh silently.

JSON success envelopes generally contain `status` and `result`; the per-status schema below is authoritative. Binary downloads and empty responses must not be parsed as JSON. A `202` job acknowledgment is not completed work. Conflicts require inspection and deliberate re-review; they are not force-retry instructions.

No synthetic success payload is presented as a live response. Complete schema objects are available under **Request and response schemas**, including required fields, nested definitions, enums, and bounds. Where Swagger has an underspecified object, that limitation remains visible rather than being filled with guessed fields.
