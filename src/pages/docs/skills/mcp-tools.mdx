## About

The platform MCP server lets an agent find a skill and read its files on demand. It also exposes publishing, label changes, and tag updates. These tools use the same workspace scope, [selection rule](/docs/skills/versions-and-labels#one-selection-rule), and [checks](/docs/skills/checks-reference) as REST.

These are platform MCP tools, not tools in the standalone `futureagi-mcp-server` package. Installing that package does not add Skills support.

## Connect and discover

Connect your MCP client to `https://api.futureagi.com/mcp`, or your deployment's MCP endpoint, and complete its authentication flow. The [MCP connection guide](/docs/cookbook/mcp/debug-traces-from-ide) covers client setup and OAuth. Confirm the authorized workspace before reading or changing a skill.

Ask your client to list the available tools. Use the `skills` group when selecting tool groups. If the names below are absent, check the server's deployed version and tool-group exposure; do not substitute similarly named Falcon or standalone-package tools.

| Tool | Access | Purpose |
| --- | --- | --- |
| `list_skills` | Read | Search and filter the workspace library; follow pagination. |
| `get_skill` | Read | Resolve a name and label or version to a manifest without file content. |
| `read_skill_file` | Read | Read a chunk from a path in a specific immutable version. |
| `publish_skill` | Write | Publish a complete file set by its frontmatter name, creating the skill if needed. |
| `set_skill_label` | Write | Move a label, with optional `expected_version` conflict protection. |
| `update_skill_tags` | Write | Replace the skill's tags. |

## Read a complete skill

Give the agent a task such as the following. It is an instruction for an MCP-capable client, not a shell command or an SDK method.

```text
Find support-policy in the current workspace with list_skills.
Resolve support-policy with get_skill using label production.
Keep the returned skill_id, version, version_id, and digest.
Read SKILL.md from that exact version with read_skill_file, starting at offset 0.
Append each returned text chunk in order. If eof is false, request next_offset.
Continue until eof is true. Do not treat the first chunk as the complete file.
Compute SHA-256 of the reassembled UTF-8 text and compare it with sha256.
Read supporting files from the same resolved version only when needed,
following the same chunk and digest checks.
Report the resolved version and which files were read. Do not publish or move labels.
```

The sequence is `get_skill` → `read_skill_file` for `SKILL.md` → additional file reads when needed. `get_skill` has no full file content. `read_skill_file` returns `path`, `sha256`, `size_bytes`, `total_chars`, `offset`, `next_offset`, `eof`, and `text` in the result. Its chunk budget is `24000` UTF-8 bytes.

Offsets are **character offsets**, not byte offsets. Reuse the server's `next_offset`; do not calculate it from byte length or JavaScript string length. A chunk ends at a character boundary. `eof: true` and `next_offset: null` mean the file is complete. Keep reads pinned to the resolved `version` even if someone moves the label while you are reading.

<Warning>
If a result is truncated, a chunk is missing, offsets do not progress, or the final SHA-256 differs, stop and retry the read. Do not use partial instructions. A successful fetch does not prove the agent followed them.
</Warning>

## Publish and promote deliberately

Before using write tools, review the full file set and the target workspace. `publish_skill` publishes by frontmatter name; it is not a draft-save tool. Sending a partial file set can remove files from the new version. Publishing identical content to the latest version returns `unchanged: true` rather than adding another version.

Use a flow such as this after explicitly deciding to publish:

```text
Review the complete support-policy bundle and its checks.
Ask for approval of the files, version note, and any warning acknowledgment.
Call publish_skill with the complete files, the reviewed note, and no production label.
Report the returned version.number, version.id, and version.digest.
Compare the new version with the version currently assigned to production.
Only after approval, call set_skill_label with the skill_id, label production,
the target version, and expected_version equal to the observed current version.
If label_conflict occurs, read the current label again and request a new decision.
```

The publish result contains the version UUID as `version.id`; resolution exposes it as `version_id`. Use the actual tool schema from your connected server for arguments. REST request and response fields are listed in the [API reference](/docs/skills/api-reference).

For a label that does not yet exist, `expected_version: null` means “create only if still absent.” Omitting `expected_version` makes the move unconditional. Never silently retry a conflict as an unconditional write. `latest` cannot be assigned; it always resolves to the highest published version.

`update_skill_tags` changes library metadata, not file contents. Existing tags are replaced by the supplied list. These tools do not add protected labels, approval gates, or a read-only API-key scope. Keep write-tool approval controls in your MCP client.

## What usage records

MCP resolution and initial file reads are counted under the `mcp` channel. A file read records a fetch only at `offset == 0`, not for every subsequent chunk. These are request counts, not counts of unique agents, model invocations, successful tasks, or verified skill use.
