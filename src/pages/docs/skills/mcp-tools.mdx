## About

The platform MCP server lets an agent find a skill and read its files on demand. It also exposes publishing, label changes, and tag updates. These tools use the same workspace scope, [selection rule](/docs/skills/versions-and-labels#one-selection-rule), and [checks](/docs/skills/checks-reference) as REST.

These are platform MCP tools, not tools in the standalone `futureagi-mcp-server` package. Installing that package does not add Skills support.

## Connect and discover

Connect the MCP client to `https://api.futureagi.com/mcp`, or the deployment's MCP endpoint, and complete its authentication flow. The [MCP connection guide](/docs/cookbook/mcp/debug-traces-from-ide) covers client setup and OAuth. Confirm the authorized workspace before reading or changing a skill.

Ask the client to list the available tools. The preview `skills` catalog has **10 reads and 3 writes**. Earlier deployments may expose only the original six tools. If a name is absent, check the deployed version and tool-group selection; do not substitute a similarly named standalone-package tool. The extra seven reads grant no new write authority.

| Tool | Access | Purpose |
| --- | --- | --- |
| `list_skills` | Read | Search and filter the workspace library; follow pagination. |
| `get_skill` | Read | Resolve a name and label or version to a manifest without file content. |
| `read_skill_file` | Read | Read a chunk from a path in a specific immutable version. |
| `list_skill_versions` | Read | List a leaf skill’s published versions, digests and current labels. This is history, not a fetch. |
| `list_agent_contexts` | Read | Find contexts by name, tag or label in the current workspace. |
| `get_agent_context` | Read | Inspect release state, the latest published version and your draft. No draft is a valid result. |
| `list_agent_context_versions` | Read | List a context’s immutable snapshots. Use a context ID, not a leaf skill ID. |
| `get_agent_context_snapshot` | Read | Inspect the entrypoint, pinned skill links and paged file inventory. It does **not** deliver file contents. |
| `get_skill_usage` | Read | Compare recorded loads and trace outcomes by version or agent over an explicit time window. |
| `get_latest_skill_load` | Read | Check for the newest recorded load since a given time. Fetch information is reported separately. |
| `publish_skill` | Write | Publish a complete file set by its frontmatter name, creating the skill if needed. |
| `set_skill_label` | Write | Move a label, with optional `expected_version` conflict protection. |
| `update_skill_tags` | Write | Replace the skill's tags. |

## Read a complete skill

Give the agent a task such as the following. It is an instruction for an MCP-capable client, not a shell command or an SDK method.

```text
Find support-policy in the current workspace with list_skills.
Resolve support-policy with get_skill using label production.
Keep the returned skill_id, version, version_id, and digest.
Read SKILL.md from that exact version with read_skill_file, starting at offset 0.
Append each returned text chunk in order. If eof is false, request next_offset.
Continue until eof is true. Do not treat the first chunk as the complete file.
Compute SHA-256 of the reassembled UTF-8 text and compare it with sha256.
Read supporting files from the same resolved version only when needed,
following the same chunk and digest checks.
Report the resolved version and which files were read. Do not publish or move labels.
```

The sequence is `get_skill` → `read_skill_file` for `SKILL.md` → additional file reads when needed. `get_skill` has no full file content. `read_skill_file` returns `path`, `sha256`, `size_bytes`, `total_chars`, `offset`, `next_offset`, `eof`, and `text` in the result. Its chunk budget is `24000` UTF-8 bytes.

Offsets are **character offsets**, not byte offsets. Reuse the server's `next_offset`; do not calculate it from byte length or JavaScript string length. A chunk ends at a character boundary. `eof: true` and `next_offset: null` mean the file is complete. Keep reads pinned to the resolved `version` even if someone moves the label while the operator is reading.

<Warning>
If a result is truncated, a chunk is missing, offsets do not progress, or the final SHA-256 differs, stop and retry the read. Do not use partial instructions. A successful fetch does not prove the agent followed them.
</Warning>

## Publish and promote deliberately

Before using write tools, review the full file set and the target workspace. `publish_skill` publishes by frontmatter name; it is not a draft-save tool. Sending a partial file set can remove files from the new version. Publishing identical content to the latest version returns `unchanged: true` rather than adding another version.

Use a flow such as this after explicitly deciding to publish:

```text
Review the complete support-policy bundle and its checks.
Ask for approval of the files, version note, and any warning acknowledgment.
Call publish_skill with the complete files, the reviewed note, and no production label.
Report the returned version.number, version.id, and version.digest.
Compare the new version with the version currently assigned to production.
Only after approval, call set_skill_label with the skill_id, label production,
the target version, and expected_version equal to the observed current version.
If label_conflict occurs, read the current label again and request a new decision.
```

The publish result contains the version UUID as `version.id`; resolution exposes it as `version_id`. Use the actual tool schema from the connected server for arguments. REST request and response fields are listed in the [API reference](/docs/skills/api-reference).

For a label that does not yet exist, `expected_version: null` means “create only if still absent.” Omitting `expected_version` removes only that pointer comparison; it does not waive protected-label authorization or required aggregate release-revision checks. Never silently retry a conflict as an unconditional write. `latest` cannot be assigned; it always resolves to the highest published version.

`update_skill_tags` changes library metadata, not file contents. Existing tags are replaced by the supplied list. These tools do not add protected labels, approval gates, or a read-only API-key scope. Keep write-tool approval controls in the MCP client.

## Inspect an agent context without installing it

Use `list_agent_contexts` to get a context ID, then `list_agent_context_versions` to choose a published version. Pass that ID and version number to `get_agent_context_snapshot`. Use `manifest.next_file_offset` for the next page, without changing the version. A blocked snapshot can be inspected subject to permission; do not recommend installing it. Inspection is not a fetch, an installation or a trace load.

The three version or context list reads (`list_skill_versions`, `list_agent_contexts`, `list_agent_context_versions`) take `page` and `page_size`, at most 25 items per page. Snapshot manifests take `file_offset` and `file_limit`, also at most 25. Use the [read-only install flow](/docs/skills/safe-installation) to deliver reviewed bytes; do not pass a consumption credential to the MCP inspection tools.

## Find which agent loaded a version

1. Resolve the leaf skill to obtain its `skill_id` and immutable `version_id`.
2. Call `get_skill_usage` with `kind=skill`, `resource_id`, `version_ids`, `group_by=agent`, and ISO 8601 `from` and `to`. Use a window of at most 30 days ending no later than now. Keep the filters and window unchanged when following `next_cursor`. The default and maximum `limit` is 100; a smaller limit can avoid a client response-size ceiling.
3. For a new integration, call `get_latest_skill_load` with `kind`, `resource_id` and `since`. If `load` is null, no load was recorded in that interval. A returned `fetch` is **not** a substitute for a load.

A verified load identifies the version delivered; it does not prove the model followed the skill or that the skill caused a change in latency or failures. [Open the matching traces](/docs/skills/trace-skills) to investigate.

## What usage records

MCP resolution and initial file reads are counted under the `mcp` channel. A file read records a fetch only at `offset == 0`, not for every subsequent chunk. These are request counts, not counts of unique agents, model invocations, successful tasks, or verified skill use.
