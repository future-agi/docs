## Availability

**Pilot preview.** This guide describes the intended qualified workflow, not a claim that every deployment or SDK already supports it. Before starting, check the [compatibility and release requirements](/docs/skills/compatibility). A missing capability is unavailable; do not substitute an older Skills endpoint or an unreleased SDK method.

## What an agent context contains

An agent context is one immutable release of standing instructions and explicitly linked skills. It is not a hosted agent, a tool permission policy, or writable memory. Keep the application's code, tool authorization, state, tracing, and regression pipeline in their existing systems.

| Part | Behavior |
| --- | --- |
| `AGENTS.md` | Nonempty standing instructions. It does not need YAML frontmatter or a fabricated `SKILL.md`. |
| Owned supporting files | UTF-8 reference text edited with the root. |
| Linked skills | Published leaf skills from the same workspace, mounted read-only under `skills/<name>/`. |
| `.futureagi/context.json` | Generated descriptor recording purpose, owned paths, selector intent, and exact accepted child versions. Inspect it; do not edit it. |

For example, a root can explain routing without granting tool access:

```markdown
# Support context

Use the refund procedure for refund eligibility questions.
Use the chargeback procedure for disputed card transactions.
Do not claim an external action succeeded without its tool result.
```

The compiled tree must fit the limits in [Compatibility](/docs/skills/compatibility#content-limits), including the root, descriptor, all child files, and mount prefixes. Twenty links is a ceiling, not a promise that twenty arbitrary skills fit.

## Create and edit a context

1. In the enabled **Agent contexts** library, choose a new context or import an `AGENTS.md` root. Supply an immutable name and a purpose. Import reviews must list unsupported or nested members rather than silently discarding them.
2. Review the complete owned file set. A context starts as your private, revisioned draft; it does not change production.
3. Add each published leaf explicitly. Choose a pinned version or a following label. Missing `production` is an error, not a fallback to latest.
4. Review the proposed dependency resolution and apply it to the draft. Linked files and the generated descriptor are read-only.
5. Edit the root, supporting files, and purpose in the same draft. Wait for all saves, including edits queued during an earlier save, before testing or reviewing publication.
6. Open the full-page release review. Inspect the root first, changed files, dependency changes, checks, and evidence. Publish the immutable version. Moving a label is a separate authorized operation.

A standalone skill remains a standalone skill: its root is `SKILL.md`, its existing identity and digest are unchanged, and legacy skill routes remain skill-only. Do not pass a context UUID to a legacy skill route.

## Follow does not mean silently update

A following selector records intent; the **accepted lock** records the exact included version. If a draft accepts child v8 and the child's production later advances to v9, the draft still contains v8. Ordinary edits, long-running tests, and a preview expiring do not refresh that lock.

To update, inspect authorized dependents, select follower contexts, preview the new child resolution, and explicitly apply it to each draft. Pins stay pinned. Test and review each complete parent, publish, then authorize its label movement. A changed selector can change the parent digest even if the child bytes happen to match.

Other contexts' label moves and consumer heartbeats are not changes to your candidate. Current authorization and quarantine still apply.

If saving local edits fails before a queued dependency update, that update remains blocked. A later successful ordinary save must not make testing or publication available as though the update happened. Explicitly retry the failed mutation or reload after preserving local work, then inspect the accepted lock and acknowledged revision.

## Repair the historical version you intended

Use **Edit viewed vN** rather than assuming that Edit means production or latest. If another personal draft exists, preserve it through the available checkpoint/export/suspension operation before switching. There is only one live personal draft for a context.

A repair can originate from v4 while latest is v6. The review must distinguish:

- Changes from content origin v4.
- Candidate differences from latest v6.
- Your explicit acknowledgment that this v4-derived repair will become the next latest version.

A new publication records origin v4 and publication parent v6; it must not copy unrelated v6 bytes into the repair. If latest moves after review, publication conflicts. Renew the head review without replacing the candidate. There is no context force-publication shortcut.

## Document editing and draft recovery

Where Document mode is offered for a leaf skill, description and body edit one canonical source string. Unsupported or malformed YAML stays intact and uses Source mode rather than being normalized invisibly. Changing views must not publish or reset undo history.

On a save conflict, compare base, local, and server content. Export unsent changes before reloading or replacing them. Checkpoints are owner-private and bounded; inspect their expiry. Restoring a checkpoint creates a newer draft revision, not a published version or a label move. General semantic merging and unlimited checkpoint history are not promised.

## Test the right claim

A **text comparison** evaluates supplied text and file delivery. The standing AGENTS root has no activation score. A child-only test is not whole-context evidence.

A **native application comparison** is separate evidence from an explicitly qualified actual application entrypoint. It must pin code, runtime, tools, fixtures, model, state, and the full context. Natural child selection, delivered files, executed tools, and answer correctness remain separate. A forced invocation does not establish natural selection.

Start with [the reversible pilot](/docs/skills/reversible-pilot), then use [reviewed releases](/docs/skills/reviewed-releases) and [safe installation](/docs/skills/safe-installation). Neither a passing comparison nor a publication proves that an existing thread received new instructions.
