## Package and deployment prerequisites

The SDK source contains `fi.context` transport and CLI interfaces. That is different from a verified package release. This page documents the inspected interface, not a successful clean-install or native-host qualification. An operator must obtain the deployment-compatible released package and its provenance before use. No `pip install` version is asserted here.

The context **Install** tab offers a staged preview installation: **Choose your tool**, **Create a read-only key**, **Preview the changes**, then **Install**. The badge **Preview: not yet tested with Claude Code** (or **Codex**) is not a qualification claim. The page provides separate plan/inspect and apply commands; it does not run them. Review the full plan before applying it, and supply the scoped key through `FI_CONTEXT_CREDENTIAL`, never inside a copied command. [Compatibility](/docs/skills/compatibility) lists the supported-subset conditions.

## Install the fagi command-line tool

The Future AGI command-line tool, `fagi`, is distributed on npm as `@future-agi/cli` and needs Node.js 22.15 or later:

```bash
npm install -g @future-agi/cli
fagi --help
```

To run it once without installing, use `npx -p @future-agi/cli fagi --help`. npm is the only installation method documented here.

Installing the published CLI is not evidence that your version includes the preview Skills sync commands. Check your binary’s help before scripting against it. The commands copied by the current **Install** tab use `python -m fi.context` or `python -m fi.skills`, not the Go CLI.

| If you need to… | Use | What you can verify |
| --- | --- | --- |
| Put reviewed files in a coding host’s project folder | The dashboard’s **Install** preview. Teams testing the separate Go CLI preview can record hosts once, sync version pins, and verify the lock offline. | A matching digest proves the installed bytes. Check host discovery and activation separately. |
| Load a skill from a running application | The Python or TypeScript SDK with a scoped consume credential and a tracing provider | The SDK can record the immutable version and loading agent on the trace. |
| Let a connected agent inspect the library on demand | The [platform MCP tools](/docs/skills/mcp-tools) in the authorized workspace | MCP can inspect snapshots and read existing usage evidence. A tool call is not a project install or proof of model use. |


## Configure one authentication mode

The CLI reads these environment variables:

| Variable | Meaning |
| --- | --- |
| `FI_CONTEXT_ORIGIN` | Explicit API origin, without a resource path |
| `FI_CONTEXT_ORGANIZATION_ID` | Organization UUID |
| `FI_CONTEXT_WORKSPACE_ID` | Workspace UUID |
| `FI_CONTEXT_CREDENTIAL` | Isolated credential value, supplied through a secret mechanism |

The wire header is `Authorization: Context <credential-id>.<secret>`. A consume credential reads only its grants; a report credential records observations for declared bindings. Neither is a broad authoring key. Secrets belong in neither a plan nor a checked-in lock. [Safe installation](/docs/skills/safe-installation#use-one-authentication-mode) covers issuance, expiry, revocation, and mixed-auth rejection.

## Python transport

The inspected SDK exports `ContextClient` and `AsyncContextClient` from `fi.context`. Both wrap a caller-owned platform client. Their `resolve(name, label=..., version=...)` operation selects one immutable identity and reconstructs all manifest pages. A snapshot exposes `identity`, `read_file(path)`, and `read_all()`; asynchronous reads must be awaited.

`read_all()` verifies the complete file set rather than assuming a single resolve response contains every file. `check_access(identity, lease)` reauthorizes the exact bytes; it does not renew the lease or report model delivery. The transport does not itself install a project, configure a native agent, or start an application.

Python sync/async and TypeScript transport parity is a separate qualification requirement. A TypeScript transport does not establish a native JavaScript application adapter. Exact consumption schemas are in [the sealed API reference](/docs/skills/sealed-api).

## Diagnose skill tracing

The preview telemetry interface is separate from the local-installation doctor. It requires SDK 0.8.0 or later (Python `futureagi` 0.8.0 or later; TypeScript `@future-agi/sdk` 0.3.0 or later). These pages do not state that those versions are published; confirm the release in PyPI or npm first. The older source/package evidence above does not establish it.

```bash
python -m fi.telemetry doctor
npx -p @future-agi/sdk futureagi-telemetry doctor
```

These commands report tracing mode, provider discovery, processor state, naming, the load rule, and corrective guidance without printing keys or file contents. They do not run an application, install files, approve a release, or send a test load. A separate CLI process cannot inspect another process's provider or last load: call `fi.telemetry.status()` / TypeScript `status()` in the application for that information.

The two main controls are `FI_SKILLS_TRACING=on|load_only|off` and `configure`; programmatic configuration takes precedence. Use `agent_scope` / `withAgentScope` to name the agent, and `declare_skill` / `declareSkill` only for an explicit **Reported by the app** load. [See which agents load a skill](/docs/skills/trace-skills) provides preview examples, the provider truth table, and Install's **Check tracing** flow.

Python and TypeScript high-level snapshot reads share the load contract, but TypeScript has no installer, session adapter, or Deep Agents adapter in this scope. CLI/installer operations themselves never emit customer loads. A complete context read does not emit loads for its linked skills. Generated low-level platform methods remain untraced.

## Inspect the CLI before applying changes

The inspected entrypoint is `python -m fi.context`. These commands describe source interfaces, not cloud-verified installation examples:

```bash
python -m fi.context --help
python -m fi.context inventory --repositories selected-repositories.json
python -m fi.context inspect --plan reviewed-plan.json
python -m fi.context verify --project /path/to/project
python -m fi.context doctor --project /path/to/project
```

The inventory input is a JSON array of explicit `repository_id` and `project` selections. Inventory reads selected repositories without hooks or writes. `inspect --diff` explicitly includes bounded source/local text; operators should treat that output as potentially sensitive.

## Plan, then apply

| Command | Interface and review boundary |
| --- | --- |
| `plan` | Requires `--name`, `--client` (`codex` or `claude-code`), `--project`, and `--out`. `--label` and `--version` are mutually exclusive. |
| `inspect` | Requires `--plan`; the operator reviews additions, replacements, removals, collisions, and source/destination identities. |
| `apply` | Requires `--plan`; `--quiescent` is the explicit local-reader coordination option. Application rechecks approved preimages. |
| `update` | Accepts `--lock` or `--project`, writes a new plan through `--out`, and supports read-only `--check`. |
| `restore` | Uses a retained lock and creates a reviewed plan; it is not a production-pointer mutation. |
| `remove` | Plans removal of unchanged owned files, preserving modified and unowned content. |
| `recover` | Requires `--project` and supports `--quiescent`; recovery reconciles an interrupted local journal. |

`--adopt-local` and `--allow-preview` are explicit plan options. They must not be added as routine workarounds for a collision or unqualified host. A preview profile is not delivery evidence. The guide intentionally does not supply a copy-and-run mutating installation recipe until the package and host prerequisites are established.

## Restore from a retained lock in one command

`restore` can read the retained lock of one exact commit with `--lock-from-git COMMIT` (a full lowercase commit id; the CLI runs a read-only `git show` of the lock file in `--project`). Adding `--apply` replaces the separate plan file (do not pass `--out`): it plans, applies, and verifies in one command and prints the plan review and digest, the byte verification, and any preserved local files. It requires `--quiescent`. Discovery and delivery are reported as `not_observed`. This is a local file restoration. It does not move a production label and does not change a conversation that already holds earlier instructions.

## Author, test, publish, and request release for a set of contexts

Four modules take one reviewed plan per step across several contexts. They use a user-bound platform client with `FI_API_KEY`, `FI_SECRET_KEY`, `FI_ORGANIZATION_ID`, and `FI_WORKSPACE_ID`. These are the broad authoring variables, not the `FI_CONTEXT_*` consumption variables above. Each plan file is written with owner-only permissions and its digest binds what the operator saw: a changed plan file is refused, and each execute command requires the exact digest through `--reviewed-plan`.

| Module and commands | What it does | What it does not do |
| --- | --- | --- |
| `python -m fi.context.authoring plan-create` and `apply-create` | Creates one draft per name from shared standing instructions, previews linking every published skill by label (each `--pin NAME:SKILL=VERSION` is an explicit exception), and applies each context's own previewed dependency update after `--accept-resolved-versions`. | Publishes nothing and moves no label. |
| `python -m fi.context.testing plan-set` and `run-set` | Previews one whole-context test per context for a request and an expected literal answer (`--reviewed-case` states they were reviewed; `--draft` or `--version N` selects the candidate; `--reference N` adds a historical version; `--limit` sets the spend ceiling). `run-set` creates one private run per previewed context. | `run-set` refuses without `--reviewed-inventory`, `--no-known-answer-keys`, and `--acknowledge-provider-processing`. Flagged files need `--classify-flagged` and a `--reason`. A run is not a release approval. |
| `python -m fi.context.release plan-publish` and `publish-set` | Prints every changed file, the accepted dependency lock, the reviewed publication head, and the static-check summary. `publish-set` records the reviewed head and publishes each context separately (`--reviewed-changes` is required). | Moves no label. |
| `python -m fi.context.release plan-release` and `request-set` | Previews each exact label move (`--version N`, `--label`, default `production`) and sends one independent review request per context to `--reviewer`. | Releases nothing; a different authorized person reviews and releases each exact parent. |

The single-context test client is also available as `python -m fi.context.testing preview|create|list|get|results|attempt|cancel CONTEXT_ID`. `create` needs `--idempotency-key`, and provider processing must be acknowledged explicitly.

These commands automate transport and checks. They do not replace review, and a reduction in commands is not a claim about operator effort. No package release containing them is established here.

## Verify the right result

Byte verification, client discovery, and model-boundary delivery are separate results. The installer must preserve local policy, reject changed preimages, journal multi-file changes, and commit the ownership lock last. A pointer move does not update checked-in locks or old threads.

[Safe installation](/docs/skills/safe-installation) describes those invariants. [Updates and recovery](/docs/skills/rollout-recovery) explains exact restoration, clean-thread upgrades, and unknown consumers.
