## About

Import existing skill folders without rewriting them in the editor. Preview the upload, select the skills to publish, and review the result for each bundle. The **GitHub** tab supports a separately reviewed public source; [retained migration](/docs/skills/migration) accepts a reviewed subset as drafts. None of these paths executes imported scripts. The upload-and-publish flow below is distinct from those draft-only intake paths.

## Prepare the files

Each bundle needs a root `SKILL.md` with YAML frontmatter containing `name` and `description`. Supporting files keep their relative paths.

```text
team-skills/
  support-policy/
    SKILL.md
    references/
      policy.md
  incident-triage/
    SKILL.md
    references/
      severity-matrix.md
```

You can upload a ZIP, choose a folder, or select loose files. Folder uploads must preserve relative filenames, including paths such as `support-policy/references/policy.md`. Text files must be valid UTF-8. Binary assets are not supported, including binary images placed under `assets/`.

The importer discovers directories containing `SKILL.md`. When one bundle contains another `SKILL.md` deeper in its tree, the outermost bundle wins; the inner candidate is reported as `ignored_nested`, not imported as a second skill. A valid frontmatter `name` determines the skill name; otherwise the directory name is used for preview, and the frontmatter still needs to pass checks before publishing.

## Preview and import

<Steps>
  <Step title="Upload your files">
    In **Skills**, select **Import**. Drop a ZIP, select a folder, or choose files. Uploads are checked before they become published versions.
  </Step>
  <Step title="Review the preview">
    Check each bundle's name, file count, size, status, and checks. Inspect the rejected and skipped entries as well as the valid bundles.

    ![Import preview with New, Changed, Up to date, and Invalid synthetic bundles](/images/docs/skills/skills-import-preview.png)
  </Step>
  <Step title="Select and publish">
    Select the bundles to import. Invalid bundles cannot be selected. Optionally choose `staging` or `production` under **Also label as**. This moves that label on the selected skills when publishing.

    Review warnings for selected bundles and acknowledge them only after you accept their consequences. Select **Import**.
  </Step>
  <Step title="Inspect every result">
    Review the created, updated, unchanged, and failed lists. Each bundle publishes in its own transaction, so one failure does not undo other successful imports. Correct failed bundles and upload them again.

    ![Import result with created, updated, unchanged, and failed counts](/images/docs/skills/skills-import-result.png)
  </Step>
</Steps>

| Preview status | Meaning |
| --- | --- |
| `new` | No live skill with this name exists in the workspace. |
| `changed` | A skill exists and the uploaded file digest differs from its latest version. |
| `unchanged` | Content matches the latest version; the UI shows **Up to date**. No duplicate version is needed. |
| `invalid` | Blocking checks prevent publishing. Fix the files and preview again. |

## Import with REST

The following Bash example previews a ZIP. Set the credentials and workspace UUID in your environment first. Do not set a multipart `Content-Type` header yourself; curl supplies the boundary.

```bash
export HOST_API="https://api.futureagi.com"
: "${FI_API_KEY:?Set FI_API_KEY}"
: "${FI_SECRET_KEY:?Set FI_SECRET_KEY}"
: "${FI_WORKSPACE_ID:?Set FI_WORKSPACE_ID}"
curl -fsS -X POST \
  -H "X-Api-Key: $FI_API_KEY" \
  -H "X-Secret-Key: $FI_SECRET_KEY" \
  -H "X-Workspace-Id: $FI_WORKSPACE_ID" \
  -F 'files=@team-skills.zip;type=application/zip' \
  "$HOST_API/model-hub/skills/import/preview/"
```

Use the returned bundle `key` values, not guessed skill names, for `selected`. Re-upload the same ZIP when importing. In this second example, `SELECTED_KEYS` must contain a JSON array of the exact keys you reviewed, for example a value you copied from the preview. It is not a file path.

```bash
export HOST_API="https://api.futureagi.com"
: "${FI_API_KEY:?Set FI_API_KEY}"
: "${FI_SECRET_KEY:?Set FI_SECRET_KEY}"
: "${FI_WORKSPACE_ID:?Set FI_WORKSPACE_ID}"
: "${SELECTED_KEYS:?Set to a JSON array of reviewed preview keys}"
curl -fsS -X POST \
  -H "X-Api-Key: $FI_API_KEY" \
  -H "X-Secret-Key: $FI_SECRET_KEY" \
  -H "X-Workspace-Id: $FI_WORKSPACE_ID" \
  -F 'files=@team-skills.zip;type=application/zip' \
  --form-string "selected=$SELECTED_KEYS" \
  --form-string 'labels=["staging"]' \
  --form-string 'acknowledge_warnings=false' \
  "$HOST_API/model-hub/skills/import/"
```

For loose files, use a repeated `files` field and set each part's filename to the relative path, such as `-F 'files=@policy.md;filename=support-policy/references/policy.md'`. Include the corresponding `support-policy/SKILL.md` part. The complete response shapes are in the [API reference](/docs/skills/api-reference#import-preview).

## Limits and rejected entries

| Import limit | Maximum |
| --- | --- |
| Compressed ZIP size | 10 MiB |
| ZIP entries | 1,000 |
| Total uncompressed ZIP size | 20 MiB |
| Per-entry compression ratio | 100 |
| Skills per import | 50 |
| Loose-file upload | 200 files |

Every resulting skill must also meet the [file, path, and version limits](/docs/skills/checks-reference#limits). A ZIP under 10 MiB can still fail because its expanded contents are too large.

Absolute paths, traversal paths, symlinks, encrypted ZIP entries, and duplicates are rejected. Nested ZIPs are reported but not opened. `__MACOSX/**`, `**/.DS_Store`, and `.git/**` are skipped and reported. Review these reports before assuming the upload contained everything you expected.

## Import a public GitHub source as a draft

1. In **Skills → Import → GitHub**, the maintainer enters **Public repository URL** and optionally **Branch, tag or full commit**.
2. **Preview source** resolves an immutable commit and inspects the source. For multiple roots, the maintainer chooses **Skill folder**, then **Preview this folder at the same commit**. Branch movement must not change that retained choice.
3. The maintainer reviews the complete files, checks, provenance, and inherited LICENSE/NOTICE text. The rights confirmation and rights-review note are explicit; a public repository is not automatic permission to reuse it.
4. **Import as draft** creates unpublished content. Publication and label movement remain separate decisions.

This flow is bounded to the supported public source contract. It does not establish broad private-repository connector support. The registered operations are GitHub preview creation, retained preview read, and import; see [the complete API reference](/docs/skills/sealed-api).

## Review an upstream update

The skill source records the imported commit, upstream digest, and source revision. **Check updates** creates a retained preview rather than overwriting content. The maintainer reviews the upstream replacement diff and any local divergence. An existing personal draft blocks staging until its work has been deliberately preserved or discarded.

Staging the reviewed source creates a draft without changing published versions or labels. Retrying the same operation reconciles the original receipt rather than creating a second draft save. A locally customized publication must retain honest source provenance, not claim byte identity with upstream.
