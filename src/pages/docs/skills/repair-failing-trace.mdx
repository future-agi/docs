## About

This guide follows one failure from a production trace to a release decision: the trace is captured as a reviewed regression case, the failure is reproduced against the version that produced it, a repair is published from that version, the repair is verified on the pinned application next to the working cases, and the evidence is prepared for a separate release review.

The run behind the screenshots used a synthetic support application, a synthetic refund failure, and a container runtime recorded in the product as **evidence class: synthetic fixture**. It shows the product flow on that fixture. It is not evidence about a customer's application.

Read [Tests and evidence](/docs/skills/tests) first for the claims each result supports, and [Reviewed releases](/docs/skills/reviewed-releases) for the release decision.

## 1. Find the failing trace

In **Observe → Tracing**, the operator opens the trace. In the fixture, a user asked for a refund of a cracked mug, and the assistant told the user that a $25 refund was issued. The trace carries the context digest that handled it, so it can be tied to the exact context version.


## 2. Capture a reviewed case

1. From the trace, the operator chooses **Save as test case**. The review opens in the context the span was delivered from, with every supported segment of the span preselected. The physical trace identity and the selected request and tool text are carried into the review; they are not retyped. The reviewer can leave the span's delivered context and choose another one.
2. In **Save test case**, the operator removes private text from the request and tool result, and sets **Expected answer must contain**, a literal text check and not a model judgement.
3. Under **Required application behavior**, the operator selects, from the context, the skill the application must load and the business action it must take. In the fixture these were the refund policy skill and **Issue a refund**.
4. The operator confirms that the expected behavior was decided independently of the failed answer, and chooses whether to share the redacted case with the workspace.

![Save test case dialog with the redacted request, tool result, expected answer, and required skill and business action chosen from the context](/images/docs/skills/workflow-repair-captured-case.png)

A link to an incident is not a reproduced failure. The next step establishes that.

## 3. Reproduce on the recorded version

1. On the context's **Tests** tab, the operator confirms the **Application target**: its configuration is pinned, and the runtime and evidence class are shown. If none is registered, **Add application target** shows the configuration the runtime measured from its live image and mounts, and **Pin this configuration** records it.
2. In **Test on the application**, the operator selects the case and uses **Test version**, **Compare with**, and **Was failing on** to choose the candidate, comparison, and recorded reference. The panel plans the run from stored data: the recorded version is carried from the captured case, and the production version defaults to the `production` label, or to the context's single live runtime binding. With several runtime bindings there is no default and the reviewer chooses. Planning is read-only: nothing launches and nothing is spent until the reviewer accepts the paid ceiling. A preview states the cell count and paid ceiling, and the operator must accept the charge before running.
3. Read the result's conclusion: it must confirm that **the recorded failure reproduced** on the recorded version before a repair is meaningful, as in the matched-results screenshot in step 5. While a failure remains on the candidate, the page holds the release rather than offering it.

![Plan for a matched application run: nine cells, the paid ceiling, the candidate, recorded reference, and production versions, and the spend acceptance](/images/docs/skills/workflow-repair-reproduced.png)

## 4. Repair from the version that failed

1. The operator chooses **Repair from recorded v4**, which starts the repair from the recorded version. The repair keeps the original content origin even though a newer version exists. See [Agent contexts](/docs/skills/agent-contexts#repair-the-historical-version-that-was-intended).
2. The operator edits the context, reviews it against the current publication head, and publishes the repair as a new immutable version. In the fixture this created v7 with no production label.

## 5. Verify on the application

1. The operator selects the repaired version as the candidate, the recorded version as reference, and the current production version, and includes the working neighboring cases alongside the failing one. In the fixture this was nine cells: three examples across three versions.
2. Each cell is graded on four separate outcomes: skill selected, file delivered, business tool, and answer.
3. The run records that the runtime proved read-only source, read-only context, and closed paid egress.

In the fixture, the working chargeback and shipping cases passed every outcome on all three versions. The original refund failure passed every outcome on the repaired version and failed the business tool on production and on the recorded reference. A passing answer with a failed business tool is a failed cell, not a pass.

![Matched results for nine cells across the repaired candidate, production, and recorded reference, with the original refund failing its business tool on the latter two](/images/docs/skills/workflow-repair-matched-results.png)

The result leads with **Repair verified** only when the server establishes it, followed by the candidate's passing cases, the reproduced historical failure, and the regression coverage. Cases not selected remain explicitly untested. This conclusion describes the matched run only. It does not release anything: the evidence goes to the separate release review below.


## 6. Inspect and annotate

Selecting a cell opens what the application observed: skills opened, business actions and whether they were declined, the answer, and the context and session identity. The human review can record **Agree**, **Disagree**, or **Cannot assess**. It is appended beside the automatic outcome and never replaces it, and a new annotation can make an earlier release approval stale.

![Cell observation for the original refund failure on the recorded reference, with the application's actions, the four automatic outcomes, and the human review form](/images/docs/skills/workflow-repair-cell-observation.png)

## 7. Prepare the release decision

1. The operator records the retained regression pipeline run, its configuration identity, and its decision, and then selects **Share evidence and prepare packet**. In the fixture the pipeline reference was an operator-recorded value and the packet was prepared for the repaired version with one shared evidence item.
2. The packet is submitted for the separate release review. The reviewer approves or requests changes against that exact packet. Preparing a packet releases nothing.
3. If the matched results show a failing neighbor, a failing business tool, or a changed target, the release stays on hold. An earlier approval does not carry over to changed content.


## What this evidence does not show

- Behavior on a customer's application, tools or traffic.
- That an existing conversation received the repaired instructions. Follow **Delivery: see Consumers** to inspect observations; an absent installation or delivery observation remains **Not observed**.
- That the retained pipeline run was executed by Future AGI. The pipeline reference is recorded by the operator.
