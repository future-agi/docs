## About

An [Observe](/docs/observe) project can collect traces without investigating them. Its Error Feed sampling rate starts at 0%. Raise the rate to select new traces for investigation, not to change what Observe stores or which traces your eval tasks run on.

## Enable sampling for a project

Use a workspace with access to **Error Feed** and a project that already receives traces. If your agent hasn't sent a trace yet, start with the [Observe quickstart](/docs/observe/quickstart).

<Steps>
  <Step title="Open the project's settings">
    In **Observe**, open your project. For example, open `ridgeline-support`, the test project for Ridgeline Outfitters' returns agent. Select the **Settings** gear in the project header to open **Configure Project**.

    {/* MEDIA: The Settings gear in the ridgeline-support Observe project header. */}
  </Step>
  <Step title="Set the sampling rate and save">
    Set **Sampling rate** above 0%, then select **Update**. For a test project, use 100% so that sampling won't exclude your test request. For production, choose the fraction of traces you want to investigate: more investigations can use more credits. Leave **Contact attribute for eval sampling** unchanged; it isn't an Error Feed setting.

    {/* MEDIA: Configure Project with the Error Feed sampling rate at 100%, the separate eval contact field, and the Update button. */}
  </Step>
</Steps>

A rate between 0% and 100% selects by trace ID. Retrying the same trace isn't another chance to be selected. Increasing the rate doesn't backfill previously skipped traces. To stop selecting new traces, save a rate of 0%.

### Verify the saved rate with cURL

Set `PROJECT_ID` to the UUID after `/dashboard/observe/` in the project URL. With your workspace's [API key pair](/docs/admin-settings/api-keys) in `FI_API_KEY` and `FI_SECRET_KEY`, run this read-only request with cURL and `jq`. If you self-host, set `API_BASE` to your API URL without a trailing slash.

```bash
curl --fail --silent --show-error \
  "${API_BASE:-https://api.futureagi.com}/tracer/project/${PROJECT_ID:?Set PROJECT_ID}/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" |
  jq -e '.result | {project: .name, sampling_percent: (100 * .sampling_rate)}'
```

For the test project, expect `project` to be `ridgeline-support` and `sampling_percent` to be `100`. This confirms the setting, not that an investigation has run.

## Follow one completed request

Ask the Ridgeline test agent, “Can I return boots I bought last week?” For a recognizable failure, try a case where the returns tool rejects the request but the agent tells the customer the return was approved. Once the agent replies, open the new trace in Observe and note its ID. Look for the **root span**: the outermost operation, with no parent. It must have an end time. A completed tool call inside an unfinished request isn't enough.

{/* MEDIA: The Ridgeline return request in Observe, with its trace ID and completed root above a child tool call. */}

How that root reaches Error Feed depends on how the trace was stored:

| Ingestion path | What triggers investigation sampling |
| --- | --- |
| Inline (Django) | While storing the spans, the backend records the ended root directly for Error Feed. This path doesn't need Kafka. |
| Trace collector (`fi-collector`) | After ClickHouse confirms the root's synchronous insert, the collector publishes a `root_span_written` notification. A running consumer must deliver it to the backend. It identifies the stored trace; it doesn't contain the conversation. |

The backend applies the project's rate to the notified trace. If selected, the trace gets an investigation job. If the investigation finds a problem that groups into an issue, open **Error Feed**, filter by **Project**, and open the issue's **Traces** tab to look for the trace ID. The request may contribute to an existing issue instead of creating a row. A completed investigation with no finding won't create an issue.

{/* MEDIA: The Traces tab of a Ridgeline issue with the example request identified in the Trace ID column. */}

## If the trace is in Observe but the feed is empty

First confirm the rate on the same project and try a fresh request. For a self-hosted collector, [check notification delivery](/docs/error-feed/troubleshooting/no-issues-in-the-feed#the-traces-came-in-through-the-collector): with no `FI_ERROR_FEED_KAFKA_BROKERS`, ingestion can succeed without notifying Error Feed. Waiting won't create the missing notification.
