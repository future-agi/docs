## About

An [Observe](/docs/observe) project can collect traces without investigating them. Its Error Feed sampling rate starts at 0%. Raise the rate to select new traces for investigation, not to change what Observe stores or which traces your eval tasks run on.

## Enable sampling for a project

Use a workspace with access to **Error Feed** and a project that already receives traces. If your agent hasn't sent a trace yet, start with the [Observe quickstart](/docs/observe/quickstart).

<Steps>
  <Step title="Open the project's settings">
    In **Observe**, select **Tracing** and open your project. For example, open `support-agent`, the test project for Ridgeline Outfitters' support agent. Select the **Settings** gear in the project header to open **Configure Project**.

    ![The support-agent Trace view with the Settings gear immediately to the left of Share in the upper-right corner](/images/docs/error-feed/turn-on-error-feed/observe-project-settings-gear.png)
  </Step>
  <Step title="Set the sampling rate and save">
    Set **Sampling rate** above 0%, then select **Update**. For a test project, use 100% so that sampling won't exclude your test request. For production, choose the fraction of traces you want to investigate: more investigations can use more credits. Leave **Contact attribute for eval sampling** unchanged; it isn't an Error Feed setting.

    ![Configure Project for support-agent with the eval contact field empty, Sampling rate at 100%, and Update at the bottom right](/images/docs/error-feed/turn-on-error-feed/configure-project-sampling-rate.png)
  </Step>
</Steps>

A rate between 0% and 100% selects by trace ID. Retrying the same trace isn't another chance to be selected. Increasing the rate doesn't backfill previously skipped traces. The worker checks the rate again when it claims a queued job. Leave the rate at 100% until you finish the test. To stop selecting new traces, save a rate of 0%.

### Verify the saved rate with cURL

Run `export PROJECT_ID=YOUR_PROJECT_ID`, replacing the placeholder with the UUID after `/dashboard/observe/` in the project URL. With your workspace's [API key pair](/docs/admin-settings/api-keys) in `FI_API_KEY` and `FI_SECRET_KEY`, run this read-only request with cURL and `jq`. If you self-host, set `FI_BASE_URL` to your API URL without a trailing slash.

```bash
set -o pipefail
curl --fail --silent --show-error \
  "${FI_BASE_URL:-https://api.futureagi.com}/tracer/project/${PROJECT_ID:?Set PROJECT_ID}/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" |
  jq -e '.result | {project: .name, sampling_percent: (100 * .sampling_rate)}'
```

Check that `project` names the intended project and `sampling_percent` matches the percentage you saved. For `support-agent`, `100` means sampling won't exclude the request; `0` means no new trace will be selected. Neither value tells you whether an investigation has run.

## Follow one completed request

Ask the Ridgeline test agent, “Can I return boots I bought last week?” For a recognizable failure, try a case where the returns tool rejects the request but the agent tells the customer the return was approved. Once the agent replies, open the new trace in Observe. Use the copy button next to **Trace ID** to save the full ID; the header shows a shortened version. Look for the **root span**: the outermost operation, with no parent. It must have an end time. A completed tool call inside an unfinished request isn't enough.

![The boot_return_request root shows OK and a duration of 1.6 seconds. Its authorize_return child has an error indicator, but the reply says the boot return was approved.](/images/docs/error-feed/turn-on-error-feed/boot-return-completed-trace.png)

How that root reaches Error Feed depends on how the trace was stored:

| Ingestion path | What triggers investigation sampling |
| --- | --- |
| Inline (Django) | While storing the spans, the backend records the ended root directly for Error Feed. This path doesn't need Kafka. |
| Trace collector (`fi-collector`) | After ClickHouse confirms the root's synchronous insert, the collector publishes a `root_span_written` notification. A running consumer must deliver it to the backend. It identifies the stored trace; it doesn't contain the conversation. |

The backend applies the project's rate to the notified trace. If selected, the trace gets an investigation job. If the investigation finds a problem that groups into an issue, open **Error Feed**, select **Filter** and choose **Project**, and open the issue's **Traces** tab to look for the trace ID. If the tab shows fewer traces than the cluster total, a missing ID isn't proof that the trace was skipped. The request may contribute to an existing issue instead of creating a row. A completed investigation with no finding won't create an issue.

## If the trace is in Observe but the feed is empty

First confirm the rate on the same project and try a fresh request. For a self-hosted collector, [check notification delivery](/docs/error-feed/troubleshooting/no-issues-in-the-feed#the-traces-came-in-through-the-collector): with no `FI_ERROR_FEED_KAFKA_BROKERS`, ingestion can succeed without notifying Error Feed. Waiting won't create the missing notification.
