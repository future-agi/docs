Error Feed's list page, in the left sidebar under **Error Feed** (see the [overview](/docs/error-feed) if you haven't opened it yet), shows every detected issue across your projects, scoped to the last 7 days until you change the range. A full feed is a queue, not a to-do list: some rows need attention today, most don't.

This guide takes you from a full feed to a handled list: narrow it to what's worth looking at, scan the table for what actually decides priority, then act on what you find, one issue at a time or several at once. Workspace admins can also [change when issues escalate](#change-when-issues-escalate).

## Narrow the feed

Type into the search box (placeholder **Search errors**) to match against the error name, issue group, or category. Next to it, the time range opens already scoped to Last 7 days, and **Filter** opens a panel where you narrow by project, status, severity, fix layer, or source. The **Filter** button shows how many filters are active. See [Issue fields & filters](/docs/error-feed/reference/issue-fields) for the exact set of values each one accepts.

<Tip>
Start from **Severity: Critical** and **Status: Escalating**. Critical narrows to what matters most, and Escalating means Error Feed confirmed the issue's findings are running well above usual, so together they find the critical issues that are getting worse. See [Severity & Status](/docs/error-feed/concepts/severity-and-status) for when to pick each one.
</Tip>

## Scan the table

Each row is one issue. Eight columns run left to right: **Error**, **Severity**, **Status**, **Events**, **Users**, **Fix Layer**, **Trend (14d)**, and **Last seen**.

Three of them decide priority. **Severity** says how bad it is, **Status** says where it sits in your workflow (hover an issue's status to see why it has that status; the issue page shows the same reason under its title), and **Trend (14d)** shows whether it's climbing, flat, or settling down.

The rest is context:

- **Error** names what's failing
- **Events** and **Users** size the blast radius
- **Fix Layer** points at where in your system the fix belongs
- **Last seen** says when it last fired

At the bottom, **Rows per page** sets how many issues each page shows, and the arrows next to it move through the rest.

## Act on what you find

<Note>
**Picking a status yourself turns off automatic status changes for that issue.** Any status you pick, from any of the three ways below, is never changed automatically afterwards. Picking the status an issue already has counts too, and keeps it there.
</Note>

Three ways to act, each suited to a different job in the triage workflow:

- **Handle many at once** for many rows moving to the same status
- **Resolve or acknowledge one issue** for a quick resolve, acknowledge, or move to review from the issue header
- **Change status, severity, or assignee from the sidebar** for a status, severity, or assignee change on a single issue

### Handle many at once

Tick the checkbox on any row and a bulk-select toolbar appears above the table. Tick more rows, then open **Bulk actions** and pick **Mark as Resolved**, **Mark as Acknowledged**, **Mark as For Review**, or **Mark as Escalating** to move every selected issue to that status in one go.

### Resolve or acknowledge one issue

Click a row to open the issue. Its header carries three status buttons: **Resolve** moves the issue to resolved, **Acknowledge** moves it to acknowledged, and **Move to review** moves it to For review. All three disable themselves while the update is in flight.

### Change status, severity, or assignee from the sidebar

Every issue also has a metadata sidebar on the right. Its **Status** and **Severity** rows each open a menu to set a new value directly. The **Status** menu lists all four statuses with the current one highlighted. The **Assignee** row reads **Assign** until someone's on it; click it to open a menu headed **Assign to**, listing everyone in your org plus an **Unassign** option once someone's set.

<Note>
Assigning someone to an issue only records it on the issue itself. It sends no notification of any kind, so tell them yourself if it needs to reach them.
</Note>

<Note>
None of the three ways above show a toast. There's no confirmation of success and no warning on failure, so the save happens silently either way. To check a change went through, re-check the **Status** (or **Severity**) column for that row, or refresh the feed; if the value hasn't moved, repeat the action.
</Note>

## Change when issues escalate

Error Feed moves issues between For review and Escalating on its own. You can change how readily it does that, for example if issues escalate too late or too often for your traffic. The settings apply to every project in your workspace.

Only workspace admins can change these settings. Other members can open the dialog to view them: it shows **Only workspace administrators can change these settings.**, the controls are disabled, and the footer button reads **Close** instead of **Cancel**. See [Roles & permissions](/docs/roles-and-permissions) for who counts as an admin.

1. In the Error Feed page header, click the gear button (tooltip **Escalation settings**) next to **Alert rules**. The **Escalation settings** dialog opens

   <img src="/images/docs/error-feed/guides/escalation-settings-button.png" alt="The Error Feed page with its issue table, and a callout on the gear button in the page header, just left of Alert rules" style={{ borderRadius: '5px' }} />
   *The gear button is in the page header, so it's there whichever filters you have set*
2. Under **Sensitivity**, pick a preset: **Sensitive** (Catches early), **Balanced** (Most teams), or **Calm** (Big spikes only). Pick **Custom** to set each value yourself. The example under the presets shows when an issue that usually gets a given number of findings an hour would escalate and recover; changing that number only changes the example

   <img src="/images/docs/error-feed/guides/escalation-settings-dialog.png" alt="The Escalation settings dialog for Default Workspace with Balanced selected among Sensitive, Balanced, Calm, and Custom, an example of when an issue escalates and recovers, and callouts on the presets and the Save button" style={{ borderRadius: '5px' }} />
   *The example under the presets updates as you switch, so you can compare them before you save*
3. Optionally, open **Fine-tune**. It has two groups, **Escalate** and **Recover**, each with four values: **Findings**, **Times usual**, **Above usual**, and **Hold for**. Editing any value switches **Sensitivity** to **Custom** and shows an **Edited** tag; an invalid value shows an error under the field, and clicking **Save** opens **Fine-tune** at the first one to fix
4. Optionally, open **Preview on a sample issue** to see an example issue's findings over time and when it would escalate and recover with your values
5. Click **Save**. It is enabled only after you change something, and a successful save shows **Escalation settings saved**. To go back to the defaults, click **Reset to defaults**, then **Save**

After you save, open issues are checked again against the new settings. Statuses people picked by hand stay as they are.

Closing the dialog with unsaved changes asks **Discard changes?** first.

### If saving doesn't go through

- **Could not save escalation settings. Your changes are retained.** means the save failed; your edits are still in the dialog, so try **Save** again
- **Settings changed. Reload the latest settings before saving.** with a **Reload settings** button means someone else saved while your dialog was open; reload, redo your change, then save
