A full feed is a queue, not a to-do list: some rows need attention today, most don't. Use [Error Feed](/docs/error-feed) to find the [issues](/docs/error-feed/concepts/understanding-error-feed) that need attention now. Filter by [severity and status](/docs/error-feed/concepts/severity-and-status) before changing anything, then reload one issue to verify the change.

<Prerequisites title="Before you start">
- A project with detected issues. For a practice run, use test issues you intend to acknowledge.
</Prerequisites>

## Narrow the list without changing issues

1. Open **Error Feed** in the left sidebar.

   The list starts with the last seven days across projects.

2. Select the project you want to triage.
3. Set **Severity** to **Critical**.
4. Set **Status** to **Escalating**.

   Critical narrows to what matters most, and Escalating is the one status of the four that hasn't settled into Acknowledged, For review or Resolved. Only matching issues remain. If there are no matches, widen the time range before assuming the project has no issues.

You can also filter by **Fix Layer**. Type in **Search errors** to match an error name, issue group or [category](/docs/error-feed/reference/error-taxonomy). Project, status, severity and fix layer start at their **All** values; [issue fields and filters](/docs/error-feed/reference/issue-fields) lists their options.

**Clear** (tooltip: "Clear all filters") appears when project, status, severity or fix layer is set. It resets those four **and the search text**, but **not the time range**. If only search is set, erase the text directly.

## Decide which rows to handle

Each row is one issue. Three columns decide priority: **Severity** says how bad it is, **Status** says where it sits in your workflow, and **Trend (14d)** shows whether it's climbing, flat or settling down. The rest is context.

| Column | Question it answers |
| --- | --- |
| Error | What failed? |
| Severity | How serious is it? |
| Status | Is it escalating, for review, acknowledged or resolved? |
| Events | How many occurrences does the list report? |
| Users | How many [users](/docs/observe/concepts/users) are affected? |
| Fix Layer | Where does the fix belong? |
| Trend (14d) | Is the issue growing, flat or settling down? |
| Last seen | When did it last occur? |

**Results per page** offers 10, 25 or 50 rows. Use **Back** or **Next** to change pages.

## Acknowledge selected issues

1. Select the checkbox on an issue you intend to acknowledge.

   You should see the bulk toolbar above the table.

2. Select any other issues that need the same status.
3. Open **Bulk actions**.
4. Choose **Mark as Acknowledged**.

   Acknowledged rows no longer match the Escalating filter. Other bulk choices are **Mark as Resolved**, **Mark as For Review** and **Mark as Escalating**.

5. Change the status filter to **Acknowledged**.
6. Reload the feed.
7. Check the **Status** of one of the rows you selected.

   There is no success or failure toast. If the change did not persist, confirm the row and repeat the action.

## Change a single issue

1. Open the issue's row.
2. Choose the action that matches the change:

   - **Resolve** or **Acknowledge** in the header changes status directly. **Ignore issue** sets it to **Escalating**, despite the label. Header buttons disable while updating.
   - **Status** or **Severity** in the metadata sidebar opens a menu of values.
   - **Assign** opens **Assign to**, which lists people in your organization. An assigned issue also offers **Unassign**.

3. If you opened a menu, select the new value.
4. Reopen the issue to check the saved value.

   None of these actions shows a toast, on success or on failure. If the value hasn't moved, repeat the action.

Assigning someone records the assignee but sends no notification. Contact them separately if they need to act.

## Read the list from code

The [error clusters reference](/docs/sdk/reference/error-clusters#error_clusterslist) documents the read operation: `client.error_clusters.list` in Python, `client.errorClusters.list` in TypeScript, `list_error_clusters` in MCP, and the feed list over REST. For the same selection, the SDK list filters are `project_id`, `severity` (`critical`) and `status` (`escalating`). You can also narrow by `search`, `fix_layer` or `time_range_days`. Listing does not change the returned issues; use the dashboard steps above to acknowledge them.
