When an [Error Feed issue](/docs/error-feed) groups several [traces](/docs/observe/concepts/traces), use their shared pattern to decide whether you're looking at one failure or several. Compare a failing run with a working one if available, then check whether errors are rising faster than traffic.

<Prerequisites title="Before you start">
- An issue in the Feed with a [cluster](/docs/error-feed/concepts/understanding-error-feed) of failing traces.
</Prerequisites>

## Read the issue

1. Select the issue in the Feed.

   You should see **Overview**, **Traces**, **Trends** and **Fix**; [Fix](/docs/error-feed/guides/run-root-cause-analysis) is where you request a written analysis.

2. Check the breadcrumb, error-type chip, title, [status and severity](/docs/error-feed/concepts/severity-and-status), and trace count in the header.

   The header and right sidebar stay in place across tabs; the sidebar lets you change status, severity and assignee.

Use **Copy cluster ID** for an identifier to paste into a ticket or message, or **Share** for a direct link to the issue.

## Read the pattern on Overview

1. Read the pattern-summary cards on **Overview**, the default tab.

   The cards describe what is common across the whole cluster, not one trace. In the example below, scans flag “answered text” in 97 of 126 traces for an issue about answering without calling a tool. That gives you a pattern to check in a run, not yet a root cause.

2. Compare events with affected [users](/docs/observe/concepts/users) in the chart below the cards.

   Look for a steady trickle versus a recent spike.

<img src="/images/docs/error-feed/guides/overview-tab-annotated.png" alt="Overview tab with the pattern-summary cards, the events-and-users chart, and the trace evidence reel labeled" style={{ borderRadius: '5px' }} />

If the cards point to one failure mode, inspect the pair below. If they point in different directions or you want a specific run, go straight to **Traces**. The **Cluster Analysis** card at the top of **Overview** offers **Debug this cluster** before an analysis; afterward it shows the root cause and fix, with the confidence level in its collapsed header.

## Compare a matched pair

1. Select **Failing** in the evidence reel to inspect one of the traces behind the pattern.
2. Choose a view mode in the switcher above the reel.

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| View | Question it answers |
| --- | --- |
| **Breadcrumb** | What happened step by step? Start here for a linear read. |
| **Agent Graph** | Is the failure on one possible path or on the only path? |
| **Agent Path** | Which sequence did this run actually take? |

</div>

3. Select **Split with working**.

   When a match exists, you should see the failing trace beside the nearest successful one, paired in advance by Error Feed.

4. Find the first step where the two runs differ.

   Use **Single view** to return to one trace at a time; **Working** shows the successful match on its own.

## Inspect individual traces if there is no match

Not every cluster has a working trace to pair against. If none was found, split compare has nothing to show, so work from **Traces** instead. Use the same tab when the pattern on **Overview** doesn't hold up or you need one specific run.

1. Open **Traces**.

   You should see one row per trace, with **Total traces**, **Avg score**, **Avg turns**, **P50 latency** and **P95 latency** above the grid.

2. Locate the run by **Trace ID** or **Input**.

   The other columns are **Start Time**, **Duration**, **Tokens**, **Cost** and **Score**.

3. Select the row to open the [trace drawer](/docs/observe/guides/explore-dashboard#open-a-trace).

   Inspect the steps of that run rather than treating it as a matched comparison. [Voice](/docs/observe/features/voice) and [simulator projects](/docs/environments/guides/read-run-results) use different drawers.

## Judge urgency on Trends

1. Open **Trends**.
2. Compare errors and traffic over the same interval on the chart's two axes.

   Rising errors on flat traffic suggest the system got worse. If errors rise in proportion to traffic, more requests can explain the count without a higher failure rate.

## Read a cluster from code

The [error cluster reference](/docs/sdk/reference/error-clusters) covers the read-only detail lookup by cluster ID in Python, TypeScript, REST and MCP. The [MCP server](/docs/falcon-ai/guides/use-the-mcp-server) also offers `get_error_cluster_overview` and `list_error_cluster_traces` in its read-only `error_feed` group. Those return data; the split comparison and Trends chart described here are dashboard controls.
