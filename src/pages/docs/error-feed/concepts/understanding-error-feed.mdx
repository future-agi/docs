## About

Two customers ask the Ridgeline Outfitters support agent whether a tent is in stock. Both inventory lookups hit a rate limit. On the first request, a retry returns the stock count. On the second, the agent stops without an answer. Both requests can appear as [traces in Observe](/docs/observe/concepts/traces), but only the second rate limit is an unresolved problem.

[Error Feed](/docs/error-feed) distinguishes a **finding** (one problem an investigation identified) from an **issue** (the group of occurrences you triage). If another inventory lookup ends the same way, its finding can join the existing issue instead of creating a second row. Explained failures from evaluation tasks can also become issues, through a separate path.

## When to use

- You see a trace in Observe but no corresponding row in Error Feed.
- An apparently successful trace appears among an issue's affected traces.
- Two evaluations returned the same low score, but only one contributed to an issue.

## From a stored trace to a published issue

| Stage | What it tells you |
| --- | --- |
| Admission | When the collector reports that it stored a completed root span, Error Feed checks whether scanning is on for the project and applies its [sampling rate](/docs/error-feed/guides/turn-on-error-feed). A selected trace gets an investigation job. Seeing the trace in Observe confirms receipt, not selection or completion. |
| Investigation | The investigator examines the trace evidence and records a report. The report has an overall outcome and can contain zero, one, or several findings. Finishing the investigation does not create an issue. |
| Grouping | Error Feed considers eligible findings from the **current, completed** report. It looks for occurrences of the same problem. A finding waiting for grouping is not yet a member of an issue. |
| Publication | Grouping can add the finding to an existing issue, create an issue for it, or defer it. A deferred finding does not appear as an occurrence on any issue. |

Grouping is on by default for eligible projects. On a self-hosted installation, raising the sampling rate does not start the investigation worker. The worker must be running and receive [trace notifications](/docs/self-hosting/configuration/reference#observed-attribute-catalog).

## Which investigation findings qualify?

The overall outcome describes the task. Recovery describes what happened to a particular problem. For new reports, a finding qualifies for grouping when the investigation records **no recovery**. It does not need to name a violated requirement. The same rule applies to findings from an [Environment](/docs/environments) call.

| What happened on Ridgeline's lookup | Overall outcome | Is the rate-limit finding eligible? |
| --- | --- | --- |
| A retry succeeds and the agent gives the customer the stock count. | Success | No. The agent recovered from this failure. |
| The lookup stops at the rate limit. The investigator cannot judge whether the customer got an answer. | Unknown | Yes. The rate limit went unhandled, even though the investigator could not identify a failed requirement. |
| The agent meets the stated requirement to send a product link but leaves the customer's stock question unanswered after the rate limit. | Success | Yes. Meeting the stated requirement did not resolve the lookup failure. |

A failed outcome alone does not supply a finding to group. Conversely, an eligible finding need not produce a **new** issue. The broader recovery rule did not automatically regroup previously published reports; older reports can still reflect the earlier rule that required both a failed outcome and a violated requirement.

## Which evaluation results qualify?

An issue marked **Eval**, rather than **Scanner**, comes from a [regular evaluation task](/docs/observe/guides/setup-evals). Error Feed considers results created in the last 60 days, even if the task evaluated an older trace. A result needs both a nonempty explanation and one of these failures:

| Result type | Failure rule |
| --- | --- |
| Boolean | The result is `false`. |
| Numeric | The score is strictly below the template's pass threshold. The default is `0.5`. |
| Scored choice | The selected choice maps to a score below the same threshold. For multiple selections, Error Feed averages the scores of the choices the template can map. |

Suppose Ridgeline's *Inventory answer* evaluator maps “No stock answer” to `0.2`. At the default threshold, that result qualifies if it includes an explanation such as “The agent sent a product link but never answered whether the tent was in stock.” The same `0.2` with no explanation does not qualify. A score of `0.5` meets the threshold and does not qualify either.

Error Feed groups similar failure explanations within the same project, eval name, and target type (span, trace, or session). [Instant eval](/docs/observe/features/instant-eval) answers do not enter these groups. A regular eval task can contribute results whether it evaluates historical data or new incoming data. An inline evaluation with no task cannot. The four [per-trace Error Analysis scores](/docs/error-feed/concepts/trace-error-analysis) are separate from both paths.

## What an issue carries

The issue title names the shared problem. Its counts, affected traces, and first and last occurrences describe the group, not one request. [Severity and status](/docs/error-feed/concepts/severity-and-status) tell you how serious it is and where it stands in triage. A fix layer, when present, suggests where to make a change, for example in a tool or in orchestration.

The automatic investigation examines one trace before grouping. **Analyze this cluster** on an existing issue's **Fix** tab asks a different question: what explains the problem across calls? It can compare failing calls with passing ones and suggest a fix. If the evidence does not establish a cause, the analysis can say so. You do not need to run it for an issue to appear.
