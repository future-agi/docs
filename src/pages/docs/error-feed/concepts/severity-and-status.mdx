## About

The Ridgeline Outfitters support agent promises a refund without checking return eligibility. Its issue in Error Feed might read **Scanner · Pending · Escalating**. Those labels answer three different questions:

| Question | Label in this example | What you know |
|---|---|---|
| Who detected the problem? | Scanner | The built-in scanner found it. An **Eval** issue comes from an evaluation task instead. |
| How serious is it? | Pending | The findings are already grouped, but the scanner issue doesn't have an impact grade yet. |
| Where does it stand in triage? | Escalating | This is the initial workflow status. It doesn't mean the impact is high or increasing. |

## When to use

- You need to tell a failed refund-policy eval apart from a scanner finding about the same conversation.
- You're counting Medium issues and need to know which ones actually received that grade.
- You've acknowledged the refund problem and want to keep your impact decision when more evidence arrives.

## Severity: read the badge before the number

A grouped scanner issue can appear in the feed before its severity assessment finishes. The assessor looks at evidence from up to five current findings, not every trace in the issue. To assign **Critical**, **High**, **Medium**, or **Low**, it must give a reason and cite evidence from those findings. The assessment can also conclude that the evidence is insufficient. It does not set the issue’s triage status.

| What you see in Severity | How to read it |
|---|---|
| Pending | The issue still has the default severity and an assessment is pending. The stored `medium` is a compatibility value, not a judgment about impact. |
| Unassessed | The issue still has the default severity and no established grade. For example, the assessor may not have found enough evidence to assign one. This is not a Low grade. |
| A grade, such as Medium | Hover over the badge in the list or issue header for the reason, when available. An assessed Medium has `severity_source=llm` and `severity_assessment_status=completed`. A manual or legacy grade can have the same badge. |
| A grade with a tooltip that says “reassessment pending” | This is the previous grade, not a new decision. For example, High stays visible while the assessor reviews new refund findings. |

**Pending** and **Unassessed** are assessment states, not fifth and sixth severity levels. The severity filter matches the stored priority. That’s why a **Medium** filter can return a **Pending** row. In the [issue fields](/docs/error-feed/reference/issue-fields#severity-assessment-fields), read `severity` alongside `severity_source`, `severity_assessment_status`, and `severity_reason`.

## Manual severity and triage status

If you set the refund issue's severity to **Critical**, the badge shows your grade and its tooltip reads “Set by a user.” A pending automatic result cannot overwrite it, and another matching occurrence does not reset it. You can still choose another grade yourself.

Status records what your team is doing, not how much harm the issue caused:

| Status | How to use it |
|---|---|
| Escalating | The starting status for a new issue. Inspect the findings before deciding what to do. |
| For review | Flag an issue for a closer look. A resolved scanner issue can also return to For review when a new matching occurrence is attached. |
| Acknowledged | Record that you’ve recognized the problem. The Critical refund issue can be Acknowledged and still be Critical. |
| Resolved | Mark the problem as fixed. This is a triage decision, not a change to its severity. |
