## Two axes, one issue

Every [issue](/docs/error-feed/concepts/understanding-error-feed) in the [feed](/docs/error-feed/concepts/understanding-error-feed) carries two labels that change independently of each other. **Status** is the [triage](/docs/error-feed/guides/triage-issues) axis: where the issue sits in your team's workflow. **Severity** is the impact axis: how bad the problem is. A newly created issue starts at status For review and severity Medium.

## Status: the triage axis

Status has exactly four values, and a person can pick any of them. Error Feed only ever moves an issue between For review and Escalating; it never sets Acknowledged or Resolved.

| Status | What it means |
|---|---|
| Escalating | Findings are running well above usual, so look at these first. Error Feed confirmed it (see the automatic moves below), or a person picked it |
| For review | The default for a newly created issue. Open and waiting for a closer look |
| Acknowledged | Confirmed as real |
| Resolved | The underlying problem has been fixed |

These are the same four values you'll see spelled `escalating`, `for_review`, `acknowledged`, and `resolved` in the data and filters, just written out for reading here.

Error Feed checks open issues on its own, counting each issue's findings. A finding is one recorded occurrence of the problem; for evaluation-based issues, each failed evaluation counts as one. Error Feed moves an issue from For review to Escalating when its findings run well above that issue's usual rate and stay that high for a while. It moves the issue back to For review once they settle down and stay down, even if no new findings arrive.

Any status a person picks is never changed automatically afterwards, so Error Feed will not move it back to For review or on to Escalating. That covers the issue's Status menu, the header buttons, and Bulk actions. It includes picking the status the issue already has, which is how you keep an issue at its current status.

## Severity: the impact axis

Severity also has exactly four values, describing how bad the problem is: critical, high, medium, and low, with medium as the default for a newly created issue. That's a different question from the quality [scores](/docs/error-feed/concepts/trace-error-analysis) a trace receives.

<Note>
Severity is stored as `priority` on the issue: critical maps to `urgent`, high to `high`, medium to `medium`, and low to `low`.
</Note>

Severity is a label your team sets, then filters and sorts by. See [Issue fields & filters](/docs/error-feed/reference/issue-fields) for the full value table and the feed's other filterable fields.

## How the two axes relate

The two axes are independent, so an issue can sit in any combination of the two. A critical issue can still be at For review: its impact is as bad as it gets, but its findings haven't grown past that issue's usual rate. A low-severity issue can be Escalating if its findings are growing. Status can say nothing about how bad an issue is, and severity can say nothing about where it stands in triage.

## Why it matters

Because the axes are separate, you can tell "critical but quiet" apart from "growing right now".
