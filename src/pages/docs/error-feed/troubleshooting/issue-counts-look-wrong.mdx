---
title: "Issue counts look wrong"
description: "Rows are showing in the feed, but a count, a row, or a sparkline doesn't match what you expected. Five causes, each with a fix."
---

## Symptom

The feed isn't empty, but a number on it doesn't add up: an issue's Events count is higher than the number of traces you counted yourself, a row you were tracking yesterday isn't there anymore, or the Trend sparkline on a row doesn't seem to move with the time range you set. Rows are present, so work through the causes below rather than assuming the underlying data is wrong.

## Quick checks

- Check the project's sampling rate before comparing a count to what you expected to see
- Confirm which count you're reading: **Events** and **Users** are different fields, and neither is a trace count
- Check the feed's **time range** filter, and remember the Trend column doesn't follow it
- Check whether the count you're looking at mixes scanner-found and eval-created issues

## Causes and fixes

| Cause | What you see | Fix |
|---|---|---|
| Sampling limits what's ever scanned | An error you know fired several times shows a much lower Events count | Error Feed only counts traces it actually scanned. At a 20% sampling rate, five identical failures average out to about one scanned occurrence (5 × 0.2 ≈ 1). Raise the [sampling rate](/docs/error-feed/features/sampling) if the count needs to track closer to the true occurrence rate; the number itself isn't wrong |
| Duplicate clusters get merged | An issue you were tracking is gone, or another issue's count jumped | A background merge pass folds near-duplicate clusters together, but only within the same error category, and only when two clusters are each other's closest match by similarity, above a fixed threshold, capped at 50 merges per pass. The absorbed row's occurrences now count under the issue it merged into |
| Events, traces, and users are three different counts | The Events number reads higher than the number of traces you'd count by hand | An issue tracks total events, unique traces, and unique users as three separate counts. The feed table shows Events and Users, not a trace count. If the same error fires three times in one trace and once in another, that's four events across two traces, so Events will normally run ahead of whatever trace count you're expecting |
| The time range filter and the Trend column don't share a window | Narrowing the time range changes the Events count, but the row's Trend sparkline looks unchanged | The feed's time range filter clips the window Events and Users are computed over. The Trend column is a fixed 14-day sparkline regardless of that filter, so it won't shrink or grow to match it |
| Scanner and eval issues are combined | The list, or a project's total, has more issues or events than the scanner alone would explain | The feed mixes issues the scanner found on its own with issues created from evaluation runs. Filter by the `source` field (`scanner` or `eval`) on the feed API request to see just one origin |

## Diagnostic checks

- Open the row's [Traces](/docs/error-feed/features/traces) tab and count the traces listed there. Compare that number, not the Events count, against how many individual failures you expected.
- Open the project's sampling rate in Observe settings before trusting a raw comparison across projects or time periods; a cluster from a lower sampling rate represents more real occurrences than the same count from a higher one.
- Re-check the feed's time range filter, then look at the Trend sparkline separately. They're computed over different windows by design.
- If you only want one kind of issue, request the feed with `source=scanner` or `source=eval` rather than reading the combined list.
