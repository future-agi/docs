## About

If Ridgeline Outfitters logged several incorrect refund promises, why does **Error Feed** show only one issue? The number beside the page title counts matching issues. Multiple findings can belong to the same issue, and multiple findings can come from the same trace. Check what the number measures before comparing it with your logs.

## The list mixes scanner and eval issues

The built-in scanner and failed eval tasks both produce rows. In the **Error** cell, look below the title: **Scanner** or **Eval** identifies the source; the badge next to it identifies the error type. On a refund-policy eval issue, for example, **Eval** is the source, not the name of the eval task.

Open **Filter → Source → is → Eval** to count only eval issues. Switch the value to **Scanner** to count scanner issues with the same project and time range. Remove the Source filter to bring both back. The API equivalents are `source=eval` and `source=scanner`.

![Error Feed counts four issues with Source set to Eval. The first issue, “Refund confirmed before the pending charge settled,” has the labels Eval and Ridgeline refund policy.](/images/docs/error-feed/issue-counts-look-wrong/eval-issue-count.png)

## Medium results include Pending or Unassessed

Filtering on **Severity** matches stored priority, not the text on the badge. A scanner issue that hasn't received a grade can store `medium`. This means the number of issues matching **Medium** is not the number that an automatic assessment graded Medium.

Hover over the badge for its explanation. If you're counting automatically assessed Medium grades in the API, request `severity=medium`. On each page, count only rows with `severity_source=llm` and `severity_assessment_status=completed`. These last two fields are response fields, not list filters. Check `severity_reason` for the explanation. A previous grade can still be visible while reassessment is pending; a manual Medium has `severity_source=manual` instead.

## Events counts traces or sessions

| If you want to count… | Read… |
|---|---|
| Issues matching your filters | The number beside **Error Feed**, or `result.total` in the list response |
| Occurrences grouped into one issue | `occurrences` on that issue's list row |
| Distinct traces for that issue, or distinct sessions for a session-targeted eval | **Events** (`trace_count`) |
| Distinct end users found on those traces | **Users** (`users_affected`) |

For example, if two refund findings on one trace and a third on another trace group into a single scanner issue, that is **one issue**, **three occurrences**, and **two Events**.

## The time range drops rows, but not their counts

The list checks when each issue was **Last seen**. An issue last seen yesterday may fall outside **Last 24 hours** even if you remember seeing it this week. Widen the range to **Last 7 days**. The **Events** and **Users** on a matching row describe the issue, not just the portion of it inside the selected range.

The **Trend (14d)** sparkline has its own 14-day window and counts occurrences by day. It is not a breakdown of the distinct traces in **Events**.

## Counts only cover what got scanned

For **Scanner** rows, project sampling controls which traces can be investigated. A sampling rate of 20% does not mean exactly one trace out of every five will produce a finding. Even a sampled trace may contribute no issue. Don't extrapolate from the combined Scanner and Eval list to a total number of failed requests. Check the project's [Error Feed sampling settings](/docs/error-feed/guides/turn-on-error-feed) if too few traces are being investigated.

## Duplicate clusters get folded together

A grouped scanner issue can disappear from the feed after a merge. If you have the old issue link, open it: when the retired issue has a redirect, the detail page takes you to the active issue. A missing row by itself does not mean the problem was resolved.
