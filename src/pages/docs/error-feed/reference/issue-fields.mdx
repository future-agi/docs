## About

Use this reference to interpret a row from `GET /tracer/feed/issues/`. Each row in `result.data` describes one issue. `result.total` counts the matching issues across pages, not the number of traces or occurrences.

## Feed filters

**Search errors** matches the title, issue group, or category. The time range is separate from the **Filter** panel; it starts at **Last 7 days**. The panel displays the equality operator (`equals`) as **is** for these fields. Remove a field to stop filtering by it.

| Filter | UI values | Query parameter |
|---|---|---|
| Project | An accessible project | `project_id` |
| Status | Escalating, Acknowledged, For review, Resolved | `status` |
| Severity | Critical, High, Medium, Low | `severity` |
| Fix layer | Prompt, Tools, Orchestration, Guardrails | `fix_layer` |
| Source | Scanner, Eval | `source` |

The time range choices are **Last 24 hours**, **Last 7 days**, **Last 14 days**, **Last 30 days**, and **Last 90 days** (`time_range_days` of `1`, `7`, `14`, `30`, or `90`).

## Source values

The **Error** cell shows `error.name` as its title. Under it are two badges: `source` identifies how the issue was detected; `error.type` identifies its category or group, such as the name of the failing eval task. For example, **Eval** and **Ridgeline refund policy** describe the same row, not two sources.

| Source badge | Filter in the UI | API or SDK value |
|---|---|---|
| Scanner | Filter → Source → is → Scanner | `scanner` |
| Eval | Filter → Source → is → Eval | `eval` |

Eval issues group failures from a span-, trace-, or session-targeted eval. The **Eval** badge identifies the pipeline, not the target type.

## Severity values & priority

The list’s `severity` query parameter matches the stored `priority`. Sorting on severity also uses priority. Neither operation requires a completed assessment.

| Severity value | Grade label | Stored priority |
|---|---|---|
| `critical` | Critical | `urgent` |
| `high` | High | `high` |
| `medium` | Medium | `medium` |
| `low` | Low | `low` |

### Severity assessment fields

Read these fields together. `severity_source` is not `source`, and `severity_assessment_status` is not the issue’s `status`.

| Field | Meaning |
|---|---|
| `severity` | The stored grade, including a compatibility value of `medium` when impact has not been established. |
| `severity_source` | `default` means the compatibility value; `llm` means an automatic evidence-backed grade; `manual` means a person set it. `legacy` preserves a grade without recording it as an evidence-backed assessment. |
| `severity_assessment_status` | The state of the assessment, for example `pending`, `completed`, `insufficient_evidence`, `failed`, `unassessed`, or `manual`. You cannot filter for these as severity levels. |
| `severity_reason` | Reason from the latest assessment, when available. An inconclusive reassessment updates this reason but keeps the previous grade. The reason can be blank. A manual edit sets it to `Set by a user.` |

For example, `medium` + `default` + `pending` displays **Pending**. `medium` + `default` + `insufficient_evidence` displays **Unassessed**. In contrast, `medium` + `llm` + `completed` displays **Medium**. With `high` + `llm` + `pending`, the badge stays **High** while the tooltip notes the pending reassessment. See [Severity & Status](/docs/error-feed/concepts/severity-and-status) for how to interpret manual grades.

## Status values

`status` describes triage, independent of the grade and its source.

| Status value | Label |
|---|---|
| `escalating` | Escalating |
| `for_review` | For review |
| `acknowledged` | Acknowledged |
| `resolved` | Resolved |

## Event count & time fields

| List row field | Meaning |
|---|---|
| `occurrences` | Number of occurrences grouped into the issue. Not the **Events** column. |
| `trace_count` | Shown as **Events**. Counts distinct traces for trace-based issues and distinct sessions for session-targeted eval issues. |
| `users_affected` | Distinct end users found on affected traces. Shown as **Users**. |
| `first_seen`, `last_seen` | When the issue was first and last seen. The time range filters issues by `last_seen`, not by the start time of each affected trace. |
| `trends` | Daily occurrence counts for the **Trend (14d)** column. |

## Sort keys & directions

| `sort_by` | Sortable column |
|---|---|
| `last_seen` (default) | Last seen |
| `severity` | Severity |
| `unique_traces` | Events |
| `first_seen`, `error_count` | API only |

`sort_dir` takes `asc` or `desc` and defaults to `desc`.

## Traces tab columns & aggregates

The columns are **Trace ID**, **Input**, **Start Time**, **Duration**, **Tokens**, **Cost**, and **Score**. The summary shows **Total traces**, **Avg score**, **P50 latency**, and **P95 latency**. Voice projects also show **Avg turns** when that measurement is available.

## List & query limits

These are API limits. The **Traces** tab requests up to 200 rows, rather than using the API default of 50.

| Parameter | Applies to | Minimum | Default | Maximum |
|---|---|---|---|---|
| `limit` | Feed list | 1 | 25 | 200 |
| `offset` | Feed list and Traces tab | 0 | 0 | No maximum specified |
| `time_range_days` | Feed list | 1 | No API time filter | No maximum specified |
| `limit` | Traces tab | 1 | 50 | 500 |
| `rep_limit` | Overview tab | 1 | 20 | 200 |
| `days` | Trends tab | 1 | 14 | 90 |

In the feed table, **Rows per page** offers 10, 25, or 50 issues.
