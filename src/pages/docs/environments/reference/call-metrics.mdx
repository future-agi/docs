## About

When a caller talks over your agent, **Stop latency** tells you how long the agent kept speaking. **AI interruptions** counts the opposite event: your agent talking over the caller. Use the call recording to hear the difference, then use the run table to see whether it happens across trials.

## Read one call

1. Open your environment, choose **Runs**, and open a voice run. In **Test runs**, use **Columns** to show **Stop latency** and **AI interruptions** under **System metrics**. Chat runs don’t have these voice columns.
2. Click a call and open **Call Analytics**. Compare **Latency** with **Stop latency**: one measures how long the agent takes to *start* a reply, the other how long it takes to *stop*.
3. Open **Transcript** on the left. On a recording with separate speaker tracks, click a timestamped turn or function call to seek to that point and press play. If you only have a mixed recording, use the waveform and the timestamp. For a tool call, compare its arguments and result with what the agent says next.

{/* MEDIA: Ridgeline voice call drawer showing the customer's interruption, Latency of 850ms and Stop latency of 640ms in Call Analytics. */}

For example, a Ridgeline Outfitters caller asks about returning a rain jacket. They start speaking at **5.000 s** while the agent is greeting them. The greeting ends at **5.640 s**. That overlap contributes **640 ms** to stop latency, not to the agent's interruption count. Later, the caller finishes giving their order number at **9.800 s**. The agent looks up the order at **10.000 s** and starts its answer at **10.650 s**: an **850 ms** response latency.

| What you want to know | Field or drawer label | How to read it |
|---|---|---|
| How long did the agent take to yield? | `avg_stop_time_after_interruption` | Mean time in **milliseconds** from the caller interrupting to the agent stopping. `640` displays as `640ms`; `0` is a measured `0ms`. A dash means no stop time was measured. |
| How long did the agent take to reply? | `avg_agent_latency` (voice detail), `latency_ms` (v3 list) | Average gap from the end of the caller's speech to the start of the agent's reply. Chat can report `avg_latency_ms` instead. |
| How long did each reply last? | `response_time_ms` | When computed from voice turns, this is the average duration of the agent’s replies. It measures speaking time, not the wait before a reply. |
| Who interrupted whom? | `user_interruption_count`, `ai_interruption_count` | **User Int.** counts the caller interrupting the agent. **AI Int.** counts the agent interrupting the caller. The corresponding `user_interruption_rate` and `ai_interruption_rate` are counts per minute, not percentages. |
| Who did most of the talking? | **User / AI**, `talk_ratio` | The drawer shows percentages of speaking time, caller first. The API ratio is agent speaking time divided by caller speaking time. A ratio of `2` means the agent spoke twice as long, not 2% of the time. |
| How fast did they speak? | **User WPM** (`user_wpm`), **Agent WPM** (`bot_wpm`) | Words per minute for each speaker. These measure speaking pace, not time spent waiting for a reply. |
| Where did the time go? | **TTFW**, **Silence**, **Turns**, **Words** | Time to first word is the start of the first caller or agent turn. Silence adds up gaps longer than 0.3 seconds. Turns and words describe the conversation, not how many tools ran. |
| How satisfied did the caller sound? | **CSAT** (`csat` in the v3 list) | A customer satisfaction score for the interaction, when available. It is not a count of passed evaluations. |

## Read the hosted call receipt

A hosted call receipt records what happened on one attempt. The **target** is your agent; the **caller** is the simulator testing it. Only the target's provider can report its own cost and token usage. Don't estimate those from transcript length or substitute the simulator's usage.

| Evidence | Where to find it | How to use it |
|---|---|---|
| Call identity | `call.target_metrics.provider_call_id` in the receipt; `customer_call_id` in call detail | Use this ID to find the same call at the target provider. Use the separate call execution `id` when querying Future AGI. |
| Why the call ended | `call.stop_reason` and `call.target_metrics.provider_end_reason` | **Ended** (`ended_reason`) on a hosted call shows the simulator's stop reason. The provider can report a different reason for the same disconnect. Neither is the evaluation verdict. |
| Duration | `call.duration_ms` in the receipt; `duration_seconds` in the run table's API response | The receipt uses milliseconds; the list uses seconds. Neither is an offset into the recording. |
| Target tokens | `call.target_metrics.usage`; `input_tokens`, `output_tokens`, `total_tokens` in detail | These are the provider's prompt, completion and total token counts when supplied, not tokens the simulator used to play the caller. |
| Target cost | `call.target_metrics.cost_cents`; `customer_cost_cents` in detail | Both are in cents. The v3 list's `cost_cents` is this target cost. The detail's `cost_cents` is the platform-side cost, not another copy of the provider's charge. Neither field is a count of credits. |
| Target latency | `call.target_metrics.latency`; `customer_latency_metrics` in detail | Stage and per-turn timings depend on what the provider reports. Use them to investigate a slow reply; they don't measure barge-in stop latency. |

For example, if Ridgeline’s provider reports 96 prompt tokens, 24 completion tokens and a cost of 3 cents, the target used 120 tokens. Those figures say nothing about how many tokens the simulated caller used. A missing provider ID, cost or token count means **not reported**, not zero.

## Align turns and tools with the recording

A call can start before the recorder attaches, and the recorder can start before anyone speaks. In a hosted voice **transcript artifact**, `recording_offset_ms` is the measured gap from recording start to first speech. It is not a receipt field. An offset of `3000` puts the first word at **0:03**. The call detail's `start_time_ms` values already use that timeline: don't add the offset a second time.

If no offset is available, the platform uses the call start when it is at or before the first word, or the first word otherwise. A timestamp can then differ from what you hear. Without speech timestamps at all, treat the transcript as an ordered conversation, not a stopwatch.

For the jacket return, find **Function call · lookup_order** at **0:10**. Check that the argument is order `RG-1042` and that the result says the return is eligible. Listen to the next agent turn to see whether it used that result correctly.

{/* MEDIA: Recording playback seeking to lookup_order at 0:10, with the order ID, eligibility result and agent's following turn visible. */}

- **Voice:** When the agent and the LiveKit hook record the same invocation, the timeline keeps the executed arguments and result with the hook's timestamp. Two calls with the same tool name are not necessarily duplicates: a failed attempt and a successful retry can both appear.
- **Chat:** A timed message's `at` is when the turn was delivered, not when the transcript was saved. Timed tool calls share that clock, so a lookup made before the reply appears between the question and answer. An untimed tool entry at the end is not evidence that the tool ran after the conversation.

If a hosted voice call reports `transcript_finalization_failed`, the runner could not capture the complete transcript. Listen through the end of the recording or compare the retained turns with the target provider’s record. A missing last line is not proof that the agent never answered.

## Reconcile the group average

In **Test runs**, choose **Group by** → **Use case**. The header reports a mean **per call**, not a total interruption count or an average of the visible rows. Each metric uses all matching calls in that group **after filtering**, even across pages. It includes measured zeros and excludes `null` independently for each metric.

| Ridgeline jacket return call | Stop latency | AI interruptions |
|---|---:|---:|
| Caller and agent each interrupt once | 640 ms | 1 |
| Neither interrupts | Not measured | 0 |
| No conversation captured | Not measured | Not measured |
| **Gear returns group** | **640 ms** (one measured call) | **0.5 per call** (two measured calls) |

A reported stop time of `0` would change the mean: `640` and `0` average to **320 ms**. A `null` does not change it. If no calls have a value, there is no mean to report.

{/* MEDIA: Test runs grouped by Use case, with the Gear returns group expanded to show the difference between zero, a dash and a fractional group average. */}

To check the same calculation through the API, set `FI_API_KEY` and `FI_SECRET_KEY` to your workspace credentials. Set `EXECUTION_ID` to the run execution UUID (the last path segment of the open run URL). This requests one row but returns the full matching group's aggregates. The example uses [jq](https://jqlang.org/) to show only the relevant fields.

```bash
curl --fail-with-body --silent --show-error --get \
  "${FI_BASE_URL:-https://api.futureagi.com}/simulate/v3/test-executions/${EXECUTION_ID:?Set EXECUTION_ID}/calls/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  --data-urlencode 'group_by=goal' --data-urlencode 'page_size=1' |
  jq '{calls: [.results[] | {id, avg_stop_time_after_interruption, ai_interruption_count}],
       groups: [.groups[] | {label, total, stop_ms: .aggregates.avg_stop_time_after_interruption,
                             interruptions_per_call: .aggregates.ai_interruptions}]}'
```

Use a returned `id` as `CALL_ID` to compare the exact call with the drawer. This returns `null` for an unmeasured value rather than converting it to zero.

```bash
curl --fail-with-body --silent --show-error \
  "${FI_BASE_URL:-https://api.futureagi.com}/simulate/v3/call-executions/${CALL_ID:?Set CALL_ID}/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" |
  jq '{id, customer_call_id, ended_reason, duration_seconds, avg_agent_latency,
       avg_stop_time_after_interruption, user_interruption_count, ai_interruption_count,
       total_tokens, customer_cost_cents, function_calls}'
```
