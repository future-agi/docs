Look up what a label on a connected agent means, what you can do with a version, and the limits you can hit. [Agents & versions](/docs/environments/concepts/agents-and-versions) explains the model, and [Supported agents](/docs/environments/reference/supported-agents) covers sources, frameworks and reading limits. Text in angle brackets, such as `<label>`, stands for a value on screen.

## Version origins

Each version's name starts with what made it, then a summary of what changed, for example "Synced: Source changed". The summary reads "Source changed", "Prompt changed", a count of variables, "First version" for the first one, or "No change" when nothing differs.

| Name starts with | What made it |
|---|---|
| Connected | [Connecting the agent](/docs/environments/guides/connect-your-agent) |
| Created | Building an environment with the agent |
| Synced | **Sync** found a new commit |
| Source pushed | A push to the agent's GitHub branch |
| Source uploaded | **Upload new version** |
| Prompt edited | A prompt edit |
| Agent settings changed | A change to the agent's settings, such as a phone agent's number |
| Credentials changed | New credential values saved |
| Provider synced | **Sync** found a change at Vapi or Retell |
| Backfilled | A version recorded rather than made by one of the changes above |

The meta line next to a version's time uses shorter forms: Pushed, Uploaded and Settings changed, "Built with an environment" for Created, and Recorded for Backfilled.

Version numbers count up over every version ever made and are never reused. Making the same content again returns the version that already stands for it instead of making another.

## Check states

A new version is checked before it can be used. A code version from GitHub or an upload goes through three steps, and a version of a Vapi, Retell, LiveKit or phone agent gets one check.

| Step | What happens | Chip while it runs |
|---|---|---|
| 1. Code stored | The code is stored | Storing code |
| 2. Agent read | The agent's tools, prompt and model are read from the code | Reading |
| 3. Checked | The credentials are checked | Checking |

A version on the same code as its parent reuses the parent's reading, so no new reading runs.

### What each state allows

| Chip | Meaning | Build from it | Set as production | Discard | Retry |
|---|---|---|---|---|---|
| Storing code, Reading, Checking | The check is running | No | No | Yes | After an hour |
| Draft | The check passed, and the version isn't in production | Yes | Yes | No | No |
| In production | The agent's production version; following environments test it | Yes | Already is | No | No |
| Check failed | The check failed, with the reason under the label | No | No | Yes | When the reason can be retried |
| Discarded | Set aside by hand | No | No | No | No |
| Superseded | Set aside because a newer version replaced it | No | No | No | No |

A check still running after an hour shows a banner saying it "may have stopped", and **Retry** appears. An older version with no check status shows no check chip.

Two more chips describe a version rather than its check. **Latest** marks the newest version. `Running in <n> environment(s)` counts the environments that have the version as their default, and a version with it can't be discarded.

A burst of pushes can make several versions at once. The older ones still waiting on their check are set aside as "Superseded by a newer version", unless an environment asked for them.

### Why a check fails

| Reason shown | Retry offered | What to do |
|---|---|---|
| `Missing credentials: A, B` | No | Fill in the form on the banner and click **Save credentials**. That makes a new version with them |
| `Reading the agent stopped before it finished` | Yes | Click **Retry** |
| `Reading the agent took too long and was stopped` | No | On an uploaded agent, click **Upload new version**. On a GitHub agent, push a new commit, or connect the agent again. **Sync** starts a new reading only when another version is in production; see [Watching GitHub](#watching-github) |
| `The reading couldn't run. Try again in a moment` | Yes | Click **Retry** |
| `The source couldn't be prepared for reading. Try again` | Yes | Click **Retry** |
| `The upload expired; upload the folder again` | No | Click **Upload new version** |
| `The check could not be started; retry it` | Yes | Click **Retry** |

## Version actions

These act on one version. All except **Make default** are on the version's row on the **Versions** tab. **Make default** is in the environment's agent versions, opened with **Manage versions** in the **Test subject** section of its **Overview**, which shows only when environment versioning is on.

| Action | Available when | Not available when |
|---|---|---|
| Set as production | The check passed | The check hasn't passed, the version is discarded or already in production, or an environment manages the agent |
| Retry | The check failed for a reason that can be retried, or has run for over an hour | Any other state |
| Discard | The check is running or failed | The check passed, or the version is in production or an environment's default |
| Compare | A code agent, with an older code version to compare against | A hosted agent, where Compare is coming soon |
| Make default | The check passed and the version isn't discarded | Any other state |

Members without edit access don't see **Set as production**, **Retry** or **Discard**. When an environment made the agent, the header reads "Managed by" with that environment's name and **Set as production** isn't offered, so change its version from that environment.

### New versions from the header

The header button that makes a new version depends on the agent's source.

| Button | Shown for |
|---|---|
| Sync | GitHub, Vapi and Retell agents |
| Upload new version | Folder upload agents |
| Add version | Phone and LiveKit agents |

Without permission, the button is disabled with "You don't have permission to add versions."

## Environment policies

An environment testing a connected agent either follows production or is pinned to a version. A new environment built from an agent starts pinned. A version offered to an environment arrives as a [rebuild card](#the-rebuild-card) in its build console.

| Policy | What it does |
|---|---|
| Pinned | Keeps its version when production changes, and is offered the new production |
| Following | Moves to the new production when the change is compatible |

The agent's **Environments** tab labels each environment row with its policy:

| Row label | Meaning |
|---|---|
| Default: production | The environment follows production |
| `Default v<N>` | Pinned to version N |
| `Default v<N> · v<M> in production` | Pinned to version N while version M is in production |

| Button | Shown on | What it does |
|---|---|---|
| Open | Every row | Opens the environment |
| Default to production | Pinned environments that are behind production | Moves the environment to production and has it follow production |
| Follow production | Pinned environments that aren't behind | Makes the environment follow production |

Both buttons need edit access, and confirm with `<environment name> now tests what's in production`.

## What a production change does

The first version that passes its check becomes production when the agent has none yet. After that, a version that passes moves no environment: each environment whose default is another version is offered it through a rebuild card. Only **Set as production** moves environments, like this:

| Environment | Result |
|---|---|
| Following, compatible change | Moves now |
| Following, major change | Offered, never applied |
| Following, change that can't be judged yet | Offered, never applied |
| Following, not built yet | Moves now |
| Following, busy with a rebuild | Moves once the rebuild ends |
| Already on that version | Nothing changes |
| Pinned | Keeps its version and is offered the new one |

A follower's move is also held back, and the version offered instead, when its default was changed by hand in the meantime or the version can't be picked for it. Setting an earlier version as production works the same way, so following environments are carried back to it.

### The rebuild card

The card names the version and what changed, such as changed files, the prompt, settings, tools, outside services, rules or the model. It reads "Agent `<label>` changed: `<changes>`. Rebuild the environment?" when the environment's default moved, and "Agent `<label>` is available (`<changes>` changed). Rebuild this environment with it?" when the version is only offered.

| Button | Shown | What it does |
|---|---|---|
| Rebuild | While the card waits for an answer | Rebuilds the environment on the version |
| Skip | While the card waits for an answer | Leaves the environment as it is |
| Stop | While the rebuild runs | Stops the rebuild |
| Rebuild again | After the rebuild failed | Starts the rebuild again |

A skipped card is asked again if the same version is later made the default by hand. No card is raised when a version changes nothing for the environment.

## Change classes

A change is judged by comparing what was read from the version the environment was last built from with what was read from the new version. If any part of the change is major, the whole change is major.

| Kind of change | Counts as |
|---|---|
| Only the prompt, model, voice or instructions changed | Compatible |
| A tool or an outside service was added | Major |
| A tool was removed, or takes different arguments | Major |
| A new rule appeared in the [contract](/docs/environments/concepts/contracts) | Major |
| What was read from either version isn't stored | Can't be judged yet |

Tools are matched by name. A tool takes different arguments when its argument names, required arguments, kind or full argument shape differ, including types, enums, formats, bounds and nesting. Reworded tool descriptions, titles and examples don't count.

## Sync and watching

### Sync by source

| Source | A new version is made when | Nothing changes when |
|---|---|---|
| GitHub | The branch's head is a new commit | The agent is already at the head: `<label> is already at the latest commit` |
| Folder upload | The folder differs from the recent uploads | The same folder contents again: `<label> already has this code` |
| Vapi | A later Sync finds a change | The first Sync, which records what Vapi holds, or a later one that finds nothing new |
| Retell | A later Sync finds a change | The first Sync, which records what Retell holds, or a later one that finds nothing new |
| Phone number or LiveKit | The values you enter in **Add version** differ from the current version | The values match: `<label> already matches your agent` |

A Retell agent can be synced when it runs on a retell-llm or conversation-flow engine. [Sync a hosted agent](/docs/environments/guides/sync-a-hosted-agent) lists what a Vapi or Retell Sync keeps and what it hides.

### Watching GitHub

A GitHub agent's header shows when its branch was last checked, such as "Synced 4m ago", or "Not synced yet".

GitHub branches are checked on every push and every 10 minutes, and private repositories are watched too, through the workspace's GitHub installation. Only a branch is watched; an agent connected at a commit never moves. A commit gets one version, whichever of Sync, a push or the 10-minute check sees it first.

When a commit already has a version, what happens next depends on how that version ended:

| That version | Push or 10-minute check | Sync |
|---|---|---|
| Failed its check | Makes no new version | Makes a new version |
| Was discarded | Makes a new version | Makes a new version |

The table holds when another version is in production. Sync, a push and the 10-minute check all start from the production version, or from the newest version when none is in production. So when that newest version is already at the branch head, as with a newly connected agent whose v1 failed, nothing new is made and Sync answers `<label> is already at the latest commit`. Push a new commit, or connect the agent again.

When Sync finds the same version and its check never began or has run for over an hour, it restarts the check, as **Retry** does.

## Code view limits

The **Files** card and **Compare** read the code stored with a version, so they work for GitHub and folder upload agents.

### Files card

| Limit | What you see |
|---|---|
| Over 5,000 entries | The first 5,000 entries, sorted by path |
| A file over 1 MiB | "This file is over 1 MiB; it isn't shown here." and the file's kind |
| A binary file | "This file is binary; nothing to show." and the file's kind |

### Compare

Compare puts the older version on the left and shows 3 lines of context around each change. With no version chosen, it compares against the version before.

| Limit | What you see |
|---|---|
| Over 300 changed files | The summary says `showing the first <n> files` |
| A diff over 400 changed lines or 20 KB | Collapsed until you click **Load diff** |
| A file over 5,000 lines on either side | `This diff is too large to show` |
| A binary file | `Binary file not shown` |
| A compare that runs for a few seconds | It stops computing, and the files it didn't reach load when you open them |
| A renamed file | Found by identical content; a rename with edits shows as removed plus added |

## Deleting

| What | Rule |
|---|---|
| A single version | Can't be deleted, only discarded. A discarded version stays in the list and keeps its number |
| An agent | Can't be deleted while any environment tests it. **Delete** is disabled with `Tested by <n> environment(s). Delete those environments first` |

An environment counts as testing the agent from the moment it's created, before any run. Deleting an agent removes it and its versions from **Connected agents**, and runs that already happened keep their results. Members without edit access don't see the **More actions** menu that holds **Delete**.
