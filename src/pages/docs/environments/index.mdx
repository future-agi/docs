## About

An environment lets you test an agent on the tasks you expect it to finish. Suppose the Ridgeline Outfitters support agent tells a shopper, “I've started your return.” If you connect the agent's code, you can test more than the reply: did the agent actually create the return in the test order system? Open **Simulate** in the dashboard and choose **Environment** to build and run that test.

## Choose where to run the test

| What you want to do | Where to start | What you run |
|---|---|---|
| Test the connected returns agent and review failed calls in the dashboard | **Simulate → Environment** | Connect a repository, upload code, or connect an agent on a hosted platform. Run the environment's scenarios and open a call to see which goal failed. |
| Keep the returns test in your repository and run it locally or in CI | [Agent Learning Kit for Python](https://pypi.org/project/agent-learning-kit/0.3.7/) | In a separate Python environment, install `agent-learning-kit==0.3.7`. Create a starter case with `alk init ridgeline-returns --preset run` and run it with `alk run ridgeline-returns/manifests/run.json`. You supply a file, not a dashboard ID. |
| Rerun a test already saved in the legacy **Run Simulation** workflow | [Platform SDK simulation reference](/docs/sdk/reference/simulation) or the MCP `run_simulation` tool | Pass the saved test's `run_test_id`, not an environment ID. `client.simulation.tests.run` starts an execution of that test; `client.simulation.scenarios` and `client.simulation.executions` also belong to the legacy API. |

**Why is Environment the only item under Simulate?** In the [Python platform client](/docs/sdk/reference#the-client), read `client.account.whoami().restrict_simulate_to_environments`. If it is `True`, **Environment** is the only Simulate menu item for your organization. If it is `False`, you can also see **Scenarios** and **Run Simulation**. This flag describes dashboard navigation, not API permissions. An MCP client can still list `run_simulation` if that tool is enabled; it runs a saved test, not an environment or a local ALK manifest.

## From a failed call to a change you can review

The builder reads your agent, records its tools and rules in a [contract](/docs/environments/concepts/contracts), and writes [scenarios](/docs/environments/concepts/scenarios-and-trials) to exercise them. For the Ridgeline agent, a scenario can start with an order for a rain jacket and require the agent to record a return. With a test world built from the agent's code, the missing return can fail the call even when the transcript sounds right. If you connect a live Vapi assistant instead, its data stays on the provider. A promise in the transcript is not proof that the order changed.

<img src="/images/docs/environments/environment-flow.svg" alt="Connect an agent, build its environment, run the scenarios, and inspect failed calls before rerunning the same cases." style={{ border: 'none', width: '100%', maxWidth: '860px', margin: '1.75rem auto', display: 'block' }} />

On a finished run, open **Debug failures**. For an eligible agent connected from source or uploaded code, choose **Improve** once the diagnosis identifies a problem. This opens [Epoch](/docs/environments/guides/run-epoch), where you choose which failures to fix and which passing cases to protect. A provider-hosted assistant can be tested, but Epoch cannot edit its code. The Python platform SDK (`futureagi` 0.8.0) has no `client.environments` resource, and `fagi` 0.2.2 has no Epoch command.
