Writing a scenario is the easy part of testing an agent. The hard part is the world it acts in: the records it reads, the tools it calls, and what those tools say back when it gets something wrong.

## What is an environment?

An **environment** is a complete test built around one of your agents, from the world it acts in to the scenarios it has to get through. You connect the agent as a code repository, uploaded code, or an agent running on a platform like Vapi or Retell AI. The builder, an agent that reads yours, then writes its [contract](/docs/environments/concepts/contracts), sets up a **world** with a test version of its data and tools, and generates the [scenarios](/docs/environments/concepts/scenarios-and-trials) to run against it. You run those scenarios as voice or chat calls, and each call is graded on what the agent did, not just what it said. When a call fails, you fix the agent and run again.

You drive all of this from **Environment** under **Simulate** in the dashboard. Beside each environment, a chat with the builder lets you ask about what it made and steer it, as [Chat orchestration](/docs/environments/concepts/chat-orchestration) describes. [Understanding Environments](/docs/environments/concepts/understanding-environments) explains each piece.

## Catch the call that sounded right

An agent can tell a caller their ride is cancelled while the booking stays active, and the transcript reads as a pass. An environment checks the world after every call, so the booking that never cancelled shows up in a test run, not on a customer's bill. An agent hosted on a platform keeps its data on that platform, so its environment has no world and its calls are judged on the conversation.

Every run is inspectable. Each call comes back with:

- the full transcript, with every tool call the agent made, and the recording for voice
- a score for each of the scenario's sub-goals and each evaluation you added, so a failure is something you open and read
- call metrics like turns and latency
- **Debug failures**, which reads the whole run and groups its failures into issues, ranked by what to fix first

## The testing loop

You build the environment from your agent, then run the same scenarios against it every time you change it.

<img src="/images/docs/environments/environment-flow.svg" alt="Your agent, connected as a code repository, uploaded code, or an agent on a hosted platform, goes to the builder, which makes its environment: the contract, the world, and the scenarios. You then run it as often as you need: a run plays each scenario as a call, every call is graded as a pass, a fail, or not decided, Debug failures shows what failed so you can fix your agent, and you run again, each call starting from a clean world." style={{ border: 'none', width: '100%', maxWidth: '860px', margin: '1.75rem auto', display: 'block' }} />

Each call starts from the same clean world, so a failing call points to something in your agent to change, and running the same scenarios again shows whether the fix worked.

## How it connects

- [Evaluation](/docs/evaluation) provides the evaluations that grade every call alongside each scenario's own sub-goals
