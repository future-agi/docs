## About

“Your tent rental for Saturday is cancelled.” The customer heard a clear confirmation. But if Ridgeline Outfitters still has the tent reserved, its booking agent didn't cancel anything.

A **scenario** describes one task, who brings it to the agent, what is true at the start, and what must be true at the end. A **trial** is one attempt by your agent: a voice call or a chat. The scenario defines success before the conversation; the trial supplies the evidence of what actually happened.

## When to use

- You want to know whether the agent changed the right booking, not just whether it said it did.
- A cancellation works on a quiet line. You want to find out whether it still works when the caller is at a busy shop and the agent asks them to repeat a reference.
- You have room for one more scenario and need to decide whether it tests a new decision or just rephrases an existing request.

## How a scenario earns its place

The builder starts from a use case in your agent's [contract](/docs/environments/concepts/contracts). A useful scenario gives the caller one end-to-end task with something at stake. For Ridgeline, the caller can't make Saturday's pickup. They have an existing reservation and know its reference. The agent needs to find that reservation, cancel it and tell the caller the outcome. The caller doesn't need a script of what the agent should say or the names of its tools.

| Proposed test | What it would prove |
|---|---|
| “The agent understands the caller's change of plans.” | Nothing you can check directly. Ask what understanding should look like: does the agent identify the right rental and cancel it? |
| “The agent attempts a cancellation.” | An agent could pass even if the tool refused the request. Check the completed result and the booking it leaves behind instead. |
| “Cancel the caller's tent rental before pickup.” | Start with that booking reserved. An actual cancellation can pass; doing nothing must not. Check the agent's confirmation separately. |

The builder checks that the starting booking exists and, where the environment can run the reference actions, tries a correct solution. A check for cancellation should pass after the booking changes and fail if the agent does nothing or the cancellation fails. An action only your agent can run isn't proved by the reference solution.

Changing the caller's name doesn't add a new case if the coverage values and sub-goals are the same. To change what a case tests, ask the builder to [revise the scenario](/docs/environments/concepts/chat-orchestration). Editing **Passes when** changes the description, not the sub-goals.

## How a call is decided

A **sub-goal** asks one question about the task. Pick the evidence that can answer it:

| Question | Evidence | What it tells you at Ridgeline |
|---|---|---|
| What would success look like? | The **reference solution**: one correct way to handle the request, including the values the caller or policy fixes. | The cancellation must apply to the caller's booking. The reference isn't a required transcript or proof that your agent ran those steps. An extra lookup is fine if it leads to the same allowed outcome. |
| What did the agent do? | A completed tool call with its arguments and actual result, not just a tool name or a request to run it. | A successful lookup finds the rental. It doesn't cancel it. A cancellation tool returning an error is an attempt, not a completed change. |
| What changed? | The test world's state after the call. For a native agent, the environment can use a read-only observation sealed into its definition, such as a lookup of the final booking status. | Compare the booking after the call with the expected `cancelled` status. If it is still `reserved`, the state check fails even if the agent said “cancelled.” |
| What did the caller hear? | The transcript and, for voice, the recording when available. | A communication sub-goal can check whether the agent named the tent and the pickup day. Passing that check doesn't establish that it told the truth about the cancellation. |

By default, the model judges the call's conversational sub-goals together. It uses the agent's instructions and the reference solution for context, but decides each sub-goal against its own criteria. For voice, the recording can settle a word the transcript got wrong. If the recording is missing or won't play, the judge uses the transcript and recorded actions. If the joint judge misses a sub-goal, the model judges that one separately. A sub-goal that requires both a state check and a model judgement passes only if both pass.

A phone-only connection doesn't give the environment access to Ridgeline's booking records. In that case, test what the caller can hear, such as whether the agent read back the right reference. Don't interpret that result as proof of a database update.

### Failed, inconclusive, or not applicable?

- **Failed:** The booking is readable and still reserved. When grading completes, this failed state check makes the scenario fail even though the agent named the right item and day.
- **Inconclusive:** The check applies, but the judge can't tell which day the agent said from either the transcript or the recording. The sub-goal stays undecided. If no other sub-goal failed, the hosted trial reports **Error**: grading couldn't finish. That is not a failure by the agent.
- **Not applicable:** The caller never mentions a second rental. If the criteria say to pass when that situation doesn't arise, the judge records a pass with a `Not applicable:` reason, not a separate call status. Skipping a required step doesn't make it optional.

## Repeats and voice trials

**Repeats** sets how many times to play each selected scenario, from 1 to 20. Two repeats of the Ridgeline scenario start from the same reservation and the same caller facts. They are two new conversations, not two plays of the same audio. Both callers might hear the same confirmation, but if only one booking ends up cancelled, only one trial passes the state check. Two passes tell you what happened twice, not what will happen on every call.

| Part of the call | What stays fixed or varies |
|---|---|
| Caller and surroundings | The scenario supplies the persona. In **Edit scenario**, you can change available traits such as **Personality**, **Communication style**, **Languages** and **Accent**. **Age group** is read-only and can influence which voice the simulator uses. Under **Background noise**, choose an available setting such as **Shop / mall**, or **Off** for a quiet line. Background sound doesn't add a second speaker you can script. |
| Language and opening | The persona guides what the caller speaks. The simulator selects how to transcribe the *agent* using the caller's languages and the languages the agent declares. Who opens depends on call direction: for an outbound agent, the simulated customer answers the phone. |
| Timing and interruptions | Callers can phrase a correction differently, wait silently when put on hold, or check back if the agent doesn't return. An interruption can occur during a voice trial. The platform controls that behavior; there is no caller barge-in slider or guarantee that the caller will interrupt on a particular word. |
| References and endings | The caller is instructed to speak a mixed letter-and-digit reference one character at a time. It should answer an outstanding question and wait for the answer to its own question before saying goodbye. Those are behaviors to listen for, not fixed lines in a transcript. |

## How scenarios cover your agent

[Coverage](/docs/environments/guides/work-with-scenarios#check-coverage) describes the scenarios you have, not their pass rate. It groups them along eight axes:

| Axis | What varies |
|---|---|
| **Task** | The job in the contract, such as cancelling a rental |
| **Who is calling** (**Who is asking** in chat) | The kind of person or account being served |
| **Their situation** | A condition or behavior that changes what the agent needs to handle |
| **Line and speech** (**How they write** in chat) | The conditions in which the caller speaks or writes |
| **How the call goes** (**How the chat goes** in chat) | The shape of the exchange, such as a caller correcting an earlier detail |
| **Attack**, **Attack method**, **Attack intensity** | What pressure the agent faces, where it comes from, and how overt it is |

The builder doesn't promise every combination or a fixed percentage of attacks across your whole suite. For example, when a fixed batch of at least four planned scenarios includes attack levels, the builder reserves at least one fifth of that batch for them, rounded up. A batch of six with attack levels therefore needs two; one planned without attack levels doesn't. The rule doesn't apply when you grow an existing suite through chat. Running the same cancellation twenty times gives you more evidence about that case, not twenty new kinds of coverage.
