## What an epoch is

**Epoch** searches for a better version of your agent. It starts from the failing [scenarios](/docs/environments/concepts/scenarios-and-trials) of a finished run in an [environment](/docs/environments/concepts/understanding-environments), tries changes to your agent, and keeps the one that fixes the most without breaking anything. Each search is one **epoch**, numbered in the order you start them: Epoch 1, Epoch 2, and so on. Each version of your agent that an epoch tries is a **candidate**, numbered the same way: Candidate 1, Candidate 2.

An epoch never changes your agent by itself. It hands you the best candidate to review, with the evidence for it. Your agent changes only when you ship that candidate, as a pull request on your repository or as the environment's new default version.

## The scenarios an epoch works with

You start an epoch from [Debug failures](/docs/environments/guides/debug-failures) on a finished run, and you choose which of the run's scenarios it works on. Each scenario takes one of three roles:

- **Target scenarios** are the failing scenarios the epoch works on. Every candidate is tried against them
- **Held-back scenarios** are failing scenarios the epoch never sees while it searches. Once you pick 12 or more failing scenarios, some of them are held back, and the launch form shows how many. After the epoch picks its best candidate, it runs the held-back scenarios to check that the fix works on cases it wasn't tuned on
- **Must-pass scenarios** are all the other scenarios in the run. A scenario that passed every time before must not get worse beyond normal run-to-run variation. The passing scenarios you **protect** at launch are in this group by name

An epoch needs 12 failing scenarios. With fewer, it first writes three variations of each one you picked, and keeps the variations your current agent also fails. It needs at least three failing scenarios to start this way, and it holds back some of them together with their variations. With fewer than six, it can't hold back enough to tell whether a fix generalizes.

A candidate that fixes only the target scenarios has learned those scenarios, not the problem. The held-back scenarios catch that. The must-pass scenarios catch a fix for one case that breaks another.

## What an epoch is held to

When you start an epoch, you set its limits, and it works only inside them:

- it changes only the parts of your agent you allow: its **Instructions**, **Tools**, **Settings** or **Code**
- it never edits a file you lock
- its candidates call only the models you approve, which start as the models your agent called in the run
- its candidates can't reply more slowly, or cost more for each conversation, than the margin you allow
- it stops at its budget in credits or its time limit, whichever comes first. Reaching the budget ends it as **Stopped at budget**, and reaching the time limit ends it as **Failed**, because it ran out of time

A candidate that changes something it may not, or goes over a model, reply time or cost limit, is rejected however well it does on the target scenarios. The model and cost checks need your agent's model calls to be measured; [Run Epoch](/docs/environments/guides/run-epoch#set-what-it-may-change) covers when they aren't.

## How an epoch ends

An epoch that finds a candidate that passes every check ends **Ready for review**. Every other ending leaves your agent as it was: **No safe improvement**, **Could not reproduce**, **Stopped at budget**, **Stopped**, **Too few failing scenarios**, or **Failed**. A failed epoch you may retry shows **Retry Epoch**. The other endings show **Run Epoch again**. [Review an epoch](/docs/environments/guides/review-an-epoch#when-an-epoch-ends-without-a-winner) says what each ending means and what to do next.

A result that is Ready for review is only as strong as the scenarios it was proven on, so the page says when the proof is weaker than usual:

- **Limited validation**: one to three failing scenarios were held back, too few to tell whether the fix works on cases the epoch never saw
- **Proven on the targets only**: nothing was held back, so the winner is proven only on the scenarios it was tuned on

For an agent on GitHub, a result with either label opens its pull request as a draft. When neither label shows, the winner held up on four or more scenarios the epoch never saw.

## Why it matters

Fixing an agent by hand is a loop: read the failing calls, change the instructions, run again, and hope the change didn't break something that worked. A change that fixes the calls you read can still fail the next caller who says it differently.

An epoch runs that loop for you, with the checks that are easy to skip by hand. It tries each change on the target scenarios, then checks the best one on scenarios it never saw and on every scenario that must keep passing, and it shows you the numbers before you decide. You review a change together with its evidence.
