## One conversation runs the environment

An **environment** is a test world built around one agent: seeded data for its tools to act on, scenarios to play against it, and the grading that judges each conversation. The **builder** is the Future AGI agent that reads your agent and makes all of it, and **chat orchestration** is how you keep working with the builder once it has: a conversation, on the left of every environment's workspace, that takes requests in plain language and carries them out across the whole environment.

You don't open a scenario editor to add ten scenarios, or hunt for the field that holds a tool's arguments. You say what you want in the **Reply to the builder…** box, under the heading **Ask, correct, or steer what it builds**, and the builder works out which part of the environment the request belongs to, does the work, checks it, and reports back. Everything you ask for is kept in the conversation, so the history of how the environment came to be sits next to the environment itself.

## How a request is carried out

The builder made the environment in stages: reading your agent into a [contract](/docs/environments/concepts/contracts), building the world, writing scenarios, and running them. Chat orchestration keeps those stages, and each request is routed to the one that owns it.

Each step the builder takes shows up as a line under its reply: a green dot when the step succeeded, a red dot when one of its own checks turned the step away. A red dot needs nothing from you. It means the builder caught a problem before it reached your environment, and it fixes the problem and tries again. The reply itself reports only what was kept.

When the builder genuinely needs something only you know, such as which of two meanings you intended, it asks, and the question appears in the conversation for you to answer. While it is working, the box reads **Working on your last message…**, and you can stop the turn.

## What the checks catch

The checks are what make a scenario written through chat as trustworthy as one written at build time. A scenario is only kept if it can be set up in the world, a correct agent can solve it, and a wrong one would fail it, and the builder holds a suite to a few more rules on top. In practice, these are the reasons you'll see a scenario turned away and rewritten:

| Turned away because | Why it matters |
|---|---|
| The caller is told to say a value, such as a date of birth, that the world doesn't hold | The agent could never confirm it, so the scenario would fail for the test's fault |
| The caller's instructions already assume what the agent will decide | The scenario is meant to test that decision, so it can't be handed to the caller |
| It repeats a plain version of a task the suite already covers | A second ordinary pass proves nothing new; a variant has to say what makes it harder |
| A caller has the same name as one already in the suite | Two results under one name can't be told apart in a report |
| Too many callers share an accent with the place they're calling from | Callers who moved or are visiting keep the suite realistic |

Say you ask a pharmacy refill line's environment for three scenarios with callers in a particular city. The builder routes the request to scenarios, drops redundant ones if the suite is full, and submits each new one. One caller is told to read back a birth year the world never stored, so that scenario is turned away and rewritten; another shares a name with an existing caller and gets a new one. The reply lists the three that were kept, each with the use case it tests and what the caller does.

## What it can change

Chat orchestration changes the test environment. For example:

| Ask for | Such as |
|---|---|
| An answer about the build, a run or a scenario | "What stage is the build at?" or "Why does this scenario expect a transfer?" |
| More scenarios, past the count you set at build | "Add five scenarios where the caller is in a hurry" |
| A scenario removed, or replaced with a harder one | "Replace the plain refill scenario with one where the caller corrects their date of birth" |
| A different caller | "Make this caller impatient and give them a different account number" |
| A contract correction | "The refund tool needs the order ID, not the email address" |

A contract correction changes the environment's understanding of your agent, so the scenarios and grading that follow use the corrected version, and the contract keeps the correction apart from what was read from source. [Review the contract](/docs/environments/guides/review-the-contract) covers corrections step by step. While a run is going, its progress also appears in the conversation under **Background run activity**, and you can ask about it there.

## What it refuses

The line is simple: chat orchestration never changes the agent under test, or how the environment reaches it. It refuses, straight away and without starting work, to:

- change the phone number a simulation dials, or the assistant ID, agent ID, URL or credentials it connects with
- change the agent's model or voice settings
- edit or deploy the agent's prompt, instructions, source code or platform configuration

<Note>
A phone number inside a scenario, such as the number a caller says they are calling from, is test content and chat orchestration can edit it. The number a simulation dials is your agent's connection and it can't. If a request could mean either, it asks which one you mean.
</Note>

Make those changes where your agent lives, on its hosted platform or in its code, then [run a simulation](/docs/environments/guides/run-a-simulation) against it. The chat can still help on either side of that: it can draft a prompt change for you to apply yourself, and add a scenario that tests whether the change worked.

## When it is available

The conversation opens once the environment shows **Ready**. While it is being built, the box is locked and reads **Environment is still being built**, and the workspace fills in as each stage of the build lands. Results from runs that already finished are never changed by a request; edits apply to the runs that come after. If a request is refused or the chat stays locked, [Environment FAQ & fixes](/docs/environments/troubleshooting) covers why.
