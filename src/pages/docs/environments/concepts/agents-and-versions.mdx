## A connected agent

A **connected agent** is the agent you already run, registered once so environments can test it. It lives on the **Agents** page under **Connected agents**, and comes in two kinds:

- **Code agents**, connected from [GitHub or an uploaded folder](/docs/environments/guides/connect-your-agent)
- **Hosted agents**, made for you when you [build an environment](/docs/environments/guides/build-an-environment) on Vapi, Retell, LiveKit or a phone number

## Versions

A **version** is a numbered, kept snapshot of the agent: its code or its settings, plus the credentials it needs. Versions read v1, v2, v3 and so on. A new one is made whenever the agent changes:

- a sync finds a change: a new commit, or a changed Vapi or Retell agent
- you upload a new folder
- you change the agent's credentials
- you edit the agent's prompt

A GitHub agent picks up new commits on its own. A Vapi or Retell agent picks up changes when you [sync it](/docs/environments/guides/sync-a-hosted-agent), and a LiveKit or phone agent when you add a version to it.

### The check

Each new version is checked on its own to confirm it can be used. For a code agent, the check first reads the agent's tools, prompt and model from its code. Its progress shows as a banner on the agent page, and a failure shows there with the reason. Until a version passes, it can't be built from or set as [production](#production), the version environments default to.

When a check fails, the banner tells you what to do next:

- **Credentials missing**: fill in the fields in the banner and choose **Save credentials**. A new version is made with them and checked again
- **Retryable failure**: choose **Retry** in the banner to read the version again
- **Anything else**: fix the cause, then push a new commit or upload again for a new version, or [discard](#deleting-and-discarding-versions) the failed one. **Sync** makes nothing new while the failed version is the newest and none is in production

A check still running after an hour shows a warning that it may have stopped, with a **Retry** button.

### Deleting and discarding versions

A version is never deleted, but one that hasn't passed its check can be discarded, which sets it aside.

- **Not removable**: you can't delete a single version, because environments stay pinned to the versions they test
- **Discarded**: a version that failed its check, or is still waiting on it, can be discarded. It stays in the list, set aside. Nothing runs it and it can't become production

## Production

**Production** is the version environments default to.

- The first version that passes its [check](#the-check) becomes production, when the agent has none yet
- A later version that passes waits until you [set it as production](/docs/environments/guides/manage-agent-versions)
- Any checked version can be set as production, including an earlier one, and it replaces the previous one. Environments that follow production may move with it (see [How environments use versions](#how-environments-use-versions))

A later version never takes over by itself, so a new commit can't change what your environments test without a decision.

A hosted agent belongs to the environment that made it, and its header shows "Managed by" with that environment's name. It has no production step of its own: the environment moves to a new version when you rebuild it.

## How environments use versions

Each environment tests one version of an agent, and follows one of two policies:

- **Pinned** keeps the environment on its version until you change it. A new environment starts pinned to the version it was built from. Pin for a stable baseline
- **Following** moves with production when the change is compatible. Follow to always test what you've promoted

When production changes, the environment's policy and the kind of change decide what happens. A change is **compatible** when only the prompt, model, voice or instructions changed, and **major** otherwise (see [Compatible and major changes](#compatible-and-major-changes)).

| Policy | Compatible change | Major change |
|---|---|---|
| Pinned | Stays on its version and is offered a rebuild | Stays on its version and is offered a rebuild |
| Following | Moves to the new production version | Stays on its version and is offered a rebuild |

A **rebuild** updates the environment for the new version and makes it the environment's default agent when the update lands. The offer arrives as a rebuild card in the environment's own build console, where you [build an environment](/docs/environments/guides/build-an-environment) and choose to rebuild or skip.

### Compatible and major changes

| Change | What it covers | Following environment |
|---|---|---|
| Compatible | Only the prompt, model, voice or instructions changed | Moves to the new production version |
| Major | A tool is added or removed, a tool takes different arguments, the agent calls a new outside service, or a new [rule](/docs/environments/concepts/contracts) appears | Is offered the new version |

A reworded tool description doesn't count as a change.

Setting an earlier version as production works the same way: following environments are carried back to it when the change is compatible, and offered it when the change is major.

## Why it matters

One agent can serve many environments, each testing the version it should. The environment and its scenarios are versioned too, and every [run](/docs/environments/guides/read-run-results) is pinned to one version of each, so its name reads like `Run 3 · agent v4 · env v2 · scenarios v3`. Because versions are kept and production only moves when you decide, results from different runs stay comparable, and a change in a score traces back to a change you made.
