---
title: "Add test conditions"
description: "Make one of your agent's tools time out, lose its answer, fail or need approval on purpose in a scenario"
---

A **test condition** makes one of your agent's tools misbehave on purpose in a [scenario](/docs/environments/concepts/scenarios-and-trials): the call times out, the answer is lost, the service is down, or the change needs someone's approval first. Real systems fail like this, and the conditions show whether your agent retries safely, tells the caller the truth, or waits for an approval instead of going ahead. This guide adds a condition to a scenario and shows where its effect appears after a run.

<Note>
Test conditions sit in the same switch as [actors](/docs/environments/concepts/actors). If you can't find them in the scenario editor, they aren't turned on for your deployment; a self-hosted install controls them with `HARNESS_ACTORS_ENABLED` in the [configuration reference](/docs/self-hosting/configuration/reference#agent-simulations-in-hosted-sandboxes).
</Note>

## Open the scenario

Open the environment's **Scenarios** tab and click the pencil icon on the scenario's row to open **Edit scenario**, as in [Work with scenarios](/docs/environments/guides/work-with-scenarios#edit-a-scenario). Scroll to **Hidden · test conditions**. It's hidden because neither the caller nor your agent is told about it: your agent meets the failure the way it would in production. A scenario without any reads **Tools behave normally**.

## Add a condition

Click **Add a test condition**, pick the **Tool** it applies to, and choose **What happens**:

| What happens | What your agent sees |
|---|---|
| **Times out before it runs** | The call waits, then times out. Nothing changes in the world |
| **Runs, then the answer is lost** | The world makes the change, then your agent hears a timeout. A retry makes it twice |
| **Unavailable** | The service answers that it is down |
| **Answers with an error** | The service answers with the status and message you set |
| **Needs approval first** | The world refuses the change until an actor records an approval of it |

Then fill in the fields the choice needs:

- **On which call**: which call to that tool fails, counting from 1, so you can let the first lookup succeed and fail the second
- **Delay in seconds**: how long a timeout waits, from 0 to 30
- **Status** and **Message**: for **Answers with an error**, a status from 400 to 599 and the message the service returns, up to 500 characters
- **Approval it needs**: for **Needs approval first**, the world action that records the approval, listed with the actor who can take it, such as `approvals.put, by Dana Brooks`. **Approved when** (optional) sets the values that make it an approval, such as `{"status": "approved"}`

{/* SCREENSHOT TODO: test-condition-approval.png. A test condition on issue_refund with What happens "Needs approval first" and Approval it needs set to an action held by a manager actor. Callout on "What happens". Clean-capture rules apply */}

Not every tool offers every choice. **Runs, then the answer is lost** and **Needs approval first** only apply to a tool that changes records, and **Needs approval first** also needs an actor who can record the approval. A tool that runs inside your agent can't be given a condition at all, and the editor says **This tool runs inside the agent, so it cannot be held**.

A scenario can carry more than one condition. Save the scenario as you would any other edit. If the test world can't apply a condition, the editor says which one and why.

## Read the result

Run the scenario, then open a call from it in [Read run results](/docs/environments/guides/read-run-results#world-state). The call's **World state** shows what the condition did: a faulted attempt in the counts, **Committed but answered with a timeout** for a lost answer, and the request and decision under **Approvals** for a change that needed approval, including whether the agent waited for the decision.

Compare that with the transcript. An agent that handles a lost answer well checks whether the change went through before it tries again, and one that handles a timeout tells the caller what happened instead of claiming success.
