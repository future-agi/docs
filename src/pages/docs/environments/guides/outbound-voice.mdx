## About

An outbound call starts with your agent. For example, Ridgeline Outfitters calls to say a tent repair is ready. Use a hosted Retell phone run to test whether the call connects. Use an outbound voice scenario in an environment to test what the agent says when a mailbox, rather than a customer, picks up.

## Test the Retell phone route

You need a Retell test agent, a Retell number that can place outbound calls, and a hosted Agent Learning Kit runner with voice and number leasing enabled. The two phone numbers have different owners:

| Number | Who supplies it | What it does |
| --- | --- | --- |
| Originating number | You | Retell places the call **from** this number. Use your agent's number in E.164 format (a `+`, country code and number, as in `+12025550141`), not a customer's number. |
| Destination | Future AGI | The runner reserves a number for the simulation, has Retell dial it, and releases it when the run ends. You do not enter it in the agent definition. |

1. In the voice **agent definition**, choose **Retell** under **Voice/Chat Provider**. Enter the test agent's Retell ID under **Assistant ID** and its **Provider API Key**. Select **Phone**, set the direction to **Outbound Calls**, and enter the originating number using **Country Code** and **Contact Number**. **Web** does not place a phone call.
2. [Create a run test](/docs/api/run-tests/createruntest) for that agent version. Start with two scenarios of one row each: in one, the customer can collect the tent today; in the other, they ask about collecting it tomorrow. Use one row if your runner does not support sequential reuse.

{/* MEDIA: Retell voice agent definition with Phone and Outbound Calls selected; mask the key, agent ID and originating number. */}

Start the saved test with **Run New Simulation**, or use the request below **instead**. Both actions place real calls. For the request, set `FI_API_KEY` and `FI_SECRET_KEY` to your Future AGI credentials, `RUN_TEST_ID` to the saved test UUID, and `TODAY_ID` and `TOMORROW_ID` to the two scenario UUIDs attached to it.

```bash
curl --fail-with-body --silent --show-error \
  --request POST "https://api.futureagi.com/simulate/run-tests/${RUN_TEST_ID:?Set RUN_TEST_ID}/execute/" \
  --header "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  --header "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  --header 'Content-Type: application/json' \
  --data "{\"scenario_ids\":[\"${TODAY_ID:?Set TODAY_ID}\",\"${TOMORROW_ID:?Set TOMORROW_ID}\"]}"
```

The response's `execution_id` identifies the run, not an individual call. With reuse enabled, Retell dials the same destination **one call at a time**. The runner finishes the first call and clears the room before admitting the next. If the room is still occupied, it refuses to dial rather than connect a customer from the wrong scenario.

In the [call history](/docs/api/run-tests/getcallexecutions), look for two call records belonging to that execution, not two destination numbers. For each call Retell accepted, its provider receipt has a distinct `call_id`. Read `call_status` and `disconnection_reason` on that record before comparing transcripts: in Retell's outbound transcript, `agent` is the Ridgeline agent and `user` is the simulated recipient.

## Test what the agent says to voicemail

The environment's **Hosted platform** phone connection and the leased Retell runner above are different: the environment runner dials the contact number you supply. Setting a scenario to outbound changes the roles in the conversation; it does not make that connection lease a destination. To test the conversation without dialing a phone number, use a [hosted voice environment](/docs/environments/guides/build-an-environment) with a **Web** connection.

1. In your voice environment, ask the builder for a mailbox case. For example: *Add one outbound scenario for the tent repair callback. A personal mailbox says “You've reached Sam. Leave a message.” Check that the agent waits for the tone, names Ridgeline Outfitters, explains the pickup, and tells Sam how to follow up without asking a question.*
2. In the authored scenario, `call_direction` must be `outbound` and `answered_by` must be `voicemail`. Put the greeting in `persona.initial_message` and choose `voicemail_style` explicitly. If you omit `answered_by`, a person answers; if you request voicemail but omit the style, you get `personal`.
3. In **Scenarios**, select the case, set **Repeats** to **1×**, and choose **Run simulation**. [Open the call](/docs/environments/guides/read-run-results) and listen to the greeting, the tone if there is one, and the agent's next words. A mailbox greets once and stays silent even if the agent asks a question.

{/* MEDIA: Outbound mailbox scenario selected for one repeat, followed by the call recording and transcript showing a greeting and no further mailbox reply. */}

### Compare mailboxes on the same callback

| `voicemail_style` | What the agent hears | What to check for Ridgeline |
| --- | --- | --- |
| `personal` | A named personal greeting, then a tone | After the tone: “Sam, this is Ridgeline Outfitters. Your tent repair is ready. Please call the store to arrange pickup.” No need to wait for an answer. |
| `carrier` | The network's default greeting, no name, then a tone | Leave a callback message without claiming to have reached Sam personally. |
| `operator` | A longer, formal announcement before the tone | Listen for the start of the message **after** the announcement. If the agent spoke over it, the recipient may miss who called. |
| `full` | An announcement that the mailbox cannot accept messages. No tone. | End the call without leaving a pickup message. Silence after the announcement is not evidence that a recording started. |

To compare the first and last rows, ask the builder for a second case with `voicemail_style` set to `full`, the greeting “This mailbox is full and cannot accept new messages,” and the expected outcome *ends without leaving a message*. Select both cases for the run. Do not require the customer to confirm a pickup time or the agent to record an agreed date. Neither can happen on a mailbox call.

## Limits and unexpected results

- **Only one row allowed:** Leased-number reuse requires a compatible runner **and** reuse enabled. If the run refuses multiple rows, use one row per run. Separate runs do not reserve the same destination for you.
- **Rejected or unanswered:** Check the provider's call status and disconnect reason before reading evals. Retell's `not_connected` is a terminal call record, not a failed conversation. By contrast, talking over an operator greeting on a connected call is behavior you can evaluate.
- **Too many mailbox cases:** The environment harness allows up to 5% of the authored suite to be voicemail, rounded up. A 20-scenario suite can contain one; a 21-scenario suite can contain two. If you include two or more, vary both the greeting and the style. You can run just those cases from a larger suite. A suite does not have to contain voicemail.
