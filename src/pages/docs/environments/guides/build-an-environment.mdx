## About

Build an [environment](/docs/environments/concepts/understanding-environments) to generate test scenarios for your agent without starting a scenario run. A phone preflight checks the setup without dialing the number; a LiveKit preflight can start a short, billable session with your worker.

## Choose how to connect

In the sidebar, open **Simulate** > **Environment**, then select **Build environment**. Under **Or connect your own agent**, choose the source that matches what you want to test:

| Source | Choose it when |
|---|---|
| **Hosted platform** | You want to test the agent you already deployed. It stays on its provider and keeps using its own tools and data. |
| **Source repository** | You want the builder to read your agent's code from GitHub and build the environment from that code. |
| **Code upload** | You want the same code-based build, but the source is in a folder on your machine. |

<img src="/images/docs/environments/guides/build-an-environment/build-environment-tab.png" alt="Build environment tab with Source repository, Code upload and Hosted platform under Or connect your own agent" style={{ borderRadius: '5px' }} />

For example, Ridgeline Outfitters wants to check that its returns agent asks for an order number before discussing a return. To call the deployed **test** agent, choose **Hosted platform**. To inspect the code that implements the return lookup, choose a code source instead.

## Connect a hosted agent

On **Hosted platform**, choose the **Agent type** and **Platform**. Use a test deployment with synthetic orders. Connecting to a hosted agent does not clone it or redirect its tools: if its refund tool points at a live payments service, a simulated customer can still trigger a real refund.

### LiveKit: reach a worker by name

Choose **Voice** and **LiveKit**. This connection uses a WebRTC room in your LiveKit project, so there is no phone number or **Web**/**Phone** switch. Fill in all five fields:

| Field | What to enter |
|---|---|
| **Agent name** | The exact dispatch name your running worker registered, for example `ridgeline-returns`. This is not the name you want to give the environment. |
| **LiveKit URL** | The URL of the LiveKit project where that worker is registered. |
| **LiveKit API key** | A key from that project. |
| **LiveKit API secret** | The secret paired with that key. |
| **System prompt** | The test agent's current instructions, up to 65,536 characters. Include the return policy and what the agent should ask the caller to provide. |

{/* MEDIA: Hosted platform with Voice and LiveKit selected, all five fields visible, credentials masked and no phone selector. */}

LiveKit does not expose the worker's prompt or tool schemas. The builder uses the pasted prompt to write scenarios; it does not change the live prompt. Mentioning a lookup tool, or filling in **GitHub repo** on this hosted form, does not import the tool's definition. Use **Source repository** or **Code upload** if the builder needs to read that code.

### Phone: connect a number your agent answers

Choose **Voice**. The Environment runner calls the **Contact Number** you supply over the platform's SIP trunk. How the builder learns about the agent depends on whether you have its provider credentials:

| Setup | What you supply | What the builder can learn |
|---|---|---|
| **Others** (phone only) | A test number and the agent's **System prompt** (up to 65,536 characters). No provider ID or key. | Scenarios come from your description. The builder cannot verify the live prompt or discover tool schemas. **Inbound Calls** is locked on. |
| **Vapi** or **Retell AI**, then **Phone** | A test number plus **Assistant ID** and **Vapi API key**, or **Agent ID** and **Retell API key**. | The builder can read the provider's agent definition, including available tools. A successful agent lookup does not verify that the number belongs to the agent. |

Select **Country Code**, then enter the national digits in **Contact Number**, without repeating the country code. Together they form an international E.164 number (`+`, country code, then national number). Turn on **Agent speaks first** if the simulator should wait for your agent's greeting.

{/* MEDIA: Retell AI Phone form with Inbound Calls on, Contact Number masked and Agent speaks first visible. */}

For **Vapi** and **Retell AI**, turning off **Inbound Calls** changes the scenario direction; the Environment still dials your number. To test an actual outbound Retell call, use the [hosted voice simulation runner](/docs/self-hosting/configuration/reference#voice-simulations-distributed) with outbound Retell support. There the number you supply is your Retell **originating** number. The runner leases the **destination** for your agent to call. Reusing that destination for multiple scenarios requires a compatible runner with reuse enabled.

<Warning>
Phone runs place real calls and can incur carrier and provider charges. Use only test numbers you control or have permission to call. For an inbound test, confirm the number routes to the test agent, not a customer service queue. A bare phone connection gives you the conversation, not a log of the agent's internal tool calls or proof of a refund.
</Warning>

### Other hosted connections

For a Vapi or Retell voice agent that you want to call without telephony, choose **Web** instead of **Phone**. Use the same provider ID and key; no phone number is needed. For Retell chat, choose **Chat**, then **Retell AI**, and enter the **Chat agent ID** and **Retell API key**.

## Connect from code instead

Provide a Docker Compose file or Dockerfile that starts the agent you want to test. A chat agent must also accept conversations over HTTP or a JSON WebSocket. The **Entry path** and **Entry file** fields do not override what the container starts. See [Repository and upload requirements](/docs/environments/reference/supported-agents#repository-and-upload-requirements) for supported endpoints and dependencies.

- **Source repository**: choose GitHub, enter **Repository** as `owner/repo`, and set **Branch or tag** (`main` by default). For **Private** visibility, provide the **GitHub App installation ID** that grants access to this repository.
- **Code upload**: before selecting **Choose folder**, remove secrets such as service-account JSON files from the source folder. The upload skips local `.env` files and common generated folders, but it is not a secret scanner. If you need a smaller folder, keep the container definition and everything its build and startup commands use.

{/* MEDIA: Source repository form showing the repository, branch and visibility controls. */}
<img src="/images/docs/environments/guides/build-an-environment/source-repository-form.png" alt="GitHub source form with Repository, Branch or tag, Entry path and visibility fields" style={{ borderRadius: '5px' }} />

On either code form, open **Environment values (optional)** to supply the values the agent needs at startup. Use **Paste .env contents** for `NAME=value` pairs, one per line. In **Additional egress domains**, enter any extra public hostnames your agent needs, separated by commas or newlines. The sandbox blocks requests to hosts outside its allowlist. For Google service-account credentials, use **Upload credential file** beside the expander; it accepts a service-account JSON file up to 5 MiB.

### Turn on observability

Select **Turn on observability** on a repository or upload if your code already emits OpenTelemetry or traceAI telemetry. This does not instrument your code. If observability cannot be enabled, the build can still finish without it. For a worker you deploy yourself, see [Trace a LiveKit agent](/docs/integrations/traceai/livekit).

## Run preflight

<Steps>
  <Step title="Choose how many scenarios to generate">
    Set **Scenarios to generate** to `2` for Ridgeline. This sets how many scenarios to write, not which cases they cover or how many calls to place. The default is 10. The form accepts 1 to 1,000; your deployment can set a lower limit.
  </Step>
  <Step title="Set concurrency">
    Leave **Parallel worlds** at `1`. Where parallel execution is enabled, you can request up to 4; preflight can admit fewer. This setting does not isolate a hosted agent's backend.
  </Step>
  <Step title="Check readiness">
    Select **Run preflight** and look for **Ready to build**. If a check fails, correct its cause and run preflight again. Changing a field invalidates the previous result.
  </Step>
</Steps>

**For LiveKit**, preflight checks the key and secret, creates a temporary room in your project and dispatches the named worker. It waits up to **8 seconds** for the participant assigned to that dispatch to join, then requests room cleanup. A different worker already in the room does not count. This is a real, short session: LiveKit and the model providers used by your worker may charge for it. It does not consume Future AGI credits or start a scenario run.

| Preflight result | What to do |
|---|---|
| LiveKit rejects the credentials (HTTP 401 or 403) | Check that the URL, key and secret belong to the same test project. |
| Credentials accepted, but no agent with that name joined within 8 seconds | Check the dispatch name and that the worker is running in that project. For example, if the worker registered as `ridgeline-returns`, entering `ridgeline-support` will not reach it. A valid key alone cannot prove the worker is online. |
| `LiveKit agent 'ridgeline-returns' joined a test room` | The named worker joined. This checks reachability, not whether it follows the return policy. |
| Phone preflight reports `phone_dialer_not_configured` | The platform's outbound SIP calling setup is missing. Ask your administrator to check the trunk, caller ID and simulator LiveKit configuration. Do not enter your own SIP credentials. |

### Example: check a phone-only target by API

This request checks the number format and platform dialer configuration. It does **not** call the number or verify who answers. Set `FI_API_KEY` and `FI_SECRET_KEY` to your Future AGI API key pair. For a self-hosted deployment, replace `https://api.futureagi.com` with your deployment’s API origin. The example number is fictional; use your own authorized test number when you build.

```bash
curl --silent --show-error --fail-with-body \
  'https://api.futureagi.com/simulate/api/harness-jobs/preflight/' \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{
    "agent": {
      "connector": "phone",
      "mode": "connect_only",
      "config": {
        "phone_number": "+12025550146",
        "target_system_prompt": "You handle returns for Ridgeline Outfitters. Ask for the order number before discussing a return."
      }
    },
    "scenario_count": 2,
    "artifacts": {"level": "full"},
    "metadata": {"name": "ridgeline-returns"}
  }'
```

| Result | What it means |
|---|---|
| HTTP 200 with `"ready_to_submit": true` | Preflight passed. No call was placed. |
| HTTP 400 with `phone_number must be in E.164 format` in the message | Send the complete international number as a string, including the leading `+`. |
| HTTP 503 with `"error": "phone_dialer_not_configured"` | Ask your administrator to configure the platform dialer. The `message` lists the missing settings. |

## Build and decide whether to run

Once preflight passes, select **Build environment**. The workspace opens while the builder reads the agent, writes its [contract](/docs/environments/concepts/contracts), and generates and validates scenarios. You can return to it from **My Environments**. If it shows **Failed**, open the failed step for the reason. If it shows **Ready**, [review the contract](/docs/environments/guides/review-the-contract) and scenarios before placing calls.

A sealed build is not a completed test. The builder explains what is ready. If a behavior still needs a call to confirm it, the builder recommends the smallest run that covers it, naming the scenarios and the call count. The recommendation alone does not add a run under **Runs**. You can stop here, approve the proposal in chat, or [start a run yourself](/docs/environments/guides/run-a-simulation).

For Ridgeline, look for one scenario in which the caller has an order number and another in which they don't. If either is missing, [ask the builder to add it](/docs/environments/concepts/chat-orchestration) before requesting a run.

| What you ask the builder to run | Scenarios | Trials per scenario | Calls requested |
|---|---:|---:|---:|
| Both order-number cases once each | 2 | 1 | 2 |
| Only the missing-order-number case once | 1 | 1 | 1 |

Open **Runs** and compare **Scenarios**, **Trials** and **Simulations** with your request. In a completed call, use the transcript's speaker labels to check whether the agent asked for the order number. If a recording is available, listen to that exchange. The builder reports errored calls instead of automatically requesting another run.
