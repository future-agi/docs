---
title: "Manage agent versions"
description: "Promote a checked version, choose which version each environment tests, compare versions, and clear out the ones that failed"
---

Every change to a connected agent becomes a numbered version. This guide covers what you do with them: look one over, compare two, promote one to production, choose which version each environment tests, and deal with the ones that fail their check. [Agents & versions](/docs/environments/concepts/agents-and-versions) explains how versions and production fit together.

A few terms used throughout:

- **Version**: one numbered state of the agent, made by each change to it
- **Check**: every new version is checked before it can be used
- **Production**: the version your environments test unless told otherwise
- **Follows production or pinned**: an environment either follows production or is pinned to one version
- **Code agent or hosted agent**: a code agent is one connected from GitHub or an upload. A hosted agent is one connected from a provider such as Vapi or Retell

## What do you want to do

- **My version shows Check failed**: [Retry a failed version](#retry-a-failed-version), then [discard it](#discard-a-version) if it can't be fixed
- **I want a version to become production**: [Set a version as production](#set-a-version-as-production)
- **I want an environment to test a certain version**: [Choose which version each environment tests](#choose-which-version-each-environment-tests)
- **I want to see what changed**: [Compare two versions](#compare-two-versions)

## Find a version

Open the agent from **Agents** > **Connected agents** and go to its **Versions** tab. The list runs newest first. Each new version is checked on its own before it can be used, and its row shows where it stands with chips such as **Latest**, **In production** or **Check failed**. A version whose check passed shows no check chip. The row also shows where the version came from and when, and its commit message when it has one.

Click a row's label to select that version. The selected version is the one in view, and the **Definition** tab and the **Compare** card start from it. The page address keeps it as `?v=`, so a link you share opens on the same version.

## See what a version holds

The **Definition** tab shows the version in view, read-only: what was read from it, such as its framework, model, prompts and tools, and where it came from, such as the repository, branch and commit.

For a code agent, the **Files** card lists the version's files and marks the ones changed since the previous version. Click a file to read it, and turn on **Diff vs previous** to see that one file against the version before.

## Compare two versions

This applies to code agents only. Hosted agents don't have **Compare** yet.

To see everything that changed between any two versions of a code agent, use the **Compare** card on the **Versions** tab.

It starts with the version in view against the next older version made from GitHub or an upload. Pick other **Older** and **Newer** versions to change that, or click **Compare** on a row. The summary line counts the files and lines that changed, and the tree on the left jumps to each file's diff. Switch between **Unified** and **Split** to suit the change.

**View file** opens a file on the **Definition** tab. When both versions are commits of the same GitHub repository, **Open in GitHub** opens the same comparison there.

## If a version shows Check failed

A failed check is the one place you can get stuck, so the two steps are here, before the sections on production.

### Retry a failed version

A version whose check fails shows **Check failed** with the reason under its label. When it's the newest version, a banner on the agent page shows the reason too. [Environment FAQ & fixes](/docs/environments/troubleshooting#fixes-while-connecting-an-agent) explains the common reasons. What you do next depends on what you see.

- **The banner asks for credentials**: it shows a field for each missing name and a **Save credentials** button. Fill in each field and save. That makes a new version with them and checks it
- **The row or banner shows Retry**: click it to run the check again. It shows when the failure can be retried, and when a check has run for a long time and may have stopped
- **Neither shows**: the check can't be retried from here, so [discard the version](#discard-a-version) and make a new one

### Discard a version

You can't delete a single version, but you can discard one that failed its check or is still waiting on it. Click **Discard** on its row and confirm. The version stays in the list, set aside: nothing runs it and it can't become production.

You can't discard the version in production, or one an environment uses as its default. Set another version as production, or [change that environment's default](#choose-which-version-each-environment-tests), first.

## Set a version as production

If the agent's header shows **Managed by**, an environment built this agent, so it has no **Set as production**. This applies to agents an environment built. That environment picks up new versions when you rebuild it, as [Sync a hosted agent](/docs/environments/guides/sync-a-hosted-agent) covers.

A version needs a passed check to become production. A passed check shows no chip, and a failed one shows **Check failed**. The first version that passes becomes production on its own when the agent has none yet, and every later one waits for you.

Click **Set as production** on the version's row and confirm. What happens next depends on each environment's policy, which is either following production or pinned to a version, and on the size of the change:

- **Major**: a tool is added, removed or takes different arguments, or a new [rule](/docs/environments/concepts/contracts) appears in the contract
- **Compatible**: anything smaller
- **Can't be judged yet**: the new version, or the one the environment was built from, has no read definition to compare

An environment is offered a version when it is told about a newer version but does not move to it. The offer shows on the **Agents** panel of the environment's **Overview** and as a rebuild card in the environment's build console, where you can [rebuild or skip](#rebuild-or-skip-an-offered-version).

| Environment policy | Change | Outcome |
| --- | --- | --- |
| Follows production | Compatible | The environment moves to the new version |
| Follows production | Major | The environment is offered the new version and stays where it is |
| Follows production | Can't be judged yet | The environment is offered the new version and stays where it is |
| Pinned | Any | The environment keeps its version and is offered the new one |

The confirmation says how many following environments moved. An environment that's busy moves once it's free.

**Roll back** by setting an earlier version as production. It works the same way and carries following environments back to it.

## Choose which version each environment tests

Pin an environment when you want a stable baseline that only changes when you say so. Let it follow production when it should always test what you've promoted.

Open the agent's **Environments** tab. It lists each environment that tests the agent, with the version it's testing, its last result and its status. The label on each row is the environment's policy. Here, default means the version the environment tests. **Default: production** means it follows production, and **Default v2** means it's pinned to v2. The buttons use the same words: **Default to production** and **Follow production** both make an environment follow production, and **Make default** pins it.

### Make a pinned environment follow production

An environment you [build](/docs/environments/guides/build-an-environment) from the agent starts pinned to the version it was built from. A pinned environment's row has one of two buttons:

| State | Button | What it does |
| --- | --- | --- |
| Pinned and behind production | **Default to production** | Moves the environment to the version in production now, and it follows production from then on |
| Pinned and not behind | **Follow production** | Makes the environment follow production from now on |

### Pin an environment to a specific version

To have one environment test a different version, open the environment and find the **Agents** panel on its **Overview**. Click **Make default** on the version you want, and confirm. This pins the environment to that version, and new runs in it use that version.

### Rebuild or skip an offered version

When an environment is [offered a version](#set-a-version-as-production), the offer shows on the same **Agents** panel, and as a rebuild card in the environment's build console. Click **Rebuild** to move the environment to it, or **Skip** to stay on the version it has.

## Delete the agent

Open **More actions** at the top right and choose **Delete**. The agent and its versions are removed from **Connected agents**, and runs that already happened keep their results.

**Delete** stays disabled while any environment tests the agent, and says how many do. An environment counts as soon as it's created, even before its first run, so delete those environments first.
