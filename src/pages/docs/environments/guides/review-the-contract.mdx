If the builder misses a tool or weakens a rule, the runs that follow test the wrong thing. The [contract](/docs/environments/concepts/contracts) is the builder's record of your agent's tools, rules and use cases, and every [scenario](/docs/environments/concepts/scenarios-and-trials) and grade is written from it. The usual mistakes are a tool that was missed, a rule that was paraphrased into something weaker, and a use case the agent doesn't actually handle.

Review the contract once, after the environment shows **Ready** and before your first run. Compare it with your agent's source, correct any mismatch in chat, and check that a scenario exercises the correction.

<Prerequisites title="Before you start">
- A [built environment](/docs/environments/guides/build-an-environment) that shows **Ready**.
- The agent's tool definitions and instructions to compare with the contract.
</Prerequisites>

## Check what the builder read

1. Open the environment from **My Environments**.

   **Overview** opens with a strip of facts about what was connected:

| Fact | What it states |
|---|---|
| Channel | Voice or chat |
| Connector | The platform the agent was reached through, such as Vapi |
| Domain | The field the agent works in, when the builder could tell |
| Direction | For a voice agent, whether calls come in or go out |
| Source | Where the agent was read from: a repository with its branch, an uploaded folder, or a hosted platform |
| Mode | How the agent is run, such as **Connect only** for an agent that stays on its own platform |
| Parallel worlds | How many scenarios run at the same time |

2. Check **Test subject** against the agent you meant to test.

   **View agent** opens that agent's own page.

3. Under **Capabilities**, find **Read from source** and compare **Tools** with your agent's tool names.

   The list holds every tool the agent can call, as it is named in your agent. A tool missing here is a tool no scenario will exercise.

4. Compare **Rules** with the hard constraints in the agent's instructions.

   Rules are quoted from the instructions, so check the wording: a paraphrase can weaken a rule without omitting it altogether. A rule missing here is a rule no run will check.

## Check the world for your source type

Further down, **The world** shows what the agent works against. **What it depends on** lists the services built and torn down with the environment, such as a database. What to check for data depends on the source:

- **Repository or code upload:** **Seeded data** lists each table filled before the agent arrives, with its row count. Compare them with what the tools need. The rows are rebuilt for every task, so nothing carries over between calls.
- **Hosted platform:** the agent keeps its data on its own side, so it has no seeded data.

## Compare the contract with the source

1. Open **Contract**.
2. Expand **Capability graph**.
3. Compare the listed flows, guardrails, world state, tools and end conditions with the source.

   For example, the pharmacy contract below says `find_patient` identifies a caller by phone number or by full name and date of birth. The source rule adds a condition: use full name and date of birth if the caller's number is not on file. Check that the rule survived under **Guardrails**, not just that the tool name appears under **Tools**.

| Section | Check that |
|---|---|
| Capability graph | Every item under **Flows** is a use case the agent is built for, and **Guardrails** matches the rules on Overview. The graph starts folded |
| World state | The tables and row counts mirror the data your agent's tools act on |
| Tools | Every tool is there, including any Overview missed |
| Run end conditions | The limits fit how long a real conversation with your agent takes |

If everything matches, the environment is ready to run.

## Correct what is wrong

1. Submit the specific mismatch in [chat orchestration](/docs/environments/concepts/chat-orchestration) on the left of the workspace.

   Name the tool or quote the rule and say what the source actually requires. For example:

   - "The agent also has a `cancel_order` tool that takes an order ID"
   - "There is a rule that the agent never quotes a delivery date; add it"
   - "The refund tool needs the order ID, not the email address"

2. Reopen **Contract** (or **Overview** for a tool or rule listed there).
3. Check the corrected detail against the source again.

   For the refund example, look for the order ID rather than an email address; if it hasn't changed, restate the exact argument in chat.

4. Ask for scenarios that exercise the correction, for example, "add two scenarios that test the new rule".

   The correction applies to what the builder writes from then on.

5. Open **Scenarios**.
6. Select a scenario meant to cover the corrected behavior.

   Inspect **Situation**, **Sub-goals** and **Ideal outcome**. Sub-goals are named after what they test: on the pharmacy line, `identifies_patient_before_discussing_prescriptions` covers the identification rule.

<Note>
A correction changes the environment's understanding of your agent, never the agent itself. If the agent's own behavior is what is wrong, change it where the agent lives, on its hosted platform or in its code, then run the environment again.
</Note>

## Check the build settings

**Settings** records how the environment was built, including its [environment values](/docs/environments/guides/build-an-environment#add-environment-values). Everything there is fixed at build time except the name:

- **Environment info**: rename the environment here
- **Environment variables**: the values the agent was built with, with secrets never shown

To build from a different source or with different values, build a new environment.
