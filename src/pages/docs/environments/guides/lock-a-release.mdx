---
title: "Lock a release"
description: "Lock an environment's versions into a release with train and test splits, so scores on it stay comparable"
---

A score only means something next month if it was measured on the same tasks and graded the same way. **Lock** turns the environment's current versions into a **release**: its scenarios, their train and test splits and the scorer can't change after that, so every score on the release compares fairly.

## What a release holds

A release is the environment's default **environment version** and **scenario version**, locked together. Versions never change once they're saved, so the release stays exactly as it was. When you edit the environment, the edit makes a new, unlocked version, and the release keeps the old one.

Every release splits its scenarios into two sets:

- **Train**: the scenarios a team or a coding agent learns from
- **Test**: the scenarios that check the result, which the learning never sees

Only scenarios with checks to score them get a split. The split is picked for you, so nobody can tune the test set by hand:

- The test set is about 30% of a small suite and 20% of a large one, and never more than 30%. A suite of 20 scenarios gets 6 test scenarios. A suite of 500 gets 100.
- Each use case is split in proportion. A use case with two or more scenarios keeps at least one in train. Use cases with a single scenario are split together as one group.
- A scenario keeps the split it got the first time it was locked, in every later release. A growing suite adds new scenarios to fill the test set. It never moves a test scenario into train.

## Lock the current versions

Open the environment and go to **Overview**. The **Release** card shows:

- the versions it would lock, as `agent v4 · acme/support-bot@main · a1b2c3d · environment v3 · scenarios v5`
- **Reference passes**: **Passed** when the scenario version was proved against this environment version, or **Not proved**
- the split it would get, for example `Train 14 · Test 6 tasks once locked`

Click **Lock this release**, then **Lock release** to confirm. The card now reads **Release 2026.11.1** with the **Locked** badge, the date and its train and test counts. The label is the month you locked it in, then its count in that month.

Workspace members who can edit the environment can lock it. Viewers can't.

### When you can't lock yet

The card says why, in one sentence, and **Lock this release** stays off:

- **Add scenarios to lock: a test split needs at least 4.** A suite needs at least 11 scenarios with checks for the test set to reach 4. Click **Add scenarios** to open the Scenarios tab, then add and save them.
- **This environment is building or its last build failed. Lock it once a build finishes.** Wait for the build to finish, or fix it and build again.

If someone changed the default versions while you had the page open, the lock is refused and the card shows the current versions. Check them and lock again.

## Unlock a release

An owner or admin of the organization, or a workspace admin, can unlock a release. On the **Release** card, click **Unlock** next to the release, then **Unlock release** to confirm.

Unlocking changes nothing about the release itself. Its versions, its scores and the split of each scenario stay as they were. The release is still listed under **Earlier releases**, marked unlocked. Lock the same versions again, and you get a new release with a new label and the same splits.

## Delete an environment with a locked release

An environment with a locked release can't be deleted. Deleting it shows **Unlock release 2026.11.1 first.** Unlock its releases, then delete it. A release stays locked when you edit the environment, so look under **Earlier releases** too: each locked one there has its own **Unlock**.
