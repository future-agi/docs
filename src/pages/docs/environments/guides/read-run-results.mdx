## About

Open a run to see what your agent said and how it scored on each **call** (one scenario played once). If the run stopped early, you can see what finished and, when eligible, resume just the calls that did not.

## Open the run

Open the environment, go to **Runs** and click a run. The header names the run, its status, the environment, how many tasks are in the run and when it started. If you came to find out why calls failed, **Debug failures** is the shortcut: it opens a diagnosis of the failing calls, covered [below](#let-the-run-be-diagnosed-for-you). The other actions beside it:

| Action | What it does |
|---|---|
| Run evals | Grade this run's finished calls again, or with evaluations you added since; see [Add evaluations](/docs/environments/guides/add-evaluations#grade-a-run-that-already-finished) |
| Export | Download the run's results as a CSV file |
| [Resume](#resume-an-interrupted-run) | Continue an interrupted run without repeating its finished calls |

To run calls again, tick them in the table and use **Re-run**, covered [below](#re-run-selected-calls).

Use **Test runs** for individual calls and **Analytics** for the whole run. **Trials** also appears if this run has optimization trials.

## Find what failed

**Test runs** has one row per call. Calls are grouped by **Use case**, the job each scenario tests, and **Group by** regroups them by **Sub-goal**, **Accent**, **Age**, **Attack**, **Task** or **Status**, or turns grouping off with **No grouping**. Turn on **Expand all** to open every group, and filter with the chips above the table:

- **Failed**: the agent was measured and did not pass
- **Error**: the call was canceled or errored, for example when a connection failed; this is not a failed evaluation
- **Inconclusive**: there is no conclusive verdict, for example because an evaluation errored or no evaluation scored the call
- **Passed**: the agent was measured and passed

While a run is still going, **Queued** and **In progress** count the calls that haven't finished.

Each row names the scenario and its trial, such as `check-refill-status-processing · Trial 2`, with its outcome and duration, and lists the scenario's sub-goals beneath it with a mark for each one that held. The columns are grouped:

- **Run details**: the use case the call belongs to
- **Scenario details**: the **Persona** the caller played, with their name, voice, age and traits, and the **Scenario**
- **System metrics**: **CSAT**, **Turns**, **Latency** and more, with values past a warning threshold flagged in red
- one column per evaluation, with the call's score. A cell with no score says why: **Failed**, **Timed out** or **Not scored**, with the reason when you hover it, and a dash when the evaluation doesn't apply to that scenario or the call never ran

Group rows show averages. **Columns** chooses which columns show, including each evaluation on the run.

## Read a single call

Click a row to open the call. Start with the call's **Evals** tab on the right: it gives each evaluation's verdict and the reason behind it, and the reason names what went wrong, such as a date of birth read back incorrectly. Then find that moment in the **Transcript** on the left, by its timestamp or its words.

<img src="/images/docs/environments/guides/read-run-results/voice-call-drawer.png" alt="A voice call drawer with the masked call ID, the Transcript and Traces tabs, the recording waveform and timestamped transcript on the left, and the Evals tab on the right with a failed evaluation expanded to show its reason" style={{ borderRadius: '5px' }} />
*Read the Evals reason, then find the moment in the transcript*


### The right of the drawer

For a chat call, use **Chat analytics**, **Evals**, **Messages** and **Attributes**. For a voice call, the top holds the call's details, including its duration, average latency and **Ended**, the reason it ended, such as `silence-timed-out`. Below them are tabs:

- **Call Analytics**: timing, turns, talk split, silence, interruptions and speaking rate; [Call metrics](/docs/simulation/reference/call-metrics) defines each one
- **Evals**: each evaluation's verdict and its reason
- **Scenario**: the scenario the caller was playing, so you can check what the agent was asked to do
- **Messages**, **Logs** and **Attributes**: the call's raw messages, logs and attributes

### The left of the drawer

Read the **Transcript** turn by turn. If a recorded tool call is involved in a failure, check its arguments against what the caller asked for. A voice transcript can also show silences and interruptions. When audio is available, use the **Recording** above the transcript to hear what happened.

Beside **Transcript**, **Traces** lists the traces your agent sent during the call, when it has [observability](/docs/environments/guides/build-an-environment#turn-on-observability) turned on; click one to open it. A call with none reads **No trace for this call**.

## Resume an interrupted run

Suppose you stop a Ridgeline returns run after 8 of its 10 calls finish. **Resume** starts a new attempt for the other 2 calls. You keep the same run ID, agent version, environment version, scenario suite and assembled bundle. The first 8 results stay in place, and you aren't charged for those calls again.

For a saved environment, a run counts as interrupted when the job that runs its calls is canceled or fails with calls left unfinished. This can happen when you confirm **Stop simulation**, a usage limit prevents more calls from starting, or a worker fails. Wait for execution and grading to stop. The run's status alone doesn't tell you whether you can resume it: even a run marked **Completed** can be resumable if a previous resume stopped before all its calls finished. An Epoch check run can't be resumed here.

| What happened to a call | What Resume does |
|---|---|
| It has no result, was skipped, or never started (for example, setup failed or you reached a usage limit). | Runs the call and its evaluations. |
| An infrastructure, connectivity or platform sync failure ended it. | Runs the call and its evaluations. |
| It ran and was billable, even if the agent failed an evaluation or the simulated caller went off script. | Keeps its result. To repeat it deliberately, use [Re-run](#re-run-selected-calls). |

### In the dashboard

1. Open the environment's **Runs** tab and select the interrupted run. Look for **not finished** next to the task count in the header.
2. If a usage limit stopped the run, make sure you have enough capacity for the remaining calls. Select **Resume**. You don't need to tick any calls.
3. Stay on **Test runs** to follow the new attempt. The header shows when you last resumed the run. **Resume** isn't offered while the attempt is running or grading. If it stops early again, check the header for **Resume**.

### Through the API

Use curl 7.76 or later and `jq` in the same Bash session for both requests. Set `FI_API_KEY` and `FI_SECRET_KEY` to your workspace credentials. In the open run's URL, the ID after `runs/{testId}/` is the **test execution ID**. Replace the placeholder below with that ID, not the environment or job ID. For self-hosting, set `FI_BASE_URL` to your API origin.

```bash
set -o pipefail
export RUN_ID="YOUR_TEST_EXECUTION_ID"
export base="${FI_BASE_URL:-https://api.futureagi.com}"
curl --fail --silent --show-error \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  "${base%/}/simulate/v3/test-executions/$RUN_ID/calls/?page_size=10" |
  jq -c '{execution: (.execution | {id, pinned_agent_version, environment_version, suite_version, resume}),
          calls: [.results[] | {id, outcome, started_at, completed_at}]}'
```

This shows the run's pins and up to ten call IDs with their verdicts and timestamps. Inside `execution.resume`, `finished` and `unfinished` count calls across the whole run. Use these counts rather than guessing from timestamps or verdicts. If `resumable` is `false`, the counts are `null`; don't submit a resume. If it is `true`, send this request once. Omit call IDs, `select_all` and `environment_values`: the run determines both the selection and the environment.

```bash
set -o pipefail
curl --fail-with-body --silent --show-error \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  -H 'Content-Type: application/json' \
  --data '{"rerun_type":"call_and_eval","unfinished_only":true}' \
  "${base%/}/simulate/test-executions/$RUN_ID/rerun-calls/" |
  jq -c '.'
```

HTTP `202` means the attempt was accepted, not that the calls passed. `test_execution_id` is unchanged; `total_processed` and `successful_reruns` give the count and IDs of the selected calls. Read the calls endpoint again to see the new entry in `execution.resume.history`: `at` is the time, `by` identifies who resumed the run, and `calls` is the number selected. If you get `409`, read the response before retrying. For example, `nothing_to_resume` means every call finished, and `resume_version_missing` means a pinned version is gone. To use a different version, start a new run instead.

## Re-run selected calls

Tick calls in the **Test runs** table to run them again. A group's checkbox selects its eligible calls on the current page. The header checkbox selects the whole page. If the filter matches more than one page, a banner then offers **Select all** to include the other pages. The bar above the table counts the calls you ticked and the scenarios behind them.

Open **Re-run** and pick how to run them:

- **Re-run in this run** makes the ticked calls again inside this run, and their new results replace the old ones
- **Run as a new simulation** runs the scenarios behind the ticked calls as a new run, with the **Repeats** you set above it, which start at this run's trials. The new run opens when it starts, and appears on the **Runs** tab next to the one you re-ran, so the two can be compared directly

**Re-run** stays disabled while the run is still running or grading.

## Read the patterns

The **Analytics** tab summarizes the whole run. Its top cards are the quickest health check: **Calls passed**, **Drop-off**, **Response time p95**, **Cost / pass**, **CSAT satisfied** and **Change vs last run**. Below them, charts cover outcomes, latency, tools, and the slowest and most expensive calls. Of the charts, open these first:

- **Reliability across trials**: select **Show detailed analytics** to see how consistently each scenario passed across trials and the 95% range when available
- **Weakest scenarios**: the scenarios with the lowest pass rates, with those that have fewer than three evaluated calls ranked last
- **How calls ended**: every end reason from the platform, mapped onto one list

## Act on what you find

For a failed verdict, compare the evaluation's reason with the transcript before changing your agent. Two common causes are an agent mistake and a test that asks for the wrong behavior. If the call shows **Error** instead, inspect the call's end reason and logs where available.

The agent is wrong when the transcript shows it breaking one of its own rules, calling a tool with the wrong arguments, or telling the caller something false. Fix it where it lives, then [re-run](#re-run-selected-calls) the failing calls, inside this run or as a new run to compare on **Runs**.

The test is wrong when the **Scenario** tab asks for something the agent was never meant to do, or a sub-goal checks the wrong thing. Fix it through [chat orchestration](/docs/environments/concepts/chat-orchestration), for example "this scenario expects a transfer, but the agent is allowed to answer opening hours itself", so the next run tests the right thing.

### Let the run be diagnosed for you

Open **Debug failures** in the run's header to see which goals failed and the calls behind each finding. [Debug failures](/docs/environments/guides/debug-failures) covers the drawer.

If Epoch is enabled and the completed diagnosis has findings, select **Improve** at the bottom of the **Diagnosis** tab to open the launch form. Epoch can try a change against the failing scenarios before you decide whether to use it. [Run Epoch](/docs/environments/guides/run-epoch) covers it.
