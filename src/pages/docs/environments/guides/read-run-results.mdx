A run finished and some calls failed. Before you change anything, you need to know which calls the agent got wrong, which ones never ran, and what the evidence says. This guide goes from the failing calls to a single call, then to the whole run, and ends with what to do about what you find.

<Prerequisites title="Before you start">
- Open an [environment](/docs/environments/concepts/understanding-environments) that has a run. A call is one [scenario played once](/docs/environments/concepts/scenarios-and-trials).
- To re-run calls, wait until every call in the run has finished. **Re-run** stays disabled until then.
</Prerequisites>

## Find a measured failure

1. In the environment, open **Runs**.
2. Select the run you want to investigate.

   The header shows the run name, status, environment, task count and start time.

3. Stay on the **Test runs** tab, which shows the call count and has one row per call.
4. Click the **Failed** chip above the table to see the calls that were measured and did not pass.

<img src="/images/docs/environments/guides/read-run-results/run-results-test-runs.png" alt="The Test runs tab of Run 2 grouped by use case, with Failed 3 and Passed 5 filter chips and each call listing its sub-goals, persona, scenario, CSAT, turns and latency" style={{ borderRadius: '5px' }} />

| Outcome | How to read it |
| --- | --- |
| Failed | The agent was measured and did not pass. Inspect the verdict. |
| Error | The call could not run, such as a connection that never came up. It never counts against your agent. |
| Inconclusive | The call ran but was not evaluated. It never counts against your agent either. |
| Passed | The agent was measured and passed. |
| Queued or In progress | The call has not finished yet. |

**Group by** defaults to **Use case**. You can group by **Sub-goal**, **Accent**, **Age**, **Attack**, **Task** or **Status** instead, or choose **No grouping**. **Expand all** opens every group; group rows show averages.

A row names the scenario and trial, such as `check-refill-status-processing · Trial 2`, its duration and the sub-goals it met or missed. Use **Columns** to choose what else appears:

| Columns | What to look for |
| --- | --- |
| Run details | The use case tested by the call. |
| Scenario details | The scenario and the caller's persona: name, voice, age and traits. |
| System metrics | **CSAT**, **Turns**, **Latency** and more. Values past a warning threshold are flagged in red. |
| One column per evaluation | The call's score. A cell with no score says why: **Failed**, **Timed out** or **Not scored**, with the reason when you hover it. A dash means the evaluation doesn't apply to that scenario or the call never ran. |

## Compare the verdict with the conversation

1. Click the failed call's row to open it.
2. On the right, open the **Evals** tab.
3. Expand the failed evaluation.

   Each evaluation has a verdict and the reason behind it. The reason names what went wrong.

4. Find that moment in the **Transcript** on the left, by its timestamp or its words.
5. Compare the caller's words with the agent's reply and with any tool call the agent made.

   When a tool call is involved in a failure, its arguments usually show the mistake directly.

<img src="/images/docs/environments/guides/read-run-results/voice-call-drawer.png" alt="A voice call drawer with the masked call ID, the Transcript and Traces tabs, the recording waveform and timestamped transcript on the left, and the Evals tab on the right with a failed evaluation expanded to show its reason" style={{ borderRadius: '5px' }} />

In the pictured `authenticate-caller-dob-correction · Trial 2`, the caller starts to correct a date: “wait, sorry, April fifteenth”. At 0:15 the agent interrupts with “Just a sec.” The `advice_authority_boundary` verdict says the agent later asked the caller to confirm a date the caller had not supplied. **Ended** reads `silence-timed-out`. That explains how the call ended, not why the evaluator marked it **Fail**.

### What else the drawer shows

| Where to look | What you can check |
| --- | --- |
| Transcript and Recording | The conversation turn by turn with timestamps, the silences between turns, interruptions, and every tool call the agent made with its arguments. A voice call also has its **Recording** above the transcript, with the talk ratio between caller and agent and a filter for either side. |
| Traces | The traces your agent sent during the call, when it has [observability](/docs/environments/guides/build-an-environment#turn-on-observability) turned on. Click one to open it. A call with none reads **No trace for this call**. |
| Call details | At the top right: the call's duration, average latency and **Ended**, the reason it ended. |
| Call Analytics | Timing, turns, talk split, silence, interruptions and speaking rate. |
| Scenario | The scenario the caller was playing, so you can check what the agent was asked to do. |
| Messages, Logs and Attributes | The call's raw messages, logs and attributes. |

## Act on what you find

Every failing call has one of two causes: the agent did the wrong thing, or the test asked for the wrong thing. Telling them apart decides where the fix goes.

<Mermaid chart={`

    accTitle: Decide where to fix a failed call

    Q -->|"yes: the agent is wrong"| A["Fix the agent where it lives,<br/>on its platform or in its code"]

The agent is wrong when the transcript shows it breaking one of its own rules, calling a tool with the wrong arguments, or telling the caller something false. Fix it where it lives, on its platform or in its code, then [re-run](#re-run-selected-calls) the failing calls.

The test is wrong when the **Scenario** tab asks for something the agent was never meant to do, or a sub-goal checks the wrong thing. Fix it through [chat orchestration](/docs/environments/concepts/chat-orchestration), for example “this scenario expects a transfer, but the agent is allowed to answer opening hours itself”, so the next run tests the right thing.

### Let the run be diagnosed for you

**Debug failures**, in the run's header, reads every call in the run and reports which goals your agent broke, the ways each one broke, and the calls behind each. It needs a finished run with at least 15 connected calls and at least one failing call; [Debug failures](/docs/environments/guides/debug-failures) covers the drawer.

Once the diagnosis has finished, **Run Epoch** at the bottom of the drawer searches for a version of your agent that fixes the failing scenarios, and proves it before anything changes. Epoch changes an agent you connected as a source repository or a code upload. It can't change an agent on a hosted platform, so fix that agent on its platform instead.

## Re-run selected calls

1. Tick the calls to run again in the **Test runs** table.

   Ticking a group's row ticks every call in it, and the box in the header ticks the page. A banner then offers **Select all** for every call that matches the current filter. The bar above the table counts the calls you ticked and the scenarios behind them.

2. Open **Re-run**.

   **Re-run** stays disabled until every call in the run has finished.

3. Pick how to run them:

   - **Re-run in this run** makes the ticked calls again inside this run, and their new results replace the old ones.
   - **Run as a new simulation** runs the scenarios behind the ticked calls as a new run, with the **Repeats** you set above it, which start at this run's trials. The new run opens when it starts and appears on the **Runs** tab next to the one you re-ran, so the two can be compared directly.

To check a fix, open the new result for the same scenario and compare the verdict with the transcript again. Choose a new simulation if you want to keep the original results.

## Look across the run

The **Analytics** tab summarizes the whole run. Its top cards are the quickest health check: **Calls passed**, **Drop-off**, **Response time p95**, **Cost / pass**, **CSAT satisfied** and **Change vs last run**. Below them, charts cover outcomes, latency, tools, and the slowest and most expensive calls. Open these first:

- **Reliability across trials:** when a run has more than one trial, the pass rate with its 95% range, which tells you how much to trust it.
- **Weakest scenarios:** the scenarios that failed most often.
- **How calls ended:** every end reason from the platform, mapped onto one list.

Two more actions sit in the run's header:

| Action | What it does |
| --- | --- |
| Run evals | Grades this run's finished calls again, or with evaluations you added since. See [Add evaluations](/docs/environments/guides/add-evaluations#grade-a-run-that-already-finished). |
| Export | Downloads the run's results as a CSV file. |
