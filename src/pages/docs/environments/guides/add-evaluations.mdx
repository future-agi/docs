## About

Add an evaluation to score future calls, or add it from a finished run to score that run as well. For example, you can check whether the Ridgeline Outfitters support agent got consent before issuing a replacement without asking the customer to repeat the conversation.

## Add an evaluation

Start with a [built environment](/docs/environments/guides/build-an-environment) that has scenarios and a call to preview. If this is your first run, [run a simulation](/docs/environments/guides/run-a-simulation) to generate call data for the input picker. Choose where to open the picker based on which calls you want to grade:

| Start here | What happens when you add the evaluation |
| --- | --- |
| **Evaluations → Add evaluations** | The environment uses it for future calls. Its column can appear on an old run, but adding it here does not fill in old scores. |
| **Runs → select a completed run → Run evals → Add evaluations** | The environment keeps the evaluation for future calls **and** queues it for eligible finished calls in this run. You do not need to click **Run** again. Other runs are not backfilled. |

For Ridgeline, add the consent check from **Evaluations**, then start a new run that includes the replacement scenario. To check whether the agent also invented a return policy, add `knowledge_gap_handling` from that completed run. Map `conversation` to `call.voice_recording` and both `context` and `agent_prompt` to `call.agent_prompt`, where Ridgeline keeps its policy. If the agent promises a refund the policy does not support, look for `unsupported_answer` and read the explanation.

Use the trash icon on an evaluation's row to stop using it for future calls. Removing it leaves previously recorded verdicts on their calls. To check tool choice, arguments and timing across calls, connect your agent and turn on **Enable tool call evaluation**. This switch is separate from the consent evaluation and from the [sub-goals](/docs/environments/concepts/contracts) specific to each scenario.

## Edit an evaluation without changing past scores

1. On **Evaluations**, click the pencil on the evaluation's row. From a completed run, you can instead open the evaluation column's menu and choose **Edit**, or click the pencil in **Run evals → All Evaluations**.
2. To judge the written conversation instead of the audio, edit `knowledge_gap_handling`. Change `conversation` from `call.voice_recording` to `call.transcript` and leave `context` pointed at the return policy. Click **Update Evaluation**. This saves the environment's input mapping, not a new score. The evaluation name stays the same.
3. If you edited from the run, the confirmation asks **Changes saved. Re-run this evaluation?** Choose **Not now** to keep the new settings and leave historical scores alone. Choose **Re-run** to apply them to this run's existing calls, for this evaluation only.

## Grade a run that already finished

To apply a saved edit later, open the completed run. In **Test runs**, open the menu on the evaluation's **column header**, choose **Re-run**, and confirm with **Run Evaluations**. Do not select and re-run the call rows: that repeats the conversations instead.

To grade several checks together, open **Run evals**, tick the checks in **All Evaluations**, then choose **Run (N)** and confirm. **Evals (N)** selects all regradable checks; the button becomes **Run All (N)**. Wait for grading to finish before editing again.

For Ridgeline, re-run only `knowledge_gap_handling` and open the same replacement call. Its call ID and transcript stay the same. After grading finishes, the knowledge verdict uses the transcript; the `action_confirmation_gating` verdict is unchanged. A regrade does not have to produce a different verdict.

### Regrade one evaluation with cURL

Set `FI_API_KEY` and `FI_SECRET_KEY` to your API key pair. Set `WORKSPACE_ID` to the `id` of the environment's workspace from `result.workspaces` in `GET /accounts/workspaces/`. Use the same API key headers as in the request below. You also need three IDs:

- `ENV_ID` and `EXECUTION_ID`: take these from the run URL, `/dashboard/simulate/environments/ENV_ID/runs/RUN_TEST_ID/EXECUTION_ID`.
- `EVAL_CONFIG_ID`: use the applied evaluation's `id` from `evaluations.selected` in `GET /simulate/api/harness-environments/ENV_ID/`. The library template ID is not the same ID.

To look up the environment before you queue anything, list the environments visible to the key pair. This Bash command uses `jq`:

```bash
set -o pipefail
curl --fail --silent --show-error "${FI_BASE_URL:-https://api.futureagi.com}/simulate/api/harness-environments/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" |
  jq '{count, environments: [.results[] | {id, name}]}'
```

If the list is empty, check the workspace and build an environment before continuing. This request queues grading, not a new call:

```bash
curl --fail-with-body --silent --show-error \
  -X POST "${FI_BASE_URL:-https://api.futureagi.com}/simulate/api/harness-environments/${ENV_ID:?Set ENV_ID}/runs/${EXECUTION_ID:?Set EXECUTION_ID}/evaluations/run/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  -H "X-Workspace-Id: ${WORKSPACE_ID:?Set WORKSPACE_ID}" \
  -H 'Content-Type: application/json' \
  --data "{\"eval_config_ids\":[\"${EVAL_CONFIG_ID:?Set EVAL_CONFIG_ID}\"]}"
```

For a run with one call, a successful request returns HTTP `202` with `{"call_execution_count":1}`. It means grading was queued, not that the score is ready. Open the run to see the updated verdict when grading finishes.

## Limits and troubleshooting

| What you see | What to do |
| --- | --- |
| An evaluation is missing from the initial set | The builder chooses zero to six names from the catalog that match the agent's modality. Six is not a limit on manual selection. The manual picker lets you configure other single evaluations if you can supply their inputs; it does not offer composites. |
| A chat run has no recording to map | Of the ten built-in voice and chat agent behavior checks, all ten work with voice and nine with chat. `unclear_audio_handling` needs actual audio, not a transcript. These counts describe that group of checks, not the whole library. |
| A knowledge verdict doesn't reflect a retrieved document | Check **Reads**. In the builder's mapping for `knowledge_gap_handling`, `context` is **Agent instructions**, not a separate set of retrieved documents. |
| The API returns `404` with `Environment not found` | Check `ENV_ID` and make sure `WORKSPACE_ID` is the workspace that owns the environment. |
| The API returns `409` | Check that the run has finished, at least one call completed, and grading is not already in progress. A run with no completed calls cannot be regraded. |
| **Edit** or **Re-run** is disabled | Wait for the run and any grading to finish. An evaluation with its own input mapping can be edited. A score filled by the harness (the runner that played the scenario) cannot be edited here. Some built-in harness checks can still be regraded from saved inputs; the confirmation warns that platform scores will replace the harness scores. If the control says **Only a call rerun refreshes this**, you must repeat the call to refresh that check. |
| A removed evaluation still has a column | Its historical verdict is still visible, but the column has no active evaluation to edit or re-run. |
| Adding succeeded but grading failed | The evaluation is still on the environment. In that run's picker, expand **Added evaluations** and click **Grade this run** on its row to retry missing grades. Calls already graded, recently queued, or still being processed are skipped. To replace existing scores after an edit, use the column's **Re-run** instead. |
