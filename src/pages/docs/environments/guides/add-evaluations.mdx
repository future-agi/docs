## About

Add an evaluation to an environment to score future calls. Add it from a finished run to **also score the calls in that run**. Neither action repeats a conversation. For example, Ridgeline Outfitters can check whether its support agent got consent before issuing a replacement, even if nobody thought to check until after the calls finished.

## Add an evaluation

Start with a [built environment](/docs/environments/guides/build-an-environment) that has scenarios. Choose where to open the picker based on which calls you want to grade:

| Start here | What happens when you add the evaluation |
| --- | --- |
| **Evaluations → Add evaluations** | The environment uses it for future calls. Its column can appear on an old run, but adding it here does not fill in old scores. |
| **Runs → select a completed run → Run evals → Add evaluations** | The environment keeps the evaluation for future calls **and** queues it for eligible finished calls in this run. You do not need to click **Run** again. Other runs are not backfilled. |

For Ridgeline's voice agent, also map `transcript` to `call.transcript` so the judge can compare the customer's spoken consent with the replacement tool call, if the transcript includes it. Map `agent_prompt` to `call.agent_prompt` if the agent's instructions specify a confirmation policy. Click **Add Evaluation**.

    {/* MEDIA: The confirmation check's mapping form with the recording, transcript and agent prompt selected. */}

For Ridgeline, add the consent check from **Evaluations** before running the replacement scenario. Later, if you want to know whether the agent invented a return policy, add `knowledge_gap_handling` **from that completed run**. Map `conversation` to the call and `context` to the agent instructions that contain the policy. The new check grades the same conversation alongside the consent verdict you already have.

Use the trash icon on an evaluation's row to stop using it for future calls. To check tool choice, arguments and timing across calls, connect your agent and turn on **Enable tool call evaluation**. This switch is separate from the consent evaluation and from the [sub-goals](/docs/environments/concepts/contracts) specific to each scenario.

## Edit an evaluation without changing past scores

1. On **Evaluations**, click the pencil on the evaluation's row. From a completed run, you can instead open the evaluation column's menu and choose **Edit**, or click the pencil in **Run evals → All Evaluations**.
2. Change the settings. For example, if Ridgeline's `knowledge_gap_handling` check was reading the conversation as `context`, map `context` to `call.agent_prompt` to judge the answer against the return policy in the agent's instructions. Click **Update Evaluation**. This saves the environment's configuration, not a new score.
3. If you edited from the run, the confirmation asks **Changes saved. Re-run this evaluation?** Choose **Not now** to keep the new settings and leave historical scores alone. Choose **Re-run** to apply them to this run's existing calls, for this evaluation only.

{/* MEDIA: A completed run's evaluation column menu, followed by the post-save dialog with Not now and Re-run. */}

## Grade a run that already finished

To apply a saved edit later, open the completed run. In **Test runs**, open the menu on the evaluation's **column header**, choose **Re-run**, and confirm with **Run Evaluations**. Do not select and re-run the call rows: that repeats the conversations instead.

To grade several checks together, open **Run evals**, tick the checks in **All Evaluations**, then choose **Run (N)** and confirm. **Evals (N)** selects all regradable checks; the button becomes **Run All (N)**. Wait for grading to finish before editing again.

For Ridgeline, re-run only `knowledge_gap_handling` and open the same replacement call. Its call ID and transcript stay the same. The knowledge verdict now uses the corrected input; the `action_confirmation_gating` verdict is unchanged. A regrade does not have to produce a different verdict.

### Regrade one evaluation with cURL

With your API key pair and workspace ID set in the shell, export three IDs:

- `ENV_ID` and `EXECUTION_ID`: take these from the run URL, `/dashboard/simulate/environments/ENV_ID/runs/RUN_TEST_ID/EXECUTION_ID`.
- `EVAL_CONFIG_ID`: use the applied evaluation's `id` from `evaluations.selected` in `GET /simulate/api/harness-environments/ENV_ID/`. The library template ID is not the same ID.

This request queues grading, not a new call:

```bash
curl --fail-with-body --silent --show-error \
  -X POST "${FI_BASE_URL:-https://api.futureagi.com}/simulate/api/harness-environments/${ENV_ID:?Set ENV_ID}/runs/${EXECUTION_ID:?Set EXECUTION_ID}/evaluations/run/" \
  -H "X-Api-Key: ${FI_API_KEY:?Set FI_API_KEY}" \
  -H "X-Secret-Key: ${FI_SECRET_KEY:?Set FI_SECRET_KEY}" \
  -H "X-Workspace-Id: ${WORKSPACE_ID:?Set WORKSPACE_ID}" \
  -H 'Content-Type: application/json' \
  --data "{\"eval_config_ids\":[\"${EVAL_CONFIG_ID:?Set EVAL_CONFIG_ID}\"]}"
```

A `202` response includes `call_execution_count`. It means grading was queued, not that the scores are ready.

## Limits and troubleshooting

| What you see | What to do |
| --- | --- |
| An evaluation is missing from the initial set | The builder chooses zero to six names from the catalog that match the agent's modality. Six is not a limit on manual selection. The manual picker lets you configure other single evaluations if you can supply their inputs; it does not offer composites. |
| A chat run has no recording to map | Of the ten built-in voice and chat agent behavior checks, all ten work with voice and nine with chat. `unclear_audio_handling` needs actual audio, not a transcript. These counts describe that group of checks, not the whole library. |
| A knowledge verdict doesn't reflect a retrieved document | Check **Reads**. In the builder's mapping for `knowledge_gap_handling`, `context` is **Agent instructions**, not a separate set of retrieved documents. |
| **Edit** or **Re-run** is disabled | Wait for the run and any grading to finish. An evaluation with its own input mapping can be edited. A score filled by the harness (the runner that played the scenario) cannot be edited here. Some built-in harness checks can still be regraded from saved inputs; the confirmation warns that platform scores will replace the harness scores. If the row says **Only a call rerun refreshes this**, you must repeat the call to refresh that check. |
| Adding succeeded but grading failed | The evaluation is still on the environment. In that run's picker, expand **Added evaluations** and click **Grade this run** on its row to retry missing grades. Calls already graded, recently queued, or still being processed are skipped. To replace existing scores after an edit, use the column's **Re-run** instead. |
