Send Dify chat, chatflow, workflow and agent runs to a Future AGI **Observe** project. Dify 1.20.0 added a generic **OpenTelemetry** tracing provider that exports each run over OTLP/HTTP, and the Future AGI collector accepts that export directly. You configure one Dify app at a time; you do not change your flows or install a Future AGI package.

## Before you start

- A self-hosted Dify **1.20.0 or later**. The OpenTelemetry provider is not in Dify 1.19.0 or earlier. Dify's API image installs it by default (it is part of Dify's `trace-all` dependency group); a source install needs `uv sync --group trace-otel` or the default groups.
- A [Future AGI API key and secret key](/docs/admin-settings/api-keys).
- An Observe project name for the app. Create the project in Future AGI first.

If **OpenTelemetry** is not in the app's provider list, your Dify version does not include it. Dify Cloud is not covered by this guide.

## Configure the provider

1. Open the app in Dify and go to **Monitoring**.
2. In **Tracing app performance**, open the provider list and select **Config** on **OpenTelemetry**.
3. Fill in the four fields:

| Field | Value |
| --- | --- |
| **Endpoint** | `https://api.futureagi.com/tracer/v1/traces`. Enter the full URL. Dify keeps a custom path as you typed it and adds `/v1/traces` only to a bare origin. For self-hosted Future AGI, use your collector's trace endpoint from [OpenTelemetry GenAI compatibility](/docs/integrations/traceai/otel-genai-conformance#export-settings). |
| **HTTP headers (JSON)** | `{"X-Api-Key": "your-futureagi-api-key", "X-Secret-Key": "your-futureagi-secret-key"}` |
| **Service name** | Any label, for example `dify`. It is sent as `service.name`; it does not choose the Future AGI project. |
| **Resource attributes (JSON)** | `{"project_name": "my-dify-app", "project_type": "observe"}` |

4. Save. Dify checks the endpoint by sending an empty OTLP export with your headers. A wrong key pair fails the save.
5. Switch tracing on for the app if it is not already **In Service**.

Dify stores the headers encrypted with the workspace's key and never shows them again. Leave the field blank to keep the saved headers, or enter `{}` to remove them. Changing the endpoint clears the saved headers, so enter them again with the new endpoint.

`project_name` is required; the Future AGI collector rejects an export without it. Each Dify app has its own tracing configuration, so two apps can send to two projects.

If you run self-hosted Future AGI on a private address, Dify's outbound requests follow its SSRF proxy policy. Allow the collector's host in that policy, or the save fails.

## Verify

Run the app once from its web app, API or the debugger. A run is exported after it finishes, not while it streams.

Open **Observe** in Future AGI and select `my-dify-app`. The run appears as one trace. If it does not, open the run's details in Dify: its **External tracing** status says whether the export was sent, failed, or not confirmed.

## What gets traced

The provider exports Dify's trace tree with the original span and parent IDs, timings and status. It uses the OpenTelemetry GenAI attribute names, which Future AGI reads natively.

| Span | Attributes |
| --- | --- |
| Every span | `gen_ai.span.kind` (`LLM`, `TOOL`, `RETRIEVER`, `AGENT` or `CHAIN`), `input.value` and `output.value` as JSON, `gen_ai.session.id` (the Dify conversation) when the run has one, `gen_ai.user.id` when the run has a user, and Dify IDs such as `dify.app_id`, `dify.workflow_run_id` and `dify.message_id`. |
| LLM | `gen_ai.request.model`, `gen_ai.provider.name`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.total_tokens`, the input and output messages, and time to first token when Dify reports it. Wrapper spans do not repeat the usage. |
| Tool | `gen_ai.tool.name`, the call arguments and result, and the Dify tool provider. |
| Retriever | The retrieval query and the returned documents. |
| Agent | `gen_ai.agent.name`. |

Future AGI uses `gen_ai.span.kind` for the span type, and the model and token attributes for model and usage. See [OpenTelemetry GenAI compatibility](/docs/integrations/traceai/otel-genai-conformance) for how each attribute is stored. When Dify has a cost for an LLM call, it is sent as `dify.cost.amount` and `dify.cost.currency`.

## Privacy

The provider exports what Dify passes to it, including prompts, model responses, node inputs and outputs, tool arguments and results, and retrieved text. Use synthetic or approved data, or route the export through an OpenTelemetry Collector that removes sensitive attributes before it reaches Future AGI. Future AGI SDK settings such as `FI_HIDE_INPUTS` do not apply to Dify.

`gen_ai.user.id` carries the user identifier Dify records for the run. If your client passes a `user` value to the Dify API, send an opaque ID, not an email address.

## Troubleshooting

| What you see | What to check |
| --- | --- |
| Save fails with an authentication or permission error | The header names must be exactly `X-Api-Key` and `X-Secret-Key`, and both keys must belong to the same Future AGI workspace. A bearer token is rejected. |
| Save fails with a connection or endpoint error | Dify cannot reach the endpoint. For a private collector, allow it in Dify's SSRF proxy policy. |
| Save succeeds but no trace appears | Check `project_name` in **Resource attributes (JSON)**; the collector rejects exports without it. Then check the run's **External tracing** status in Dify. |
| Headers field is invalid | Enter a JSON object of strings. Dify rejects duplicate names and transport headers such as `Content-Type`. |
| **OpenTelemetry** is not in the provider list | Upgrade to Dify 1.20.0 or later, and on a source install include the `trace-otel` dependency group. |

Do not point Dify's **Arize** or **Phoenix** provider at Future AGI. They send different authentication headers and project attributes, which the Future AGI collector does not accept.
