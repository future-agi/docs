## About

Dify is a platform for building LLM apps, chatflows, workflows and agents. Each Dify app can send its runs to one tracing provider, picked under the app's **Monitoring** page. The Future AGI provider adds **Future AGI** to that list. Every run of the app becomes a trace in an Observe project: the workflow and each node in the order Dify ran them, LLM calls with model and token counts, tool calls, knowledge-base retrievals, errors, the Dify conversation as the session, and the end user.

You configure Dify only: four fields and a switch per app. Nothing is installed in your apps or workflows.

| | |
| --- | --- |
| Tested with | Dify `1.17.1`, the latest stable release (2026-09-10), with the provider applied, and the fork branch [`future-agi/dify` `feat/th-8222-futureagi-trace`](https://github.com/future-agi/dify/pull/1), which is upstream `main` at `1cbb6dc` (2026-10-03, still versioned `1.17.1`) plus the provider. API and Celery worker on Python `3.12.10`, PostgreSQL 16, Redis 7, plugin daemon `0.6.10-local`. |
| Not supported | Stock Dify images from Docker Hub, Dify releases from upstream, and Dify Cloud (`cloud.dify.ai`). None of them contains the Future AGI provider yet. |
| Future AGI side | A self-hosted Future AGI stack built from `dev` (collector on `/tracer/v1/traces`). The hosted URL `https://api.futureagi.com` was **not** called. |
| Models used | A real GPT model through Dify's OpenAI-API-compatible model plugin (`langgenius/openai_api_compatible` 0.0.68), pointed at a local OpenAI-compatible endpoint. |
| Libraries inside Dify | `opentelemetry-sdk` and `opentelemetry-exporter-otlp-proto-http` `1.44.0`, the versions Dify already locks. No Future AGI package. |

## Before you start

- A self-hosted Dify you can build from source or from your own images. The provider is in the fork pull request linked above, not in a Dify release.
- A Future AGI API key and secret key, and the name of the Observe project the traces should go to. The self-hosted build we tested created the project on first use. Whether the hosted service does the same was not tested, so create the project first.

## Run Dify from the fork

The provider is a Dify trace package (`api/providers/trace/trace-futureagi`) plus the Monitoring tile in the web app. Run the fork branch the way Dify's [source deployment guide](https://docs.dify.ai/en/getting-started/install-self-hosted/local-source-code) describes, with the middleware (PostgreSQL, Redis, plugin daemon) from Dify's `docker/docker-compose.middleware.yaml`:

```bash
git clone https://github.com/future-agi/dify.git
cd dify
git checkout feat/th-8222-futureagi-trace   # until the pull request is merged into the fork's main

cd api
cp .env.example .env                        # set SECRET_KEY, database, Redis and plugin daemon values
uv sync                                     # installs dify-trace-futureagi with the other trace providers
uv run flask db upgrade
uv run flask run --host 0.0.0.0 --port 5001
uv run celery -A celery_entrypoint.celery worker -P gevent -c 2 --loglevel INFO \
  -Q ops_trace,workflow,workflow_based_app_execution,conversation,workflow_storage,app_rbac,plugin,mail,api_token,dataset,priority_dataset
```

Then start the web app from `web/` as Dify's guide describes. Traces are sent by the Celery worker from the `ops_trace` queue, never from the request that answered the user, so the worker must consume `ops_trace`.

If you deploy Dify with Docker Compose, build the `api` and `web` images from this branch with Dify's own Dockerfiles and point your compose file at them. We did not test the images.

## Turn it on for an app

1. Open the app and go to **Monitoring**.
2. In **Tracing app performance**, open the provider list and select **Config** on **Future AGI**.
3. Fill in:

| Field | What to enter |
| --- | --- |
| API Key, Secret Key | Your Future AGI keys. Dify stores both encrypted with the workspace's key, like every other tracing provider secret, and shows them masked afterwards. |
| Project | The Observe project for this app. |
| Endpoint | Leave empty for `https://api.futureagi.com`, or enter your self-hosted collector, for example `http://localhost:4318`. Dify adds `/tracer/v1/traces` unless the URL already ends with it. |
| Redact inputs and outputs | Off by default. See [Privacy](#privacy). |

4. Select **Save & Enable**. Dify checks the keys first by sending an empty export to the collector. Wrong keys fail the save with *The tracing configuration could not be verified.* and nothing is stored. The app keeps answering either way.
5. Use the app (web app, API or the debugger). The trace appears in the Observe project a few seconds after the answer.

The provider sends the headers `X-Api-Key` and `X-Secret-Key` and the resource attributes `project_name` and `project_type=observe`. You do not type them. Each app has its own configuration: two apps can send to two projects, and an app's keys are never used for another app.

To stop sending, switch tracing off in the same panel or pick another provider. Runs after that are not exported. Future AGI keeps what it already stored.

## What you see in Observe

| App type | Traces per run |
| --- | --- |
| Chatflow, workflow | A workflow trace: `chatflow_<run id>` (chatflows) or `workflow_<run id>` root, the workflow span, and one span per node in execution order. LLM nodes are LLM spans, tool nodes tool spans, knowledge-retrieval nodes retriever spans, everything else (start, answer, if/else, code…) chain spans. Dify also adds a wrapper span per iteration or loop round (not exercised in our tests). A chatflow also sends a short message trace per turn (`message` and `llm`), which is how Dify reports every chat message. |
| Chat and agent apps | A message trace: `message` root with an `llm` span, plus one tool span per tool call and a `dataset_retrieval` retriever span when the app queries a knowledge base. |
| Any app with a conversation | The first message of a conversation adds a `generate_name` span (Dify naming the conversation), under that turn's trace. |

Real examples from the tested apps:

- Chatflow turn: `chatflow_…` (6.6 s) > `workflow_…` > `start_Start`, `llm_Plan` (`gpt-6-luna`, 341 prompt / 64 completion tokens), `tool_Current Time`, `llm_Reply` (349 / 17), `answer_Answer`.
- Knowledge chatflow: `knowledge-retrieval_Handbook Search` (retriever, with each retrieved segment's text, document, dataset and score) feeding `llm_Grounded Reply` (403 / 20).
- Agent app: `message` > `llm` (797 / 43), `current_time` tool, `generate_name`.
- Four apps, five runs: 8 traces and 37 spans in one project, the same on both tested Dify versions.

| Attribute | Source |
| --- | --- |
| `session.id`, `gen_ai.conversation.id` | The Dify conversation id. Observe groups the turns of one conversation into a session. Omitted when the run has no conversation. |
| `user.id` | On workflow traces, the `user` value your client sent to the Dify API (for example `user-42`). On message traces, Dify's internal end-user id (a UUID). Dify fills these two differently. |
| `llm.model_name`, `llm.provider`, `llm.token_count.prompt`, `llm.token_count.completion` | On LLM spans, when Dify reported them. Nothing is estimated. The `llm` span of a chatflow's message trace carries no tokens, because the workflow's LLM node spans already count them. |
| Chat messages | `llm.input_messages.*` and `llm.output_messages.*`, so Observe shows LLM spans as a conversation (system, user, assistant, tool calls). |
| `input.value`, `output.value` | Node inputs and outputs, tool arguments and results, retrieved segments, as JSON. |
| `dify.app_id`, `dify.tenant_id`, `dify.workflow_version`, `dify.span.id` | From Dify's trace metadata. `dify.workflow_version` is the published workflow's version stamp. |
| Resource `dify.version` | The Dify release, for example `1.17.1`. |

Not captured: the app name (Dify fills it only when its enterprise telemetry is on), the app mode (not in Dify's trace metadata), embedding calls, per-token streaming spans (a streamed answer is one span with the final text), and cost when Observe has no price for the model.

## Privacy

Like Dify's other tracing providers, the Future AGI provider exports prompts, responses, node inputs and outputs, tool arguments and results, and retrieved text by default.

To export metadata only, switch on **Redact inputs and outputs** for the app. With it on:

- `input.value`, `output.value` and the chat messages are not exported, and every span carries `dify.redacted=true`.
- A failed span is still ERROR, but without Dify's error text. Dify's error text can quote the user's input; a tool that rejects an argument repeats it, for example `Failed to invoke tool time: '<what the user typed>'`.
- Span names, the trace shape, model, token counts, timings, status, session id, user id and the Dify ids stay.

This was checked, not assumed. A unique marker went into the questions of all four apps and, through the failing tool, into an error message, with redaction on. Every stored column of every span in that project (ClickHouse `spans`, 46 columns including resource attributes, span events and the extra-attributes column) was then searched: the marker was in none of the 37 spans, on both tested Dify versions. With redaction off, the same marker was found in the input, output, attribute and status-message columns.

In both modes:

- No stack traces. The provider exports Dify's error message only.
- The resource carries only `project_name`, `project_type` and `dify.version`. No hostname, OS user, process or file path. A search of every stored column for the OS user name, hostname, home directory, stack-frame lines, the Dify admin's email address and the API keys found none of them.
- `user.id` is exported as your client sends it to Dify, and redaction does not remove it. Send an opaque id, not an email address.

## Errors and delivery

A failed node is ERROR, and so are the workflow span and the root: in the tested chatflow the failing tool node, `workflow_…` and `chatflow_…` were all ERROR with the tool's message.

Tracing never changes the answer, because the export runs later in the Celery `ops_trace` queue:

- **Collector down.** The app answered normally. Dify retried the trace dispatch every 5 seconds (`OPS_TRACE_RETRYABLE_DISPATCH_DELAY_SECONDS`), up to 780 times (`OPS_TRACE_RETRYABLE_DISPATCH_MAX_RETRIES`), and when the collector came back all 9 spans of the run arrived once.
- **One export rejected part way through a trace.** Dify retried the whole trace. Span and trace ids are derived from Dify's own ids, so the retry overwrote the spans that had already arrived: 2 traces and 9 spans, no duplicates.
- Each export call times out after 10 seconds. Compression is always off (the collector does not accept gzip), even if `OTEL_EXPORTER_OTLP_COMPRESSION` is set for Dify's own telemetry.
- Dify reads the app's tracing configuration when it sends a trace, not when the run happened. A trace still waiting in the queue goes to the configuration the app has when it is sent.

Dify's two tracing runtimes (`OPS_TRACE_UNIFIED_ENABLED=false`, the default, and `true`) export the same spans. Both were tested.

## How this differs from related integrations

- **Dify's Arize Phoenix provider.** Do not point it at Future AGI. It sends an `api_key` header and a bearer token, which the Future AGI collector does not accept, and it sets `openinference.project.name` instead of `project_name`.
- **Dify's Langfuse, LangSmith and other providers.** They speak their own vendor's API. Future AGI does not import their data.
- **traceAI packages.** Those instrument code you write. Dify runs its own server, so use this provider instead of adding a traceAI package to Dify.
- **Flowise and Langflow.** The same idea for those visual builders, each in its own Future AGI fork, with its own page.

## Limits and what was not tested

- Fork only. Until the provider is in an upstream Dify release, stock Dify, Dify images from Docker Hub and Dify Cloud do not have it.
- Upstream Dify `main` has since rewritten the Monitoring settings components; the tile in the fork is written against the tested base and has to be ported before the provider can be proposed upstream. The API side applies to `1.17.1` and the tested base unchanged.
- The hosted endpoint, Docker images of the fork, Dify Cloud, model providers other than the OpenAI-API-compatible plugin, and Dify's code, HTTP-request and iteration nodes were not run.
- Keys that stop working after the configuration was saved (revoked, rotated) fail every export, and Dify keeps retrying that trace for up to about 65 minutes (780 tries, 5 seconds apart) before it gives up. The app is not affected.

## Troubleshooting

| What you see | What it means |
| --- | --- |
| *The tracing configuration could not be verified.* on save | Wrong API key or secret key, or Dify cannot reach the endpoint. Nothing was saved. |
| No traces, and the worker log has no `Future AGI` lines | The Celery worker does not consume the `ops_trace` queue, tracing is switched off for the app, or the app uses another provider. |
| `Retryable trace dispatch failure … Future AGI span export failed` in the worker log | The collector refused or could not be reached. Dify retries; the answer was not affected. |
| `Retryable trace dispatch failure … Pending trace parent context` | Normal. A tool or name trace waited for its parent span, and Dify retries it a few seconds later. |
| Traces in the wrong project | The app's **Project** field. Each app has its own configuration. |
| Input and Output empty, error without message | **Redact inputs and outputs** is on for the app. |
| Model or tokens missing | The model plugin did not report them. Missing is unknown, not zero. |
