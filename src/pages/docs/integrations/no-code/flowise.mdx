## About

Flowise is a visual builder for LLM apps. Each chatflow or agentflow can turn on analytics providers in its **Configuration > Analytics** settings. The Future AGI provider sends every prediction (from the Flowise chat panel, the prediction API or an embed) to an Observe project as one trace: chain, LLM, tool and retriever spans nested the way Flowise ran them, with the model name, token counts, the chat id as the session and, when you pass one, a user id.

You configure Flowise only: one credential and one switch per flow. There is no Future AGI package to install in your flows.

| | |
| --- | --- |
| Tested with | Flowise `3.1.4`, the final upstream release (2026-07-29), built from the fork branch [`future-agi/Flowise` `feat/th-8223-futureagi-trace`](https://github.com/future-agi/Flowise/pull/1) on Node `24.15.0`. The branch is upstream `main` (`3.1.4` plus 10 later fixes, none in the analytics code). |
| Not supported | Stock Flowise from npm or Docker Hub, and Flowise Cloud. Neither contains the Future AGI provider. See [Flowise is archived](#flowise-is-archived). |
| Future AGI side | A self-hosted Future AGI stack built from `dev` (collector on `/tracer/v1/traces`). The hosted URL `https://api.futureagi.com` was **not** called. |
| Models used | A real GPT model through a local OpenAI-compatible endpoint (the ChatOpenAI node's BasePath), and Google Gemini embeddings for the retrieval flow. |
| Libraries inside Flowise | `@arizeai/openinference-instrumentation-langchain` 2.0.0 (already a Flowise dependency), `@opentelemetry/sdk-trace-base` 1.27.0, `@opentelemetry/exporter-trace-otlp-proto` 0.54.0 |

## Flowise is archived

FlowiseAI announced the end of Flowise on its [sunset page](https://flowiseai.com/sunset) (read 2026-10-16): code freeze and no more pull requests on 2026-07-29, repository archived on 2026-08-10, end of life on 2026-08-31. The [FlowiseAI/Flowise](https://github.com/FlowiseAI/Flowise) repository is archived (checked 2026-10-16). The Apache-2.0 code stays available and FlowiseAI encourages teams to run their own forks.

That means the Future AGI provider cannot ship in an upstream Flowise release. It lives in the [future-agi/Flowise](https://github.com/future-agi/Flowise) fork. If you already run your own Flowise fork, the change is self-contained (one credential, one analytics node, two new branches in `packages/components/src/handler.ts`, the Analytics dialog entry, and a flush on shutdown) and can be cherry-picked from the fork pull request.

## Before you start

- A Future AGI API key and secret key, and the name of the Observe project you want the traces in. The self-hosted build we tested created the project on first use. Whether the hosted service does the same was not tested, so create the project first.
- Git, Node 24 and pnpm 10 to build Flowise (Flowise's own requirements).

## Build and start Flowise from the fork

```bash
git clone https://github.com/future-agi/Flowise.git
cd Flowise
git checkout feat/th-8223-futureagi-trace   # until the pull request is merged into the fork's main
pnpm install
pnpm build
pnpm start                                  # http://localhost:3000
```

The first start asks you to create the admin account. Keep your existing database and secret-key paths (`DATABASE_PATH`, `SECRETKEY_PATH`) if you are moving an existing Flowise install onto this build.

## Add the credential

1. Open **Credentials**, select **Add Credential** and choose **Future AGI API**.
2. Fill in:

| Field | What to enter |
| --- | --- |
| API Key, Secret Key | Your Future AGI keys. Both are stored in Flowise's encrypted credential store, like every other Flowise credential. |
| Endpoint | `https://api.futureagi.com`, or your self-hosted collector, for example `http://localhost:4318`. Flowise appends `/tracer/v1/traces`. |
| Project | The Observe project. Optional: the flow's Analytics settings can override it, and the fallback is `default`. |
| Hide Inputs, Hide Outputs | Off by default. See [Privacy](#privacy). |

The tracer sends the headers `X-Api-Key` and `X-Secret-Key` and the resource attributes `project_name` and `project_type=observe`. You do not type them.

## Turn it on for a flow

1. Open the chatflow or agentflow, select the settings button, then **Configuration > Analytics**.
2. Expand **Future AGI**, pick the credential, optionally set **Project Name**, and switch **On/Off** on.
3. Select **Save**.
4. Ask the flow something in the chat panel, or call the prediction API. The trace appears in the Observe project a second or two after the answer.

Turn the switch off and later predictions of that flow are not exported. Flows without the provider export nothing; we checked that a flow with analytics off left no spans in any project.

### Pass a user id

Add the caller's id under `overrideConfig.analytics.futureAgi.userId`. It becomes `user.id` on every span of that prediction:

```bash
curl http://localhost:3000/api/v1/prediction/<flow-id> \
  -H 'Content-Type: application/json' \
  -d '{
        "question": "What is 17 * 23?",
        "chatId": "support-chat-1042",
        "overrideConfig": { "analytics": { "futureAgi": { "userId": "user-42" } } }
      }'
```

- **Chatflows** ignore `overrideConfig` until you switch on **Configuration > Override Config > Enable Override Configuration** for that chatflow. This is a Flowise security setting. With it on, `analytics` is always accepted; no node parameter needs to be ticked.
- **Agentflows (V2)** accept `overrideConfig.analytics` without that switch.
- The value is exported as you send it. Use an opaque id, not an email address.

## What you see in Observe

One trace per prediction.

| Flow type | Trace shape |
| --- | --- |
| Chatflow (LangChain chains and agents) | The LangChain run tree, nested: for a Tool Agent, `AgentExecutor` > `RunnableAgent` > `ChatOpenAI` (LLM), the `Calculator` tool span, and the agent's next step. A Conversational Retrieval QA chatflow adds a `VectorStoreRetriever` (retriever) span. |
| Agentflow V2 | A `Flowise` root span covering the whole run (real input, output, status and duration), with the agentflow's chain span and one LLM span and one tool span per call under it. Flowise reports agentflow LLM and tool calls to analytics as children of the run, so they sit side by side under the root rather than under the agent node. |

Every span carries:

| Attribute | Source |
| --- | --- |
| `session.id` | The Flowise chat id (`chatId`). Observe groups the predictions of one chat into a session. |
| `user.id` | `overrideConfig.analytics.futureAgi.userId`, when passed. Omitted otherwise. |
| `flowise.chatflow_id` | The chatflow or agentflow id. |
| Model and tokens | `llm.model_name` and token counts on LLM spans, when the model provider returned them. Nothing is estimated. Streaming answers are one LLM span with the final output. |
| Input and output | The prompt, messages, tool arguments and results, and retrieved text, unless hidden. |

Real example from the tested chatflow: `AgentExecutor` (5.7 s) with two `ChatOpenAI` LLM spans (`gpt-6-luna`, 384/21 and 417/5 prompt/completion tokens) and one `Calculator` tool span, 18 spans in all. The tested agentflow: `Flowise` root (4.0 s), agent chain, one LLM span (554/25 tokens), `calculator` and `current_date_time` tool spans.

Not captured: embedding calls (LangChain embeddings emit no callbacks, so the retriever span shows the search, not the embedding request), cost when the model or tokens are missing, a Flowise version attribute, and anything from flows whose provider is off.

## Privacy

Like Flowise's other analytics providers, the Future AGI provider exports prompts, responses, tool arguments and results, and retrieved text by default. That follows the traceAI convention: content is on unless you hide it.

To hide content:

- **Per credential:** switch on **Hide Inputs** and/or **Hide Outputs** in the Future AGI credential.
- **For the whole Flowise server:** set `FI_HIDE_INPUTS=true` and/or `FI_HIDE_OUTPUTS=true` in the Flowise environment (the same names the traceAI packages use). The server setting can only hide; a credential with the switch off does not reveal what the server hides.

Hide Inputs removes `input.*`, `llm.input_messages.*`, `llm.prompts`, prompt-template variables and embedding text. Hide Outputs removes `output.*`, `llm.output_messages.*`, retrieved documents and reranker documents. The trace shape, span names, model, token counts, timings, status, session and user id stay.

This was checked, not assumed. A unique marker and an email address were put into the questions of a chatflow, an agentflow and a retrieval chatflow whose credential had both switches on. Every stored column for that project (ClickHouse `spans`, including resource attributes, span events and the extra-attributes column, plus the Postgres tracer tables) was then searched: neither was found in any of the 41 spans. With the switches off, the same marker was found in the input and output columns. With only `FI_HIDE_OUTPUTS=true` on the server, the marker was found in input columns only and every output column was empty.

In both modes:

- Error messages are exported **without stack traces**. LangChain appends the full stack (with absolute file paths) to every error; the provider keeps only the message. Home directories, the OS user name, the hostname and email addresses inside error text are masked.
- The resource carries only `project_name`, `project_type`, `service.name`, `service.version` and the OpenTelemetry SDK name and version. No hostname, user name or process path. A search of every stored column for the OS user name, hostname, home directory, stack-frame lines and `node_modules/` found none of them.
- `user.id` is exported as passed, and is not hidden by the switches. Do not pass email addresses.

## Errors

A failed run is marked ERROR. A wrong model name in the tested chatflow gave `AgentExecutor`, `RunnableAgent` and `ChatOpenAI` spans with status ERROR and the message `400 unknown provider for model …`; in the agentflow, the `Flowise` root, the agentflow chain and the LLM span were ERROR. The retriever span is ERROR when the embedding call fails.

Tracing never changes the answer. With wrong keys or a stopped collector the predictions in our runs answered normally and in their usual time (about 3.5 to 4.4 seconds), the spans were dropped, and Flowise logged at most one line a minute for each credential and project:

```text
[Future AGI] dropped 5 span(s), export failed: Unauthorized. Predictions are not affected. Check the API key, secret key, endpoint and project of the Future AGI credential.
```

Spans are exported in batches (about once a second, queue of 2048 spans, 10-second export timeout). On a graceful stop Flowise exports the last batch before it exits (`SIGTERM` was tested; `SIGINT` takes the same shutdown path). In our test all 18 spans of a prediction answered just before `SIGTERM` were stored. A hard kill loses up to about a second of spans.

## How this differs from related integrations

- **Flowise's Phoenix or Arize provider.** Do not point them at Future AGI: they send an `api_key` header and a bearer token, which the Future AGI collector rejects, and they do not set `project_name`. They also register a process-wide tracer and patch LangChain for the whole Flowise process. An earlier build of this provider used that same pattern, and spans from other flows (including flows with analytics off) landed in the first flow's project. The Future AGI provider now traces each prediction with its own credential and never registers a process-wide tracer: we ran two flows with two credentials at the same time and each trace landed only in its own project.
- **traceAI LangChain packages.** Those instrument LangChain code you write. Flowise runs LangChain inside its own server, so use this provider instead of adding a traceAI package to Flowise.
- **[n8n](/docs/integrations/traceai/n8n).** The n8n node fetches prompts from Future AGI. It does not send traces.

## Limits and what was not tested

- Fork only. Stock Flowise, Flowise Cloud and the archived upstream do not have this provider, and no upstream release will add it.
- The hosted endpoint, the embedded chat widget, queue (worker) mode, PostgreSQL or MySQL Flowise databases, Docker images of the fork, Flowise versions before 3.1.4, and model providers other than OpenAI-compatible chat models were not run.
- The chatflow tracer uses the OpenInference LangChain tracer from inside `@arizeai/openinference-instrumentation-langchain`, which only exports its process-wide instrumentation. If a future version of that package moves the file, chatflow spans stop (agentflow spans are unaffected); nothing leaks.
- Turning on Phoenix or Arize and Future AGI on the same flow was not tested. Use one OpenTelemetry-based provider per flow.

## Troubleshooting

| What you see | What it means |
| --- | --- |
| `[Future AGI] ... export failed: Unauthorized` in the Flowise log | Wrong API key or secret key. The answer is unaffected. |
| `[Future AGI] ... export failed: connect ECONNREFUSED ...` | The endpoint is unreachable. Check the credential's Endpoint (Flowise adds `/tracer/v1/traces` itself). |
| No traces and no log line | The flow's Future AGI switch is off, the flow uses another credential, or this Flowise build does not have the provider (stock Flowise). |
| No `user.id` on chatflow traces | **Override Config** is off for that chatflow, or the key is not exactly `overrideConfig.analytics.futureAgi.userId`. |
| Traces are in the wrong project | The flow's **Project Name** overrides the credential's **Project**. |
| Input and Output are empty | **Hide Inputs** / **Hide Outputs** is on in the credential, or `FI_HIDE_INPUTS` / `FI_HIDE_OUTPUTS` is set on the server. |
| Model or tokens missing | The model provider did not return them. Missing is unknown, not zero. |
