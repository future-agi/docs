## About

[goose](https://goose-docs.ai) is an open source AI agent for coding and other tasks, now maintained under the Agentic AI Foundation. It ships its own OpenTelemetry exporter, so there is no plugin, wrapper, or code to add. goose sends its spans to a small OpenTelemetry Collector running next to it, which forwards them to Future AGI:

```
goose  ──OTLP/HTTP──▶  otelcol-contrib (localhost:4318)  ──▶  Future AGI
                       removes your OS user name, host name,
                       and goose's log-line span events,
                       labels agent spans, adds your keys
```

Each goose reply (one prompt and everything the agent does to answer it) arrives in Future AGI as one trace with the agent turn, every model call with its token usage, and every tool call. Traces from the same goose session share a session id, so they group together in the Sessions view.

By default goose does not export prompt text, model responses, tool arguments, or tool results. You can turn that on with one variable when you need it. goose always attaches your OS user name and machine host name to its spans and has no switch for them; the collector removes them.

This is not the same as:

- **A model-provider instrumentor.** goose calls the model itself and reports each call as a span. Do not also wrap that provider with a traceAI package, or every model call is counted twice.
- **goose anonymous usage telemetry.** That is a separate opt-in switch that reports usage to the goose maintainers, not to your Future AGI project.
- **goose Desktop.** It runs the same agent code, but an app started from the Dock or Finder does not see variables exported in your shell. Only the CLI was tested.

## 1. Run the collector

Download the example collector config and start `otelcol-contrib` with your Future AGI keys (get them from [API keys](/docs/admin-settings/api-keys)):

```bash
git clone --depth 1 https://github.com/future-agi/docs.git fi-docs
export FI_API_KEY="your-futureagi-api-key"
export FI_SECRET_KEY="your-futureagi-secret-key"
export FI_PROJECT_NAME="goose-sessions"
otelcol-contrib --config fi-docs/examples/coding-agents/goose/otel-collector.yaml
```

It listens on `127.0.0.1:4318` (set `GOOSE_OTLP_LISTEN` to change it) and sends traces to `$FI_BASE_URL/tracer/v1/traces` (default `https://api.futureagi.com`; set `FI_BASE_URL` for a self-hosted Future AGI). Keep it running while you use goose, or run it as a service.

| Collector step | Why |
| --- | --- |
| Adds `X-Api-Key`, `X-Secret-Key`, `project_name`, and `project_type=observe` | Authenticates the export and files the traces under your project, so no Future AGI credential is set in goose's environment. |
| Deletes resource `user.name` and `host.name`, and span `session.user` and `session.host` | goose 1.54.0 always sets them from `$USER` and the machine's host name. See [Privacy](#privacy). |
| Drops span events | goose attaches its own log lines to spans as events, for example `Loading config from: "/Users/<you>/.config/goose/config.yaml"`. They can hold local paths. |
| Sets `gen_ai.span.kind=AGENT` on goose's `invoke_agent` spans | Future AGI does not map `invoke_agent` by itself, so `reply` and `reply_stream` would show as `unknown`. |
| Drops logs and metrics | Future AGI accepts traces only. |

It also sends uncompressed: the Future AGI collector answers gzip-encoded OTLP requests with HTTP 400.

## 2. Point goose at the collector

In the shell where you start goose, export the standard OpenTelemetry variables goose reads at startup:

```bash
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT="http://127.0.0.1:4318/v1/traces"
export OTEL_TRACES_EXPORTER="otlp"
export OTEL_METRICS_EXPORTER="none"
export OTEL_LOGS_EXPORTER="none"
```

| Variable | Why |
| --- | --- |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | The collector's traces URL. goose uses a signal-specific endpoint as is; it only appends `/v1/traces` to the generic `OTEL_EXPORTER_OTLP_ENDPOINT`. |
| `OTEL_TRACES_EXPORTER=otlp` | Turns trace export on. |
| `OTEL_METRICS_EXPORTER=none`, `OTEL_LOGS_EXPORTER=none` | goose can also export metrics and logs; Future AGI does not ingest them. |

goose sends OTLP/HTTP protobuf. It is built without gRPC, so `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` disables export instead of switching transport.

A copy of these settings is in the docs repo at `examples/coding-agents/goose/futureagi-otel.env`.

<Tip>
goose's `config.yaml` also accepts `otel_exporter_otlp_endpoint` and `otel_exporter_otlp_timeout`, and environment variables override it. The environment variables above are enough; no credential goes into goose's config.
</Tip>

## 3. Run goose

Start goose from the same shell. Nothing else changes: your provider, model, and extensions stay as they are.

```bash
goose session
# or, headless:
goose run -t "List the files in this folder and read README.md"
```

goose batches spans and flushes the last batch when the process exits, and the collector forwards every 2 seconds, so a `goose run` appears in Future AGI a few seconds after it finishes. An interactive `goose session` exports in batches while it runs.

## 4. See the trace

Open **Observe** in Future AGI and pick the `goose-sessions` project. Each row in the trace list is one goose reply, named `reply`, with its latency and total tokens. A `goose run` with one prompt that lists files and reads a file looks like this:

```
reply                                   goose turn: total tokens for the reply
└── reply_stream                        model and provider for the turn
    ├── stream_response_from_provider   model call: model, tokens, finish reason
    ├── dispatch_tool_call              tool: tree
    ├── stream_response_from_provider
    ├── dispatch_tool_call              tool: shell
    └── stream_response_from_provider   model call that writes the answer
```

The **Sessions** tab groups the replies of one goose session (same `session.id`) together.

## What is captured

| goose span | `gen_ai.operation.name` | Shown in Future AGI as | Attributes |
| --- | --- | --- | --- |
| `reply` (root) | `invoke_agent` | Agent | `session.id`, `gen_ai.agent.name`, total `gen_ai.usage.input_tokens` / `output_tokens` for the reply |
| `reply_stream` | `invoke_agent` | Agent | `session.id`, `gen_ai.conversation.id`, `gen_ai.request.model`, `gen_ai.provider.name`, `gen_ai.request.max_tokens`, token totals. Status `ERROR` when the model call fails. |
| `stream_response_from_provider` | `chat` | LLM | `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.provider.name`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, cache read and cache creation tokens, `gen_ai.response.finish_reasons`, `gen_ai.response.id` |
| `dispatch_tool_call` | `execute_tool` | Tool | `gen_ai.tool.name` (for example `shell`, `tree`, `edit`), `gen_ai.tool.call.id` |

The collector labels goose's `invoke_agent` spans as agent spans (`gen_ai.span.kind=AGENT`). Their token counts are the totals for the reply; the trace list shows the reply total, not the sum of every span.

goose also attaches code-location attributes (`code.file.path`, `thread.name`) to spans; they point into goose's own source, not your files. goose's log-line span events (for example `WAITING_TOOL_END: shell`) are dropped by the collector.

Resource attributes on every span: `service.name=goose`, `service.version` (the goose version), `service.namespace`, and the OpenTelemetry SDK name and version, plus `project_name` and `project_type` from the collector.

**Session grouping**: every span carries `session.id`, goose's session id (for example `20261015_7`). One trace is one reply. A multi-turn session, interactive or resumed with `goose run -r`, produces one trace per reply, all with the same `session.id`.

**Errors**: when a model call fails (for example an unknown model name), goose marks `reply_stream` with status `ERROR`. The error text is not exported.

## Privacy

Content capture is off unless `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` is exactly `true`. With it unset, goose exports no prompt text, no model output, no system prompt, no tool arguments, and no tool results. Tool names, model names, and token counts are still exported.

To include content, for example while debugging a recipe:

```bash
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true
```

With it set, goose adds `gen_ai.input.messages` and `gen_ai.output.messages` to the turn and model-call spans, `trace_input`, `trace_output`, and `user_message` to the turn spans, and `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`, `input`, and `output` to tool spans. In Future AGI the text appears in each span's **Attributes**, not in the trace list's Input and Output columns.

<Warning>
Tool arguments and results can contain file contents, shell output, environment values, and secrets. goose does not redact them. Turn content capture on only for projects where that is acceptable.
</Warning>

Even with content off, goose 1.54.0 exports your OS user name (resource `user.name`, span `session.user`), your machine's host name (resource `host.name`, span `session.host`), and log-line span events that include local paths such as your goose config file. goose has no switch for any of them. The collector config removes all of them before anything reaches Future AGI, which is why this page sends goose through it instead of straight to Future AGI. If you point goose directly at Future AGI, those values are stored with every trace.

To keep goose's log-line span events (for debugging goose itself), remove `filter/goose-log-events` from the `traces` pipeline in `otel-collector.yaml`. The user and host name stay removed.

## Not available

| Item | Status |
| --- | --- |
| Cost | goose does not export cost. Future AGI computes cost only when it knows the model's price. |
| Failed tool calls | goose 1.54.0 leaves the tool span status unset when a tool returns an error (tested with a missing file read through `shell` and the editor). Only failed model calls are marked `ERROR`. |
| User prompt and response text | Only with the content opt-in above. |
| Subagents and recipes as separate traces | Not verified on 1.54.0. Subagent spans, if emitted, inherit the parent's session. |
| gRPC export | goose is built with OTLP/HTTP only. |
| Metrics and logs | goose can export them, but Future AGI accepts traces only. |
| Reading goose session files from disk | Not part of this integration. Only what goose exports over OTLP is traced. |
| goose anonymous usage telemetry | A different switch that reports to the goose maintainers, not to your Future AGI project. |

Tool span timing covers goose's dispatch of the call. For long-running tools, the parent `reply_stream` span is the better measure of wall-clock time.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| No traces | Check that the collector is running and that its log shows `Everything is ready`. Check `OTEL_TRACES_EXPORTER=otlp` and that `OTEL_SDK_DISABLED` is not `true`. Start goose from the shell where you exported the variables. |
| No traces, endpoint ends in `/v1/traces/v1/traces` | You set `OTEL_EXPORTER_OTLP_ENDPOINT` to the full `/v1/traces` URL, so goose appended `/v1/traces` again and the collector answers `404`. Use `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` for the full URL, or set `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`. |
| No traces, collector log shows `401` | `FI_API_KEY` or `FI_SECRET_KEY` is missing or wrong in the shell that started the collector. |
| Traces land in the wrong project | `FI_PROJECT_NAME` in the collector's environment decides the project. Restart the collector after changing it. |
| Model and tool spans but no `reply` root | goose sends the root spans in its last batch, when it exits. If that export does not finish (process killed, or the collector not running), the trace has no root. Let goose exit normally, and stop the collector gracefully (Ctrl-C) so it flushes its last batch. |
| Export stopped after setting a protocol | goose has no gRPC transport. Leave `OTEL_EXPORTER_OTLP_PROTOCOL` unset or set it to `http/protobuf`. |

To see what goose sends before the collector filters it, set `OTEL_TRACES_EXPORTER=console` and run goose once.
