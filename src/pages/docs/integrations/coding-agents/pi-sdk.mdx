## About

The [Pi Coding Agent SDK](https://pi.dev/docs/latest/sdk) embeds the Pi coding agent in a Node.js process: `createAgentSession()` returns an `AgentSession` that you prompt from your own code, and `session.subscribe()` streams its run, turn, message, and tool events. The `@traceai/pi-coding-agent` package subscribes to those events and exports them to Future AGI, so every `session.prompt()` shows up as one trace:

```
invoke_agent pi                one agent run (session.prompt), session.id = Pi session id
├── pi.turn                    one model response and the tools it called
│   ├── chat gpt-6-luna        model call: model, provider, tokens, cost, finish reason
│   └── execute_tool ls        tool call: name, call id, duration, error flag
├── pi.turn
│   ├── chat gpt-6-luna
│   └── execute_tool read
└── pi.turn
    └── chat gpt-6-luna        final answer
```

This is not the same as:

- **Pi, the command-line app** (`pi`). Interactive Pi sessions are traced with a Pi extension, not with this package. See the Pi page in this section.
- **Oh My Pi** (`omp`, the omp.sh fork). It has its own hook API and its own page.
- **Model-provider tracing.** `@traceai/openai` or `@traceai/anthropic` trace raw provider calls. Pi makes its model calls itself; running a provider instrumentor in the same process adds duplicate model spans.

## 1. Install

```bash
npm install @traceai/pi-coding-agent @traceai/fi-core @earendil-works/pi-coding-agent
```

## 2. Add your Future AGI keys

```bash .env
FI_API_KEY=your-futureagi-api-key
FI_SECRET_KEY=your-futureagi-secret-key
FI_PROJECT_NAME=my-pi-agent
```

`@traceai/fi-core` reads these and sends the keys as the `X-Api-Key` / `X-Secret-Key` headers. They are never written onto spans. For a self-hosted Future AGI, also set `FI_BASE_URL` to your collector, for example `http://localhost:14338`.

## 3. Trace your sessions

The Pi SDK is ESM-only, so its exports cannot be patched in place. Wrap `createAgentSession` once and create sessions through the wrapper:

```typescript
import { register, ProjectType } from "@traceai/fi-core";
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";
import { PiCodingAgentInstrumentation } from "@traceai/pi-coding-agent";

const tracerProvider = register({ projectType: ProjectType.OBSERVE });
const instrumentation = new PiCodingAgentInstrumentation({ tracerProvider });
const createTracedSession = instrumentation.wrapCreateAgentSession(createAgentSession);

const { session } = await createTracedSession({ sessionManager: SessionManager.inMemory() });
try {
  await session.prompt("List the files in this folder and read README.md");
} finally {
  session.dispose();               // ends any span still open
  await tracerProvider.shutdown(); // flush before the process exits
}
```

If something else creates the session (for example an `AgentSessionRuntime`), trace it directly before you prompt it:

```typescript
const stop = instrumentation.instrumentSession(session); // stop() ends tracing for that session
```

An `AgentSessionRuntime` creates a new `AgentSession` on new, resume, fork, and import. Call `instrumentSession(runtime.session)` again after each replacement, as Pi's docs require for any subscription.

The model and credentials come from Pi as usual: `~/.pi/agent/models.json` and `auth.json`, or `PI_CODING_AGENT_DIR`. The tracing does not change which endpoint Pi calls.

## 4. Run it

A runnable copy is in [examples/coding-agents/pi-sdk](https://github.com/future-agi/docs/tree/main/examples/coding-agents/pi-sdk). `run_e2e.sh` creates an isolated Pi agent directory and a throwaway project, then runs one prompt that uses the `ls` and `read` tools:

```bash
FI_API_KEY=... FI_SECRET_KEY=... FI_PROJECT_NAME=pi-sdk-e2e \
PI_PROVIDER=my-gateway PI_MODEL=gpt-6-luna MY_GATEWAY_API_KEY=... \
examples/coding-agents/pi-sdk/run_e2e.sh
```

Open the project in **Observe**. Each run is one trace; all runs of a session share the same `session.id` and group under **Sessions**.

## What is captured

| Pi SDK event | Future AGI span | Fields |
| --- | --- | --- |
| `agent_start` .. `agent_settled` | **invoke_agent pi** (`AGENT`) | `session.id`, `gen_ai.conversation.id`, `pi.session.name`; run totals (`pi.agent.attempts`, turn, model-call and tool-call counts, `pi.agent.usage.*`, `pi.agent.cost.total`); retry and compaction events |
| `turn_start` .. `turn_end` | **pi.turn** (`CHAIN`) | turn index, stop reason, tool-result count |
| assistant `message_start` .. `message_end` | **chat &lt;model&gt;** (`LLM`) | `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.response.id`, `gen_ai.provider.name`, `pi.api`, `gen_ai.usage.input_tokens` / `output_tokens` / `total_tokens` / `cache_read_tokens` / `cache_write_tokens`, `gen_ai.cost.total` when Pi priced the call, finish reason, names of the tools it called. Start and end come from the message's own request timestamp and duration |
| `tool_execution_start` .. `tool_execution_end` | **execute_tool &lt;tool&gt;** (`TOOL`) | `gen_ai.tool.name`, `gen_ai.tool.call.id`, duration, `pi.tool.is_error`. A tool called by another tool (`parentToolCallId`) nests under the calling tool |

Input tokens follow the OpenTelemetry convention and include cached tokens. Pi's own `usage.input` excludes cache reads and writes, so it is kept separately as `pi.usage.uncached_input_tokens`. Run totals use `pi.agent.*` keys, not `gen_ai.usage.*`, so a trace's tokens are not counted twice.

Errors:

- A model call that ends with `stopReason` `error` or `aborted` is `ERROR`, with the provider's error message as the status. Its turn is `ERROR` too.
- A run that ends aborted, or whose last model call failed, is `ERROR`. When Pi retries a failed call and the retry succeeds, the run is `OK` and the failed call keeps its own `ERROR` span.
- A tool result with `isError` is `ERROR`.
- Disposing the session mid-run ends the open spans with `pi.incomplete=true`.

## What is not available

- **The model request payload.** Session events do not include the transcript Pi sends on each call, so model spans carry no input messages. The user prompt is on the run span when you opt in to content.
- **Streaming detail.** No time to first token and no per-delta events; `message_update` deltas are not traced.
- **Cost for custom models.** Models you add in `models.json` without prices report a cost of 0, and no cost attribute is written.
- **The system prompt.** Never exported, even with content on.
- **Extension-only events.** `before_provider_request`, `before_provider_headers`, and other extension hooks are not part of `session.subscribe()` and are not used.

## Privacy

By default only structure and metadata leave your process: session id, model, provider, token counts, finish reasons, tool names and call ids, durations, and statuses.

- **Not exported by default:** the user prompt, tool arguments, tool results (file contents, command output), assistant text, tool-call arguments, and tool error text.
- **Never exported:** the system prompt and the Pi working directory.

To include content, opt in with either the instrumentation options or environment variables:

```typescript
new PiCodingAgentInstrumentation({ tracerProvider, traceConfig: { hideInputs: false, hideOutputs: false } });
```

```bash
FI_HIDE_INPUTS=false    # prompt (run span input), tool arguments
FI_HIDE_OUTPUTS=false   # answers (model and run span output), tool results, tool error text
```

Only the exact value `false` turns capture on; any other value keeps content hidden. An explicit `traceConfig` value wins over the environment. Each value is cut at 16,384 characters (`maxContentLength`).

## Troubleshooting

**No trace appears.**
1. `register()` needs a project name (`FI_PROJECT_NAME` or `projectName`) and both keys.
2. A short script must `await tracerProvider.shutdown()` before it exits, or the last spans are lost.
3. The session must be traced before `prompt()`: create it through the wrapper, or call `instrumentSession()` first.

**Traces stop after `/new`, `/resume`, or a fork.** An `AgentSessionRuntime` replaced the session object. Call `instrumentSession(runtime.session)` again.

**The run span is not under my request span.** The run is parented to the active span only when your app registered an OpenTelemetry context manager (for example `AsyncLocalStorageContextManager`); otherwise each run starts its own trace.

**Every model call appears twice.** A provider instrumentor (`@traceai/openai`, `@traceai/anthropic`) is also tracing Pi's HTTP calls in the same process. Remove it, or accept both.
