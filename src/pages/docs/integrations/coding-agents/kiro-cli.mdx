## About

Kiro CLI (`kiro-cli chat`) runs [hooks](https://kiro.dev/docs/hooks/) when a session starts, a prompt is submitted, a tool runs, and the agent stops, and passes each hook a JSON payload on stdin. This page registers the Future AGI [hook-to-OTLP emitter](/docs/integrations/coding-agents/hook-to-otlp) on those hooks, so every Kiro CLI session shows up in Future AGI as one trace:

```
Kiro CLI session               one kiro-cli chat session (session_id)
└── Kiro CLI turn              one prompt, from Prompt Submit to Agent Stop
    ├── file_search            tool call (Post Tool Use): name, status
    └── read_file              ERROR when the tool reports failure
```

This is not the same as:

- **Kiro IDE.** The IDE has its own setup and adapter: see [Kiro IDE](https://docs.futureagi.com/docs/integrations/coding-agents/kiro-ide).
- **`kiro-cli settings telemetry.enabled`.** The [settings reference](https://kiro.dev/docs/reference/settings/) lists it as "Enable/disable telemetry collection" for Kiro itself. It has no endpoint setting, no Kiro page documents it as an OpenTelemetry export, and it is not used here.
- **Kiro enterprise OpenTelemetry.** That admin feature pushes daily usage metrics, including a `KIRO_CLI` client type, once a day. It has no per-session trace.
- **Model-call tracing.** Kiro calls models on AWS; hooks do not expose the model, tokens, or cost.

<Note>
In CLI V3, `SessionStart` is the canonical start trigger, and `AgentSpawn` / `agentSpawn` are accepted spellings of it. CLI 2.x embedded hooks in the agent config with camelCase names (`agentSpawn`, `userPromptSubmit`, `preToolUse`, `postToolUse`, `stop`). The adapter maps both. To move 2.x hooks to the V3 format, run `/upgrade-agent` in a chat (or `kiro-cli agent upgrade`) yourself; this setup does not rewrite your agent configs.
</Note>

## 1. Install the hook

Clone the examples and run the installer against your project. It copies the emitter and the Kiro CLI adapter into `.kiro/fi-hook-to-otlp-kiro-cli/` and writes `.kiro/hooks/fi-hook-to-otlp-kiro-cli.json`. An existing file with that name is left alone (the installer says when it differs from the current template).

```bash
git clone --depth 1 https://github.com/future-agi/docs.git fi-docs
fi-docs/examples/coding-agents/kiro-cli/install.sh /path/to/your/project
```

To trace every project, install global hooks into `~/.kiro/` instead (or into `$KIRO_HOME` when it is set; the installer then writes that path into the commands):

```bash
fi-docs/examples/coding-agents/kiro-cli/install.sh --user
```

Install either `--user` or per project, not both: Kiro runs global and project hooks side by side, so every event would be exported twice. The installer refuses a project install when the global file exists. It cannot see your other projects, so `--user` only warns about a project install in the directory you run it from; after a `--user` install, remove `.kiro/hooks/fi-hook-to-otlp-kiro-cli.json` (and `.kiro/fi-hook-to-otlp-kiro-cli/`) from any project you installed before.

The hook file registers guarded, observe-only commands for `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Stop`, and `SessionEnd`, and passes the trigger name to the emitter. It intentionally does not register `PreToolUse`, because that trigger can gate tools. Each entry looks like this:

```json
{
  "version": "v1",
  "hooks": [
    {
      "name": "Future AGI tracing: tool end",
      "trigger": "PostToolUse",
      "matcher": ".*",
      "action": { "type": "command", "command": "(python3 -B .kiro/fi-hook-to-otlp-kiro-cli/emit.py kiro_cli PostToolUse 2>/dev/null || true)" },
      "timeout": 10
    }
  ]
}
```

<Note>
The emitter only observes, and every command is guarded. Kiro blocks a tool when a `PreToolUse` command exits with code `2` and adds a command's output to the agent's context on `SessionStart` and `UserPromptSubmit`. `|| true` turns any failure (emitter file missing, `python3` missing, crash) into exit `0`, `2>/dev/null` keeps Python's error text away from Kiro and the model, and the adapter prints nothing. The parentheses run the command in a subshell, so the payload reaches `python3` whether it arrives on stdin or as a trailing heredoc. `-B` keeps `__pycache__` out of your repository. Project hooks run in the workspace, so the path starts with `.kiro/`; the global file uses `"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py"` and works from any directory.
</Note>

On macOS and Linux, Kiro runs each command through a POSIX shell. Native Windows is not tested; there, use WSL or write the equivalent for the shell Kiro uses, and keep it exiting `0` with no output on failure.

### Kiro IDE in the same project

Kiro IDE also loads `.kiro/hooks/*.json` and `~/.kiro/hooks/*.json`. With this hook file in a project (or after `--user`), Kiro IDE sessions there are exported as **Kiro CLI** sessions, and the [Kiro IDE](https://docs.futureagi.com/docs/integrations/coding-agents/kiro-ide) recipe has the same reach in the other direction. The installer refuses when it finds the Kiro IDE hook file in the project or in `~/.kiro/hooks/`, because both files would fire in every session and export it twice.

If you use Kiro IDE in the project without tracing it, put the hooks in a CLI agent profile instead. The `hooks` field of a custom agent adds profile-scoped hooks in CLI V3 ([agent configuration reference](https://kiro.dev/docs/custom-agents/configuration-reference/#hooks-field)) and runs only in sessions that use that agent. Those sessions still load every standalone `.kiro/hooks/*.json` file as well ([hooks migration](https://kiro.dev/docs/cli/v3/hooks-migration/)), so an agent profile does not get around a tracing hook file that is already in scope:

- `--agent-profile` refuses when `~/.kiro/hooks/` (or `$KIRO_HOME/hooks/`) has the Kiro IDE recipe or this recipe's global file: every session that uses the agent would be exported twice.
- It warns when the directory you run it from has either file in `.kiro/hooks/`. Do not use the agent in a project that has the Kiro IDE recipe or this recipe's project hook file.
- Project and `--user` installs warn when an agent profile in `~/.kiro/agents/` (or the project's `.kiro/agents/`) already runs this emitter, and name the profile to clean up.

Install the emitter without a hook file:

```bash
fi-docs/examples/coding-agents/kiro-cli/install.sh --agent-profile
```

Then add these entries (also printed by the installer, from `agent-profile-hooks.json`) to the `hooks` array of the agent profile, for example `~/.kiro/agents/<name>.json`, and start the CLI with `kiro-cli chat --agent <name>`:

```json
{
  "hooks": [
    {
      "name": "Future AGI tracing: session start",
      "trigger": "SessionStart",
      "action": {
        "type": "command",
        "command": "(python3 -B \"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py\" kiro_cli SessionStart 2>/dev/null || true)"
      },
      "timeout": 10
    },
    {
      "name": "Future AGI tracing: prompt",
      "trigger": "UserPromptSubmit",
      "action": {
        "type": "command",
        "command": "(python3 -B \"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py\" kiro_cli UserPromptSubmit 2>/dev/null || true)"
      },
      "timeout": 10
    },
    {
      "name": "Future AGI tracing: tool end",
      "trigger": "PostToolUse",
      "matcher": ".*",
      "action": {
        "type": "command",
        "command": "(python3 -B \"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py\" kiro_cli PostToolUse 2>/dev/null || true)"
      },
      "timeout": 10
    },
    {
      "name": "Future AGI tracing: agent stop",
      "trigger": "Stop",
      "action": {
        "type": "command",
        "command": "(python3 -B \"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py\" kiro_cli Stop 2>/dev/null || true)"
      },
      "timeout": 10
    },
    {
      "name": "Future AGI tracing: session end",
      "trigger": "SessionEnd",
      "action": {
        "type": "command",
        "command": "(python3 -B \"$HOME/.kiro/fi-hook-to-otlp-kiro-cli/emit.py\" kiro_cli SessionEnd 2>/dev/null || true)"
      },
      "timeout": 10
    }
  ]
}
```

## 2. Add your Future AGI keys

Export the keys in the shell that runs `kiro-cli`, or put them in the emitter's env file so every shell and CI job picks them up:

```bash
mkdir -p ~/.config/fi-hook-to-otlp
cat > ~/.config/fi-hook-to-otlp/env <<'EOF'
FI_API_KEY=your-futureagi-api-key
FI_SECRET_KEY=your-futureagi-secret-key
FI_PROJECT_NAME=kiro-cli-sessions
EOF
chmod 600 ~/.config/fi-hook-to-otlp/env
```

For a self-hosted Future AGI, also set `FI_BASE_URL` (traces go to `$FI_BASE_URL/tracer/v1/traces`). All settings are on the [hook-to-OTLP page](/docs/integrations/coding-agents/hook-to-otlp#configuration).

## 3. Run a session

Interactive:

```bash
cd /path/to/your/project
kiro-cli chat --v3 "List the files in this folder and read README.md"
```

Headless, for example in CI (needs `KIRO_API_KEY`, see [Headless mode](https://kiro.dev/docs/cli/headless/)):

```bash
kiro-cli chat --v3 --no-interactive --trust-tools=read_file,list_directory,file_search "List the files in this folder and read README.md"
```

V3 tool ids are `file_search` and `list_directory`; `glob` is the CLI 2.x spelling. In hook payloads, MCP tools use the documented `@<server>/<tool>` name form. A tool you do not trust in a non-interactive run is denied, and a denied or blocked tool has no `PostToolUse`, so it does not appear in the trace.

Open **Observe** in Future AGI and select the project (`kiro-cli-sessions` above). The session appears as one trace named **Kiro CLI session**, with one **Kiro CLI turn** per prompt.

## What is captured

| Kiro CLI trigger | Future AGI span | Fields |
| --- | --- | --- |
| `SessionStart` (or `AgentSpawn`, `agentSpawn`) | **Kiro CLI session** (root) | `session.id` = Kiro `session_id` |
| `UserPromptSubmit` | **Kiro CLI turn** start | prompt length |
| `PostToolUse` | completed tool span, named after the tool (`read_file`, `file_search`, `execute_bash`, `@<server>/<tool>`, ...) | `gen_ai.tool.name`; status `ERROR` when `tool_response.success` is `false`; no vendor duration |
| `Stop` | **Kiro CLI turn** end | |
| `SessionEnd` | closes a turn that is still open (`kiro.turn.ended_by=SessionEnd`) | Fires when a V3 session shuts down. It is not a terminal end: `kiro-cli chat --resume` or `--resume-id` continue the same session id, and the resumed chat continues in the same trace with the next turn number. |

When a hook fires under a CLI 2.x camelCase name (`agentSpawn`, `userPromptSubmit`, `postToolUse`, `stop`), every span it produces also carries `kiro.hook.trigger` with that spelling.

Kiro sends no turn id and no tool call id. A `Stop` closes the open turn, and each `PostToolUse` becomes its own span under that turn, marked `coding_agent.turn.inferred=true` because the turn was matched by time rather than by an id.

## What is not available

- **Model, token counts, and cost.** Kiro hook payloads do not include them.
- **Model request spans.** There is no hook per model call.
- **Tool call ids and tool duration.** Tool spans have a name but no vendor call id, and no duration: `PreToolUse` is a gating hook and is not registered.
- **File and spec-task triggers.** They are not mapped; tool spans already cover the agent's file writes.
- **Session history.** The emitter never reads `~/.kiro` or `$KIRO_HOME` session stores; it only sees hook payloads as they fire.
- **Daily usage metrics** from Kiro enterprise OpenTelemetry are not joined to sessions.

## Privacy

By default only structure and metadata leave your machine: session id, tool names, prompt length, statuses, and timing.

- **Not exported by default:** prompt text, tool input, tool output, the assistant's final response.
- **Never exported:** `cwd`. The emitter reads only the stdin payload, not the `USER_PROMPT` environment variable, and never opens files named in a payload.

To include content, add `FI_HOOK_CAPTURE_CONTENT=1` to the env file. The prompt becomes the turn's `input.value`, the `Stop` payload's `assistant_response` its `output.value`, and tool input and output go on the tool span. Each field is capped at 4096 characters and common key formats are replaced with `[REDACTED]`. See [Privacy](/docs/integrations/coding-agents/hook-to-otlp#privacy).

## Troubleshooting

**No trace appears.**
1. Run `/hooks` in a chat to list the hooks Kiro loaded.
2. Set `FI_HOOK_LOG_FILE=/tmp/fi-hook.log` and send another prompt. No lines: Kiro did not run the command, or the emitter found no `FI_API_KEY` / `FI_SECRET_KEY` (check `~/.config/fi-hook-to-otlp/env`). `error=` lines: the collector is unreachable. `http=401`/`403`: wrong keys.
3. Standalone hook files need the V3 agent. If your CLI still starts the V2 engine, run `kiro-cli chat --v3`.

**Tools appear directly under the session.** A tool hook arrived without an open turn. It is attached to the session rather than guessed.

**A turn has `kiro.turn.ended_by=SessionEnd`.** The session shut down before `Stop` fired for that turn, for example when you pressed Ctrl+C and exited. The turn was closed at that point.

**The turn is marked incomplete.** You sent a new prompt in the same session before `Stop` fired for the previous turn. The previous turn is closed with `coding_agent.incomplete=true`.

## Uninstall

Remove the hook file first, then the emitter, so Kiro never runs a hook whose emitter is gone:

```bash
rm /path/to/your/project/.kiro/hooks/fi-hook-to-otlp-kiro-cli.json
rm -r /path/to/your/project/.kiro/fi-hook-to-otlp-kiro-cli
```

For a `--user` install, remove `~/.kiro/hooks/fi-hook-to-otlp-kiro-cli.json` and then `~/.kiro/fi-hook-to-otlp-kiro-cli` (under `$KIRO_HOME` if you set it). For `--agent-profile`, delete the entries from the agent profile first. The guarded commands make the reverse order safe too: a hook whose emitter is missing exits `0` and does nothing.
