## About

If a Temporal worker restarts, it can replay a workflow's history without running its completed activities again. `traceAI-temporal` sends Temporal's native spans to Future AGI so you can tell a replay from a second attempt. In this example, Ridgeline Outfitters checks a return window once, then replays the workflow without a second return check.

## Set up tracing

<Steps>
<Step title="Start Temporal and install the adapter">

Use Python 3.10 through 3.13. The adapter installs a compatible Temporal Python SDK (1.34 or 1.35). If you don't already have a development server, install the [Temporal CLI](https://docs.temporal.io/cli) and run this in a separate terminal:

```bash
temporal server start-dev
```

In your application terminal, create an environment and install the published adapter:

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install 'traceAI-temporal==0.1.1'
export FI_PROJECT_NAME=ridgeline-returns
```

Load `FI_API_KEY` and `FI_SECRET_KEY` from your [Future AGI API keys](/docs/admin-settings/api-keys) into that terminal. The adapter sends them as `X-Api-Key` and `X-Secret-Key` headers. For Future AGI Cloud, the default base URL is `https://api.futureagi.com`. For self-hosting, set `FI_TRACES_URL` to your collector's **base URL**, for example `http://localhost:4318` for a local collector. Do not append `/tracer/v1/traces`: the adapter adds it. An explicit `configure(base_url=...)` takes precedence over `FI_TRACES_URL`, which takes precedence over `FI_BASE_URL`. Remote collectors require HTTPS.

</Step>
<Step title="Define the workflow separately from the activity">

Save this as `returns_workflow.py`. The workflow schedules an activity by name. It doesn't import the model SDK or tracing code, both of which belong outside the replayed workflow. This example allows only one attempt so you can count exactly what ran.

<CodeGroup titles={["returns_workflow.py"]}>
```python
from datetime import timedelta

from temporalio import workflow
from temporalio.common import RetryPolicy


@workflow.defn
class ReturnWindow:
    @workflow.run
    async def run(self, days_since_delivery: int) -> str:
        return await workflow.execute_activity(
            "check_return_window",
            days_since_delivery,
            start_to_close_timeout=timedelta(seconds=60),
            retry_policy=RetryPolicy(maximum_attempts=1),
        )
```
</CodeGroup>

</Step>
<Step title="Connect the client and run the worker">

Save this as `run_return.py` in the same directory. Call `configure()` **before** `Client.connect()`: it installs Temporal's replay-safe provider and returns the native plugin. The worker inherits that plugin from the client. If your starter and worker run in separate processes, configure each once with the same `FI_PROJECT_NAME`, and pass the plugin to each client. Do not call `register()` as well or attach the plugin again to the worker.

<CodeGroup titles={["run_return.py"]}>
```python
import asyncio
import os
from uuid import uuid4

from temporalio import activity
from temporalio.client import Client
from temporalio.worker import Replayer, Worker
from traceai_temporal import configure

from returns_workflow import ReturnWindow


@activity.defn
async def check_return_window(days_since_delivery: int) -> str:
    decision = "Within the 30-day window" if days_since_delivery <= 30 else "Outside the 30-day window"
    if not os.getenv("RIDGELINE_MODEL"):
        return decision

    from openai import AsyncOpenAI

    async with AsyncOpenAI(max_retries=0) as model:
        reply = await model.chat.completions.create(
            model=os.environ["RIDGELINE_MODEL"],
            messages=[{"role": "user", "content": f"Explain this return decision in one sentence: {decision}."}],
        )
    return reply.choices[0].message.content or decision


async def main():
    telemetry = configure()
    try:
        if os.getenv("RIDGELINE_MODEL"):
            from traceai_openai import OpenAIInstrumentor

            OpenAIInstrumentor().instrument(tracer_provider=telemetry.provider)

        client = await Client.connect("localhost:7233", plugins=[telemetry.plugin])
        workflow_id = f"return-{uuid4().hex}"
        async with Worker(
            client,
            task_queue="ridgeline-returns",
            workflows=[ReturnWindow],
            activities=[check_return_window],
        ):
            handle = await client.start_workflow(
                ReturnWindow.run, 12, id=workflow_id, task_queue="ridgeline-returns"
            )
            print(workflow_id, await handle.result())
            history = await handle.fetch_history()

        await Replayer(workflows=[ReturnWindow], plugins=[telemetry.plugin]).replay_workflow(history)
    finally:
        if not telemetry.shutdown(timeout_millis=3000):
            print("Tracing shutdown did not finish; the final batch may be missing.")


if __name__ == "__main__":
    asyncio.run(main())
```
</CodeGroup>

Run it without a model key:

```bash
unset RIDGELINE_MODEL
python run_return.py
```

The program prints a `return-` workflow ID and `Within the 30-day window`. It then replays the completed history. Replay consumes the recorded activity result; it doesn't call `check_return_window` again.

</Step>
</Steps>

## Find the activity in Observe

Open **Observe**, select `ridgeline-returns`, and open the `StartWorkflow:ReturnWindow` trace for the run. For the 12-day return you should see one of each span, in this order from parent to child:

| Span | What it records |
| --- | --- |
| `StartWorkflow:ReturnWindow` | The starter's request to start the workflow. |
| `RunWorkflow:ReturnWindow` | The workflow execution. This span is exported when the workflow finishes. |
| `StartActivity:check_return_window` | The workflow scheduling the check. |
| `RunActivity:check_return_window` | The worker executing the check. With retries enabled, each real attempt has its own span here. Replay adds none. |

Temporal assigns deterministic span IDs and suppresses exports for replayed work. This keeps replay from looking like a retry; it is not a guarantee of exactly-once delivery to Observe.

{/* MEDIA: Expanded StartWorkflow:ReturnWindow trace in the ridgeline-returns project, showing one StartActivity and one RunActivity after history replay. */}

To find the run later, open the project's **Sessions** tab and look for the workflow ID the script printed. The adapter maps the Temporal **workflow ID**, not the run ID, to `session.id` on the native spans and nested model or tool spans. For example, a signal from an uninstrumented client can start a different trace but still belong to the same workflow session. An explicit application session on a span or in its local context takes precedence over the workflow-ID fallback.

## Add a model reply (optional)

The Temporal plugin doesn't instrument model SDKs. The optional branch in `run_return.py` instruments the OpenAI SDK once with `telemetry.provider` and makes the call **inside the activity**. To run it, load your provider's `OPENAI_API_KEY` into the application terminal, then run:

```bash
python -m pip install 'traceAI-openai==0.1.16' openai
RIDGELINE_MODEL=gpt-4o-mini python run_return.py
```

For an OpenAI-compatible endpoint, also set `OPENAI_BASE_URL` and choose a model ID your provider serves. This run creates a new workflow ID. Open its trace: one model span should appear **under** `RunActivity:check_return_window`, with model and token usage when the provider reports them. The replay does not make or bill a second model request.

## Privacy and troubleshooting

The adapter exports metadata by default, including span names, IDs, timings, status and model usage. It filters prompt and response content, exception messages and stack traces from this destination. Use opaque workflow IDs and span names: allowed metadata values are not scanned for secrets. To export supported content, opt in with `configure(capture_content=True)`; error text also requires `keep_error_text=True`. `FI_HIDE_*` settings still apply. Stack traces stay excluded. These settings do not redact Temporal history, other exporters or application logs.

| Symptom | What to check |
| --- | --- |
| A global tracer provider already exists | Configure once at process startup, before other instrumentation. The plugin requires Temporal's replay-safe provider, not a regular OpenTelemetry provider. |
| Model calls start separate traces | Connect both the starter and worker clients with the plugin. Give the model instrumentor that same process's `telemetry.provider` and keep network calls inside activities. |
| Spans are missing or split across projects | Check both credentials, the collector base URL and the project name in both processes. A running workflow has no completed `RunWorkflow` span yet. |
| The last spans disappear when a process exits | Stop the worker before `telemetry.shutdown()`. Use `telemetry.force_flush(timeout_millis=3000)` to drain ended spans without closing the provider. Both methods bound the wait, not delivery; neither ends an unfinished workflow span. |
