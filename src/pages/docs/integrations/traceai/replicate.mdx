`traceAI-replicate` traces the official [Replicate Python client](https://github.com/replicate/replicate-python) (`replicate`). Replicate's API is predictions, not OpenAI chat completions, so `traceAI-openai` does **not** trace it: pointing `openai.OpenAI` at `api.replicate.com` traces nothing. Use this package for `replicate.run`, `replicate.stream` and the prediction lifecycle.

**Streams carry no status or token counts by default.** With the default `stream_reload_seconds=0`, a `replicate.stream` span ends at `done` with the prediction id and stream output only, without `replicate.prediction.status`, `predict_time` or `gen_ai.usage.*`; there is no request after the stream and no worker thread is started. To opt in, set `stream_reload_seconds` from above `0` to `10`; the package then looks up the prediction once, and a non-final answer once more, using its own pool and sending a real request to your client's `base_url`. The read is skipped, with the reason recorded, for unsupported transports, detected HTTP/socket mocks, or past the 64-pending-span/read caps. Flush, shutdown, exit and `uninstrument()` end pending spans and cancel their reads; `uninstrument()` never waits for a read (bounded waits for reads are opt-in for flush, and for shutdown and exit), and like flush, shutdown and exit it waits up to 5 s for the one span the package's finisher thread is exporting. See [the opt-in read after a stream](#the-opt-in-read-after-a-stream).

## 1. Installation

```bash
pip install traceAI-replicate
```

It accepts `replicate>=1.0.0,<2` and `fi-instrumentation-otel>=1.1.0`, on Python 3.10 to 3.13.

## 2. Set environment variables

```python
import os

os.environ["FI_API_KEY"] = "your-futureagi-api-key"
os.environ["FI_SECRET_KEY"] = "your-futureagi-secret-key"
os.environ["REPLICATE_API_TOKEN"] = "your-replicate-api-token"
```

The Replicate client reads `REPLICATE_API_TOKEN` itself. The instrumentor never reads it.

## 3. Register and instrument

Call `register()` **before** `instrument()`, and instrument before you use the client.

```python
import replicate
from fi_instrumentation import register
from fi_instrumentation.fi_types import ProjectType
from traceai_replicate import ReplicateInstrumentor

trace_provider = register(project_type=ProjectType.OBSERVE, project_name="my-replicate-app")
ReplicateInstrumentor().instrument(tracer_provider=trace_provider)

output = replicate.run(
    "meta/meta-llama-3-8b-instruct",
    input={"prompt": "Write a one-line caption about a quiet field."},
)
print("".join(output))
```

`replicate.run`, `replicate.async_run`, `replicate.stream` and `replicate.async_stream` looked up after `instrument()`, and every `replicate.Client` method, are traced. A function imported earlier with `from replicate import run` keeps the untraced original.

`instrument()` also accepts `config` (a `fi_instrumentation.TraceConfig`), `max_pending_seconds` (default `600`, see [create, wait and cancel](#create-wait-and-cancel)), and three options for [the opt-in read after a stream](#the-opt-in-read-after-a-stream), each from `0` to `10` seconds and `0` by default: `stream_reload_seconds` (the read's budget; `0` means no read), `stream_flush_wait_seconds` (how long `force_flush()` waits for reads in flight) and `stream_shutdown_wait_seconds` (how long `shutdown()` and process exit wait for them). A call made while OpenTelemetry instrumentation is suppressed in your context is not traced.

<Warning>
**Stream spans have no status or token counts by default.** Replicate's event stream reports no status, `predict_time` or token counts, and with the default `stream_reload_seconds=0` the package does not fetch them: a `replicate.stream` span ends at the stream's `done` event, on your thread, OK, with the prediction id and the output, and without `replicate.prediction.status`, `predict_time` or `gen_ai.usage.*`. Nothing is requested after the stream and no thread is started, so `force_flush()`, `shutdown()`, `uninstrument()`, exit and `fork()` wait for no read and no package thread. They still end, inside the call, the spans that are due (held create spans, and those of streams dropped since the last traced call); with an exporter that runs inline those spans are exported there, even by `force_flush(timeout_millis=0)`. A referenced stream or run iterator still open at provider shutdown or exit also ends then as cancelled. A stream that stops before `done` keeps the output it had received. `replicate.run` and create + `wait()` spans have status and tokens either way.

To get them on stream spans, opt in: `ReplicateInstrumentor().instrument(tracer_provider=trace_provider, stream_reload_seconds=2)`. Each stream then costs one request, or two while Replicate still reports a non-final status, against your API rate limit, sent to your client's `base_url` (a stub server in your tests receives it too; keep the default `0` there). The read uses the package's own pool for a plain `httpx` transport (replicate's default, `transport=` or `mounts=`); it is skipped (`custom_transport`) for unsupported transports, subclasses, instance changes (including `HTTPXClientInstrumentor.instrument_client()`), a subclass's `_transport_for_url`, custom network backends and proxies. Detected HTTP mocks and integrations that replace httpx's send path (`patched_http`: respx, pytest-httpx, VCR.py, Sentry's `HttpxIntegration`) and socket-level changes (`patched_socket`: mocket, httpretty, gevent, `truststore.inject_into_ssl()`) also skip the read. Past 64 waiting stream spans / live reads a stream ends without one. Flush, shutdown and exit end pending spans and cancel reads in flight; bounded waits for reads are opt-in for `force_flush()`, and for `shutdown()` and exit. `uninstrument()` never waits for a read; like the other three, it waits up to 5 s for the one span the finisher thread is exporting. See [the opt-in read after a stream](#the-opt-in-read-after-a-stream).
</Warning>

## What is captured

| Call | Span |
|---|---|
| `Client.run`, `async_run` (and `replicate.run`) | One `replicate.run` span. The create request and the client's own polling add no span. |
| `Client.stream`, `async_stream` (and `replicate.stream`) | One `replicate.stream` span for the whole stream, not one per event. The span starts at the first `next()` (the client sends nothing before that), so a stream that is never iterated has no span. The stream is complete at its `done` event: stopping your loop there and closing the stream is a completed stream, not a cancellation. `send()` / `asend()` step it as `next()` does; `throw()` / `athrow()` end it with that error. By default the span ends there, without status or token counts (the event stream reports none). With `stream_reload_seconds` the prediction is then read once more in the background ([the opt-in read after a stream](#the-opt-in-read-after-a-stream)); your loop never waits for it. |
| `predictions.create`, `models.predictions.create`, `deployments.predictions.create` (sync and async) | One `replicate.predictions.create` span. |
| `Prediction.wait`, `cancel`, `predictions.cancel(id)` (sync and async) | Ends the open create span of that prediction, or opens one `replicate.prediction.wait` / `replicate.predictions.cancel` span. |
| `trainings.*`, `predictions.get` / `list`, file uploads | Not traced. |

Spans nest under the active span, so an agent or chain span becomes their parent. Each span records:

- provider `replicate` (`gen_ai.provider.name`) and model `owner/name` (`gen_ai.request.model`);
- span kind `LLM` when the output is text, otherwise `CHAIN` (image or file URLs, or no output, such as a call that failed before any); a stream stopped before `done` keeps the text it had received and stays `LLM`;
- prediction id, status (as the client returns it: `starting`, `processing`, `succeeded`, `failed`, `canceled`; the read after a stream also knows `aborted`), version (not the placeholder `hidden` that official models report), deployment, `predict_time`;
- input and output: text, joined in order, including chunks that start like a URL (`https://`, `data:`); `data:` file payloads are shortened only when the output is files; file URLs as strings only when every chunk is a URL or a file (a stream records their count); files are never downloaded;
- token counts when the prediction reports them (`metrics.input_token_count` / `output_token_count`, which Replicate's language models return). No cost is recorded. **A stream span has none by default**; it gets them only from the opt-in read after `done`, and when that read is skipped, fails or is cut short, `replicate.stream.read` says why (`skipped` with `replicate.stream.skip_reason`, `timeout`, `failed`, `unfinished`, `flushed`, `shutdown` or `uninstrumented`);
- for a stream, `replicate.stream.done_reason` when its `done` event gives one (a `done` with reason `canceled` records status `canceled`), and `replicate.stream.truncated=true` when the stream ended without `done`.

### The opt-in read after a stream

**Off by default.** With `stream_reload_seconds=0` (the default) none of this section applies: a stream span ends at `done` with what the stream gave, no request is made after the stream and no thread is started. A `done` whose data says `{"reason": "canceled"}` still records status `canceled`.

**On.** With `stream_reload_seconds` above `0` (at most `10`), after `done` the package looks up the prediction once (`GET /v1/predictions/{id}`), and a non-final answer is looked up a second time after `poll_interval`, to record its final status, `predict_time` and token counts on the stream span. Its limits:

- **Cost and rate limit.** The read creates no prediction and is not billed, but it is an API request and counts toward your account's rate limit for requests other than creates (3000 per minute on [Replicate's rate-limit page](https://replicate.com/docs/topics/predictions/rate-limits)): one read per stream, two when the API still answers `processing` right after `done`. No read is made for a span that is not exported: one your sampler dropped, after the provider is shut down, or when the provider could not be hooked (call `register()` before `instrument()`).
- **Only through the package's own connections.** The read uses a pool owned by the package, with your client's base URL and headers. The transport the client uses for the API URL must be exactly a plain `httpx.HTTPTransport` / `httpx.AsyncHTTPTransport` over a plain pool on httpcore's default network backend, under replicate's own `RetryTransport` layers if any. This includes replicate's default, a plain transport you pass, and a plain transport mounted with `mounts=`; for example `transport=httpx.AsyncHTTPTransport(retries=2)` (its TLS context and settings are copied). **Any other transport is skipped** (`custom_transport`): a custom or subclassed transport, a transport or pool with `handle_request` / `handle_async_request` set on the instance (as `HTTPXClientInstrumentor.instrument_client(client)` does; the global `HTTPXClientInstrumentor().instrument()` is allowed), a custom network backend or backend with `connect_tcp` / `connect_unix_socket` set on the instance, a `_transport_for_url` set on the client instance or overridden by a subclass of `httpx.Client` / `httpx.AsyncClient`, a proxy transport or a client with `proxy=`, or an async-only transport. The read never calls your transport, backend, resolver or pool.
- **Not through a detected HTTP or socket mock.** A test double that replaces `httpx`'s or `httpcore`'s send path on the class (respx, pytest-httpx, VCR.py, `mock.patch`) would see the package's own request and could answer it with a response your test scripted for your own code. While a checked client, transport, pool, connection or network-backend send method is not the library's own function, no read is made (`patched_http`). The package also checks `socket.socket`, `socket.getaddrinfo`, `socket.create_connection`, `ssl.SSLContext` and its `wrap_socket` / `wrap_bio`; when one is replaced (mocket, httpretty, gevent, eventlet), it makes no read (`patched_socket`). Both checks run when the stream completes and again just before the request is sent, so a mock started while a read is already being sent can still see that one request. opentelemetry-instrumentation-httpx's wrappers are allowed; another library that replaces those methods itself also turns the read off: Sentry's `HttpxIntegration` replaces `Client.send` / `AsyncClient.send` (`patched_http`), and `truststore.inject_into_ssl()` replaces `ssl.SSLContext` (`patched_socket`). A mock below the checked HTTP and socket methods is not detected, and a stub server is not a mock (see [tests and stub servers](#tests-and-stub-servers)).
- **Off your path, until the cap.** When a stream completes, your `next()` / `__anext__()` runs the read's checks on your thread (the transport, HTTP-mock and socket-mock checks and admission against the caps, without I/O), hands the read over with one queue put and returns: your loop gets every event, `done` included, without waiting or doing I/O for the read. The package's threads start in `instrument()` (a forked child starts its own on its first completed stream). Past 64 waiting stream spans (or 64 live reads), a stream that completes ends at once on your thread without a read (`skipped`, `at_capacity`); that inline end can run an exporter, as it would with the read off, and its export is not bounded by the read's deadline. The limit is concurrent waiting spans, not total reads over a burst. The read's own work still runs in your process and costs CPU time, so the cost grows with CPU contention. With an inline exporter, shutdown and exit can still take up to 64 times its per-span export time (export, not a wait for a read; a batch span processor, `register()`'s default, only queues the spans).

  Measured on traceAI `55c5672` (the package imported from a `git archive` of that commit; Python 3.12.10, replicate 1.0.7, httpx 0.28.1; a stand-in API on loopback; load average 11 to 15 on a 10-core laptop shared with other work). The bracketed names are the probe blocks the traceAI#219 description lists. These are measurements, not a latency guarantee:
  - Time from `done` to the end of each loop, 200 concurrent async streams, median per run: one shared client [G1, 3 runs] 16.9–26.1 ms uninstrumented, 29.3–38.7 ms with the read off, 35.9–67.1 ms with the read on; a client per stream [G2, 2 runs] 18.3–21.1 ms, 28.4–106.4 ms and 42.8–87.7 ms.
  - `asyncio.run(call())` per call (10 calls, a 0.2 s read, plain `httpx.AsyncHTTPTransport`): p50 9 ms, max 10 ms with the read on, all 10 reads completed [A1]; p50 8 ms, max 9 ms with the read off [A2]; uninstrumented in the same blocks p50 7 ms and 6 ms.
  - `complete_stream()` on the caller's thread, 500 threads x 5 runs with the read on [D1]: p50 0.107–0.124 ms, p99 0.269–0.801 ms per run; maximum 0.75–2.98 ms in runs 2 to 5 and 113 ms in the first run.
  - Sustained rate [S1]: 160 streams at 20 a second with an inline exporter taking 0.1 s per span and a 2 s budget: 146 got read data, 14 were skipped `at_capacity`, 64 spans pending at peak; the caller's loop p50 2 ms, p99 113 ms.
  - A first attempt at the same commit under load average 44 to 220 from other processes measured several times higher; it is kept with the evidence, and none of its figures are quoted here.
- **Bounded.** `stream_reload_seconds` is a wall-time budget from the end of the stream, and a hard deadline: the request is cancelled and its connection closed when it runs out. The package never retries the read: a 429 or 5xx ends it, and `Retry-After` is not waited on. Name lookups are shared between reads of the same host, kept for 5 s, run on at most 2 resolver threads with at most 64 queued, and wait for a thread within the budget. The body is limited to 2 MiB as it arrives.
- **No extra span.** The read runs with OpenTelemetry instrumentation suppressed, so an HTTP client instrumentation adds no span for it.
- **When the span ends.** When the read returns or the budget runs out, whichever is first, with the stream's end as its end time. A read that is skipped, fails or runs out of time leaves the span OK with its output, without status and token counts. A background thread ends stream spans one at a time; with an exporter that runs inline, their exports queue there, but no read waits behind them.
- **Flush, shutdown, exit and `uninstrument()` do not wait by default.** Each ends the stream spans still waiting for their read at once, with what is known, so they are exported: `replicate.stream.read=flushed` for `force_flush()`, `shutdown` for `shutdown()` (including the SIGTERM/SIGINT handler `register()` installs) and process exit, `uninstrumented` for `uninstrument()`. Each cancels reads still in flight, closing their connections. `uninstrument()` never waits for a read; like a flush, a shutdown or an exit, it waits up to 5 s for the one span the package's finisher thread is exporting at that moment (that span has already ended, and the wait keeps a shutdown or exit right after from cutting its export off; after a wait that ran out, the next one does not wait until the finisher has ended another span, and `timeout_millis` does not shorten it). A flush after every request therefore costs nothing extra, but those stream spans carry no status or token counts unless their read had returned. To wait (for example in a serverless handler that freezes after it returns), pass `stream_flush_wait_seconds`: `force_flush(timeout_millis)` then waits up to that long, never more than half of `timeout_millis` (default 30 s), and the provider's own flush gets the time that is left, so with a batch span processor (`register()`'s default) the call never takes longer than you asked; with an exporter that runs inline (`register(batch=False)`), each span it ends is exported inside the call, which can take longer. `stream_shutdown_wait_seconds` does the same for `shutdown()` and also applies at process exit; no option makes `uninstrument()` wait for a read. Every flush first ends held create spans and the spans of dropped streams, so `force_flush(timeout_millis=0)` still exports those inline with an inline exporter. A stream or run iterator still open at provider shutdown or process exit ends then as cancelled. A stream still open after `uninstrument()` is not ended until it is dropped, the next traced call or exit. The provider is shared: a flush ends every request's stream spans, not only its own.
- **Forks.** Before starting its workers, `instrument()` imports AnyIO's lazily loaded asyncio backend on your thread, so a package thread is never in that import when a fork happens (otherwise the child could inherit its import lock and hang its own async httpx code). At `os.fork()`, the package pauses its read loop between steps and its finisher between span ends, giving the fork up to 5 s total to wait for one export; after that it proceeds and a child could inherit an exporter lock held mid-export. A fork whose wait ran out does not make the next forks wait for that thread again until it has moved on (the loop has taken a step, the finisher has ended a span), so a finisher stuck in an export costs one fork up to 5 s, not every fork. The dispatcher and resolver threads are not paused. A child neither ends nor exports a stream span its parent was waiting on. Whether a span processor or exporter works in a forked child (for example a `BatchSpanProcessor` whose thread was running) is up to that processor; the package makes no claim about it. With the read off, the fork waits for nothing. Measured on traceAI `55c5672` (same setup as above): with 10 reads in flight in the parent, `os.fork()` took 2.4 ms in the parent; the child started with no package thread and nothing pending, its own async httpx call finished, and its first stream's read ended `succeeded` 3.0 s later (the stand-in answered reads after 3 s) on the child's own threads, while the parent's 10 spans ended `succeeded` [F1]. With the finisher stuck in an export, four forks in a row took 5.003 s, then 0.003 s three times [F2].

  On macOS, a forked child that looks up the system proxy settings after its parent did (CPython's `_scproxy`, which every `httpx` client with `trust_env` uses) can crash in the Objective-C runtime, with or without this package; that is why `multiprocessing` uses spawn on macOS. With the opt-in read, a child that streams builds the package's own `httpx` client for the read, and for a client whose transport replicate built that client does the same lookup. Use spawn, or set `NO_PROXY` / `no_proxy` (then the lookup reads the environment only); the fork measurements above set `no_proxy`.
- **What is kept.** Only the prediction's id, status, version, model, metrics and error, never its input, output or logs.

`replicate.stream.skip_reason`, with `replicate.stream.read=skipped`:

| Reason | No read because |
|---|---|
| `custom_transport` | The API-URL transport is not a plain `httpx` transport (under replicate's `RetryTransport` layers, if any): a custom transport or subclass; a transport / pool changed on the instance, for example by `HTTPXClientInstrumentor.instrument_client(client)`; a custom network backend; a `_transport_for_url` set on the client instance or overridden by a subclass of `httpx.Client` / `httpx.AsyncClient`; or a proxy. A plain transport mounted with `mounts=` is supported. |
| `patched_http` | A checked `httpx` / `httpcore` client, transport, pool, connection or network-backend send method was replaced on the class when the stream completed or when the read was about to be sent: respx, pytest-httpx, VCR.py, `mock.patch`, or Sentry's `HttpxIntegration` (`Client.send` / `AsyncClient.send`). |
| `patched_socket` | `socket.socket`, `socket.getaddrinfo`, `socket.create_connection`, `ssl.SSLContext` or its `wrap_socket` / `wrap_bio` was replaced: mocket, httpretty, gevent or eventlet monkey-patching, or `truststore.inject_into_ssl()` (which replaces `ssl.SSLContext`). |
| `at_capacity` | 64 stream spans were already waiting, or 64 reads were live. |
| `no_provider_hook` | The provider's `force_flush` / `shutdown` could not be hooked (for example `instrument()` before `register()`). |
| `after_uninstrument` | The stream completed after `uninstrument()`. |
| `after_shutdown` | The stream completed after the provider's `shutdown()`. |
| `client_closed` | The client's `httpx` client was closed. |
| `no_prediction_id` | The stream's prediction has no usable id. |

#### Tests and stub servers

The opt-in read is a real HTTP request, `GET {base_url}/v1/predictions/{id}`, sent to the `base_url` of the client that streamed. Only mocks inside your process (the `patched_http` and `patched_socket` cases) are detected. A local stub server your tests point the client at, such as pytest-httpserver, WireMock or Prism, is a real server: it receives that request, can answer it with a response you scripted for your own code, and counts it among the requests your test checks. Keep `stream_reload_seconds=0` (the default) in tests that use a stub server, and turn the read on only where a test expects that extra request.

### create, wait and cancel

`predictions.create` usually returns a prediction that is still `starting`. The span stays open on it: a later `wait()` or `cancel()` ends that same span with the final status, output and duration, so create followed by wait is **one** span. If nothing continues it, the span ends with its create-time status when the provider is flushed or shut down (including the SIGTERM/SIGINT handler `register()` installs), after `max_pending_seconds`, at `uninstrument()` or at exit. The package never polls a prediction you did not wait for.

### Errors

- A failed prediction (`ModelError` from `run`, or status `failed` after `wait()`) is an `ERROR` span with the prediction's error string.
- An HTTP error (`ReplicateError`: a wrong token, HTTP 401; an unknown version, HTTP 422; a rate limit, HTTP 429) is an `ERROR` span with the error type and message, and Replicate's error detail as the status message.
- A call that fails before any output has none, so its span kind is `CHAIN` even for a language model. Count failed calls by status, not by kind.
- The client does not retry a create answered 429: the span ends `ERROR`, and a retry by your code is a second span. Reads answered 429, 503 or 504 are retried inside the client, within the same span; the package's own read after a stream is never retried.
- `canceled` is a terminal state, not a failure: the span status is OK with status `canceled` (also for a stream whose `done` event says `{"reason": "canceled"}`).
- Closing or dropping a stream before its `done` event, cancelling the task that reads it, or Ctrl-C while you iterate it is an `ERROR` span with description `cancelled` and `replicate.cancelled=true`, without an exception event. Ctrl-C is recorded the same way wherever it lands: a `KeyboardInterrupt` inside `next()` ends the span there, and one in your loop body leaves the stream open, so it ends as cancelled when it is dropped or at shutdown or exit (under `register()`, SIGINT runs its handler instead, and the shutdown ends a stream still open as cancelled). Closing it after `done` is not a cancellation, and a stream closed before its first `next()` sent nothing and has no span.
- A stream or run iterator that stops before it completes (any of the above, an exception, or still open at shutdown or exit) keeps the output it had yielded so far, still subject to `FI_HIDE_OUTPUTS`, so a text stream stays `LLM`. This follows the OpenTelemetry GenAI conventions, under which output "SHOULD only be set when the operation produced output, including partial streamed output", and what the OpenTelemetry, OpenInference and OpenLLMetry OpenAI instrumentations do with a stream that ends early.

## Privacy

This package follows the standard traceAI `TraceConfig`: content is recorded by default, like every traceAI LLM integration.

| Setting | Recorded |
|---|---|
| Default | Prediction input and output, and a failed prediction's error string. |
| `FI_HIDE_INPUTS=true` and `FI_HIDE_OUTPUTS=true` (or `TraceConfig(hide_inputs=True, hide_outputs=True)`) | Input and output become `__REDACTED__`; with outputs hidden a failed prediction's error string is `__REDACTED__` too. Model, status, ids, timing and tokens stay. |
| `FI_PII_REDACTION=true` | Masks emails, card numbers, keys and similar values in recorded strings, the error status and the exception message. |

Always, in every mode:

- The Replicate API token is replaced by `[redacted]` wherever the client stored it.
- No stack trace, local file path, user name or host name is exported. An exception event carries the type and the message only.
- File outputs are recorded as URL strings and never fetched; a `data:` URI in a file output keeps only its media type, while a `data:` chunk in text output is kept verbatim.
- A webhook URL is recorded only as present. This package hosts no webhook receiver.

Replicate still receives your input either way.

## Troubleshooting

- **No Replicate spans after installing `traceAI-openai`.** That package cannot see the Replicate client. Install `traceAI-replicate`.
- **`replicate.run` is not traced.** You imported it with `from replicate import run` before `instrument()`. Call `replicate.run` after instrumenting, or instrument first.
- **A create span ends with status `starting`.** Nothing called `wait()` or `cancel()` on that prediction before the flush; the span is not a completion.
- **A `replicate.run` span shows `processing` with output.** With `Prefer: wait`, the client returns once the status is no longer `starting`; the server can answer `processing` for a finished prediction.
- **Held create spans are missing after Ctrl-C, or stream spans have `replicate.stream.skip_reason=no_provider_hook`.** You called `instrument()` before `register()`; register first so the flush and shutdown hooks land on the real provider.
- **HTTP 401 on every call.** The token is wrong; the span records the error, the instrumentor does not retry.
- **A stream span has no status or token counts.** That is the default: pass `stream_reload_seconds` (for example `2`) to `instrument()` to read the prediction after `done`. With the read on, `replicate.stream.read` on the span says why it has none: `skipped` (with `replicate.stream.skip_reason`: `custom_transport`, the API-URL transport is not a plain supported `httpx` transport or uses a proxy; `patched_http`, a detected class-level HTTP mock; `patched_socket`, a detected socket-level mock; `at_capacity`; `no_provider_hook`; `after_uninstrument`; `after_shutdown`; `client_closed`; `no_prediction_id`; `start_failed`; `interrupted`), `failed` (refused, for example HTTP 429; it is not retried), `timeout` (it did not return within `stream_reload_seconds`), `unfinished`, or `flushed` / `shutdown` / `uninstrumented` (that call ended the span before the read returned; `stream_flush_wait_seconds` / `stream_shutdown_wait_seconds` can wait during flush or shutdown; `uninstrument()` never waits). Raise the budget, let flush or shutdown wait, or check your account's rate limit.
- **A stub server in your tests receives an extra `GET /v1/predictions/{id}` after each stream.** That is the opt-in read after a stream; it is a real request to your client's `base_url`. Keep `stream_reload_seconds=0` (the default) in those tests.
- **HTTP 429 "Request was throttled" on creates.** Replicate lowers the create rate limit for accounts with little credit (its message says by how much). The client does not retry a create; add credit, slow down, or give the client a transport that retries a create answered 429 (a 429 creates nothing), in which case the span covers the wait and ends with the real answer.

## Limitations

- Python client only; the JavaScript client is not traced.
- Trainings are not traced.
- `Prediction.stream()` and `Prediction.output_iterator()` on a prediction you created yourself are not wrapped; use `replicate.stream` or `replicate.run`.
- The `Cancel-After` deadline is not recorded.
- Stream spans have no status, `predict_time` or token counts unless you opt in to the read after a stream; even then it uses its own pool only for a plain `httpx` transport (including one mounted with `mounts=`), and skips unsupported HTTP/socket mocks.
- Live-verified and stored in Future AGI: `run`, `async_run`, `stream` and `async_stream` with the read off (`stream` on the package code of this release candidate, traceAI `f0376ad`), an unknown version (HTTP 422) and a rate limit (HTTP 429). The read after `done` ran live only in its earlier designs (on by default then, traceAI `18f7f8b` to `b5df956`). Stand-in only: the opt-in read as it is now (traceAI `d610ede` on), including its skips; create followed by `wait()` (the held create span), cancel, deployments, run iterators, image and file outputs, text chunks that start like a URL, and streams stopped before `done`.
