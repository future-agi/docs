## About

Trace a return request through Ridgeline Outfitters' support graph without a model API key. Client spans show how long a caller waits for a result or keeps a stream open; server spans show how much of that time each graph node takes.

## Trace a local Python graph

Set `FI_API_KEY` and `FI_SECRET_KEY` from your [Future AGI API keys](/docs/admin-settings/api-keys) in your environment. Start in a new, empty directory so the examples do not change an existing project's configuration. Create a Python 3.12 environment there:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install 'traceAI-langchain==0.2.4' 'fi-instrumentation-otel==1.5.1' 'langgraph==1.2.24'
```

Save this as `support.py`. Register the provider and enable the [LangChain instrumentor](/docs/integrations/traceai/langchain) before running the graph. If your application already instruments LangChain, reuse its provider rather than instrumenting it again.

<CodeGroup titles={["Python"]}>

```python
from typing_extensions import NotRequired, TypedDict
from fi_instrumentation import register
from fi_instrumentation.fi_types import ProjectType
from langgraph.graph import END, START, StateGraph
from traceai_langchain import LangChainInstrumentor


class Ticket(TypedDict):
    question: str
    queue: NotRequired[str]


def route_ticket(state: Ticket):
    question = state.get("question")
    if not isinstance(question, str):
        raise ValueError("Ticket must include a string question")
    return {"queue": "returns" if "return" in question.lower() else "support"}


builder = StateGraph(Ticket)
builder.add_node("route_ticket", route_ticket)
builder.add_edge(START, "route_ticket")
builder.add_edge("route_ticket", END)
graph = builder.compile()

if __name__ == "__main__":
    provider = register(project_name="ridgeline-returns-langgraph", project_type=ProjectType.OBSERVE)
    LangChainInstrumentor().instrument(tracer_provider=provider)
    try:
        for update in graph.stream({"question": "Can I return my hiking boots?"}, stream_mode="updates"):
            print(update)
    finally:
        provider.shutdown()
```

</CodeGroup>

Run `python support.py`. The update is `{'route_ticket': {'queue': 'returns'}}`. In the sidebar, select **Tracing** under **Observe**. Open `ridgeline-returns-langgraph`, then open the `LangGraph` trace to see its `route_ticket` child.

![The LangGraph trace tree shows route_ticket beneath LangGraph. The selected node takes the hiking-boot return question as input and outputs the returns queue.](/images/docs/integrations/traceai/langgraph/local-graph-return-routing.png)

## Trace calls to a remote graph

Use this path when the graph runs in another process. You need its API URL and assistant ID or graph name, plus `LANGGRAPH_API_KEY` if your deployment requires authentication. To follow along without a deployment, serve the same `support.py` locally. In the example directory, create `langgraph.json` with this mapping. If you are adding the example to an existing configuration, add `support` to its `graphs` object rather than replacing the file.

```json
{"dependencies":["."],"graphs":{"support":"./support.py:graph"}}
```

Install and start the development server:

```bash
python -m pip install 'langgraph-cli[inmem]==0.4.43' 'langgraph-api==0.18.4'
langgraph dev --no-browser --no-reload
```

In a second terminal, open the example directory and set the Future AGI keys as above. The settings, input and expected output below are for the `support` graph. For another deployment, use its URL and assistant ID, change `input` to match its schema, and look for its own node names and output. Use Node.js 22.18 or later to run the `.mts` file directly.

```bash
export LANGGRAPH_API_URL=http://127.0.0.1:2024
export LANGGRAPH_ASSISTANT_ID=support
npm install @traceai/langchain@0.1.8 @traceai/fi-core@1.4.1 @langchain/core@1.5.0 \
  @langchain/langgraph-sdk@1.12.9 @opentelemetry/api@1.9.1 @opentelemetry/core@2.6.0
```

Save this as `remote.mts`. `wrapLangGraphClient` creates one `CLIENT` span per `runs.wait` or consumed `runs.stream` call. It does not trace `threads.create()`. The `onRequest` hook injects the active span's W3C trace context into the HTTP request. If you already use an `onRequest` hook, pass it to `langGraphTraceRequestHook(existingHook)` to preserve its changes.

<CodeGroup titles={["TypeScript"]}>

```typescript
import { Client } from "@langchain/langgraph-sdk";
import { propagation } from "@opentelemetry/api";
import { W3CTraceContextPropagator } from "@opentelemetry/core";
import { ProjectType, register } from "@traceai/fi-core";
import { langGraphTraceRequestHook, wrapLangGraphClient } from "@traceai/langchain";

const apiUrl = process.env.LANGGRAPH_API_URL;
const assistant = process.env.LANGGRAPH_ASSISTANT_ID;
if (!apiUrl || !assistant) throw new Error("Set LANGGRAPH_API_URL and LANGGRAPH_ASSISTANT_ID");

propagation.setGlobalPropagator(new W3CTraceContextPropagator());
const provider = register({ projectName: "ridgeline-returns-langgraph", projectType: ProjectType.OBSERVE });
const client = wrapLangGraphClient(new Client({
  apiUrl, apiKey: process.env.LANGGRAPH_API_KEY || null, onRequest: langGraphTraceRequestHook(),
}), { tracerProvider: provider });

try {
  const thread = process.env.LANGGRAPH_THREAD_ID ?? (await client.threads.create()).thread_id;
  console.log("Thread:", thread);
  const input = { question: "Can I return my hiking boots?" };
  console.log(await client.runs.wait(thread, assistant, { input }));

  const stream = client.runs.stream(thread, assistant, { input, streamMode: "updates" });
  for await (const chunk of stream) {
    if (chunk.event === "error") {
      console.error("Graph stream failed on thread", thread);
      process.exitCode = 1;
    } else if (chunk.event === "updates") {
      console.log(chunk.data);
      if (process.env.CLOSE_EARLY === "1") break;
    }
  }
} finally {
  await provider.shutdown();
}
```

</CodeGroup>

Run `node remote.mts`. `wait` returns the final state with `queue: 'returns'`; `stream` yields the `route_ticket` update. In the same project's **Trace** tab, choose **Display → Group traces by → Span**. Under **Display → Add custom columns**, select the three attributes below. Filter `langgraph.thread.id` to the thread printed by the client to compare the `LangGraph runs.wait` and `LangGraph runs.stream` rows:

| Attribute | What to check |
| --- | --- |
| `langgraph.thread.id` | Matches the thread printed by the client for both operations. The wrapper also sets `session.id`, but this can appear as `<redacted>` after export. Use opaque thread IDs, not customer emails or ticket text: the thread attribute can remain visible even when the session attribute is redacted. |
| `langgraph.assistant.id` | Matches `LANGGRAPH_ASSISTANT_ID` (`support` in this example). |
| `langgraph.run.id` | Different for the wait and stream: these are two runs, not two views of one run. Present when the SDK supplies `run_id` via `onRunCreated`. |

![The filtered span table shows LangGraph runs.stream and LangGraph runs.wait with identical thread IDs and the same support assistant, but different run IDs.](/images/docs/integrations/traceai/langgraph/client-wait-stream-identifiers.png)

## Connect the server's graph nodes

The client alone cannot tell you that `route_ticket` ran. To see it beneath the client span, export both sides to the same Observe project, extract the W3C `traceparent` at the server, and keep that context active where the worker runs the graph. A header at the HTTP boundary is not enough if a queue or worker drops its parent context.

For the Python development server above, stop the server, install the HTTP instrumentor, and save the following as `serve.py` next to `langgraph.json`. It instruments both the HTTP request and the LangChain callbacks before starting the server.

```bash
python -m pip install 'opentelemetry-instrumentation-starlette==0.66b2'
```

<CodeGroup titles={["Python"]}>

```python
from fi_instrumentation import register
from fi_instrumentation.fi_types import ProjectType
from opentelemetry.instrumentation.starlette import StarletteInstrumentor
from traceai_langchain import LangChainInstrumentor

provider = register(project_name="ridgeline-returns-langgraph", project_type=ProjectType.OBSERVE,
                    set_global_tracer_provider=True)
StarletteInstrumentor().instrument(tracer_provider=provider)
LangChainInstrumentor().instrument(tracer_provider=provider)

from langgraph_cli.cli import cli

try:
    cli()
finally:
    provider.shutdown()
```

</CodeGroup>

Start the server with worker context propagation enabled:

```bash
OTEL_ENABLED=true python serve.py dev --no-browser --no-reload
```

Leave `LANGGRAPH_THREAD_ID` unset to create a fresh thread, or set it to the printed ID if that thread still exists on this server and you want to reuse its state. The thread ID does not control trace propagation. Run `node remote.mts` again and open the new `LangGraph runs.wait` trace. Follow the server's `POST` request to `worker.stream_run`, then expand `support` to see `route_ticket`. These are descendants of the client span, not additional client calls. The streaming run has the same hierarchy under `LangGraph runs.stream`. If your graph calls a model or tool, look for its server-side spans inside the graph.

![The expanded LangGraph runs.wait trace follows the server POST request into worker.stream_run, then support and route_ticket. The selected node returns the returns queue.](/images/docs/integrations/traceai/langgraph/remote-wait-server-graph.png)

## Stream lifecycle and troubleshooting

| What you observe | What it means |
| --- | --- |
| No span after calling `runs.stream()` | The stream is lazy. The first pull starts its span; constructing the iterator makes no request. Consume the iterator or close it after starting it so the span ends. |
| `langgraph.stream.cancelled: true` | The consumer closed a started stream early. Try `CLOSE_EARLY=1 node remote.mts`: the `break` closes the iterator rather than reading it to completion. This flag describes the client, not whether the server finished the run. |
| `langgraph.cancelled: true` | To interrupt a request, pass an `AbortController`'s `signal` in the run options and call `abort()` on the controller. An SDK `AbortError`, or a stream that ends normally with an aborted signal, marks cancellation rather than failure. |
| A failed span | A thrown non-abort error still reaches the caller. An `error` event in the stream marks its span as an error and still reaches the consumer. |
| No prompt, result or stream event body on the client span | The wrapper records identifiers and operation status, not request or response content. Server-side instrumentation has its own [capture controls](/docs/sdk/tracing/trace-config). |
| Client and graph appear as separate traces | Check that your SDK supports `ClientConfig.onRequest` (1.12.9 does), the client uses a W3C propagator, and the server continues that context in the worker. Older SDKs without the hook can still create client spans. A matching thread ID alone does not join two traces. |
