## About

Z.ai's general platform serves an OpenAI-compatible chat API. You keep using `openai.OpenAI`, set `base_url` to the Z.ai general platform URL, and the existing [traceAI-openai](/docs/integrations/traceai/openai) instrumentor traces the call. There is no Z.ai package to install and nothing to configure on the Z.ai side.

This page is not:

- **A Z.ai export.** It traces calls your own code makes. It does not read Z.ai usage logs or billing, and it does not import history.
- **A new traceAI package.** There is no `traceai-zai`. The existing instrumentor handles the call, and [What is not captured](#what-is-not-captured) lists the gaps found.
- **Coding Plan setup.** The GLM Coding Plan is a different Z.ai product with different endpoints. See [Coding Plan is not this page](#coding-plan-is-not-this-page).
- **A recipe for Z.ai's own `zai-sdk`.** Its `ZaiClient` is not traced by traceAI-openai. See [Z.ai's own SDK is not traced](#zais-own-sdk-is-not-traced).

The provider name on the span reads `openai`, not Z.ai. That is a display limit of the instrumentor, not something this page can change.

## Install

Install the OpenAI instrumentor and the OpenAI SDK. You do not install `zai-sdk`.

```bash
pip install traceAI-openai openai
```

## Trace a chat completion

Set the three keys. The Z.ai key goes to the OpenAI client. The Future AGI keys go to `register()`. Neither key belongs on a span.

```bash
export ZAI_API_KEY="YOUR_ZAI_API_KEY"
export FI_API_KEY="YOUR_API_KEY"
export FI_SECRET_KEY="YOUR_SECRET_KEY"
```

Then register the tracer, install the instrumentor, and build the client. Replace the model with a current model code from Z.ai's model list.

```python
import os

from fi_instrumentation import register
from fi_instrumentation.fi_types import ProjectType
from openai import OpenAI
from traceai_openai import OpenAIInstrumentor

trace_provider = register(
    project_type=ProjectType.OBSERVE,
    project_name="my-chatbot",
)
OpenAIInstrumentor().instrument(tracer_provider=trace_provider)

client = OpenAI(
    api_key=os.environ["ZAI_API_KEY"],
    base_url="https://api.z.ai/api/paas/v4/",
)

response = client.chat.completions.create(
    model="your-model",
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
print(response.choices[0].message.content)
```

<div style={{ overflowX: 'auto' }}>

| Piece | Value |
| --- | --- |
| Client | `openai.OpenAI` from the `openai` package. Not `zai.ZaiClient` |
| Base URL | `https://api.z.ai/api/paas/v4/`, with the trailing slash, as Z.ai's OpenAI Python guide prints it |
| Auth | `Authorization: Bearer <ZAI_API_KEY>`, which the OpenAI client sends for `api_key` |
| Model | A current model code from Z.ai. Z.ai's own examples use `glm-5.3` (read 2026-10-15); this page does not pin one |
| Project | `project_name` in `register()`. The instrumentor does not set it |
| Self-hosted Future AGI | Also export `FI_BASE_URL` with your collector URL |

</div>

Keep the trailing slash. It is the string in Z.ai's OpenAI Python guide. Z.ai's API introduction prints the same host without the slash as the general endpoint, and the OpenAI client sends both to the same path, `/api/paas/v4/chat/completions`.

Build the client after `register()` and `instrument()`, as above. Z.ai still receives your prompt: tracing sends a copy to Future AGI and does not change what the API sees.

### Coding Plan is not this page

<Warning>
If your base URL is one of the three below, this page does not apply. Z.ai's GLM Coding Plan has dedicated endpoints for coding tools: `https://api.z.ai/api/anthropic` (Anthropic Messages), `https://api.z.ai/api/coding/paas/v4` (OpenAI Chat Completions) and `https://api.z.ai/api/v1` (OpenAI Responses). Z.ai says that incorrect endpoint configuration will result in being unable to use Coding Plan subscription quota, and that the Coding Plan is limited to its officially supported tools and products. Z.ai's Team Plan key is also not interchangeable with its other API keys. This page does not document the Coding Plan, and the example app refuses all three URLs.
</Warning>

The URLs and warnings are from Z.ai's [Coding Plan quick start](https://docs.z.ai/devpack/quick-start) and [tool integration](https://docs.z.ai/devpack/tool/others) pages, read 2026-10-15. Treat Z.ai's pages as the authority if they differ. A call to a Coding Plan URL through the OpenAI client would still be traced, because the instrumentor wraps the client and does not look at the URL. That is why this page names them: the trace would look the same and the bill would not.

### Z.ai's own SDK is not traced

Z.ai ships `zai-sdk` with a `ZaiClient`. It is not a subclass of `openai.OpenAI`, and traceAI-openai produced no spans for it while the stock `openai.OpenAI` client, pointed at the same server, produced one. This was checked with zai-sdk 0.2.3 (the version Z.ai's docs install) against the local stand-in, not against Z.ai. If you use `ZaiClient`, this page gives you no traces. Switch to `openai.OpenAI` with the URL above, which Z.ai's own OpenAI Python guide supports.

`zai-sdk` also ships `ZhipuAiClient`, whose default URL in that package is `https://open.bigmodel.cn/api/paas/v4`. That is Zhipu's mainland platform. It is not the endpoint in Z.ai's OpenAI Python guide, and this page does not cover it.

## What you get

Each call below produced the spans shown. "Stand-in" means the Z.ai-shaped local server; "real model" means the local OpenAI-compatible proxy running a real model. Neither is Z.ai.

<div style={{ overflowX: 'auto' }}>

| Call | What lands in Observe | Notes |
| --- | --- | --- |
| `chat.completions.create` | One `LLM` span with the model, input and output messages, and input, output and total tokens | On a non-streaming call the model on the span is the `model` field of the response body, not the one you sent |
| `stream=True` | One `LLM` span with a first-token event, the joined output text and token counts | Z.ai's streaming guide shows `usage` on the last chunk with no `stream_options`, so the recipe does not send one. The stand-in follows that and the span carried the counts. What live Z.ai sends was not checked |
| Tool calls | Two `LLM` spans, one per round trip. Both carry the tool definitions | Running the tool is your code. It becomes a span only if you create one. Z.ai documents `tool_choice` as `auto` only |
| A failed call | An `LLM` span with status `ERROR`, the exception type and the HTTP status in the message, and an `exception` event | Observed with a wrong key against the stand-in (shaped from Z.ai's error table) and against the proxy |
| `extra_body={"thinking": {"type": "enabled"}}` | The call is traced like any other | The field reaches Z.ai. It is not a span attribute |

</div>

Spans group under any parent span or session you create. The example app wraps its calls in one `AGENT` span and a session id so the whole run is one trace.

## What is not captured

- **`thinking` and reasoning text.** The `thinking` field travels in `extra_body`, and the instrumentor does not record it. Reasoning text in `reasoning_content`, whether in a response or a stream, is not on the span either. The span reports the response's `usage.completion_tokens` as output tokens; whether Z.ai includes reasoning tokens in that figure was not checked against a live response.
- **Finish reason.** The span does not record `finish_reason`. Z.ai documents that a stream which ends abnormally reports the cause in `finish_reason` (for example `network_error`) instead of an HTTP error. Against the stand-in, such a stream produced a span with status `OK` that shows only the text that arrived. Check `finish_reason` in your own code if truncated streams matter to you.
- **Cached tokens.** Z.ai reports `prompt_tokens_details.cached_tokens`. The span carries input, output and total tokens only.
- **The host.** The exported span carries no Z.ai hostname. Put the endpoint in your `project_name` or in your own span attribute if you need to tell Z.ai calls from other OpenAI-client calls.
- **Z.ai request ids and headers.** The `request_id` in Z.ai's response body, a `request_id` you send, and an `Accept-Language` header are not span attributes and do not become a Future AGI session id.
- **The model on streaming and failed calls, on 0.1.10.** traceAI-openai 0.1.10 leaves `gen_ai.request.model` off streaming spans and failed-call spans. [traceAI PR 249](https://github.com/future-agi/traceAI/pull/249) (open, not released) records it. The tests in the example pass on both.
- **Provider name.** `gen_ai.provider.name` is `openai` for `api.z.ai`. PR 249 adds a host-to-provider table that does not contain `api.z.ai`, so the value stays `openai` there too.
- **Cost.** The span carries no price. The local platform stored a cost of 0 for the stand-in model id and for the proxy's model id, and shows `$0.00`. Whether it prices real GLM model ids was not checked.
- **Other Z.ai APIs.** Web search, retrieval and vision tools, image and video generation, and audio were not tested. Embeddings and the Responses API were not tested either.
- **TypeScript and Java.** Only the Python client was tested. Z.ai's guide also shows the OpenAI Node and Java clients with the same base URL; those instrumentors were not run.

## Privacy

traceAI-openai follows the standard traceAI `TraceConfig` defaults: prompts, completions, tool arguments and results, and request parameters are captured unless you turn them off. Set these before the process starts, or pass the same settings to `TraceConfig`.

```bash
export FI_HIDE_INPUTS=true
export FI_HIDE_OUTPUTS=true
export FI_HIDE_LLM_INVOCATION_PARAMETERS=true
```

With those three set, the model, token counts, status and timing still arrive and the content does not. Input and output fields hold `__REDACTED__`, the request parameters attribute is absent, and a unique marker placed in the system prompt, the user prompt, the model's answer, the tool-call arguments and the tool result appeared in no stored column. With the variables unset, the same marker appeared in the prompts, answers, tool arguments and results. Content is therefore on by default. To turn it back on after hiding it, unset the variables or set them to `false`.

What the hide settings do not remove on traceAI-openai 0.1.10:

- **Tool definitions.** The name, description and JSON schema of tools you pass are still on the span.
- **Session id.** The id you set, if any, stays.
- **Error text.** The status message, such as `AuthenticationError: Error code: 401 - ...`, includes the error body Z.ai returns. The exported `exception` event also carries the exception message and a stack trace with local file paths. The local platform kept only the event's name and time and did not store the stack trace or message, but they are on the wire.

If your errors can contain sensitive text, do not rely on the hide settings for them.

## Run it yourself

The example in [`examples/providers/z-ai`](https://github.com/future-agi/docs/tree/main/examples/providers/z-ai) contains the recipe as a runnable app, a Z.ai-shaped stand-in, and tests. Its `run_e2e.sh` installs the pinned versions in a virtual environment, runs the tests, and exports to your collector.

```bash
cd examples/providers/z-ai
export FI_API_KEY="YOUR_API_KEY" FI_SECRET_KEY="YOUR_SECRET_KEY"
export FI_BASE_URL="http://localhost:4318"   # your collector, if self-hosted
./run_e2e.sh                                   # stand-in, no Z.ai account needed

ZAI_API_KEY="YOUR_ZAI_API_KEY" ZAI_MODEL="your-model" ./run_e2e.sh   # real Z.ai, may cost money
```

With `ZAI_API_KEY` set and no `ZAI_BASE_URL`, the script calls `https://api.z.ai/api/paas/v4/`. It never creates an account. Z.ai's pricing page lists some models as free of charge; check it for the model you pick.

## Troubleshooting

<div style={{ overflowX: 'auto' }}>

| Symptom | Cause and fix |
| --- | --- |
| The span says `openai`, not Z.ai | Known display limit. Look for the project and model, not the provider name |
| HTTP 401 from Z.ai | A wrong or missing key. Z.ai documents business code 1000 for a failed authentication and 1001 for a missing one, in an `error` object with `code` and `message`. Check that `ZAI_API_KEY` is a general platform key, not a Coding Plan key |
| HTTP 429 from Z.ai | Z.ai documents several 429 business codes for rate limits and usage limits, including some that name the Coding Plan. Read the `code` and `message` in the exception |
| No spans appear | Install the instrumentor with `tracer_provider=trace_provider` and use the `openai` package. Check `FI_API_KEY`, `FI_SECRET_KEY` and, if self-hosted, `FI_BASE_URL`. See [No traces appearing](/docs/observe/troubleshooting/no-traces-appearing) |
| No spans when using Z.ai's `ZaiClient` | traceAI-openai does not instrument `zai.ZaiClient`. Switch to `openai.OpenAI` |
| Calls are traced but billed differently than expected | Check the base URL. The three Coding Plan URLs above are a different product, which this page does not cover |
| `ai-evaluation is not installed, please install it to trace protect` printed at startup | Warning logged by `traceai-openai` on import. It concerns tracing Protect guardrails and did not affect chat tracing in these runs |
| `pip install` fails on Python 3.14 | traceAI-openai 0.1.10 requires Python below 3.14. Use 3.10 to 3.13 |

</div>
