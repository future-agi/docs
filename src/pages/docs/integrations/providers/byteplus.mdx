## About

BytePlus ModelArk serves an OpenAI-compatible chat API. You keep using `openai.OpenAI`, set `base_url` to the region that issued your key, and the existing [traceAI-openai](/docs/integrations/traceai/openai) instrumentor traces the call. There is no BytePlus package to install and nothing to configure on the BytePlus side.

This page is not:

- **A BytePlus export.** It traces calls your own code makes. It does not read BytePlus usage logs or billing, and it does not import history.
- **A new traceAI package.** There is no `traceai-byteplus`. The existing instrumentor handles the call, and [What is not captured](#what-is-not-captured) lists the gaps found.
- **Coding Plan setup.** Coding Plan is a different BytePlus product with a different base URL. See [Coding Plan is not this page](#coding-plan-is-not-this-page).
- **A recipe for BytePlus's own `arkruntime` SDK.** Its `Ark` client is not traced by traceAI-openai. See [What is not captured](#what-is-not-captured).

The provider name on the span reads `openai`, not BytePlus. That is a display limit of the instrumentor, not something this page can change.

## Regions

BytePlus documents two ModelArk inference regions. Both are current. They are not interchangeable.

<div style={{ overflowX: 'auto' }}>

| Region | Region ID | Base URL |
| --- | --- | --- |
| Johor, Asia Pacific | `ap-southeast-1` | `https://ark.ap-southeast.bytepluses.com/api/v3` |
| Dublin, Europe | `eu-west-1` | `https://ark.eu-west.bytepluses.com/api/v3` |

</div>

BytePlus's region page says an inference endpoint created in a region must be invoked with that region's base URL, that it cannot be called through another region's URL, and that API keys and model activation status are isolated by region. Use the URL of the region that issued your key. This page does not retry against the other region, and it does not document any other host.

The worked example below uses Asia Pacific. If your key is from Dublin, use the Europe URL from the table and change nothing else.

## Install

Install the OpenAI instrumentor and the OpenAI SDK.

```bash
pip install "traceAI-openai==0.1.10" "fi-instrumentation-otel==1.1.0" "openai==3.31.0"
```

## Trace a chat completion

Set the three keys. The BytePlus key goes to the OpenAI client. The Future AGI keys go to `register()`. Neither key belongs on a span.

```bash
export ARK_API_KEY="YOUR_BYTEPLUS_ARK_API_KEY"
export FI_API_KEY="YOUR_API_KEY"
export FI_SECRET_KEY="YOUR_SECRET_KEY"
```

Then register the tracer, install the instrumentor, and build the client. Replace the model with a Model ID or endpoint ID from your ModelArk console.

```python
import os

from fi_instrumentation import register
from fi_instrumentation.fi_types import ProjectType
from openai import OpenAI
from traceai_openai import OpenAIInstrumentor

trace_provider = register(
    project_type=ProjectType.OBSERVE,
    project_name="my-chatbot",
)
OpenAIInstrumentor().instrument(tracer_provider=trace_provider)

client = OpenAI(
    api_key=os.environ["ARK_API_KEY"],
    base_url="https://ark.ap-southeast.bytepluses.com/api/v3",
)

response = client.chat.completions.create(
    model="your-model-or-endpoint-id",
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
print(response.choices[0].message.content)
```

<div style={{ overflowX: 'auto' }}>

| Piece | Value |
| --- | --- |
| Client | `openai.OpenAI` from the `openai` package. Not `arkruntime.Ark`. |
| Base URL | `https://ark.ap-southeast.bytepluses.com/api/v3` for Asia Pacific, `https://ark.eu-west.bytepluses.com/api/v3` for Europe |
| Auth | `Authorization: Bearer <ARK_API_KEY>`, which the OpenAI client sends for `api_key` |
| Model | The Model ID or endpoint ID from your console. BytePlus's own examples use dated ids such as `seed-2-0-lite-260228`; do not copy one without checking it is available to your key |
| Project | `project_name` in `register()`. The instrumentor does not set it |
| Self-hosted Future AGI | Also export `FI_BASE_URL` with your collector URL |

</div>

Build the client after `register()` and `instrument()`, as above. BytePlus still receives your prompt: tracing sends a copy to Future AGI and does not change what the API sees.

## What you get

Each call below produced the spans shown. "Stand-in" means the ModelArk-shaped local server; "real model" means the local OpenAI-compatible proxy running a real model. Neither is BytePlus.

<div style={{ overflowX: 'auto' }}>

| Call | What lands in Observe | Notes |
| --- | --- | --- |
| `chat.completions.create` | One `LLM` span with the model, input and output messages, and input, output and total tokens | The model on a non-streaming span is the `model` field of the response body, not the id you sent. When the stand-in answered with a different model id, the span showed the response's id. The recorded response-id behavior is from the stand-in, not a ModelArk service response |
| `stream=True` | One `LLM` span with a first-token event | Token counts are present only when you pass `stream_options={"include_usage": True}`, which the ModelArk Chat API documents. Without it the span has no token counts |
| Tool calls | Two `LLM` spans, one per round trip. The first carries the tool definitions | Running the tool is your code. It becomes a span only if you create one |
| A failed call | An `LLM` span with status `ERROR`, the exception type and the HTTP status in the message, and an `exception` event | Observed with a wrong key against the stand-in and the proxy |
| `extra_body={"thinking": {"type": "enabled"}}` | The call is traced like any other | The field reaches BytePlus. It is not a span attribute |

</div>

Spans group under any parent span or session you create. The example app wraps its calls in one `AGENT` span and a session id so the whole run is one trace.

## What is not captured

- **`thinking` and reasoning text.** The `thinking` field travels in `extra_body`, and the instrumentor does not record it. Reasoning text in `reasoning_content` is not on the span either. The span reports the response's `usage.completion_tokens` as output tokens; vendor reasoning-token accounting is outside the recorded evidence. The call is still traced.
- **The region or host.** The exported span carries no BytePlus hostname and no region. You cannot filter by region from the span. Put the region in your `project_name` or in your own span attribute if you need it.
- **BytePlus request ids and headers.** A `X-Client-Request-Id` header you send is a BytePlus correlation header. It does not become a Future AGI session id.
- **The model on streaming and failed calls, on 0.1.10.** traceAI-openai 0.1.10 leaves `gen_ai.request.model` off streaming spans and failed-call spans. [traceAI PR 249](https://github.com/future-agi/traceAI/pull/249) (merged to `dev` on 2026-10-28; absent from the published 0.1.10 package as of 2026-10-29) records it. The tests in the example pass on both.
- **Provider name.** `gen_ai.provider.name` is `openai` for both BytePlus hosts. PR 249 adds a host-to-provider table that does not contain either BytePlus host, so the value stays `openai` there too.
- **Cost.** The span carries no price. The local platform stored a cost of 0 for the stand-in model id and for the proxy's model id, and shows `$0.00`. The recorded evidence contains no real ModelArk pricing result.
- **`arkruntime.Ark`.** BytePlus's own SDK (arkruntime 0.13.0, checked against the stand-in) is not a subclass of `openai.OpenAI`, and traceAI-openai produced no spans for it while the stock `openai.OpenAI` client produced one. Use the `openai` package, as on this page.
- **Other ModelArk APIs.** The Responses API (`/api/v3/responses`), embeddings, multimodal embeddings, image, video and 3D generation and context caching are outside this recipe's supported API scope. The multimodal embeddings endpoint does not have the OpenAI request shape, so `client.embeddings.create` does not call it.
- **Language scope.** This recipe covers the Python OpenAI client only; it makes no TypeScript integration claim.

## Privacy

traceAI-openai follows the standard traceAI `TraceConfig` defaults: prompts, completions, tool arguments and results, and request parameters are captured unless you turn them off. Set these before the process starts, or pass the same settings to `TraceConfig`.

```bash
export FI_HIDE_INPUTS=true
export FI_HIDE_OUTPUTS=true
export FI_HIDE_LLM_INVOCATION_PARAMETERS=true
```

With those three set, the model, token counts, status and timing still arrive and the content does not. Input and output fields hold `__REDACTED__`, the request parameters attribute is absent, and a unique marker placed in the system prompt, the user prompt, the model's answer, the tool-call arguments and the tool result appeared in no stored column. With the variables unset, the same marker appeared in the prompts, answers, tool arguments and results. Content is therefore on by default. To turn it back on after hiding it, unset the variables or set them to `false`.

What the hide settings do not remove on traceAI-openai 0.1.10:

- **Tool definitions.** The name, description and JSON schema of tools you pass are still on the span.
- **Session id.** The id you set, if any, stays.
- **Error text.** The status message, such as `AuthenticationError: Error code: 401 - ...`, includes the BytePlus error body and its request id. The exported `exception` event also carries the exception message and a stack trace with local file paths. The platform did not keep the stack trace in its span store in the runs documented here, but it is on the wire.

If your errors can contain sensitive text, do not rely on the hide settings for them.

## Run it yourself

The example in [`examples/providers/byteplus`](https://github.com/future-agi/docs/tree/main/examples/providers/byteplus) contains the recipe as a runnable app, a ModelArk-shaped stand-in, and tests. Its `run_e2e.sh` installs the pinned versions in a virtual environment, runs the tests, and exports to your collector.

```bash
cd examples/providers/byteplus
export FI_API_KEY="YOUR_API_KEY" FI_SECRET_KEY="YOUR_SECRET_KEY"
export FI_BASE_URL="http://localhost:4318"   # your collector, if self-hosted
./run_e2e.sh                                   # stand-in, no BytePlus account needed

ARK_API_KEY="YOUR_BYTEPLUS_ARK_API_KEY" ARK_MODEL="your-model-or-endpoint-id" ./run_e2e.sh   # real BytePlus, may cost money
```

With `ARK_API_KEY` set, the script calls BytePlus for `ARK_REGION` (`ap` by default, or `eu`). It never creates an account.

## Troubleshooting

<div style={{ overflowX: 'auto' }}>

| Symptom | Cause and fix |
| --- | --- |
| The span says `openai`, not BytePlus | Known display limit. Look for the project and model, not the provider name |
| HTTP 401 from BytePlus | A wrong key, or a key from the other region. BytePlus says API keys and endpoints are isolated by region, so use the base URL of the region that issued the key. Cross-region error status and body are outside this recipe's recorded evidence |
| No spans appear | Install the instrumentor with `tracer_provider=trace_provider` and use the `openai` package. Check `FI_API_KEY`, `FI_SECRET_KEY` and, if self-hosted, `FI_BASE_URL`. See [No traces appearing](/docs/observe/troubleshooting/no-traces-appearing) |
| No spans when using BytePlus's `Ark` client | traceAI-openai does not instrument `arkruntime.Ark`. Switch to `openai.OpenAI` |
| A streaming span has no token counts | Pass `stream_options={"include_usage": True}` |
| Bills do not match traces | Check the base URL. A base URL with `/api/coding` is the Coding Plan, which this page does not cover |
| `ai-evaluation is not installed, please install it to trace protect` printed at startup | Warning logged by `traceai-openai` on import. It concerns tracing Protect guardrails and did not affect chat tracing in these runs |
| `pip install` fails on Python 3.14 | traceAI-openai 0.1.10 requires Python below 3.14. Use 3.10 to 3.13 |

</div>
