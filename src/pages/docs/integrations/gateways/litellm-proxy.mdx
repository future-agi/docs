## About

LiteLLM Proxy is a server: your applications call it over HTTP and it calls the model providers. Its OpenTelemetry callback can export one trace per request over OTLP, so the proxy itself can send traces to Future AGI. Nothing is installed in your applications and there is no Future AGI package inside the proxy. You set environment variables and a callback in the proxy's config.

This is not the same as the existing [LiteLLM (traceAI) page](/docs/integrations/traceai/litellm). `traceAI-litellm` instruments the LiteLLM Python SDK **inside your own application process**. It does nothing for a LiteLLM Proxy server, which is a different process, and installing it on the proxy host does not trace the proxy. Use the traceAI page if your code calls `litellm.completion(...)` directly. Use this page if you run the proxy.

This page does not add a package, change `traceAI-litellm`, or use LiteLLM's Langfuse, LangSmith or other callbacks. It also does not cover the proxy's spend logs, virtual-key admin or guardrail product.

## 1. Pick the callback mode

LiteLLM has two OpenTelemetry implementations for the proxy. Choose one. Both were run for this page against Future AGI.

| | v2 (use this) | v1 (also works) |
| --- | --- | --- |
| Switch | `LITELLM_OTEL_V2=true` plus `callbacks: ["otel"]` | `callbacks: ["otel"]` only |
| Spans per request | 3: the HTTP request, `auth`, and `chat <model>` | 7 or more: `Received Proxy Server Request`, `auth`, `proxy_pre_call`, two `router`, `litellm_request`, `self` |
| The LLM call in Observe | Type **LLM**, named `chat <model group>`, with model, provider and tokens | Type **unknown**, named `litellm_request`, with model and tokens |
| `model` is | the model group your caller sent (`demo-model`) | the provider model the proxy called (`mock-model`) |
| Health checks (`/health/liveliness`) | not traced | can create traces of their own |
| Extra request metadata with content off | caller address and user agent on the HTTP span | caller address, user agent and inbound request headers on the LLM span |

v2 is what the rest of this page configures, because Future AGI types its LLM span as an LLM call and it adds the fewest unrelated spans. v1 is covered in [The v1 callback](#the-v1-callback). Do not turn both on.

## 2. Install

The official image already contains everything:

```bash
docker pull ghcr.io/berriai/litellm:v1.105.1
```

With `pip`, `litellm[proxy]` alone does **not** install the OpenTelemetry SDK or the OTLP exporter. Without them the proxy starts normally and logs `[Non-Blocking Error] Error initializing custom logger: No module named 'opentelemetry.sdk'`, and no traces are sent. Install them too (Python 3.10 to 3.14 is supported by LiteLLM; 3.12 was tested):

```bash
pip install "litellm[proxy]==1.105.1" opentelemetry-sdk opentelemetry-exporter-otlp opentelemetry-instrumentation-fastapi
```

`opentelemetry-instrumentation-fastapi` is what produces the HTTP request span. The tested pins are in [requirements.txt](https://github.com/future-agi/docs/blob/main/examples/gateways/litellm-proxy/requirements.txt).

Do **not** install `traceAI-litellm` for this. It does not instrument the proxy.

## 3. Configure the proxy

`config.yaml` only names the callback. Everything that points at Future AGI is an environment variable, so no key is ever in the file:

```yaml
model_list:
  - model_name: demo-model                       # the name callers send to the proxy
    litellm_params:
      model: openai/gpt-4o-mini                  # your provider model
      api_key: os.environ/OPENAI_API_KEY

litellm_settings:
  callbacks: ["otel"]                            # the proxy's OpenTelemetry callback

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY      # must start with sk-
```

Set these in the proxy's environment (a Docker `--env-file`, Kubernetes `env`, a systemd unit):

```bash
LITELLM_OTEL_V2=true
OTEL_EXPORTER=otlp_http
OTEL_ENDPOINT=http://<your-collector-host>:4318/v1/traces
OTEL_HEADERS=X-Api-Key=<your-api-key>,X-Secret-Key=<your-secret-key>
OTEL_RESOURCE_ATTRIBUTES=project_name=litellm-proxy,project_type=observe
OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT
```

| Variable | What it does |
| --- | --- |
| `LITELLM_OTEL_V2` | Turns on the v2 tracing. |
| `OTEL_EXPORTER` | `otlp_http`. Future AGI's trace ingest is OTLP over HTTP. |
| `OTEL_ENDPOINT` | The full traces URL. Self-hosted: `http://<host>:4318/v1/traces`. The hosted Future AGI URL in the SDK docs is `https://api.futureagi.com/tracer/v1/traces`; that one was not exercised for this page. LiteLLM keeps a path that already ends in `/v1/traces`. |
| `OTEL_HEADERS` | The two Future AGI key headers, comma separated, in this exact form. See [Header rules](#header-rules). |
| `OTEL_RESOURCE_ATTRIBUTES` | **Required.** `project_name` decides the Observe project. `project_type=observe` is what the Future AGI SDK sets too; it is also the default. |
| `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` | `NO_CONTENT` (also the default) keeps prompts and responses out. See [Privacy](#privacy). |

Leave `LITELLM_OTEL_INTEGRATION_ENABLE_METRICS`, `LITELLM_OTEL_INTEGRATION_ENABLE_EVENTS` and `OTEL_EXPORTER_OTLP_COMPRESSION` unset. Future AGI's collector only serves traces and rejects compressed bodies. With metrics on, the proxy posts to `/v1/metrics` every few seconds and every one of those gets a 404.

<Note>
`OTEL_RESOURCE_ATTRIBUTES` is not listed on either LiteLLM page. It works because the proxy builds its OpenTelemetry resource with the standard OpenTelemetry environment detector (verified on 1.105.1 for v1 and v2: the attribute is on every exported resource). If a LiteLLM release stops reading it, the symptom is the HTTP 400 below, not silent loss.
</Note>

### Header rules

Put the two key headers in `OTEL_HEADERS` as `X-Api-Key=...,X-Secret-Key=...`. How LiteLLM reads that string depends on the callback:

| | v2 | v1 |
| --- | --- | --- |
| Parser | The OpenTelemetry SDK's own | LiteLLM's own: split on every comma, then on the first `=` |
| Space after a comma | Ignored | Becomes part of the header name (` X-Secret-Key`), which breaks the header |
| `%20` in a value | Decoded to a space | Sent literally |
| Comma inside a value | The value is cut at the comma and the rest is skipped | Raises an error when the callback starts, and the proxy runs without tracing |
| Header names | Sent in lower case (`x-api-key`) | As written |

Write the string with no spaces and no commas inside a value and it behaves the same on both. Future AGI keys are plain strings, so this holds for them. Do not use `Authorization=Bearer ...`: the collector answers HTTP 401 to a Bearer token, and LiteLLM's own Traceloop example (`Bearer%20<key>`) would send a literal `%20` on v1.

## 4. Run it and look at the trace

Start the proxy and send one request:

```bash
docker run --env-file proxy.env -v "$PWD/config.yaml:/app/config.yaml:ro" -p 4000:4000 \
  ghcr.io/berriai/litellm:v1.105.1 --config /app/config.yaml --port 4000

curl -s http://localhost:4000/v1/chat/completions \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"model":"demo-model","messages":[{"role":"user","content":"Say hello"}]}'
```

A Docker `--env-file` takes values literally, so do not put quotes around them. The first container start can take a few minutes on a busy machine. The proxy batches spans and sends them within a few seconds. `proxy.env` is the variable block above, one `NAME=value` per line. Open **Observe** and select the project (`litellm-proxy` above). The project is created by the first batch; you do not need to create it first.

## What you see in Observe

Each request through the proxy is one trace. With the v2 callback it has three spans:

```
POST /v1/chat/completions      type unknown   the HTTP request to the proxy
├─ auth /v1/chat/completions   type unknown   the proxy key check
└─ chat demo-model             type LLM       the model call: model, provider, tokens, finish reason
```

Only the `chat <model>` span is typed as an LLM call. The other two are plain spans in the same trace. They are not model calls, so ignore them when you count LLM calls.

| Signal | Where it is | Notes |
| --- | --- | --- |
| Model | `chat` span, `gen_ai.request.model` | The model group your caller sent (`demo-model`), not the provider model. The provider model is the attribute `litellm.provider.model` (`openai/gpt-6-luna`). |
| Provider | `gen_ai.provider.name` | `openai` for any OpenAI-compatible upstream. |
| Tokens | `gen_ai.usage.input_tokens`, `output_tokens`, `total_tokens` | Present on successful calls, streamed or not. |
| Latency | every span | Streams also carry `gen_ai.response.time_to_first_chunk`. |
| Errors | `chat` and request spans | Status ERROR, `error.type`, and the message. See [Errors](#errors). |
| Tools | `gen_ai.tool.<n>.name`, `description`, `parameters` | The tool **definitions** you send. Arguments and results appear only with content capture on. |
| Cost | `litellm.cost.total`, `litellm.cost.input`, `litellm.cost.output` | LiteLLM's own figure in USD, kept as a span attribute (`0.0000756` for one 311-token request in the test, `0.0` for a model LiteLLM has no price for). Observe's cost column stays 0, so this figure is not in Observe's cost totals. |
| Who called | `litellm.api_key.hash`, `litellm.metadata.user_api_key_user_id` | A hash of the proxy key, never the key. The master key shows as the literal `litellm_proxy_master_key`. |

Not captured: sessions (nothing sets a session id, so the Sessions tab stays empty) and the proxy's spend logs.

## Privacy

With `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT` (the default), no prompt, response, tool argument or tool result leaves the proxy. Future AGI's `FI_HIDE_*` settings do not apply on this path, because nothing from the Future AGI SDK runs in the proxy.

Checked on the v2 callback: a unique marker in the prompt, the tool result, a cookie, a custom header and an `X-Api-Key` header, then a scan of every stored column of every ClickHouse table that holds project data:

| Checked | Result with content off |
| --- | --- |
| Prompt, response, tool arguments and tool results | Not stored. The marker did not appear in any column. |
| Cookie, custom header and `X-Api-Key` header values, `X-Forwarded-For` | Not stored. |
| Proxy master key, a rejected key, `Authorization` header | Not stored. A hash only. |
| Tool definitions (name, description, parameter schema) | **Stored.** They are your configuration, not request data, but check the descriptions for anything sensitive. |
| The username and hostname of the machine running the proxy | Not stored. The stack-trace paths below are the exception. |
| Provider error text | **Stored.** `error.message` and the span status message. |
| Python stack traces | **Stored.** `litellm.provider.error.stack_trace` and the `exception` event. They contain file paths inside the proxy image, for example `/app/.venv/lib/python3.13/site-packages/...`. |
| Caller address and user agent | **Stored** on the request span: `net.peer.ip`, `net.peer.port`, `http.user_agent`. |
| The proxy's own address and the upstream host and port | **Stored**: `http.host`, `http.url`, `http.server_name`, `server.address`, `server.port`. |

The last four rows are LiteLLM's own attributes. The proxy has no setting that turns them off. If provider error text, stack traces or addresses must not reach Future AGI, put an OpenTelemetry Collector between the proxy and Future AGI that removes them.

### Remove error text, stack traces and addresses

[collector/otelcol-scrub.yaml](https://github.com/future-agi/docs/blob/main/examples/gateways/litellm-proxy/collector/otelcol-scrub.yaml) is a collector config that deletes the attributes in the last four rows, empties the span status message and sends the rest to Future AGI with your two keys. It also sets `service.telemetry.metrics.level: none` and `compression: none`, which Future AGI's collector needs. Tested with `otel/opentelemetry-collector-contrib:0.162.0`.

```bash
docker run -d --name otelcol -p 4318:4318 \
  -v "$PWD/otelcol-scrub.yaml:/etc/otelcol/config.yaml:ro" \
  -e FI_TRACES_ENDPOINT=https://api.futureagi.com/tracer/v1/traces \
  -e FI_API_KEY=YOUR_API_KEY -e FI_SECRET_KEY=YOUR_SECRET_KEY \
  otel/opentelemetry-collector-contrib:0.162.0 --config /etc/otelcol/config.yaml
```

Then point the proxy at the collector. The collector holds the keys, so the proxy does not need `OTEL_HEADERS`:

```bash
OTEL_ENDPOINT=http://<collector-host>:4318/v1/traces
OTEL_RESOURCE_ATTRIBUTES=project_name=litellm-proxy,project_type=observe
```

The scrubbed trace keeps the structure, model, tokens, status and `error.type`; it loses the error message, the stack trace and the addresses. Checked the same way as above, with the proxy's HTTP 500 text carrying a unique marker: after the collector, the error text, the `/app/.venv/...` paths, the caller address, the user agent and both hosts were in no stored column. The `exception` event keeps its name but not its message or stack. The config was written and tested for the v2 callback.

### Turn content capture on

Set the variable to `SPAN_ONLY` and restart the proxy. The messages are exported as the span attributes `gen_ai.input.messages` and `gen_ai.output.messages`, JSON text that includes tool-call arguments (in the output) and tool results (in the input). They are exported to Future AGI exactly as the proxy sees them, so only do this for data you may send.

```bash
OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=SPAN_ONLY
```

In the tested Future AGI the two attributes are stored with the span's attributes, but the span's **Input** and **Output** panels stay empty, because Future AGI does not map these two keys to them today. `SPAN_AND_EVENT` gave the same span attributes and, without `LITELLM_OTEL_INTEGRATION_ENABLE_EVENTS`, sent no log events. `EVENT_ONLY` moves the messages to log events, and Future AGI's collector serves traces only, so it was not tried.

## Errors

A failed model call sets status ERROR on the `chat` span and on the request span, with `error.type` (`InternalServerError` when the upstream is unreachable or returns 5xx) and the provider's message. A request the proxy rejects before the model call fails the `auth` span instead. The caller got HTTP 500 for the first two rows and HTTP 400 for the third:

| Request | Result in Observe |
| --- | --- |
| Upstream refuses the connection | `chat <model>` ERROR with `litellm.InternalServerError ... Connection error`, and the request span ERROR. |
| Upstream returns HTTP 500 | The same two spans, with the provider's text in the message. |
| A wrong proxy key | The `auth` span and the request span are ERROR; there is no `chat` span, because no model call happened. With no database configured the message is `ProxyException: No connected db.`. |

The proxy retries a failed call before it gives up. The retries are not separate spans in v2; the `chat` span covers them.

## Join a caller's trace

Send a W3C `traceparent` header and the proxy's request span becomes a child of that trace, so the proxy call shows up under your application's trace in Observe. The caller does not need traceAI. Verified on v2 and v1: the exported root span carried the caller's span id as its parent, and the trace id was the caller's.

Do not use `OTEL_IGNORE_CONTEXT_PROPAGATION` to stop that. Only the v1 code reads it. On 1.105.1 it does nothing on v2. On v1 the request span still joined the caller's trace, and the LLM call (`litellm_request`) moved into a trace of its own, away from its request. No setting on either callback makes every proxy request its own root. If you need that, remove the `traceparent` header before it reaches the proxy (not tested).

## The v1 callback

v1 is `callbacks: ["otel"]` without `LITELLM_OTEL_V2`. It also exports to Future AGI with the same endpoint, headers and `project_name` variables, so use it only if you cannot run v2. Differences seen on 1.105.1:

- More spans. The official image exports 7 per request (`Received Proxy Server Request`, `auth`, `proxy_pre_call`, two `router`, `litellm_request`, `self`). A `pip` install with the FastAPI instrumentor adds the HTTP request span and FastAPI's own internals: 11 in the test. Observe types none of them as an LLM call; `litellm_request` carries the model and tokens.
- `gen_ai.request.model` is the provider model, and the model group is in `litellm.model_group`.
- Health checks can create traces of their own.
- A failed request adds a `Failed Proxy Server Request` span.
- It exports more request metadata with content off: `metadata.requester_ip_address`, `metadata.user_agent`, `hidden_params` (which includes the upstream `api_base`) and the inbound request headers **with their values** in `metadata.requester_metadata` and `metadata.requester_custom_headers`. In the test a custom header (`X-Custom-Token`) and `X-Forwarded-For` reached Future AGI in clear. `Cookie` was replaced by `***REDACTED***`, and a client `X-Api-Key` header and `Authorization` were not exported. v2 exported none of these headers. This is the main reason to prefer v2.
- The scrub config does not remove these v1 attributes.

Header parsing differs too; see [Header rules](#header-rules).

## Operational spans

LiteLLM can add spans for its own internals. In the tests the v2 callback added only `auth`, and v1 added `proxy_pre_call`, `router` and `self`. Spans for Redis and Postgres were **not** exercised, because the test proxy ran without either. If you run them, expect more spans of type unknown in the same trace as the LLM call.

## Limits and what was not tested

- The hosted Future AGI URL was not called. The self-hosted collector on `/v1/traces` was.
- Not run: LiteLLM with Postgres or Redis, virtual keys (so the hash of a virtual key is unchecked, and so is `metadata.user_api_key_user_email`, which v1 exports and which was empty here; the master key and a rejected key were checked), guardrails, per-team callbacks, `otlp_grpc`, several proxy replicas and Enterprise features.
- Not tested: LiteLLM 1.106.0rc4 (a release candidate) and any release older than 1.105.1. The v2 callback is opt-in and newer than v1, so pin the version and re-check the attribute names when you upgrade.
- Future AGI's collector serves traces only. The proxy's metrics and log events are off by default and must stay off.
- Observe's cost column and the span Input and Output panels are not filled from this data; see the tables above.

## Troubleshooting

| What you see | What it means |
| --- | --- |
| The proxy runs and nothing arrives, and its log has `Error initializing custom logger: No module named 'opentelemetry.sdk'` | You installed `litellm[proxy]` without the OpenTelemetry packages. See [Install](#2-install). |
| The proxy log has `Failed to export ... code: 400` and `ResourceSpan(s) have no project_name` | The batch has no `project_name`. Check `OTEL_RESOURCE_ATTRIBUTES` is set in the proxy's own environment (not your shell). |
| `Failed to export ... code: 401` | Wrong keys, or a Bearer header. Use `X-Api-Key` and `X-Secret-Key`. |
| Repeated export errors for metrics (`/v1/metrics` answers 404 on Future AGI) | `LITELLM_OTEL_INTEGRATION_ENABLE_METRICS` is on. Unset it. |
| Requests work but no trace appears | Exporter errors never fail the caller's request. Read the proxy log for `Failed to export`, then wait: the first container start takes minutes and spans are batched for a few seconds. |
| Traces appear in a different project | `project_name` is spelled differently from the project you are looking at. The first batch creates the project. |
| Prompts and responses are missing | Content capture is off, which is the default. See [Turn content capture on](#turn-content-capture-on). |
| You installed `traceAI-litellm` and the proxy still has no spans | That package traces the LiteLLM SDK inside your application. It does not trace a proxy. |
