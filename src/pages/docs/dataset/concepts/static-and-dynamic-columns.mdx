## Where a column's values come from

A [column](/docs/dataset/concepts/understanding-datasets) holds one thing: where its values come from. Every column is either **static** or **dynamic**, and that's a property of the column itself, not of any single row inside it.

A **static column** holds values you supply. You type them in, paste them, or set them through the SDK, and a cell only changes when you go back and edit it.

A **dynamic column** doesn't hold values you typed, it holds a producer. The column records a `source`, naming what kind of thing fills it (running a prompt, running an evaluation, calling an API, and more), and a `source_id` pointing at the specific instance behind it, such as one RunPrompter or one UserEvalMetric. Every cell in the column is whatever that producer computed for that row, not something you set by hand.

Take a dataset with four columns:

| user_query | expected_answer | model_response | is_correct |
|---|---|---|---|
| What is the capital of France? | Paris | Paris | true |
| Who wrote Hamlet? | Shakespeare | William Shakespeare | true |

`user_query` and `expected_answer` are static, you wrote them in. `model_response` is dynamic: a RunPrompter behind the column answers `user_query` for every row. `is_correct` is dynamic too: a UserEvalMetric behind it compares `model_response` against `expected_answer`. Looking at the table alone doesn't tell you which is which, only the column itself knows.

A static column's cells are just the values you set, there's nothing else pointing at them. A dynamic column's cells trace back through `source_id` to a single producer that fills every row it's responsible for.

## What follows from having a producer behind the column

Two consequences fall directly out of that difference, and both are the kind a reader hits by surprise.

**It carries a status while the producer runs.** A static column has no run to track, so it has no status to show. A dynamic column does: while its producer is working, the column sits in a running state, and if the producer fails, the column shows failed. That status is the tell for whether you're looking at a value you can trust yet.

**It can be re-run, and every row changes at once.** The producer behind a dynamic column doesn't disappear after the first run. Change the prompt, switch the model, fix the eval config, then re-run the column, and every cell it owns recomputes together. Editing a static column, by contrast, is you overwriting one cell at a time; nothing else moves.

**Deleting it takes the producer with it.** A dynamic column isn't just the column, it's the column plus the producer generating it. Delete the column and its producer goes too, along with anything else that was derived from it. Deleting a static column removes only the column and the values sitting in it, there's no producer behind it to clean up.

## Why it matters

Before you touch a column, it's worth knowing which kind you're looking at. Editing what looks like a normal cell in a dynamic column doesn't stick, the next run overwrites it. And deleting a column that feeds an eval or another dynamic column doesn't just remove one column, it takes its producer and everything downstream of it with it.
