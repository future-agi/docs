title: "Run an experiment"
description: "Set up an experiment, run it across your dataset, and use Choose winner to pick the best configuration."

An **experiment** runs every [prompt or agent](/docs/prompt) and model combination you set up against the same [dataset](/docs/dataset/concepts/understanding-datasets), scored by the [evals](/docs/evaluation) you attach, so you can compare configurations side by side instead of testing them one at a time.

## The experiment grid

One experiment lays your dataset's rows against every configuration you add. A **configuration** pairs one prompt or agent with one model, so attaching three models to the same prompt gives you three configurations, one column each. Every eval you attach scores every configuration against the same rows, which is what makes the columns comparable.

## Build the experiment

Click **New experiment** on the dataset to open the creation flow. The current default wizard has four steps: **Configuration → Data → Evaluations → Review & run**.

<Steps>
  <Step title="Configuration">
    Name the experiment. New experiments in the experiment wizard are **LLM-only**; **TTS**, **STT**, and **Image** are not choices for a fresh experiment.

    Add the prompts or agents you want to compare and select a saved version of each. Attach a model to each prompt. Every prompt-model pair becomes its own configuration column; an agent uses its saved version. LLM experiments can mix prompts and agents in the same run.
  </Step>
  <Step title="Data">
    Check the dataset rows the experiment uses. **All rows** is selected by default. To run a subset, select one or more split chips. Multiple splits use their **union**: a row is included if it belongs to any selected split, not only if it belongs to all of them. Clear the split selection to return to **All rows**. See [Use splits](/docs/dataset/guides/use-splits) to organize rows into reusable subsets.

    Map every required prompt or agent input variable to a dataset column and check the sample values. Unmapped inputs block **Continue** and the final run action. Select an **Expected answers column** if your evaluations need a reference answer.

    For REST experiment creation, `split_ids` is an optional, nonempty list of up to 100 distinct split UUIDs from this dataset. A selection with no live matching rows is rejected. To run all rows, omit `split_ids`; do not send an empty list.
  </Step>
  <Step title="Evaluations">
    Add at least one evaluation to score the configurations, then continue to review. Preselected dataset defaults count toward this requirement.

    To reuse evaluations across new experiments, open the dataset's evaluation drawer and enable **Use in new experiments** for the evaluations you want. This switch requires dataset edit access. Enabled evaluations are preselected when you create an experiment on that dataset and marked **Default** in this step.

    The switch controls preselection for new experiments only; it does not change existing experiment configurations. Review the selected evaluations before running.
  </Step>
  <Step title="Review & run">
    Check the runs, data, and evaluations in the summary. Resolve any issues reported by the earlier steps, then click **Run experiment** to start the configured prompt and agent runs.
  </Step>
</Steps>

The configurations run against the dataset data, with each output scored by your evals as it comes in.

<Note>
An existing TTS or STT experiment retains its selected type. New experiments use the LLM-only flow above.
</Note>

<Note>
An eval you add after the run sits queued for a few seconds before it starts scoring.
</Note>

## Stop and rerun

Each experiment stops and reruns independently. Stop a running one without touching the others in the dataset. Select more than one experiment at a time to rerun or delete them together.

Choose the action that matches how you want to iterate:

| Action | What it does |
| --- | --- |
| **Rerun Experiment** | Runs the whole experiment again without setting it up again. This overwrites its existing results. |
| **Edit and rerun** | Opens the existing configuration for editing and reruns changed outputs. Use it to change the experiment, not to preserve a separate copy of each edited variant. |
| **Re-run with changes** | Adds one new prompt variant on the same dataset snapshot while keeping earlier variants and their results. |

### Add a variant without replacing earlier results

After the experiment stops running, click **Re-run with changes**:

1. Select an **Original variant** to start from.
2. Enter a **Variant name** and choose the **Model**, **Prompt**, and **Published version**.
3. Change at least one of the model, prompt, or published version. Renaming the variant alone does not enable the run action.
4. Click **Run new variant**.

The new variant is appended to the same experiment for comparison. This action supports prompt variants, not agent variants.

For REST, send `PUT /model-hub/experiments/v2/{experiment_id}/` with `append_only: true` and exactly one new `prompt_config` entry. Do not include an existing configuration `id` or combine this request with other experiment edits. Replace the prompt and version placeholders below with the selected prompt's UUID and its published version's UUID:

```json
{
  "append_only": true,
  "prompt_config": [
    {
      "name": "revised-prompt",
      "prompt_id": "<prompt-uuid>",
      "prompt_version": "<published-version-uuid>",
      "model": "gpt-4o"
    }
  ]
}
```

## Choose a winner

The experiment summary already lists every configuration. Once every configuration has a score, click **Choose winner** to open Winner Settings, where you set the importance of Average Response Time, Completion tokens, Total tokens, and each eval. Click **Save & Run** and the summary marks the winning configuration.

## Tips

- **Failed-cell rerun**: when transient failures such as rate limits or network errors leave a cell errored, open **Data** and use the rerun control on that experiment output or evaluation cell. This retries the failed cell without rerunning successful rows. The column header does not offer a column-level rerun action.

  The cell action sends `POST /model-hub/experiments/v2/{experiment_id}/rerun-cells/` with `cells: [{column_id, row_id}]` and `failed_only: true`. The REST endpoint also accepts broader `source_ids` requests with `failed_only`; those are API operations, not a column-menu action in the UI.
