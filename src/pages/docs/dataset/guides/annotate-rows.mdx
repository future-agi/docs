---
title: "Annotate rows"
description: "Attach human labels to dataset rows to grade output or build training data"
---

Annotation puts a human judgment on a row: someone reads what a column holds and records a verdict against it, whether that's a sentiment tag, a 1–5 score, or a free-form correction. You set up what's being judged and who judges it once, then annotators work through the rows.

## Create an annotation view

An **annotation view** is what an annotator opens to work through a dataset. It fixes which columns they see for context and which column holds what they're judging. From a dataset's **Data** tab, create a new view and name it for what it collects, like "Sentiment labels" or "Fact check ratings". You'll wire it up in the next few steps.

## Define a label and its type

A **label** is the thing an annotator fills in, and its type decides what filling it in looks like:

- **Categorical**: pick one of a fixed set of options, e.g. Positive, Negative, Neutral
- **Numeric**: a value on a scale, e.g. 1–5
- **Text**: a free-form note or a corrected version of the response
- **Star**: a 1–5 star rating
- **Thumbs up/down**: a pass/fail call

Create the label once and reuse it across any view that's judging the same thing, so ratings stay comparable across annotators and rows.

## Wire the fields

Inside the view, connect three things: the **static fields**, the columns an annotator reads for context, like the original question or a reference answer; the **response field**, the column holding the output actually being judged, like a model response; and the label you just defined. Save the view once all three are set, and it's ready to hand to annotators.

## Assign annotators

Add the workspace members who'll do the labeling to the view. Only the annotators you assign see this view when they go looking for annotation work, so a view for fact-checking and a view for sentiment can go to different people without either seeing the other's queue.

## Review and edit annotations

Open the view and step through the dataset's rows, filling in the label on each one. An annotation is stored on the cell it labels, as annotation metadata alongside the cell's own value, so who annotated a row and whether it's been verified travels with that exact row and column, not a separate record you have to go find. Click an existing annotation to change it, and if you need to clear a mistake instead, select it and delete it.

The label's values also live in the grid as their own column, and Future AGI stamps it with the `annotation_label` source, the same way a Run Prompt or an eval result gets its own producer recorded on a [dynamic column](/docs/dataset/concepts/static-and-dynamic-columns). Every cell in that column holds whatever's been annotated for that row so far.

<Note>
This page covers annotating rows inside one dataset. For multi-annotator campaigns across traces, spans, sessions, and simulations, with progress tracking and agreement metrics, that's [Annotation Queues](/docs/annotations), not this workflow.
</Note>
