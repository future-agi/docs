## About

This guide runs a deterministic two-step workflow outside Future AGI, uploads its results, and compares a baseline with a candidate. Replace the `task` function with your LLM call, retrieval pipeline, tool loop, or multi-agent application. The server stores the case, trial, output, score, and trace references; it does not execute the task.

<Note>
  Draft tutorial for the external-run API. It needs a deployment containing snapshot creation and external result ingestion, an existing writable dataset, and an evaluator metric on that dataset. It uses no model and does not establish hosted, Observe, browser, or release-gate qualification.
</Note>

## Before you start

Set these environment variables:

```bash
export BASE_URL="https://your-deployment.example.com"
export DATASET_ID="YOUR_DATASET_UUID"
export METRIC_ID="YOUR_EVALUATOR_METRIC_UUID"
export FUTURE_AGI_API_KEY="YOUR_API_KEY"
export FUTURE_AGI_SECRET_KEY="YOUR_SECRET_KEY"
```

Your account needs workspace write access. `METRIC_ID` must identify a dataset evaluator binding whose definition matches this example's rule, `output == expected`, returning 1 or 0. The script calculates that rule locally and submits its result with the returned pinned version; it does not invoke a hosted evaluator.

The dataset version creation call is intentionally not idempotent. If it times out, list versions and inspect metadata before retrying. Run creation and result delivery are idempotent only when you retain the original run UUID, receipt key, and payload. Each fresh invocation of this tutorial creates a new snapshot and two new runs.

## Run the workflow

Download [`external-run-comparison.py`](/cookbook/external-run-comparison.py), then run it with Python 3.10 or newer:

```bash
python external-run-comparison.py
```

The script does the following:

1. Creates an explicit immutable version with two cases.
2. Reads it back and carries the resolved `example_id` values into both run plans.
3. Creates a baseline and a candidate external run with different caller-owned configurations.
4. Applies a retrieval function and a policy tool to each case.
5. Uploads results in two batches per run with the evaluator's pinned version.
6. Replays run creation and the terminal result delivery to demonstrate safe transport retries.
7. Compares both runs after showing the candidate's incomplete state.

The two runs both average `0.5`, but case-level comparison reports one improvement and one regression. This is why a mean alone cannot serve as a release decision.

## What to inspect

The script writes `comparison.json`. A successful run prints:

```text
Before the last result: candidate missing=1
Baseline mean=0.5; candidate mean=0.5
Case outcomes: improved=1, regressed=1, missing=0
Create replay and terminal result replay preserved the original records.
Saved full evidence to comparison.json
```

Check these fields in the saved comparison:

| Field | What it proves |
| --- | --- |
| `dataset_version_id` | Both runs used the same frozen case set. |
| `comparison.cases` | Each case aligned by `example_id` and `trial_number`. |
| `comparison.status_counts` | Missing, invalid, failed and unassessed evidence stays distinct from numeric outcomes. |
| `baseline_counts` and `candidate_counts` | Completeness is separate from score averages. |
| `trace_refs` | Caller-supplied trace/root-span references are carried to the comparison. Their existence still requires Observe ingestion verification. |

This minimal script does not configure tracing, so its trace IDs are null. Add your existing traceAI or OpenTelemetry instrumentation when replacing `task`; upload the task root's actual IDs. A submitted identifier is evidence from the caller, not proof that Observe received the trace.

The exact Python example was executed through local HTTP with real API-key authentication and disposable PostgreSQL on 2026-10-13. A separate authenticated probe verified a `409` for a conflicting terminal receipt. This establishes the deterministic API workflow, including the incomplete and replay states. It does not establish real model behavior or a CI verdict.

## Common failure modes

- **`403 Workspace write access required`**: use a member or admin key for the selected workspace. Viewers can read comparisons but cannot create versions or runs.
- **`404 Dataset version not found`**: verify the dataset and version belong to the authenticated organization and workspace.
- **`409 example plan conflict`**: use the version item's `example_id`, not the item membership row ID. Every example/trial identity must belong to the pinned plan.
- **`409 evaluator binding`**: use the `evaluator_version_id` returned in the run header. Do not resolve the current evaluator default between run creation and result upload.
- **`409 receipt conflict`**: a receipt key is tied to one payload. Recover the original payload from your delivery log and resend it unchanged, or create a new run for a new attempt.
- **`candidate missing=1`**: the comparison intentionally reports incomplete evidence. Upload the remaining planned identity; do not interpret the partial average as a pass.
