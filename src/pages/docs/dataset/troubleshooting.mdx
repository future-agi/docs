## In this page

The questions people ask most about datasets, and the errors they run into, with a direct fix for each. Jump straight to [Common errors and fixes](#common-errors-and-fixes), or read on for the background on why a few things take a moment to show up. If your answer isn't here, reach out via [support](https://futureagi.com/contact-us).

## Common errors and fixes

| Symptom | Cause | Fix |
|---|---|---|
| Upload rejected before it starts | The file isn't `.csv`, `.xls`, `.xlsx`, `.json`, or `.jsonl`, or it's over 25 MB | Convert or split the file to fit; see [Limits & Data Types](/docs/dataset/reference/limits-and-data-types) for every cap |
| "Dataset already exists" when creating | A dataset with that name already exists in your organization | Pick a different name; names must be unique per organization |
| Manual creation or a bulk add stops short | Manual creation, empty datasets, and bulk adds each have their own row and column caps | Check the exact numbers on [Limits & Data Types](/docs/dataset/reference/limits-and-data-types) |
| Upload finished but the dataset shows no rows yet | The file is still processing in the background | Wait it out; the dataset moves through queued, processing, and creating cells before it's ready |
| Image, audio, or document cells fill in slowly after upload | Media cells upload in batches, not all at once, and a failed batch retries automatically | No action needed, it catches up on its own |
| A dataset built from Observe traces fills in gradually | Spans convert into rows in batches rather than all at once | Wait for the remaining batches; the row count climbs as each one lands |
| A freshly added eval column sits idle for a few seconds | Evals are picked up by a poller, not dispatched the instant you add the column | Give it a few seconds; it starts on the poller's next pass |
| A cell is stuck showing running | The producer behind it, a run prompt, an eval, or another dynamic method, hasn't been picked up yet or is still executing | Wait a few seconds; if the column status shows `Failed` or `Error`, rerun the column |
| A cell shows error | That row failed whatever produces the column | Rerun the column; if only some rows failed, the column status shows `PartialRun` so you know how much to redo |
| Synthetic generation fails | The background generation job hit an error | Reopen it with **Configure Synthetic Data**; it starts from your saved schema |
| A column or row you expected is gone | It was deleted. Deleting a column also removes the producer behind it (a run prompt, an eval) and anything derived from it | There's no copy to restore; recreate the column or add the rows back |
| Add Row, Add Column, Duplicate, or Delete is greyed out | Your role doesn't have permission for that action on this dataset | Ask an org admin to grant you the right dataset permission |

## Why an upload doesn't show rows instantly

A file upload doesn't write rows the moment it lands. It's processed in the background: the dataset sits **queued**, then **processing**, then **creating cells**, before it flips to **completed** (or **failed** if something goes wrong). For a large file, or one with image, audio, or document columns, expect this to take a while, media cells in particular upload in batches with automatic retries, so a stalled-looking column is usually still working rather than stuck.

A dataset built from Observe traces follows the same shape for a different reason: spans convert into rows in batches, not as a single pass over everything. If you open the dataset right after creating it and see a fraction of the rows you expected, that's mid-conversion, not a failure, refresh after a bit and the rest lands.

## Why an eval column or a cell sits idle

Evals aren't dispatched the instant you attach them to a column. A poller picks up newly added or reset evals on a short interval, so a fresh eval column can sit idle for a few seconds before it starts running. The same applies to a cell showing `running`: it's either mid-execution or waiting for the next poller pass, not stuck. Give it a few seconds before assuming something's wrong; if the column itself moves to `Failed` or `Error`, rerun it.

## Why synthetic generation fails, and how to retry

Synthetic generation runs as a background job, so a dataset can sit in a generating, regenerating, or failed state instead of appearing instantly. If it fails, you'll see a **Failed to generate synthetic data** message with a **Configure Synthetic Data** button. Because the schema you set up is saved on the dataset, that button reopens the same configuration rather than making you rebuild it, fix whatever caused the failure and generate again.

## Why a column, row, or dataset disappeared

If something you expected to see is gone, someone with access to the dataset deleted it, there's no other way for a column or row to vanish. Deleting a column also removes whatever produced it, a run prompt, an eval, and anything derived from it. Deleting a dataset takes its experiments with it. None of this comes back on its own; if you need the data again, recreate the column or add the rows back. See [Manage datasets](/docs/dataset/guides/manage-datasets) for the delete and duplicate controls themselves.

## Why a control is greyed out

Add Row, Add Column, Duplicate, and Delete each check your role's dataset permission before they're clickable. If a control is disabled, it's not a bug, your role doesn't have create, update, or delete access on that dataset. Ask an org admin to update your permissions.
