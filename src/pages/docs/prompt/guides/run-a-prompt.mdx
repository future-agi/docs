Give `support-agent` a company name and a refund question in the **Playground**. You'll see the reply stream into the output panel; the prompt supplies a question and a tone, not the company's refund policy.

<Prerequisites title="Before you start">
- An open [prompt template](/docs/prompt/concepts/understanding-prompts). If you don't have one yet, [create a prompt](/docs/prompt/guides/create-a-prompt) first.
</Prerequisites>

## Write the messages

1. Open **Playground**.

   The editor on the left holds the messages, with the model picker and parameters in its header. The output panel on the right shows the response. The toolbar at the top of the workbench holds **Variables** and **Run Prompt**.

2. Enter the system message: `You are a support agent for {{company_name}}.`
3. Enter the user message: `Answer the following customer question clearly and professionally: {{customer_question}}`

   Each `{{name}}` in a message declares a variable; there's no separate declaration step.

Use **Add Message** if you want an assistant message with a sample answer. Keep at least one message: removing the last one gives **You must have at least one prompt.**

## Declare variables and supply values

1. Open **Variables** beside **Run Prompt** in the toolbar.
2. Enter `Acme` for `company_name`.
3. In the same row, enter `Do you offer refunds after 30 days?` for `customer_question`.

   You should see a complete set of values on one row. Each row is a separate run. **Import Dataset** and **Generate Sample Data** are alternatives to typing the rows.

## Choose a model and run the prompt

1. Select a model in the editor header.

   There is no default: every prompt needs a model selected before it runs.

2. Adjust any [model parameters](/docs/prompt/reference/model-configuration) you need, such as temperature, max tokens or top-p.
3. Select **Run Prompt**.

   The run waits for your most recent message, model or parameter change to save. You should see text appear progressively in the output panel.

4. Read the response alongside the input row.

   A good response is a short, direct answer to the refund question that reads as coming from Acme, in the clear, professional tone the messages ask for. If it states a return window, check the actual policy before treating the answer as correct.

To cancel a run that's taking too long or going in the wrong direction, select **Stop Generating**, which replaces **Run Prompt** while the model is responding.

## If no response appears

<div class="sdk-ref-table max-sm:[&_td]:px-1.5! max-sm:[&_th]:px-1.5!">

| What happens when you select Run Prompt | What to check |
| --- | --- |
| The **Variables** panel opens | A variable is still empty. Fill in every value before trying again. |
| The model picker opens | No model is chosen. Select one first. |
| The run stops before it starts | Another prompt in the organization already uses the same name. Rename yours to clear the conflict. |

</div>

See [Prompt troubleshooting](/docs/prompt/troubleshooting) for other blocked runs.

## Read a version's run status from code

The [prompts SDK reference](/docs/sdk/reference/prompts) separates submitting a configured version from reading its output. `client.prompts.run` returns an asynchronous receipt, not the final text. For the same version and input values, read its status with `client.prompts.run_status` in Python or `client.prompts.runStatus` in TypeScript. Pass the returned version as `template_version` so the read doesn't select a different version by default.

The corresponding MCP tools are `run_prompt` and `get_prompt_run`.
