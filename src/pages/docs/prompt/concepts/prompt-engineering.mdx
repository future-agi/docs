## What prompt engineering is

**Prompt engineering** is getting a model to do what you actually meant, through the words, structure, and examples you give it, not through a setting you flip. The same model, on the same task, produces a noticeably better or worse result depending on how the prompt is written. That's what this page is about: the quality of the output. The object you write it in, with its templates, messages, and variables, is covered in [Understanding Prompts](/docs/prompt/concepts/understanding-prompts).

## Five things that make a prompt work

- **State the task explicitly.** Say exactly what you want, not what you're avoiding. "Summarize this in three bullet points for a non-technical audience" beats "summarize this."
- **Split system and user messages.** The system message sets role, tone, and constraints once; the user message carries the input. Keeping them apart lets the same behavior run against many different inputs.
- **State the output format you want.** If you need JSON, a fixed length, or a specific structure, say so directly rather than implying it through example alone.
- **Show, don't just tell, for nuanced judgment.** An assistant message is a valid part of a prompt, so one or two example responses written as assistant turns teach a style or a judgment call more reliably than a paragraph describing it.
- **Only include context the model needs.** More context isn't automatically better; irrelevant material distracts the model and adds cost without adding accuracy.

## From symptom to lever

When a prompt's output goes wrong, it's tempting to guess at the cause. It's more useful to ask which lever above actually controls it, since most failures trace back to exactly one of the five.

| Symptom | Lever | Fix |
|---|---|---|
| Instruction gets partly ignored | Explicit task | State the instruction plainly instead of burying it in a longer prompt |
| Tone drifts across runs | System message | Define persona and tone in the system message, not left implicit |
| Format or length is inconsistent | Output format | Spell out the exact structure or length you want |
| A judgment call misses the mark | Few-shot examples | Add one or two assistant message examples showing the call you want |
| Model hallucinates or drifts off-topic | Relevant context | Give it only the context it needs, and tell it to say "I don't know" when that's not enough |

## The iteration loop

Prompt engineering rarely lands on the first try: [run the prompt](/docs/prompt/guides/run-a-prompt), [evaluate the outputs](/docs/prompt/guides/evaluate-prompt-outputs), change one thing at a time, then [commit and compare versions](/docs/prompt/guides/commit-and-compare-versions) to check whether the change helped. Changing one thing at a time isn't just discipline: version comparison is capped at three at once, so an isolated change is what actually fits in that view.

## Output quality, not product errors

Everything on this page is about the quality of what the model produces: a bad summary, a wrong answer, a format that keeps slipping. Errors and disabled buttons in the product itself belong on [Prompt FAQ & fixes](/docs/prompt/troubleshooting), not here.
