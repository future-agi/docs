## What a prompt template is

A **prompt template** is a named object saved inside a workspace. It holds three things: an ordered list of messages, a model configuration, and the variable names the messages reference.

Take `support-agent`, the template this page uses as its running example. It's built for a customer-support agent: a system message that sets the agent's role, a user message carrying `{{company_name}}` and `{{customer_question}}`, and a model configuration that picks the model and its settings. Every template you build has this same shape, whatever it does.

## The object model

A template doesn't stand alone. It can be seeded from a base template, it's filed into a folder, and every save of it produces a version.

Two of these edges are easy to miss. Seeding from a base template only sets the starting content: once `support-agent` exists, editing it never touches the base template it began from. And the save edge repeats every time you save: each save produces another [version](/docs/prompt/concepts/versions-and-labels), a snapshot of the messages, model configuration, and variables at that point. This page stops at that fact; how versions and labels work together is its own page.

## Messages and roles

The messages inside a template are ordered, and each one carries a role. The backend accepts exactly three roles: `system`, `user`, and `assistant`. A message with any other role is rejected, not just discouraged by the editor.

In `support-agent`, the system message sets the agent's behavior ("You are a support agent for `{{company_name}}`") and the user message carries the incoming question (`{{customer_question}}`).

## Variables

Variables are `{{name}}` placeholders inside a message's content, substituted with real values at run time. `support-agent`'s user message reads something like:

```
Answer the following customer question clearly and professionally:
{{customer_question}}
```

The template stores the variable names it expects, `company_name` and `customer_question`, so the platform knows what to ask for wherever the template runs.

## Placeholder messages

A placeholder message is a different thing entirely, and it's worth not confusing with a variable. A variable substitutes a value inside a message's content: it's still one string. A placeholder is a named slot in the message list itself, one that takes a whole list of messages rather than a string, so you can drop a full chat history into a template at a fixed position instead of squeezing it into one variable.

## Folders and base templates

Folders hold templates, so a workspace with a growing library stays navigable. See [Organize prompts in folders](/docs/prompt/guides/organize-prompts-in-folders) for the directory controls.

A base template is a reusable starter: instead of an empty editor, you begin from one and edit it into your own template.

## Why the object model matters

Because the model configuration and variable names live on the template itself, not as implicit context in whoever calls it, `support-agent` behaves the same wherever it runs: in the editor, against a dataset, or from your application. And because a version is a snapshot, you always know exactly what ran, not just what the editor happens to show right now.
