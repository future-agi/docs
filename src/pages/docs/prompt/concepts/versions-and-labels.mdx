## Two objects on one template

A [prompt template](/docs/prompt/concepts/understanding-prompts) carries two related objects. A **version** is a saved, immutable snapshot of the template at one point in time. A **label** is a named pointer that sits on top of a version and says which one you actually want right now. You edit the template, commit to get a version, then point a label at it. Reassigning the label later, not editing the template again, is how you promote or roll back.

The top row is the version chain: it only ever grows, one commit at a time. The labels underneath are separate objects pointing into that chain, and they can land anywhere: Staging is trying out the newest version while Production stays on an older one that's proven itself, and a custom label happens to point at the same version as Production. Promoting a version is redrawing one of those dotted arrows. Nothing in the chain above changes.

Say you edit a support template's system message. That's a draft, invisible to anything reading by label. You commit it and it becomes a new version, say v4. You point Staging at v4 to try it out, and once it looks good you move Production there too. A week later it regresses, so you point Production back at v3. The chain still has v4 in it, you've just moved a pointer.

## Versions

Committing a draft is what creates a version. Until you commit, your edits are a draft: an in-progress, uncommitted state that isn't a version yet. Each version:

- Gets a **name** the platform assigns automatically, `v1`, `v2`, `v3` and so on, and it must match the pattern `^v\d+$`. Version names aren't something you type in.
- Is **unique within its template**. A given template can't have two versions sharing a name.
- Can be marked the template's **default** version. Only one version can hold that flag at a time: marking a new one default automatically clears it from whichever version had it before. That happens without you touching the old version directly, so if a script depended on it being default, it no longer is.

<Warning>
Deleting a template deletes every version under it, not just the one you're looking at. There's no per-version undo once the template itself is gone.
</Warning>

To actually commit a draft and set or change a default, see [Commit & compare versions](/docs/prompt/guides/commit-and-compare-versions).

## Labels

A label is a pointer, not a copy. Three exist for every organization without you creating them: **Production**, **Staging**, and **Development**. Alongside those, you can create your own custom labels, for example one per region or one per customer tier. Custom label names must be unique within your organization and workspace; the three system label names are reserved globally, so nobody can create a second label called Production.

A label points at exactly one version. Assign it to a different version and it stops pointing at the old one: that's the entire mechanism behind both promoting and rolling back. Promoting a new version to Production is pointing the Production label at it. Rolling back is pointing that same label back at whatever version it pointed at before. Either way, nothing about the version itself changes, and there's no redeploy: an application fetching by label just gets whatever version the label currently points at.

For fetching and reassigning labels from your own code, see the [SDK & API reference](/docs/prompt/reference/sdk-api).

## Why it matters

Splitting "which versions exist" from "which one is live" is what makes an environment promotion a data change instead of a code change. Your application never hardcodes a version name; it asks for whatever Production currently points at. That means a rollback is as fast as a promotion, since both are the same one-pointer reassignment, and it means you can commit and compare versions freely without any of them going live until you actually move a label onto one.
